# IKPK Rebuild — Agent Guide

## Назначение проекта

Репозиторий содержит rebuild сайта `ikpk.su`:
- `web/` — новый фронтенд на Astro
- `cms/` — Strapi CMS
- `scripts/` — импорт контента и валидация URL
- `discovery/`, `docs/` — артефакты discovery, планов, проверки KPI и миграции

Цель: запустить новый сайт с функциональным паритетом, улучшенной производительностью и корректной SEO-базой без потери контента.

## Процесс разработки: SDD через OpenSpec

Проект перешёл на разработку через спецификации. Планы-документы больше не являются
источником требований — их место заняли спецификации в `openspec/`.

**Граница процесса.** Не всякая работа требует спецификации:

- **крупный блок** — новая возможность, изменение контракта (URL, данные, формы),
  редизайн, смена поведения — начинается со спецификации: change в
  `openspec/changes/`, утверждение, только затем код;
- **небольшой дефект** — начинается с падающего теста (см. «Дефекты: red/green»), без
  церемонии со спецификацией.

Если непонятно, к чему относится задача, — спросить пользователя, а не решать молча в
пользу более быстрого пути.

**Порядок работы с change:** proposal → approval → **tests** → implementation →
verification → archive. Реализация не начинается до утверждения; при архивировании
требования переезжают из change в `openspec/specs/`.

### Конвейер: кто и на чём делает каждый шаг

| Шаг | Кто делает | Что на выходе |
|---|---|---|
| 1. Спека | change в `openspec/`, сильная модель | `proposal`, `spec`, `design`, `tasks`, строгая валидация зелёная |
| 2. Ревью спеки | сабагент Codex + локальный сабагент, **затем владелец** | находки внесены, отклонённое названо с причиной |
| 3. Тесты | **отдельная сессия** с чистым контекстом | красные тесты по сценариям спеки, красный прогон предъявлен |
| 4. Реализация | **Sonnet** | тесты зелёные, спека не переписана под код |
| 5. Ревью кода | **Opus и Codex**, независимо друг от друга | подтверждённые находки исправлены |
| 6. Приёмка и архив | | гейты зелёные, change заархивирован, требования в `openspec/specs/` |

**Нормативны роли и независимость, а не названия моделей.** Этот файл общий для Claude
Code и Codex, а Codex не может переключиться на Sonnet или Opus — то есть таблица,
понятая буквально, делает конвейер неисполнимым для одного из исполнителей. Обязательно
следующее: реализация и ревью выполняются **разными** исполнителями; ревью — не тем, кто
писал; на шагах 1, 2 и 5 используется самая сильная доступная модель. Распределение в
таблице — рекомендуемое отображение при работе из Claude Code. Если названная модель
недоступна, берётся сильнейшая доступная, и это указывается в отчёте; передача шага
другому исполнителю оформляется явно, а не подразумевается.

Почему так распределены модели: на шаге 4 задача механическая — есть спека и красные
тесты, решения уже приняты, поэтому более дешёвая модель уместна и её ошибки ловятся
тестами. Шаги 1, 2 и 5 — наоборот, про суждение: там ошибка не ловится ничем
автоматическим, поэтому нужны сильные модели и **несколько независимых взглядов**.
Ревью двумя разными исполнителями даёт разные находки: за эту работу Codex и локальное
ревью пересеклись лишь частично, а владелец нашёл то, что пропустили оба.

### Baseline: фиксация уже существующего поведения

`openspec/specs/` наполняется только тем, что прошло через процесс. Авторы OpenSpec
предупреждают против массового back-fill, и довод их такой: спека на код, который вы не
меняете, ничем не привязана к реальности — её не ломает изменение кода, поэтому она тихо
расходится с ним. Довод изложен своими словами намеренно: он живёт в документации
upstream (`docs/existing-projects.md` в репозитории OpenSpec), в нашем репозитории этого
файла нет, и буквальная цитата была бы непроверяемой для читателя. Но у нас есть противоположная
проблема: принятый контракт не зафиксирован **нигде**, поэтому дельта не имеет к чему
прикладываться, и всякая возможность описывается как `ADDED`, даже когда она давно есть.

Решение — **baseline-change на функциональную область**, а не один
`baseline-current-system`: огромный baseline невозможно ни проверить, ни отревьюить.
Например: `baseline-url-routing`, `baseline-article-catalog`,
`baseline-seminars-schedule`, `baseline-seo-indexing`.

Спеку **нельзя механически снять с кода**: код содержит и контракт, и случайные детали
реализации, и дефекты. Порядок работы:

1. зафиксировать исследуемый SHA и состояние production — иначе через неделю неясно, что
   именно описано;
2. собрать доказательства: маршруты и компоненты, существующие тесты, схемы и данные,
   конфигурацию раздачи, фактическое поведение production;
3. **разделить найденное на четыре части:** принятое поведение, известные дефекты,
   детали реализации (не контракт), неопределённые места;
4. описать через `SHALL` **только принятое поведение**;
5. написать characterization-тесты, подтверждающие его на существующем коде;
6. независимое ревью в трёх соответствиях: спека ↔ код ↔ production;
7. **найти активные changes той же области и обновить их относительно baseline.**
   Overlapping baseline SHALL NOT **сливаться**, пока это не сделано. Именно сливаться, а
   не архивироваться: архив создаёт основную спеку, относительно которой дельты и
   переписываются, — запрет на архив сделал бы последовательность невыполнимой.

   **Строгой валидации здесь недостаточно, и полагаться на её зелёный цвет нельзя.** В
   OpenSpec 1.7.0 она проверяет структуру `MODIFIED`, но не существование требования в
   основной спеке — это проверяется при применении и архивировании. До архива baseline
   основной спеки вообще нет, поэтому зелёная валидация не доказывает совместимость
   дельты. Порядок внутри **одного** PR: локально заархивировать baseline → обновить
   пересекающиеся дельты относительно появившихся основных спек → строгая валидация плюс
   проверка **применимости** (применением в одноразовом worktree) → и только затем merge; Наш случай:
   `article-list-pagination` описан через `ADDED Requirements` только потому, что
   `openspec/specs/` пуст; после baseline часть его требований станет `MODIFIED`, а часть
   исчезнет как уже существующая;
8. слить PR, в котором лежат и архив baseline, и обновлённые дельты: требования
   переезжают в `openspec/specs/` одним изменением, без промежуточного состояния, где
   основная спека есть, а дельты ей противоречат.

**Здесь RED не нужен, и это не исключение из дисциплины, а другая задача.** Три ветки:

```
baseline:      код и production → доказательства и разбор → спека → ЗЕЛЁНЫЕ тесты
новый change:  утверждённая спека → КРАСНЫЕ тесты → реализация → зелёные
дефект:        наблюдённый баг → КРАСНЫЙ регресс-тест → фикс → зелёный
```

Документирование существующего поведения **не требует красного прогона и реализации**.
Оно требует зелёных characterization-тестов, независимой сверки с кодом и production и
доказательства под каждое принятое требование. Негативная проверка остаётся обязательной:
временно нарушить поведение и убедиться, что тест падает — иначе непонятно, что он ловит.

**Дефект не легализуется baseline-спекой.** Строка вида «сайт SHALL держать все статьи в
скрытом `<template>`» превратила бы дефект в норму. Вместо этого: в baseline идёт
поведение, которое система обязана продолжать давать; текущее отклонение фиксируется как
known deviation; исправление оформляется отдельным change или red/green-дефектом. Baseline
— это не «всё, что делает код», а **«что система уже обязана продолжать делать»**.

### Свой worktree каждому пишущему исполнителю

Параллельные задачи SHALL выполняться в **отдельных git worktree**. Общий worktree
означает общий `HEAD` и общий индекс: два исполнителя в одном каталоге коммитят в одну
ветку, независимо от того, какую каждый из них считает своей.

Это не предосторожность на всякий случай — так уже произошло: коммит со спекой сел на
ветку другой задачи, потому что оба агента работали в одном каталоге. Разбирать пришлось
переносом указателя ветки, и **по git виновника не найти**: `user.name` в worktree общий,
поэтому авторство у всех коммитов одинаковое.

- **работа начинается с обновления `main`, и ветка создаётся от свежего `origin/main`** —
  `git fetch`, затем `git worktree add <путь> -b <ветка> origin/main`. Брать за основу
  состояние, лежащее в локальном дереве, нельзя: оно отстаёт молча;
- **синхронизация с `main` делается ДО ревью, а не между ревью и merge.** Ветка
  перебазируется перед тем, как ревью запрошено, — тогда проходы читают то состояние,
  которое и будет слито. Опубликованную ветку после перебазирования отправлять только
  `git push --force-with-lease` (флаг принадлежит `push`, а не `rebase`): безусловный
  `--force` затирает то, что могли добавить другие.

  Если после ревью ветку всё-таки пришлось обновить (в `main` приехало нужное, конфликт,
  требование сдвинулось), то **новая голова не считается отревьюированной**: у неё другой
  SHA, а ревью относится к содержимому, а не к имени ветки. Для неё нужны заново — проверка
  применимости дельт, релевантные локальные гейты и ревью нового полного SHA. Объём
  повторного ревью соразмерен изменению: разбирать заново весь предмет не нужно, но
  утверждение «это уже ревьюировали» относится к прежнему SHA и на новый не переносится.
  Формулировка «перебазировать перед merge» без этой оговорки создаёт видимость проверенного
  состояния, которое никто не проверял.

  **Это правило и гейт ссылок взаимодействуют, и знать про это надо заранее.** Перебазирование
  с `--force-with-lease` делает недостижимой прежнюю голову своей же ветки — вместе с ней
  осиротеет любая ссылка вида `<эта ветка>@<прежний sha>`. То же произойдёт при squash-merge с
  удалением ветки: SHA ветки в `main` не попадает. Лечить это переписыванием SHA нельзя — так
  портится ровно то историческое свидетельство, ради которого привязка к ревизии и введена.
  Правильный порядок: ссылка на ревизию **вне `main`** объявляется в
  `openspec/.spec-ref-absent` в тот же момент, когда написана (этого теперь требует сам гейт), и
  объявление переживает и rebase, и удаление ветки;

  Почему это правило, а не пожелание: спека, написанная от устаревшего `main`, противоречит
  требованиям, слитым за это время, **и строгая валидация этого не видит** — она проверяет
  структуру дельты, а не её отношение к появившимся основным спекам. Замерено на
  `cms-content-authoring`: change начат от `main@1debf36`, к моменту ревью `main` ушёл на
  `57a0ae87d059a81feae63ffa449b7826886baef8`, и за это время появились четыре основные
  спеки — `rich-content-safety`, `static-serving`, `schedule-month-filter`,
  `dependency-update-automation`. Ревью нашло два блокера ровно из-за отставания: change
  вводил вторую, более слабую политику санитизации при уже принятой единой границе
  (`rich-content-safety`), и считал `serving-cache-headers` активным change, когда тот уже
  заархивирован как основная спека `static-serving`. Валидация при этом была зелёной
  12 из 12;
- пишущему исполнителю — свой worktree (`git worktree add`, или изоляция средствами
  инструмента, если он это умеет);
- общий worktree допустим **только для гарантированно чистых операций**: `git show`,
  поиск по файлам, чтение. Неподвижного `HEAD` недостаточно — сборка, тесты, генераторы и
  часть команд пакетного менеджера пишут в рабочее дерево, `dist`, кэши и lockfile.
  **Любой исполнитель, запускающий потенциально пишущую команду, получает свой worktree —
  даже если он делает ревью и коммитить не собирается;**
- перед каждым коммитом проверять состояние явно — и **ветку, и состав коммита**:
  `git status --short --branch` плюс `git diff --cached --name-status`. Одного
  `git rev-parse --abbrev-ref HEAD` недостаточно: он говорит про имя ветки и ничего не
  говорит про то, чьи файлы попали в общий индекс.
  **Detached HEAD перед коммитом — ошибка**, а не рабочее состояние: сначала выбрать или
  создать ветку;
- **указывать revision, в котором найден факт, а не только ветку.** Имя ветки
  идентификатором не является: она сдвигается, неопубликованная может исчезнуть, а
  временный worktree часто работает вообще без имени ветки. Формат — ref или PR **плюс
  полный SHA** и путь со строкой:
  `feat/demo-mode-and-hero-photo@542151bb8d5348bf2b4dd307eb6dca48edbf34c3,
  web/src/pages/statyi/index.astro:21` либо permalink GitHub на конкретный коммит.
  Сокращённый хеш допустим только как подпись рядом с полным: семь символов со временем
  становятся неоднозначными, а слово «точный» этого не допускает. Без этого номера строк невоспроизводимы: часть кода живёт
  только в неопубликованных ветках, и чтение не того состояния даёт ложное «этого не
  существует». За одну сессию это стоило трёх ложных тревог.

### Масштаб исполнителя: одна поставка на агента

Предыдущий раздел про **изоляцию** исполнителя, этот — про его **размер**. Субагент
получает одну поставку и закрывается финальным отчётом; его контекст SHALL держаться ниже
~150 К. **Стоп-порог количественный: агент с контекстом больше 200 К закрывается отчётом, а
не дополняется заданием.** Число вызовов — не приговор, а второй признак: больше ~150
вызовов при контексте в норме означает «проверить, не расползся ли предмет», потому что
агент с 500 вызовами при 120 К стоит дёшево и закрывать его незачем. Смешивать эти два
случая нельзя — иначе исправный агент попадает в один список с разорительным.

Почему порог, а не «по обстоятельствам»: контекст субагента **нельзя сжать** — `/compact`
внутри него нет — и нельзя разделить. Он растёт монотонно, и каждый следующий шаг платит
весь префикс заново. Агент на 800 К тратит ~80 К за шаг независимо от того, насколько
мелкий этот шаг.

Замерено на сессии `db3e9ed9` (`./bin/session-cost`, снято 12.08.2026, сессия ещё шла —
повторный запуск даст больше): 57 агентов дали 3 929 ответов модели из 4 807 и **75 %**
всего расхода, шесть крупнейших — 55 %. Агент `spec-payment-2` при среднем контексте 418 К
сделал 463 ответа и обошёлся в 23 М взвешенных единиц против 37 М у всего главного цикла за
тот же период: один агент — почти две трети цены сессии-хозяйки. Когда находки предъявили
сессии, новых агентов она сделала кратно меньше старых (средний контекст 114–172 К против
269–775 К), но **три из четырёх всё равно перешли 200 К по максимуму** — правило соблюдается
не «в среднем», а по пику. Старых же не закрыла, а продолжила: контекст `spec-payment-2`
дошёл до 916 К, он сделал ещё 212 ответов и съел 20 М за одно утро — в полтора раза больше,
чем главный цикл за то же время. Три пятичасовых окна кончились именно на этом.

**Считать вызовы надо по идентификатору ответа, а не по строкам транскрипта.** Один ответ
модели лежит несколькими `assistant`-записями — по записи на блок содержимого, — и в каждой
копия одного и того же `usage`. Первая версия этого раздела считала строками и завысила всё
в 1,9 раза: 9 161 «вызов» и 394 М вместо 4 796 и 203 М. Доли при этом почти не сдвинулись
(субагенты 74 % против 75 %), поэтому ошибка не видна ни по структуре вывода, ни по
выводам — только по абсолютным величинам, которые не с чем сравнить. Дедупликация сидит в
`./bin/session-cost`; при ручном разборе транскрипта её надо повторить.

- **работа размером в сессию ведётся сессией**, а не выращенным агентом: «реализуй change
  целиком, прогони гейты, исправь находки ревью» — это сессия со своим worktree, где есть
  компакция и дешёвое руление;
- **с большим агентом не переписываться** — запрашивать один финальный отчёт. `SendMessage`
  поднимает адресата с полным контекстом: 15 сообщений в агента со средним контекстом
  269 К ≈ 4 М токенов чтения только на переписку;
- **спящего агента не будить пингом** ради статуса: статус берётся из PR и списка задач,
  это бесплатно, а пинг стоит весь его контекст;
- **своя сессия режется по швам работы.** Окно 1 М снимает принудительную гигиену: на 200 К
  автокомпакция сбросила бы контекст сама, здесь его не сбрасывает ничто. В той сессии —
  **одна** компакция за 88 часов, контекст p50 = 404 К и p90 = 831 К, и правка `Edit` на
  1 КБ в конце стоила ~90 К. Раздутую сессию после долгой паузы **не возобновлять**: у новой
  префикс ~30 К, а возобновление пересоздаёт весь кэш (замерено 0,8–0,9 М записи кэша за час
  на каждом из трёх возобновлений — это 1,0–1,1 М взвешенных, потому что запись стоит
  1,25×);
- **модель ставится по таблице конвейера, а не по инерции.** В той же сессии механическая
  реализация (шаг 4, где предписан Sonnet) шла на Opus — 865 ответов, 24 % расхода, — а
  агент спеки (шаг 1, сильнейшая модель) шёл на Sonnet. Инверсия в обе стороны сразу, и
  автоматически её не ловит ничто.

Порог в 200 К на глаз не соблюдается — контекст агента не показывается нигде, — поэтому он
измеряется: **`./bin/session-cost`** печатает по сессии и по каждому агенту вызовы, средний
и максимальный контекст, расход и модель, помечает `⚠` вышедших за порог по контексту и `·`
долгоживущих при контексте в норме. Коды выхода различают три исхода, а не два: `0` — все в
пределах, `1` — контекст выше порога, `2` — измерить не удалось (нет каталога, нет сессии,
нет вызовов, транскрипт не читается); список сессий без отчёта — тоже `2`, потому что
измерения в нём нет. **Неполное измерение тоже даёт `2`, а не `0`:** если у кого-то из
исполнителей часть строк не разобралась — или его файл не разобрался целиком и он вовсе не
попал в отчёт, — то «за порогом никого не видно» ничего не значит, недосчитанный мог быть как
раз за порогом. Превышение при этом остаётся `1`: положительная находка верна и на неполных
данных. Файл, оборванный на середине последней записи (нет перевода строки в конце), теряет
**не больше одного** ответа — оборванная строка могла оказаться и не ответом модели вовсе, и
дублем блока уже учтённого, — и это **тоже неполное измерение, то есть `2`**: если потерян
ответ, то последний, а в растущей сессии контекст максимален именно у последнего, так что
выброшена самая вероятная из записей за порогом. Соблазн сделать здесь исключение «потеря-то маленькая» — это ровно тот
способ вернуть ложный зелёный, от которого весь раздел про гейты. О живости сессии обрыв при
этом **не говорит ничего**: так же выглядит транскрипт сессии, убитой посреди записи давно, и
по файлу случаи не различаются — в отчёт идёт потеря, а не догадка о причине. Битая строка,
завершённая переводом строки, — обычное повреждение, даже если она последняя.
Скрипт читает транскрипты Claude Code в `~/.claude/projects/`;
**сессии Codex он не видит**, и для них порог остаётся на внимании исполнителя. Из worktree
нужен `--project <путь к основному каталогу>`: каталог транскриптов заводится по cwd.

Экономить на самих файлах правил бессмысленно, и это тоже замерено: за ту сессию все
исполнители прочитали 9,2 МБ, из них 87 % — картинки мокапов, скриншоты и временные
worktree вне репозитория, а весь проектный markdown (`docs/`, `openspec/`, `web/`) — 8,7 %.
Сокращать `AGENTS.md` ради токенов — не тот рычаг; убрать его повторное чтение агентом,
которому он уже пришёл в префиксе, — тот.

### Plan mode: до записи артефактов, не вместо них

Встроенный plan mode (Claude Code — `permission-modes`; Codex — `/plan` или `Shift+Tab`)
с OpenSpec совместим на **любом исследовательском этапе**, но из него нужно выйти
**перед созданием или изменением** OpenSpec-файлов. Это касается и уже существующего
change: исследовать, нужен ли ему `/opsx:update`, в plan mode можно и полезно — записать
правку нельзя. Причина техническая: plan mode — это режим прав, близкий к «только
чтение», а `proposal`, `design`, `spec` и `tasks` — файлы в репозитории.

Порядок:

```
plan mode → исследовать задачу, требования, риски, альтернативы
          → выйти из plan mode
          → propose / update change → ревью → validate
          → обычный режим → apply
```

**Включать**, когда задача неоднозначна или архитектурна, scope неизвестен, надо
исследовать существующий код, есть несколько решений или цена ошибки высока.
**Пропускать**, когда требование чёткое, изменение небольшое или существующий change
уже полностью описывает работу.

Запрос в plan mode должен готовить вход для proposal, а не подменять его: «исследуй
задачу применительно к этому репозиторию, определи scope, требования, риски,
альтернативы и затронутые компоненты; код и OpenSpec-файлы не меняй».

Отсюда же граница, которую легко нарушить: **в плане нет требований, в спеке нет ветвей
и порядка merge.** План — как я работаю в этой сессии, и он не переживает сессию; спека
— что обязан делать продукт, и она версионируется с кодом. Если план переоткрывает
решённое в спеке, побеждает активный change.

Правила ревью на шагах 2 и 5: оба прохода строго на чтение, задания с **разными
уклонами** (соответствие фактам против полноты последствий — одинаковые задания дают
одинаковые находки), и ни одно утверждение не принимается на слово — проверяется по
репозиторию.

**Числа и ссылки в спеке проверяются измерением, а не заданием ревьюеру.** Уклон
«соответствие фактам» на этом проекте не отработал ни разу: за четыре запуска — ноль
отчётов, при том что находки там были. Измерение же воспроизводимо и не зависит от того,
донесёт ли исполнитель отчёт, поэтому:

- каждое числовое утверждение артефакта пересчитывается **своим выражением по данным или
  коду**, а не сверяется с текстом спеки. Сверка с текстом подтверждает опечатку, а не факт;
- **признак измерения выбирается по предмету, а не по удобству grep.** Замерено: «5 тестов
  читают контент с диска» получилось из поиска строкового литерала `discovery/entities`, и
  этот поиск не видит путей, собранных из сегментов (`join('discovery','entities',…)` в
  `web/tests/teacher-lead.test.ts`). Настоящее число — 12. Тот же класс ошибки, что
  «гейтам нужен парсер, а не регулярка», только в измерении;
- ссылки на файлы и номера строк проверяет **`./bin/check-spec-refs`** — он же стоит в CI
  (job «OpenSpec integration», шаг «Check file references in OpenSpec artifacts»). Архив не
  проверяется вовсе. **Класса «предупреждение» у него нет:** любая ненайденная ссылка либо
  объявлена в `openspec/.spec-ref-absent`, либо расхождение — и это не строгость ради строгости,
  а следствие того, что «change создаст файл сам» неотличимо от «ссылка сломана
  переименованием» никаким автоматическим признаком. Ссылка в **сборочный вывод** всегда идёт в
  поимённый реестр, а не проверяется по обстоятельствам: вердикт гейта не должен зависеть от
  того, собрано дерево или нет, иначе один и тот же реестр не может быть верным и в CI (не
  собрано), и локально (собрано). Проверка путей в собранном дереве — отдельный режим
  `--check-built`, и у него две особенности, обе — следствие того, что он стоит **в гейте
  публикации**. Первая: **корни называются явно** (`--check-built=web/dist,web/dist-demo`), и
  названный корень обязан существовать; без списка берутся все, что есть на диске, а если нет
  ни одного — код 2, а не зелёный. Прогон, которому проверять нечего, не имеет права выглядеть
  успешным именно здесь. Вторая: ссылка в корень, который **в этом прогоне не собран**
  (`cms/dist`, `payments/dist` — джоб собирает только `web`), объявляется НЕпроверенной вслух и
  расхождением не считается. Прежняя редакция считала: законная по всем документированным
  правилам ссылка на `cms/dist/**` проходила проверку ветки и валила публикацию боевого сайта,
  причём автор узнавал об этом только из CI. Коды выхода: `0` — расхождений нет, `1` — есть, `2` — **измерить не удалось**.
  Перечень причин кода 2 приведён полностью, потому что для обязательной проверки «merge встал не
  по моей вине» надо опознавать сразу: нет артефактов; не нашлось ни одной ссылки; нет реестра;
  запись реестра без внятной причины; повторяющийся ключ в реестре (последствие
  слияния); усечённый клон при ссылке на ревизию; недоступный или неразбираемый ответ CLI
  OpenSpec; ни одного `.openspec.yaml` при наличии changes; перечень корней сборочного вывода
  разошёлся с `.gitignore`; `git` не завершился нормально при чтении blob; в клоне нет ни одного
  `refs/remotes/origin/*`; в клоне нет `refs/remotes/origin/main`; режиму `--check-built` не
  досталось ни одного собранного корня, либо названный корень не существует, либо он вне перечня
  сборочного вывода. Два последних добрались в
  перечень четвёртым кругом ревью: они были в коде, но не здесь — то есть слово «полностью»
  оказалось неверным ровно про те причины, которые срабатывают в чужой среде (форк, зеркало,
  усечённый клон), а не у автора;
- **ссылка с номером строки пишется вместе с фрагментом:** ``` `web/src/lib/data.ts:45`,
  `const ENTITIES_DIR =` ```. Если предмет описан **на конкретной ревизии** — так делают
  baseline-спеки и всё, что живёт в неопубликованной ветке, — ревизия входит в саму ссылку:
  ``` `web/src/pages/statyi/[slug].astro@45297b4dd90f1f174553f9840f3a69df9d38f252:62`, `...(article.image ?` ```, и тогда гейт
  читает файл из этой ревизии, а не из HEAD. **Это не украшение.** Гейт без привязки к ревизии
  вреден: принятая спека `article-catalog` объявляет свои ссылки проверенными на `main@45297b4`,
  а гейт, читавший HEAD, потребовал заменить верные для той ревизии `:62` и `:12-13` на текущие —
  и я это сделала, испортив историческое свидетельство инструментом, который его охраняет.
  Продолжение (`` `:273` `` рядом с предыдущей ссылкой в том же абзаце) наследует и путь, и
  ревизию; продолжение без предшествующей ссылки — отказ, а не проза. Ревизия пишется **полным**
  SHA: сокращённый префикс со временем становится неоднозначным, а гейт обязателен для merge.
  Форма `<ветка>@<полный SHA>` **без пути** тоже проверяется — на достижимость ревизии; прежде
  такие ссылки не проверялись вовсе, и SHA в них мог быть любым; сколько их сейчас —
  печатает сам гейт, в тексте правил число не дублируется, чтобы не расходиться с деревом.

  **У ссылки на материал вне `main`** (неслитая ветка) есть отдельный код причины в
  `openspec/.spec-ref-absent` — `external-revision`. Пока ревизия достижима, содержимое
  сверяется; когда ветку удалят, гейт скажет «проверить нечем» и **не заблокирует merge**. Без
  этого уборка одной чужой ветки останавливала бы merge на всех PR, потому что гейт обязателен.

- **у двух реестров разная строгость, и это стоит знать перед тем, как доверять диффу.**
  В `openspec/.spec-ref-absent` **код причины обязателен** и проверяется; в
  `openspec/.spec-ref-debt` причин нет вовсе — а он в 5 раз больше (86 строк против 17).
  Владение измерено: `education-trust-and-admission-clarity` — 47 строк, `online-payment-flow` —
  20, остальные по 1–5. Отсюда два следствия: архивирование одного change механически перепишет
  **больше половины** реестра одним `--write-debt`, и отличить осмысленное изменение от
  механического можно только по составу строк — файл отсортирован, поэтому дифф минимален, но
  обоснования у строки нет. Практический вывод: **строки долга в PR перечисляются в описании**, а
  не оставляются на «дифф покажет».
- **у реестров НЕТ `merge=union`, и это решение, а не недосмотр.** Он там стоял: реестры
  пополняет каждая ветка, трогающая артефакты, поэтому обычное слияние конфликтует почти всегда,
  а разрешение «оставил свою сторону» тихо теряет чужое объявление. Но union спасает добавленные
  строки и **превращает удаление в воскрешение**, а храповик сверяется в обе стороны — значит
  воскрешённая строка красит уже `main`, на голове, которую ни один PR красной не видел.
  Архивирование change как раз требует удаления строк, то есть самый частый случай был бы и самым
  опасным. Конфликт при слиянии виден и разрешается руками; молчаливое воскрешение — нет.
- **ссылка на ревизию вне `main`** объявляется по САМОМУ SHA: `* :: <sha> :: external-revision`
  либо `<артефакт> :: <sha> :: external-revision`. Ключ по пути для этого не годится — самая
  частая форма записи «где найден факт» (`<ветка>@<sha>`) пути не содержит вовсе, и прежняя
  редакция на ней не работала: девять ссылок держались на ветке открытого PR, и её удаление
  уронило бы обязательный гейт, а «лечением» было бы стирание исторического свидетельства.
  Объявление ставится **заранее**, пока ревизия ещё достижима: «запись есть, ревизия достижима» —
  норма. **Такая ссылка требует ещё и строки в `openspec/.spec-ref-debt`**, и требует её сразу,
  пока ветка жива: членство в реестре определяется ОБЪЯВЛЕНИЕМ, а не достижимостью. Иначе главная
  гарантия не выполняется — прежняя редакция добавляла запись только в момент, когда ревизия
  становилась недостижимой, поэтому переход «ветка жива → ветка удалена» создавал новую запись и
  красил обязательный гейт кодом 1 на всех PR. Проверено мутацией достижимости: теперь оба
  состояния дают код 0 при неизменных реестрах. **Это требует сам гейт, а не дисциплина исполнителя:** ссылка на ревизию, которой нет в
  `origin/main`, без объявления — расхождение уже сейчас. Прежняя редакция только описывала
  порядок, и проверять его было нечем: гейт узнавал о проблеме в тот день, когда уборка чужой
  ветки красила обязательную проверку на всех открытых PR — то есть когда исправить ссылку было
  уже нечем, ревизия исчезла вместе с веткой. Измерено на `55f6013`: две ссылки в области
  действия гейта держались на ветках `feat/demo-mode-and-hero-photo` и
  `feat/sanitize-rich-html-content` без объявления, и зелёный цвет означал лишь «ветки пока живы».
  Мёртвым считается объявление на SHA, на который не ссылается ни один артефакт — **у обеих форм
  ключа**: форма `<артефакт> :: <sha>` прежде не проверялась ни на мёртвость, ни обратной сверкой
  (та исключает все `external-revision` целиком), то есть у неё не было ни одной проверки вовсе, и
  строка с любым текстом вместо SHA принималась молча;
- **у каждой записи в `openspec/.spec-ref-absent` обязателен код причины** (`will-create`,
  `deleted-deliberately`, `forbidden-by-invariant`, `external-revision`, `not-committed`).
  `--write-absent` причину не выдумывает: он вписывает `ТРЕБУЕТСЯ-ПРИЧИНА`, и такой файл гейт не
  принимает. Иначе один прогон превращал красное в зелёное, а диффом оставалась строка без
  объяснения — самый дешёвый способ уйти от проблемы вместо её решения;
- **сам гейт покрыт тестами** (`web/tests/spec-refs-gate.test.ts`): он обязателен для merge,
  поэтому его ложный вердикт стоит дороже, чем дефект, который он ищет. Покрытие **не полное**, и
  это надо знать: третий круг ревью отключил три ветви (`--check-built`, сверку корней сборки,
  проверку коротких имён артефактов схемы) — прогон остался зелёным. Заявлять «у каждой ветви
  есть вход» нельзя; тесты закрывают исходы по классам и обе стороны храповика, остальное
  проверяется мутацией руками. Гейт зависит от сети (`npx` спрашивает у OpenSpec
  состав артефактов схемы): при недоступности реестра npm он честно даёт код 2, но merge на это
  время встанет — это принятая цена, а не недосмотр. Без фрагмента проверять нечего — номер строки сам себя
  подтверждает, — поэтому такие ссылки идут в третий класс «неизмеримо» и перечислены
  **поимённо** в `openspec/.spec-ref-debt`; осознанная цитата на удалённый change — в
  `openspec/.spec-ref-absent`. Поимённо, а не числом: при сравнении чисел снятие одной старой
  ссылки открывает место новой, и храповик проворачивается. Оба списка сверяются в обе
  стороны и снимаются флагами `--write-debt` / `--write-absent`; выплаченный до нуля долг —
  законное состояние, а вот отсутствие самого файла реестра даёт код 2;
- **что считается ссылкой, определяется формой span, и ни в одну сторону не зависит от того,
  существует ли предмет.** Это правило пришлось выводить трижды, каждый раз после ложного
  зелёного: сначала признак опирался на набор базовых имён артефактов, снятый с дерева
  (переименование уносило признак вместе с файлом), потом на набор расширений, снятый с дерева
  (удаление единственного `.conf` убирало класс `.conf` целиком). Нынешние правила:
  - **путь с каталогом** — ссылка всегда, расширение любое (`deploy/nginx-redirects.conf`) или
    отсутствует (`bin/openspec`, `.github/workflows/`), лишь бы первый сегмент был существующей
    записью верхнего уровня репозитория. Оговорка про первый сегмент отсекает прозу с косой
    чертой (`text/html`, `application/xml`), а грубость признака намеренна: удаление
    `bin/session-cost` каталог `bin` не убирает;
  - **буквы любого алфавита**: в дереве лежит
    `web/public/terms/Пользовательское_соглашение_и_политика_конфиденциальности.pdf`, и ASCII-класс
    его не видел. Индекс читается с `core.quotePath=false`, иначе git отдаёт такие пути
    экранированными и они не совпадают ни с одной ссылкой;
  - **каталог** (`web/`, `openspec/specs/`) — законный предмет ссылки, но не файл: проверяется
    существование, считается своим числом;
  - **короткое имя без строки** строго проверяется только для артефактов **схемы** OpenSpec
    (`proposal.md`, `design.md`, `tasks.md` — состав берётся у CLI, то есть у схемы, а не у
    дерева). Для произвольного короткого имени двусмысленность настоящая: так пишут и домены
    (`ikpk.su`), и поля (`author.email`), и методы (`page.goto`) — измерено на дереве. Отсюда
    следствие для авторов: **чтобы удаление файла ловилось, ссылку надо писать путём**. Два
    исхода короткого имени раньше уходили в тишину и теперь названы: **расхождение регистра** —
    расхождение (на Linux такая ссылка не открывается, предмет ошибки тот же, что у полного
    пути), а **неоднозначность** (`spec.md` подходит к 22 файлам) — поимённый реестр, потому что
    выбор делает читатель, а не гейт. Молчание здесь позволяло бесшумно понизить точную ссылку
    до неоднозначной;
  - ссылка в **сборочный вывод** ВСЕГДА идёт в поимённый реестр — и в режиме `--check-built`
    тоже: состав реестра не должен зависеть от состояния сборки. Проверка путей в собранном
    дереве идёт шагом «Check build-output references against built trees» в джобе `Tests`, где
    оба дерева уже собраны. Корни вывода — закрытый перечень, сверяемый с `.gitignore`:
    разошёлся — отказ. «Всё, что игнорирует git» признаком не годится, иначе под «вывод сборки»
    попадают `.env`, `.mcp.json` и опечатка внутри `dist`;
  - **фрагмент отличается от ссылки формой:** сосед в кавычках считается фрагментом, если сам
    не выглядит путём (нет расширения и нет косой черты с существующим первым сегментом).
    Фрагмент может стоять и **перед** ссылкой — проза пишет в обоих порядках;
  - **ревизия, записанная не полным 40-символьным SHA в нижнем регистре, — расхождение.** Это
    касается любой негодной формы: шесть символов, 41, верхний регистр, опечатка с нехекс-символом.
    Прежняя редакция отклоняла только то, что успело разобраться (7–40 строчных hex), а остальное
    выпадало из проверки целиком — измерено: три негодные ссылки давали код 0 и не сдвигали ни
    одного счётчика, то есть строгость правила зависела от того, угадал ли автор длину;
  - **путь, уходящий за пределы репозитория по символической ссылке, — расхождение.** `statSync` и
    `readFileSync` идут по symlink, поэтому repo-путь сверялся по содержимому внешнего файла и
    счётчик «сверено» при этом РОС (измерено: 21 вместо 20, код 0). Для проверки, существующей
    ради доказуемости ссылок, это худший из исходов — она подтверждает то, чего в репозитории нет;
  - **голый SHA («точный коммит — `1ca16003…`») ссылкой не считается и НЕ проверяется.** Форма
    не называет ни пути, ни содержимого, поэтому проверять в ней нечего — но учитывается она
    обязательно: без учёта объявление на такой SHA гейт называл «мёртвым» («на этот SHA не
    ссылается ни один артефакт») при живой ссылке двумя строками выше, то есть уже потерянное
    свидетельство нельзя было ни увидеть, ни легально объявить. Гейт печатает, сколько голых SHA
    встретил и сколько из них **уже недостижимо** (на текущей голове — 4 из 27): это прямая мера
    свидетельств, которые читатель проверить не сможет никак. Отсюда правило для авторов: если
    свидетельство должно быть проверяемым, оно пишется формой `<ref>@<sha>` или
    `<путь>@<sha>:<строка>`, а не голым хешем;
  - **отбрасывание прозы идёт ПОСЛЕ всех попыток разрешить путь, а не раньше.** Форма без
    расширения (`dist/`, `specs/<capability>/`) прежде отбрасывалась по первому сегменту до
    классификации сборочного вывода и каталогов — и настоящие ссылки уходили в тишину. Измерено:
    8 ссылок вернулись в проверку (каталогов 55 → 61, сборочный вывод 17 → 19), отброшенной прозы
    стало 35 → 27. Само число отброшенного печатается с разбивкой по первому сегменту: признак
    здесь грубее предмета намеренно, поэтому потеря обязана быть видна, а не молчать;
  - **регистр пути сверяется с индексом git — по индексу, а не попыткой открыть файл.** Это
    относится и к каталогу (`WEB/`), и к сокращённому пути (`src/lib/Data.ts`): на macOS они
    разрешались кандидатом и давали «регистр», на Linux-раннере не находились вовсе и уходили в
    «ссылка в пустоту» — класс, который можно ОБЪЯВИТЬ вместо исправления. macOS не
    различает регистр, Linux-раннер различает: без сверки ссылка проходит локально и падает в CI,
    а реестры, снятые локально, в CI читаются иначе. Прежняя редакция узнавала о расхождении
    только через `existsSync`, то есть **только на macOS**: на Linux ветвь «неверный регистр»
    была недостижима вообще, ссылка шла ветвью «пути не существует», и тест на регистр проходил
    в CI по другой причине, чем в его собственном названии;
  - **содержимое огороженных блоков кода не проверяется** — там живут примеры, в том числе
    намеренно неверные;
  - ссылка на **артефакт заархивированного change** разрешается в `openspec/changes/archive/**`:
    после архивирования файл существует, он лишь переехал. Иначе обязательный шаг конвейера
    заставлял бы править чужие артефакты. **Но реестры при архивировании обновить придётся:**
    ссылки самого архива из проверки уходят, и храповик это заметит — прогоните
    `--write-debt` и `--write-absent` в том же PR;
- **числа о проверке печатаются по классам и не складываются в одно «проверено».** Две
  первые редакции этого же гейта были ложнозелёными именно на подсчёте: «128 ссылок,
  расхождений нет» при двух сверенных по содержимому, затем «проверено по содержимому 146»,
  где 142 ссылки имели проверенным только существование пути, а с номером и фрагментом их
  было **четыре**. Сумма проверок разной силы — это способ выдать неизмеренное за измеренное,
  и она обманывает даже автора гейта;
- **спека переживает код, поэтому ссылка стареет молча.** Строгая валидация OpenSpec её не
  смотрит, и зелёный цвет валидации читается как «спека в порядке». За одну сессию так
  устарели четыре ссылки из 62, включая номера строк в workflow — а рядом обнаружилось, что
  сборок в прогоне не три, а семь вызовов в трёх джобах.

### Тесты по спеке пишутся в отдельной сессии и раньше кода

После утверждения спеки следующий шаг — **не реализация, а тесты**, и они пишутся в
**отдельной сессии**, начатой с чистого контекста.

Правила этой сессии:

- на входе — только утверждённая спека (`proposal`, `spec`, `design`, `tasks`) и код
  репозитория. Обсуждение, которым спека рождалась, в контекст не переносится;
- пишутся **только тесты**, реализация не трогается. Тесты должны быть **красными** —
  красный прогон обязателен к предъявлению, иначе неизвестно, что именно они ловят;
- каждый сценарий спеки получает проверку либо явную отметку, почему проверки нет;
- каждая новая проверка проходит негативную верификацию (см. ниже);
- **у каждого сценария должен быть воспроизводимый способ проверки.** По умолчанию —
  автоматический тест. Ручная или стендовая приёмка допустима, но требует названной
  причины и сохранённого свидетельства (команда, адрес, вывод, снимок). Пример законной
  ручной проверки: фактический ответ nginx — сборка о нём не знает, а поднимать nginx в
  тестах проект не умеет;
- **дефект спеки — это сценарий, для которого нельзя определить объективный критерий**, а
  не сценарий, который не автоматизируется. Такие возвращаются в change через
  `/opsx:update`, а не переформулируются на месте под то, что удобно проверить.

Зачем отдельная сессия, а не следующий шаг в той же: автор спеки помнит, что имел в
виду, и невольно проверяет замысел вместо текста. Сессия с чистым контекстом видит ровно
то, что написано, — и находит невыполнимые сценарии, неоднозначные формулировки и
требования, держащиеся на догадке. На первой спеке проекта независимые проходы нашли
шестнадцать дефектов, из которых четыре были внесены в ходе самих исправлений; ни один
не был бы найден автором.

**Чем доказывается красный прогон.** Коммит с тестами раньше кода хранит исходник, но не
результат выполнения: при одном push CI проверит итоговую голову, а squash уберёт
промежуточный коммит из истории. Поэтому годится один из двух способов, и оба надо
называть явно:

- отдельный push коммита **только с тестами** — упавший check-run на этом SHA и есть
  свидетельство;
- либо приложенный к PR лог красного прогона с **точной командой и SHA**.

«Тесты лежат коммитом раньше» само по себе доказательством не является.

Практическое следствие для CI: PR с одними красными тестами в `main` не сливается —
тесты живут в ветке change до реализации, либо PR держится черновиком.

**Чем создаётся change:** `/opsx:propose "<что нужно>"` в Claude Code,
`$openspec-propose "<что нужно>"` в Codex. Дальше по ходу — `/opsx:update` для правки
плана, `/opsx:apply` для реализации, `/opsx:archive` по завершении. Полный список — в
`.claude/commands/opsx/` и `.codex/skills/`.

**CLI.** Не установлен ни в зависимости, ни глобально. Все вызовы идут **только через
обёртку `./bin/openspec`** из корня репозитория — она закрепляет версию и отключает
телеметрию:

```bash
./bin/openspec list
./bin/openspec validate --all --strict --no-interactive
```

Почему через обёртку, а не прямым `npx`: CLI по умолчанию отправляет анонимную
статистику использования наружу (проверено в его исходниках: отключает только
`OPENSPEC_TELEMETRY=0` или `DO_NOT_TRACK=1`, плюс сам глохнет при `CI=true` — то есть
в наших workflow добавлять ничего не нужно). Держать переменную в примерах команд
недостаточно — на любом новом вызове её легко не написать, и данные клиентского
проекта уедут молча. Обёртка убирает эту возможность целиком.

Честная оговорка: **самый первый `init`, которым этот каталог и создан, прошёл ещё без
отключения** — дисциплина появилась после него. Признак остался в
`~/.config/openspec/config.json` (файл вне репозитория): он записывается только на
ветке с включённой телеметрией. То есть одно событие о запуске команды ушло; отменить
это нельзя, поэтому фиксируем как факт, а не как «телеметрии не было».

`--no-interactive` обязателен в автоматике: без него `validate` ждёт выбора элемента.

Запускать из корня репозитория: команды работают с каталогом `openspec/` относительно
текущего, и запуск из `web/` создаст структуру не там.

**Сгенерированные скиллы пропатчены — и это долг.** Из коробки скиллы и команды в
`.claude/` и `.codex/` написаны под бинарь `openspec` в `PATH`, которого у нас нет: там
было 111 вызовов вида `openspec status`, `openspec instructions`, `openspec list`. Из
чистого окружения каждый упирался бы в `command not found`, то есть `/opsx:propose` не
работал бы вообще. Все вызовы переписаны на `./bin/openspec`, а `allowed-tools` — на
`Bash(./bin/openspec:*)`.

Отсюда следствие: **файлы в `.claude/` и `.codex/` больше не совпадают с выводом
генератора.** После любого `init` или апгрейда OpenSpec патч надо наложить заново —
иначе интеграция тихо вернётся к нерабочему состоянию:

```bash
find .claude .codex -name '*.md' -exec perl -pi -e \
  's{(?<![\w/\$.\-])openspec(?= (new|status|instructions|store|list|archive|validate|show|update|apply|diff)\b)}{./bin/openspec}g; s{Bash\(openspec:\*\)}{Bash(./bin/openspec:*)}g' {} +
```

Проверка после патча — `./bin/check-openspec-integration`. Он ловит **любой** голый
вызов, а не список известных подкоманд: первая версия проверки перечисляла
`new|status|list` и оказалась уже самого патча — при потере замены по `instructions`,
`store` или `archive` она осталась бы зелёной на нерабочей интеграции. Тот же скрипт
запускается в CI (job «OpenSpec integration» в `lint.yml`), поэтому потерянный патч
виден на PR, а не в момент, когда у кого-то не запустится `/opsx:*`.

**Не устанавливать CLI глобально** ради того, чтобы патч стал не нужен: глобальная
установка уводит вызовы из-под обёртки, и телеметрия снова включается.

**Про `CLAUDE.md`.** Claude Code читает `CLAUDE.md`, а не `AGENTS.md`, поэтому в корне
лежит `CLAUDE.md` из одной строки-импорта `@AGENTS.md`. Правила держать только здесь:
две копии неизбежно разойдутся.

## Source of Truth

Перед началом задач сверяться в таком порядке:

1. **активный change в `openspec/changes/`** — источник требований для разрабатываемой
   дельты;
2. **`openspec/specs/`** — принятое текущее поведение (туда переходят требования после
   архивирования change);
3. архитектурные и миграционные документы: `rebuild_plan.md`,
   `discovery/functional_parity_checklist.md` (критерии паритета, go-live gate),
   `docs/kpi-validation.md`, `docs/migration-runbook.md`, `docs/observability.md`, и
   этот файл — он задаёт процесс, но не заменяет спецификации продукта;
4. исторические планы в `docs/plans/` — контекст и обоснования решений, не задания.

**При конфликте побеждает активный change.** Между документами одного уровня
приоритет у более узкого и более нового.

**Статусы планов.** Все планы в `docs/plans/` — `002-parity-review-v2.md`,
`003-content-visual-parity-audit.md`, `004-mvp-plan.md` — **исторические**: заданиями
они больше не являются и требований не задают. Читать их стоит за обоснованиями
решений, а не за списком работ.

Что из них фактически закрыто, определяется **историей коммитов и составом гейтов**, а
не пометками в документе: план — снимок намерения на момент написания, и расхождение
между ним и кодом неизбежно. Проверять по `git log` и по тому, какие проверки реально
падают, если поведение вернуть.

Работа, которая ещё не сделана, оформляется как change в `openspec/changes/` — не
дописыванием пунктов в исторический план.

## Правила выполнения

- Работать итеративно: маленькие изменения, затем локальная проверка.
- Не тянуть legacy CSS-модули с хешами в новый UI; использовать компонентный rebuild.
- Для контентных страниц сначала нормализация HTML, потом рендер компонентами.
- Любые SEO/маршрутизационные правки должны учитывать будущую миграцию и карту URL.
- Новые зависимости добавлять только при явной необходимости.

## Локальные quality gates

- GitHub Actions дублируют локальные проверки, но не заменяют их: перед push или обновлением PR прогонять релевантные проверки локально в изменённых пакетах.
- **`./bin/check-spec-refs` прогонять локально:** это обязательная проверка ветки, она блокирует
  merge, и узнавать о её красноте из CI — значит узнавать позже всех. Два конкретных решения
  сближают вердикты: состав реестров не зависит от состояния сборки, а достижимость ревизии
  мерится по `refs/remotes/origin/*`, а не по локальной базе объектов. Второе пришлось вводить
  после того, как ревизия, лежащая только в клоне автора, дала локально «сверено», а в CI —
  «недостижима». **Но полного совпадения нет, и на него нельзя рассчитывать** — измерено на
  этом же PR (локально 348 имён соседних артефактов против 350 в CI, оба вердикта зелёные
  случайно: два новых span попали в класс, которого нет в храповике). Две причины:
  - `actions/checkout` на событии `pull_request` берёт **merge-коммит** с текущим `main`, а не
    голову ветки. Пока `main` идёт вперёд, CI видит дерево, которого локально нет ни у кого;
    воспроизводится локальным `git merge origin/main` во временном worktree;
  - достижимость мерится по **локальным** `refs/remotes/origin/*`, а они обновляются только
    `git fetch`, причём удалённые ветки уходят лишь с `--prune`. Поэтому «ревизия исчезла вместе
    с чужой веткой» невидимо локально у всех, кто не пруннил, и видно только в CI со свежим
    клоном — «merge встал не по моей вине» в самом чистом виде. Перед выводом «у меня зелено»
    полезен `git fetch --prune`.
- Для `web/` минимум: `npm run lint`, `npm run typecheck`, `npm run build`.
- Для `web/` дополнительно: `npm run test:build`, если затронуты стили, шрифты, layout, performance/a11y-проверки или build output assertions.
- Для `cms/` минимум: `npm run lint`, `npm run typecheck`, `npm run build`.
- Для `scripts/` минимум: `npm run lint`, `npm run typecheck`.
- Если меняются зависимости, lockfile или security/workflow-конфигурация, локально запускать и `npm run audit:prod` в затронутых пакетах до push.
- Известное исключение по `cms` — и **локальный гейт с CI-отчётом здесь путать нельзя**,
  потому что они дают противоположный сигнал:

  - **локально `cms/npm run audit:prod` не report-only, а падает.** Скрипт — это
    `npm audit --omit=dev --audit-level=critical` (`cms/package.json`), и сейчас он выходит с
    кодом `1`: в prod-дереве есть critical. То есть исполнитель, честно выполняющий правило
    «прогнать релевантные гейты локально», получит красное — и это ожидаемое состояние, а не
    его ошибка;
  - **report-only — только CI-джоб** «CMS runtime dependency audit» в
    `.github/workflows/security.yml`, и report-only он **по составу advisory, а не по своей
    исправности**: ненулевой код `npm audit` глотается адресно в своём шаге, а сбой измерения —
    битый отчёт, сеть, отсутствие файла — джоб роняет. `continue-on-error` на уровне джоба оттуда
    убран: он гасил в том числе шаг «измерение не выполнено», то есть джоб выглядел пройденным
    ровно в том случае, ради которого проверка написана. Блокирующим для PR джоб при этом не
    стал: его контекста нет в перечне обязательных проверок ветки (см. раздел про гейт
    публикации).

  Отсюда правило: красный `cms/audit:prod` **не блокирует работу**, но упоминается в summary
  задачи или PR — молча его глотать нельзя. Блокирует не факт красноты, а **регресс
  относительно известного состояния**:

  - состав advisory ухудшился — появились новые или выросла серьёзность по сравнению с тем,
    что зафиксировано в задаче или PR как исходное;
  - меняется порог или политика самого аудита;
  - задача заявлена как закрытие advisory и его не закрыла.

  Само изменение дерева зависимостей `cms` или lockfile блокировкой **не является**, пока
  состав advisory не ухудшился. Первая редакция этого пункта блокировала любое изменение
  дерева — и запрещала, в частности, добавить визуальный редактор, которого требует спека CMS,
  и любое частичное улучшение, уменьшающее риск, но не закрывающее critical целиком. Запрет на
  движение при уже известной красноте — это не защита, а стоп-кран: он оставляет систему в том
  же красном состоянии и мешает выйти из него.

  **Изменение наблюдаемости — печать, выгрузка отчёта, формулировка заметки — под блокировку
  не попадает**: оно не двигает ни зависимости, ни порог, и требовать от него зелёного аудита
  значило бы запретить улучшать видимость известной красноты. Такая задача лишь фиксирует
  известный красный baseline: сколько advisory и какой серьёзности было на момент правки.
  Первая редакция этого пункта блокировала «любую security-конфигурацию» — и первым, что она
  запрещала, оказался PR, которым сама вводилась.

  **Версию и состав advisory здесь не фиксируем.** Прежняя редакция называла Strapi 5.40.0, и
  это устарело: в `cms` стоит 5.51.2, а измерение `npm audit --omit=dev` на
  `main@cdb023a09baf99e199c509524dc4c88612ba0010` даёт 1 critical (`shell-quote`) и 8 high, включая `@strapi/upload`. Числа
  меняются быстрее, чем правится этот файл, поэтому они **измеряются перед работой**, а не
  читаются отсюда: неверная цифра в правилах хуже отсутствующей — по ней уже было написано
  ложное утверждение в спеке.
- В отчёте по задаче и перед запросом ревью перечислять, какие локальные команды были запущены и что прошло.

## Гейт публикации: что блокирует выкладку сайта

Публикация на GitHub Pages идёт не по факту push в `main`, а по событию об успешном
завершении проверок. Объём гейта намеренно узкий, и его границу надо знать, иначе зелёный
цвет соседней проверки прочитают как разрешение публиковать.

**Входит в условие публикации ровно одна проверка — `Tests`.** Её успех обязателен:
публикуется тот коммит, который она проверяла, а не текущая вершина ветки.

**Не входят в гейт и публикацию не блокируют:** `Lint and Typecheck`, `Lighthouse CI`,
`Security`, `Nightly full checks`, `Published main head monitor`,
`Dependabot auto-merge`, `Dependabot auto-merge policy`, `Dependabot auto-merge signal`,
`Dependabot rebase`, `Dependabot rebase policy`, `Dependabot rebase signal`. Их падение видно на PR и в
ленте прогонов, но выкладку оно не останавливает. `Published main head monitor` не
разрешает публикацию, а отдельно сигнализирует, если вершина `main` не опубликована за 30 минут.
Причина техническая: событие `workflow_run` подписывается на завершение workflow и не
умеет требовать успеха сразу нескольких. Расширение гейта на них потребует свести
проверки в один workflow или вынести их в reusable — это отдельная работа, а не
настройка.

**Гейт публикации и защита ветки — разные механизмы, и путать их нельзя.** Публикацию запускает
событие об успехе `Tests`; **merge** держит классическая branch protection, и в ней на 20.08.2026
**двенадцать** обязательных контекстов: `web checks`, `cms checks`, `scripts checks`,
`Unit and build tests`, `Playwright smoke (desktop + mobile)`, `Secret scan`,
`Runtime dependency audit (web)`, `Runtime dependency audit (scripts)`,
`Lighthouse budgets (4 templates, median of 5)`, `Dependency update invariants`,
`Scripts unit tests`, `OpenSpec integration` — последний добавлен вместе с этим правилом, иначе
гейт ссылок мог краснеть, не мешая merge. `strict: true` (ветка обязана быть свежей),
`enforce_admins: true` (владелец не исключение). Два следствия, которые надо держать в голове:
**`Lighthouse budgets` обязателен**, то есть ложное падение TBT из TD-11 блокирует merge, а не
просто краснеет; и **переименование джоба замораживает merge** — контекст перестанет приходить,
а обязательным останется.

Проверка `Dependabot auto-merge / Eligibility gate` обязательной **не является**: ruleset с
owner bypass отменён принятой спекой как декоративный. На человеческих PR она и
`Provenance evidence` красные по замыслу — fail-closed при отсутствии метаданных Dependabot, — и
это единственные две красноты, которые на таком PR нормальны.

Отсюда практическое следствие: **если нужно, чтобы что-то останавливало выкладку, это
что-то должно оказаться внутри `Tests`,** а не рядом с ним.

**В `Tests` входит и демо-сборка.** Джоб `unit-and-build` собирает сайт ещё и в
демо-режиме (`dist-demo`) и прогоняет проверки по этому выводу — не отдельным workflow, а
внутри того же обязательного прогона. Падение демо-проверки останавливает выкладку
**боевого** сайта: демо — часть продукта, и его дефект есть дефект продукта. Перечень
входящих в гейт workflow при этом не меняется — `Tests` по-прежнему один.

## Дефекты: red/green и негативная проверка гейтов

- Любой дефект начинается с **падающего теста** (RED), воспроизводящего именно этот
  дефект, и только потом идёт исправление (GREEN). Не наоборот: «сначала починю, потом
  напишу тест» даёт тест, который зелёный по совпадению.
- **Каждый новый гейт проверяется негативно:** вернуть дефект (правкой или временным
  откатом фикса) и убедиться, что гейт покраснел. Гейт, который не проверен так, не
  считается гейтом.
  Это не формальность: за одну сессию три гейта прошли ВМЕСТЕ с возвращённым багом —
  проверка `@keyframes` вместо правил элемента, совпадение по имени CSS-класса и
  измерение `boundingBox` вместо `transform`. Ни один из трёх не поймала обычная
  разработка, все три выявила негативная проверка.
- **Проверка обязана различать «дефектов нет» и «я не смогла проверить».** Это общая
  причина всех декоративных гейтов, что здесь встречались: отсутствие сигнала
  выдавалось за отсутствие проблемы. Практические следствия:
  - разбирать коды выхода, а не только «не ноль». У `grep` `1` — совпадений нет, `2+` —
    ошибка чтения; `if grep …` считает второе за первое и держит гейт зелёным именно
    там, где сломано больше всего;
  - если проверять нечего — отсутствуют каталоги, пустой список файлов, ноль элементов
    для валидации — это результат «не выполнено», а не успех. Либо падать, либо
    говорить о вакуумности вслух;
  - не перечислять частные случаи того, что проверяешь. Список известных подкоманд,
    имён классов, расширений отстаёт от предмета молча — ловить общий признак;
  - каждая ветка гейта должна быть хоть раз пройдена. Непройденная ветка — такое же
    обещание, как непроверенный гейт;
  - **проверка, обращающаяся к адресу, утверждает ОЖИДАЕМЫЙ код ответа и падает на
    неожиданном.** Требовать всегда `200` нельзя: есть проверки, у которых предмет — сам
    ответ, и активная спека их прямо предписывает (301 для `/statyi/page/1` и вариантов со
    слэшем, 404 за диапазоном страниц). Там ожидается именно этот код, и следовать
    редиректу запрещено — иначе предмет проверки подменяется. Само это не получается:
    `page.goto` и обычный `fetch` идут по редиректу по умолчанию, нужен либо `curl` без
    `-L`, либо `APIRequestContext` с `maxRedirects: 0`.

    `200` обязателен там, где проверяется **содержимое**: axe, разбор DOM, визуальные
    эталоны. Анализ страницы 404 проходит всегда — она маленькая, нарушений на ней нет.
    Именно так гейт axe проверял 404 на **10 шаблонах из 14**: адреса в списке шли со
    слэшем на конце, а сборка перешла на `trailingSlash: 'never'`. Прогон зелёный, в
    описании PR стояло «36 проверок доступности», проверялась одна главная. Оба факта —
    про ветку `feat/demo-mode-and-hero-photo` (PR #27, `8dbf6d6`): в `main` этой опции нет
    и обе формы адреса отдаются. Ссылка на ветку тут не формальность — без неё читатель
    отнесёт числа к своему дереву.

    Правило действует на новые проверки и на те, которых касается текущая работа;
    ретроактивной переделки всего набора оно не требует. Существующее несоответствие
    названо в `docs/tech-debt.md` (TD-6), а не оставлено молчанием — иначе правило
    читалось бы как описание уже достигнутого состояния;
  - **граф проверки моделирует конкретного потребителя, и потребитель назван в самой
    проверке.** Разные потребители видят разные рёбра, и молчание об этом даёт цифру без
    смысла. Гейт достижимости статей считал рёбрами всё подряд: с разметкой внутри
    `<template>` недостижимых 0 из 68, без неё но с картой сайта — тоже 0, без того и
    другого — 1. Три разных ответа на один вопрос, потому что вопрос не был задан точно.
    Что именно перечислять — зависит от потребителя, а не от общего слова «видит»:
    `noindex` ссылки не скрывает вовсе, он запрещает индексировать страницу, на которой
    они лежат. Обход у нас останавливает **`nofollow`** (на `/sitemap` стоит
    `content="noindex, nofollow"`), а человек без JavaScript той же картой пользуется
    свободно — там обычные `<a>` на все 68 статей без `rel`. Поэтому «недостижима одна
    статья» верно для модели поискового обхода и неверно для человека, и в проверке это
    должно быть написано, а не подразумеваться;
  - **из данных проверять вывод, а не снимок.** Гейт сравнивал сохранённый статус
    семинара с текущей календарной датой и краснел от хода времени при исправном коде.
    Выносить вывод чистой функцией с датой в аргументе и проверять фикстурами.
- **Негативная мутация выполняется в своём worktree** (это и так требует раздел «Свой
  worktree каждому пишущему исполнителю» — мутация тем более пишущая операция), **фикс к
  моменту мутации закоммичен, а восстановление подтверждается постусловием, подобранным под
  предмет мутации:**
  - мутировали отслеживаемые файлы — пустой `git status --porcelain` и отсутствие diff
    относительно **опорного SHA**: для дефекта это SHA фикса, для baseline — голова change,
    на которой характеризационные тесты зелёные (у baseline фикса нет по определению, а
    негативная проверка для него обязательна — см. раздел про baseline);
  - мутировали **сгенерированный вывод** (`web/dist/` и подобное) — контрольная сумма
    дерева до и после либо пересборка. `git status` здесь бесполезен: `web/dist/` в
    `.gitignore`, и созданный внутри него файл вывод команды **не показывает вовсе**
    (проверено). Постусловие, слепое к предмету мутации, — это снова «не смогла
    проверить», выданное за «дефектов нет».
    Сумму считать **по относительным путям и с сортировкой**: `find . -type f -exec shasum
    {} + | sort | shasum` из каталога. Без сортировки порядок обхода не гарантирован, и
    постусловие сообщает о расхождении там, где восстановление полное — ложный отказ,
    зеркало ложного зелёного. Проверено на себе: сумма разошлась при 1756 побайтово
    совпадающих файлах.

  Отдельный worktree после проверки удаляется (`git worktree remove`), и надо помнить его
  цену: `node_modules` и `dist` не разделяются, поэтому для прогона build-гейтов там нужен
  свой `npm ci` и своя сборка. Забытый worktree с мутированной сборкой — следующий источник
  ложного вывода, уже без следов в основном дереве.

  Почему коммит фикса обязателен до мутации: `git checkout -- <файл>` для восстановления
  снесёт и сам непокоммиченный фикс, а для нового, ещё не отслеживаемого файла не
  сработает вовсе — мутация останется в дереве и уедет в коммит. Оба случая уже были в
  одной сессии.
- **Мутация записывается воспроизводимо: точная команда или патч плюс два числа — до и
  после.** Пересказ не годится. У нас записанная мутация («снять любой `<aside …>`») давала
  зелёный гейт, потому что блока «Другие статьи» на странице статьи **два**, и снятие одного
  оставляет ссылки живыми; красным гейт становится только при снятии обоих (1 → 62). По
  такому описанию следующий исполнитель повторил бы мутацию, увидел зелёное и заключил, что
  гейт декоративен.
- **Судить о мутации по ИМЕНИ покрасневшего теста, а не по цвету прогона.** В том же случае
  неполная мутация всё равно красила прогон — падали два других теста, про связь между
  статьями, — и красное выглядело подтверждением, хотя проверяемый гейт был зелёным.
- **Если над тем же предметом есть другая проверка, их ответы обязаны совпадать — либо
  расхождение названо.** У нас два гейта над одним графом достижимости дают 0 и 1 и оба
  зелёные: один считает рёбрами содержимое `<template>`, другой нет. Каждый исправляет то,
  что ломает другой, и без сверки это не видно ни одному из них.
- **Мутация для негативной проверки проверяется на полноту — измерением, а не глазами.**
  Снятие блока «Другие статьи» со всех 68 страниц статей не покраснило гейт, потому что
  ссылки выживали в соседнем `<aside class="…">`, которого шаблон `<aside>` без атрибутов
  не задевал. Зелёный прогон после мутации значит одно из двух: гейт декоративен **или**
  мутация не убрала предмет. Различать эти два случая обязательно — иначе вывод о гейте
  делается по неудавшемуся эксперименту.
- Дефекты раскладки ловятся только браузерными тестами (Playwright). `lint`,
  `typecheck` и build-гейты их не видят — сборка зелёная и на сломанной вёрстке.
- В отчёте по дефекту показывать оба состояния: как тест падал до фикса и как проходит
  после.

## Изменения облика: мокапы до внедрения

Менять внешний вид (дизайн, раскладку, типографику, палитру) можно только после того,
как пользователь оценил **полноценные мокапы страниц в нескольких вариантах**.
Порядок: мокапы → выбор пользователя → внедрение. Точечные исправления дефектов
(контраст, невидимая кнопка, съехавший блок) под это правило не попадают — они идут
через red/green.

## Definition of Done

Задача считается закрытой, если:
1. Изменения реализованы в коде.
2. Локально пройдены релевантные quality gates (`lint`, `typecheck`, `build`, тесты, `audit:prod` для затронутых пакетов) или явно зафиксировано известное исключение.
3. Добавлены/обновлены тесты там, где это критично по рискам.
4. Отражено влияние на паритет (что стало лучше относительно production-версии).
5. Для дефекта: тест падал до фикса и проходит после; для каждого нового гейта
   выполнена негативная проверка.
6. Для крупного блока, который шёл через change: тесты по спеке написаны **до**
   реализации, в отдельной сессии, и предъявлен их красный прогон; пройдена
   verification; change заархивирован, требования переехали в `openspec/specs/`. Пока
   это не сделано, блок не закрыт — иначе `openspec/specs/` перестанет описывать
   текущее поведение, а вместе с этим развалится вся иерархия источников истины.

### Definition of Done для baseline-change

Этот список **полностью заменяет** общий Definition of Done, а не уточняет его: baseline
не меняет production-код, не имеет красного прогона и ничего не улучшает относительно
production — значит требование «отразить, что стало лучше» к нему тоже неприменимо.
Вместо улучшения фиксируется **подтверждённое текущее состояние паритета**: что система
уже даёт. Baseline закрыт, если:

1. зафиксированы исследуемый SHA и состояние production, по которым снималось поведение;
2. найденное разделено на принятое поведение, известные дефекты, детали реализации и
   неопределённые места; в требования попало только принятое;
3. characterization-тесты **зелёные** на существующем коде;
4. для каждого нового гейта выполнена негативная проверка — поведение временно нарушено,
   тест покраснел;
5. проведена независимая сверка «спека ↔ код ↔ production» — не автором baseline;
6. известные отклонения записаны как known deviations, а не легализованы требованиями;
7. активные changes той же области обновлены относительно baseline, заново прошли
   строгую валидацию **и проверены на применимость** — одной валидации недостаточно, она
   не проверяет существование требования в основной спеке;
