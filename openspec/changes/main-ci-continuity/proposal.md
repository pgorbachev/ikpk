## Why

Слияние через `gh pr merge --auto` с `github.token` не порождает push-событий: события,
вызванные действием с токеном по умолчанию, не создают новых прогонов workflow
(документация GitHub, «GITHUB_TOKEN» — исключения там названы поимённо, и `push` в них не
входит). Следствие: коммит, слитый автоматикой Dependabot, не получает на `main` **ни
одного** post-merge прогона — ни `Tests`, ни `Lint and Typecheck`, ни `Lighthouse CI`, ни
`Security`.

Измерено на трёх последних таких слияниях (`gh api .../actions/runs?head_sha=<sha>`,
снято 27.08.2026): у `main@0148f144137bed30a93cb72e871c3d61205f1db2`,
`main@19a919bf09f720550c3b3765c03989bbd35b019b` и
`main@44866c06a5a8a4b0fe241c1dfae7ba411f5cd2a1` нет ни одного прогона с `event=push`, при том
что у соседнего `main@4d009072d38fcbd04b04eebeb210392047c8f118`, слитого владельцем, весь
батч из четырёх присутствует. У всех трёх `merged_by=github-actions[bot]` и
`auto_merge.enabled_by=github-actions[bot]`.

Это не регресс чего-то недавнего: verification задачи 3.5 заархивированного change
проверяла, что PR слился и что каскад дошёл до соседних PR, но не проверяла, запустились
ли post-merge проверки на получившемся коммите `main`. Дефект лежал в самой приёмке.

Почему сейчас: `main` продолжает набирать непроверенные коммиты при каждой серии
автоматических слияний, а серия приходит по расписанию Dependabot, без участия человека.

## What Changes

- Появляется отдельный workflow-реконсилятор, восстанавливающий **полный** post-merge
  батч для актуальной вершины `main`: `Tests`, `Lint and Typecheck`, `Lighthouse CI`,
  `Security`.
- Реконсилятор поднимает **только отсутствующие** прогоны: для каждого workflow из батча
  он проверяет наличие прогона для текущего SHA вершины и диспатчит лишь те, у которых
  прогона нет вовсе. Состав батча задан признаком «имеет триггер `push` на `main`», а не
  перечнем имён, поэтому пятый такой workflow войдёт в батч без правки требования.
- Прогонов одной проверки для одного SHA бывает несколько — общие группы сериализации это
  гарантируют. Правило: покрыто, если есть **хотя бы один** успешный прогон.
- Красный или отменённый прогон **не перезапускается автоматически**. Автоперезапуск
  замаскировал бы настоящий дефект и дал бы петлю: реконсилятор срабатывает повторно, а
  причина красноты остаётся.
- `workflow_dispatch` добавляется в `test.yml` и `lint.yml`; в `lighthouse.yml` и
  `security.yml` он уже есть.
- Секрет не вводится: `workflow_dispatch` и `repository_dispatch` — документированное
  исключение из анти-рекурсии, они создают прогон и от токена по умолчанию.
- Принимается контракт: **полный батч обязан в итоге проверить актуальную вершину `main`;
  проверять каждую быстро перекрытую промежуточную вершину не обязательно.** Тогда одного
  батча на вершине достаточно — она содержит изменения перекрытых коммитов.
- Восстановление объявляется **eventual, а не мгновенным**. Реконсилятор просыпается по
  расписанию, а GitHub предупреждает, что запуск по `schedule` задерживается и может быть
  потерян при нагрузке. Измерено на этом репозитории по 40 последним запускам
  `Published main head monitor` при объявленном `*/10` (39 интервалов, снято 27.08.2026):
  минимум 25 минут, **медиана 49**, максимум **214**. То есть фактический интервал
  расходится с объявленным в 2,5 раза по медиане и в 21 раз в худшем наблюдённом случае.
  Гарантированный быстрый запуск на каждый merge-коммит этим механизмом не достигается и
  в требования не вносится.

**Не входит в этот change** — названо явно, чтобы объём не расползся и чтобы дельты не
столкнулись с параллельной работой:

- смена `github.token` на GitHub App или PAT в шаге слияния. Это возвращало бы push-батч
  напрямую, но требует постоянного секрета и конфликтует с принятым предусловием про
  единственного write-субъекта репозитория;
- монитор публикации `Published main head monitor`, его расписание и предмет измерения;
- контур публикации GitHub Pages;
- требование `Вершина main публикуется или об этом сообщается` — оно не модифицируется
  здесь ни в какой части.

## Capabilities

### New Capabilities

Новых capability не вводится: предмет — post-merge поведение того самого механизма
автоматического слияния, чьи требования уже живут в существующей capability.

### Modified Capabilities

- `dependency-update-automation`: дельта содержит **только `ADDED Requirements`**, три
  требования — вершина в итоге получает полный набор post-merge проверок независимо от
  субъекта слияния; восстановление избирательно и не выдаёт неудачу за покрытие; каждая
  проверка батча воспроизводима явным запуском. Существующие требования этой спеки, включая
  требование про публикацию вершины, не модифицируются.

## Impact

- **Новый файл:** workflow-реконсилятор в `.github/workflows/`.
- **Изменяются:** `.github/workflows/test.yml` и `.github/workflows/lint.yml` — добавляется
  триггер `workflow_dispatch`. Поведение существующих триггеров не меняется.
- **Права:** `actions: write` (у ключа одно значение, и запись включает чтение) плюс
  `contents: read` для выгрузки кода. Секреты не добавляются.
- **Тесты:** новые проверки в `web/tests/` — на выбор диспатчируемых workflow по
  фикстурам и на состав триггеров затронутых workflow.
- **Известное отклонение, которое этот change фиксирует, но не устраняет:** слияние,
  выполненное токеном по умолчанию, по-прежнему не порождает push-событий. Восстановление
  компенсирует последствие, а не убирает причину.
- **Обязательные контексты защиты ветки** не расширяются и не сокращаются: новый workflow
  в условие публикации не входит.
- **Побочное следствие для публикации, названное явно:** триггер публикующего workflow не
  фильтрует по событию апстрим-прогона, поэтому успешное восстановление `Tests` с большой
  вероятностью повлечёт публикацию. Требований про публикацию change не меняет, но
  утверждать «публикация не затрагивается» было бы неверно.
- **Остаточный риск прав:** `actions: write` — право уровня репозитория; ограничение целей
  диспатча держится на реализации и тесте, а не на правах.
