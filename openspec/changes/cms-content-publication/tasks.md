## 4. Журнал происхождения и ревизии

- [ ] 4.1 Неизменяемый журнал: запись на событие изменения контента — номер из возрастающей
      последовательности, отпечаток контента, номер предшествующей записи, маркер события; плюс
      высшая достигнутая отметка, не уменьшающаяся при операциях с базой
- [ ] 4.1a **Каноническая форма отпечатка:** детерминированный порядок типов, записей, связей и
      ключей; перестановка объектов в ответе, другое разбиение на страницы и другой порядок ключей
      отпечаток не меняют. Негативная проверка: перемешать порядок в ответе — отпечаток тот же
- [ ] 4.1b **Отпечаток привязан к событию, а не прочитан позже:** состояние берётся из транзакции
      этого изменения либо привязывается к глобальной ревизии источника. Проверка: два быстрых
      сохранения дают две записи с **разными** отпечатками (наивный обработчик даст оба по
      последнему состоянию)
- [ ] 4.2 Снимок несёт **два** числа: номер **наблюдённой записи** журнала (последняя запись на
      момент снятия) и **производную** ревизию контента. Ревизия: новое содержимое и ручной
      возврат текста → номер новой записи; опознанное восстановление базы → номер первой записи с
      тем же отпечатком (ниже отметки); восстановление с **неизвестным** журналу отпечатком →
      ревизия не определяется, нужно подтверждение
- [ ] 4.2a Маркер **«принятие состояния»**: подтверждение восстановленной базы записывает запись,
      и принятое содержимое получает ревизию на уровне новой отметки. Проверка: после принятия
      обычный календарный прогон идёт без подтверждения, а следующий откат — снова с ним.
      Запись создаётся **только** для состояния системы управления, не для ручной выкладки старой
      пары
- [ ] 4.3 Негативная проверка на этот случай: после восстановления базы гейт публикации обязан
      покраснеть. Прежние редакции делали это недостижимым **дважды** — сначала правилом
      «совпадение отпечатка не подменяет номер», потом сравнением устаревания по ревизии вместо
      наблюдённой записи; проверка обязана ловить оба возврата
- [ ] 4.4 Совпадение отпечатка без маркера требует подтверждения человеком
- [ ] 4.5 Журнал не переписывается; попытка изменить или удалить запись отклоняется
- [ ] 4.6 Сохранность журнала входит в резервное копирование; недоступный или пустой журнал при
      непустой истории публикаций останавливает публикацию и требует подтверждения
- [ ] 4.7 Маркер восстановления ставится процедурой восстановления базы (действие вне системы
      управления); забытый маркер даёт случай «совпадение без маркера»
- [ ] 4.8 Атомарность присвоения номера записи при конкурентных **изменениях контента** (не при
      конкурентных прогонах снимка: запись появляется на событие изменения, а два снимка одного
      состояния делят одну ревизию и один номер наблюдённой записи)
- [ ] 4.9 Стартовые значения: отметка равна нулю до первой записи, первая запись — маркер
      «первичный перенос»

## 7. Гейт публикации

- [ ] 7.1 Пара «коммит и снимок» как единица проверки; публикуется ровно проверенная пара
- [ ] 7.2 **Различить два случая, а не требовать подтверждения для всякой ревизии ниже отметки:**
      *устаревание* — есть запись новее **наблюдённой записи** снимка → выкладка отменяется
      автоматически, отмена записана, подтверждение НЕ требуется, для последней записи запущен
      прогон; *регресс* — наблюдённая запись последняя, а ревизия ниже отметки → подтверждение
      обязательно. Негативные проверки на обе ветви, включая «пять правок быстрее прогона не
      требуют ни одного подтверждения»
- [ ] 7.2a Гарантируется **прогон**, а не выкладка: при неуспехе прогона нового состояния сайт
      остаётся на прежнем опубликованном, изменение не считается опубликованным
- [ ] 7.3 Ручная публикация выкладывает **новейшую** проверенную пару вершины и называет её
      идентификатор; при отсутствии пары отказывает и не собирает из живой системы управления
- [ ] 7.4 Подтверждённый откат: явное указание идентификатора снимка, подтверждение, запись «кто,
      какая пара, почему не вершина» — **той же записью об откате, которую требует требование о
      ручной публикации**; второго журнала не заводить, и в журнал происхождения контента такая
      выкладка не пишет вовсе. Термин «журнал выкладок» из прежней редакции этого пункта снят:
      ни одно требование его не определяет. Отказ для пары старше названного срока хранения
      снимка; событийный путь исключением не пользуется

## 8. Триггеры публикации

- [ ] 8.1 Аутентифицированный запрос из системы управления запускает существующий обязательный
      прогон на вершине основной ветки
- [ ] 8.2 Перечень событий: публикация, изменение опубликованной записи, снятие с публикации,
      удаление, замена медиафайла опубликованного контента
- [ ] 8.3 Параметры запроса не влияют на собираемое; неаутентифицированный запрос игнорируется
- [ ] 8.4 Очередь на один ожидающий прогон без отмены текущего; серия правок сходится к
      публикации последнего состояния
- [ ] 8.4a **Снять противоречие с настройкой concurrency обязательного прогона.**
      `.github/workflows/test.yml:13-14`, `group: tests-${{ github.ref }}` задаёт
      `cancel-in-progress: true`, то есть на `main` каждое следующее событие **отменяет идущий
      прогон**, а принятое требование говорит «прогон отменён → публикация не запускается».
      С триггером по изменению контента и суточным прогоном отменять друг друга начнут ночной
      прогон и push в `main`. Задача 8.4 требует обратного — очереди без отмены текущего, — и
      без правки concurrency она невыполнима. Ни в Impact, ни в задачах это прежде названо не
      было.

      **РЕШЕНО (владелец, 2026-08-24), чекбокс намеренно остаётся открытым: подход выбран,
      сама правка `concurrency` в workflow — предмет реализации, а не этой правки спеки.**
      Отдельная группа concurrency для событий публикации, с `cancel-in-progress: false`.
      GitHub Actions сам держит не больше одного ожидающего
      прогона на группу и заменяет его следующим событием, не трогая текущий — это и есть
      требуемая 8.4 «очередь на один без отмены текущего», без своего замка или очереди в коде.
      Группа `tests-${{ github.ref }}` с `cancel-in-progress: true` остаётся как есть для
      обычных PR-прогонов (там отмена нужна — экономит минуты CI на серии пушей в PR); события
      публикации (8.1 внешний запрос, 8.6 календарный прогон, push в `main`) получают свою
      группу с `cancel-in-progress: false`. Заводить кастомный лок/семафор не нужно
- [ ] 8.5 Сверка при потерянном оповещении: расхождение опубликованного состояния с контентом
      обнаруживается без участия оповещения
- [ ] 8.6 Календарный публикующий прогон: **суточное** расписание (решение Q23), отставание —
      сутки плюс длительность прогона, явно заданный часовой пояс, независимость от настроек
      машины
- [ ] 8.7 Сверить с change «свежесть публикации», что триггеры не задвоены: поводы публиковать
      описаны здесь (изменение контента, календарный прогон, сверка при потерянном оповещении),
      метка `/published-at.json`, эндпоинт свежести и монитор — там. Связь числовая: порог
      протухания там выведен из суточной частоты отсюда, поэтому изменение частоты обязано
      пересматривать порог, и наоборот
