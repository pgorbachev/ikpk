## Goals / Non-Goals

**Goals:** убрать место без потери действующей серверной защиты, сохранить одну попытку
и токены неизменными, обеспечить проверяемые активацию и восстановление.

**Non-Goals:** восстановление PII из хеша, хранение полного payload, новая база/реестр,
изменение провайдера, сроков защиты или принятой границы неизвестного ключа. Утраченное
место старой попытки не восстанавливается обещанием «просто повторить».

## Decisions

### Два назначения отпечатка

Поле `fingerprint` и `keyVersion` сохраняют прежний смысл и байты: полный канонический
JSON восьми полей, HMAC-SHA256. Оно обслуживает проверку того же ID и существующий токен
подтверждения (новый ID + полный отпечаток). Новые запросы и старая кешированная форма
принимаются одним API с прежним необязательным `venue`.

Дополнение записи — необязательная пара `comparisonVersion: "without-venue-v1"` и
`comparisonFingerprint`. Второй HMAC вычисляется под **тем же** `keyVersion` записи над
доменом `ikpk-payment-without-venue-v1\n` и JSON с фиксированным порядком прежних
нормализованных полей: firstName, lastName, seminar, amount, startDate, email, phone.
Версия проекции отдельно от версии ключа: ротация секрета не меняет состав данных.
Авторитетный режим — поле верхнего уровня `comparisonMode: "preparing" | "active"`
в том же `payments.json`; отдельный файл/реестр не нужен. Парсер и каждый writer сохраняют
его вместе с records. Переход preparing → active записывается неделимо с нулевой проверкой
подходящих opaque; active → preparing при работающих оплатах запрещён. Отсутствующий или
неизвестный режим при обычном старте — закрытый отказ, а не default preparing. Первый
переход исходного legacy-файла без режима выполняется явно при остановленных писателях
после сохранения согласованной копии, до первой dual-write записи; это не автоматический
fallback для последующего восстановления. Новая пустая установка явно инициализирует режим.
Отсутствуют оба поля — legacy; неполная пара, неверный digest или неизвестная версия —
ошибка хранилища с закрытым отказом, а не молчаливое игнорирование. Дополнительные поля
сохраняются всеми путями записи, перезапуском и резервным восстановлением.

При создании запись с обоими отпечатками сохраняется **до** POST провайдера, включая
исход таймаута. При сравнении подставляется ключ версии сравниваемой записи. Прежние
canary и правила ротации сохраняются. Неизвестный ключ остаётся прежней явно принятой
границей; его удаление/ротация не используются как способ пройти миграционный gate.

### Доказуемое дополнение legacy

Поступивший валидный payload можно использовать только после точного совпадения полного
HMAC с конкретной старой записью под её историческим ключом. Совпадение даёт право добавить
пару сравнения, но не менять полный HMAC, ключ, ID, статус или времена; обычное авторитетное
обновление статуса остаётся отдельной операцией. Это применимо к тому же ID и к найденным
полным совпадениям при новом ID, в том числе с `venue: null`.

Для `succeeded` ответ `already_paid` остаётся безусловным; **дополнение данных** требует
отдельной проверки полного HMAC до раннего возврата. Знание ID, успешный статус, семь
совпавших полей или снимок браузера без полного совпадения не дают права на дополнение.
Если ключ неизвестен или payload отличается — запись не дополняется, безопасный исход
повтора остаётся прежним. Доказанную пару не перезаписывать по другому payload.

### Оpaque legacy и неделимость

Подходящая запись — та, которая по существующим `isLiveUnfinished` / `isFreshConfirmed`
входит в окно защиты и имеет известный ключ. Opaque — подходящая запись без пары сравнения.
Отменённые, истёкшие и неизвестного ключа сами по себе gate не удерживают. Граница 14 суток
и fallback времени подтверждения сохраняются; новая политика TTL здесь не вводится.

После включения сравнения семи полей сервер сначала пробует доказуемое дополнение из
полученного запроса. Если остаётся хотя бы одна opaque-запись, **любой новый ID** получает
HTTP 503 с отдельным исходом `compatibility_pending`, без ID старой записи, токена,
создания локальной попытки и POST провайдера. Это отказ проверить совместимость, а не
утверждение, что клиент уже платил. Он не помечает чужую запись для сверки и не расходует
токен. При отсутствии opaque работает обычный приоритет: незавершённое совпадение семи
полей → сверка, затем подтверждённое → явное подтверждение, иначе создание.

Проверка opaque, поиск совпадений, проверка/потребление токена, повторная проверка и
сохранение новой записи выполняются неделимо. Использовать существующую очередь
`exclusive` для **всех сохранений** записей, включая слияние результата GET статуса с заново
прочитанным состоянием. Сам сетевой GET может оставаться вне очереди, чтобы медленный
опрос не задерживал все оплаты; внутри очереди нельзя сохранять старый снимок поверх
новой записи или дополненного HMAC. Свежего merge недостаточно: результат GET применять
только если значимые наблюдённые перед сетевым запросом поля (status, ID провайдера,
confirmedAt) всё ещё совпадают с текущей записью; иначе ответ отбросить и при необходимости
проверить заново. Ни один автоматический writer не переводит уже терминальную запись
назад в незавершённую и не заменяет подтверждённый успех противоречащим поздним ответом.
Первый confirmedAt сохраняется при повторных succeeded-наблюдениях; у уже успешной legacy
без confirmedAt сохраняется прежний fallback к createdAt. Время подтверждения устанавливается
при первом авторитетном переходе к succeeded, а не каждом webhook. Дополнительный счётчик
ревизий не нужен: достаточно условного merge существующих значимых полей. Не добавлять
распределённую блокировку или реестр. Путь старого ID
не обходится созданием нового ID. Состояние, появившееся после линейной точки создания,
влияет на следующие запросы; уже принятый новый платёж задним числом не отменяется.

Поздний webhook, GET статуса, восстановление состояния или возвращение известного ключа
могут сделать ранее истёкшую/невидимую legacy-запись подходящей. Gate проверяется на каждом
новом запросе, включая подтверждающий, а не только на запуске или при выкладке.

### Форма и смешанные клиенты

Новая форма не содержит элемента места; payload новой попытки несёт null. Старое место
берётся только из снимка своей попытки с прежней нормализацией и сохраняется при повторных
POST/восстановлении/подтверждении. Новая самостоятельная попытка место не наследует.
При переназначении канонического ID сохраняется имеющийся снимок именно этой попытки;
семипольное совпадение **не доказывает её место**, поэтому пришедший снимок с другим местом
не выдаётся за доказанный старый payload. Без точного снимка безопасен прежний исход сверки,
а не повтор с догадкой или снятие удержания.

Для `compatibility_pending` обновлённый клиент сообщает: «Сейчас не удаётся безопасно начать новую оплату.
Попробуйте позже или свяжитесь с нами».
Он снимает только предварительное удержание отправленного ID и удаляет его снимок;
семь введённых значений остаются лишь в живой форме до закрытия, перезагрузки или следующей
ручной отправки. Не создавать отдельный session-draft и не сохранять эти значения после
закрытия. Новый ручной POST получает новый ID, прежний токен не переносится. Клиент не
предлагает подтверждать неустановленный дубль; другие удержания не снимаются. Это явное
узкое дополнение основных правил удержания/очистки, а не переименование 503 в валидацию.
Автоповтора POST нет. Старая кешированная форма может показать
общую ошибку и удержать свой ID; её последующие POST всё равно блокируются сервером,
проверка статуса несуществующего ID остаётся `not_found`. Это проверяется отдельно.

## Risks / Trade-offs

- [Глобальная временная недоступность новых оплат] → подготовительная запись обоих HMAC
  до включения новой семантики; gate и честный ответ обязательны, срок ожидания неизвестен.
  Это цена предлагаемого безопасного перехода; автоматического обхода по таймеру нет.
  Рассмотрено общее подтверждение для всех клиентов при opaque `succeeded`: оно могло бы
  смягчить отказ, но требует отдельного протокола неопределённого совпадения и новых текстов;
  существующее «по этим данным оплачено» без доказанного совпадения неверно. Здесь выбран
  единый временный отказ, доступность которого владелец ещё должен принять до реализации.
- [Разные реальные проведения имеют одинаковые семь полей] → считаются повтором;
  успешная прежняя оплата требует существующего подтверждения. Новый ID сам по себе не выход.
- [Потеря места в браузере] → восстановить полный HMAC нельзя; безопасная сверка сохраняется.
- [Откат старого сервера стирает проекцию] → такой откат после активации запрещён при
  открытом приёме платежей. Смена только интерфейса допустима при сохранении нового сервера.

## Migration Plan

1. До кода согласовать последствия перехода и устранить пересечение с picker, указанное
   в `proposal.md`; проверить совместную применимость. Два независимых ревью денежного риска.
2. Реализовать и отдельно проверить подготовительный сервер: читает оба формата, записывает
   два отпечатка для новых попыток, безопасно дополняет legacy; пока старая форма работает,
   поиск разных ID остаётся прежним по восьми полям. Это не активация удаления места.
3. Перед первой записью новым сервером получить согласованную копию при остановленных
   писателях: все четыре файла состояния, актуальная конфигурация/версии ключей и доступное
   защищённое средство их восстановления; проверить восстановление без реального провайдера.
   Секреты не помещать в отчёты. Идентифицировать серверный релиз и режим сравнения.
4. Подготовительный период длится до **измеренного нуля подходящих opaque**. Отчёт содержит
   только агрегаты по статусам/возрастам/версиям и хеш снимка, без PII/секретов. Нельзя
   удалять строки, менять времена или выводить ключ из обращения ради нуля. Для проверки
   активации остановить приём новых POST и сериализовать оставшиеся писатели; включить
   сравнение семи полей с повторной проверкой текущего состояния. При ненулевом числе
   активацию отложить. Возобновить сервер, затем публиковать форму без места.
5. После активации все клиенты, включая старые вкладки, обслуживаются семипольной защитой
   и runtime gate. Не возвращать сервер в подготовительный режим: форма без места может
   оставаться в кеше. Перезапуск сохраняет выбранный режим; выпуск/восстановление проверяет
   согласованность режима, кода и данных. Потеря доказательства режима — остановить создание.
6. Безопасный откат — вернуть старую форму, оставив совместимый сервер в активном режиме,
   либо остановить создание новых платежей и исправить совместимый сервер. Старый сервер
   отбрасывает новые поля при **любом** сохранении: запускать его поверх актуальных данных
   и обслуживать новые POST нельзя. Восстановление старого снимка не является откатом кода:
   нужно сохранить текущее состояние, сопоставить все попытки после снимка и восстановить
   весь согласованный комплект с ключами/токенами. До завершения сверки приём новых оплат
   закрыт; потерянные записи не считаются отсутствовавшими платежами.

Код, тесты, production-измерение, активация и восстановление в этой поставке не выполняются.
