- [ ] 1.1 Провести два независимых ревью плана: доказуемость перехода данных и последствия
  для оплаты/отката. Получить согласование временной недоступности новых оплат при opaque

- [ ] 1.2 Ограниченно обновить существующий `payment-seminar-picker` по перечню в

  валидацией и совместным применением в одноразовом worktree к свежей основной спецификации;
  последующий архив picker не должен возвращать место или ослаблять дедупликацию.

## 2. Серверная подготовка и проверки после согласования

- [ ] 2.1 В отдельной сессии с чистым контекстом подготовить RED-проверки новой защиты:
  обе формы и разные ID с одинаковыми семью полями; pending/unknown/verification/succeeded;
  разные места и null; изменения каждого из остальных полей. Отдельно — тот же ID с
  изменённым местом, неизменный полный HMAC, привязка токена ко всем восьми полям.
- [ ] 2.2 Добавить проверки legacy: полное доказанное совпадение под текущим/предыдущим
  ключом дополняет запись; тот же succeeded ID с другим payload возвращает already_paid,
  но не дополняет; семь совпавших полей без полного HMAC не дополняют. Проверить неизвестный
  ключ, обе стороны 14-суточной границы, confirmedAt/fallback, отменённые записи, неверную
  пару/версию проекции. Сравнивать байты полей и число POST провайдера, не только HTTP-коды.
- [ ] 2.3 Реализовать чтение/сохранение двух форм записей, dual-write до POST провайдера,
  доказуемое дополнение legacy и подготовительный режим с прежним полным сравнением.
  Все записи, включая свежий merge после GET статуса, сериализовать существующим механизмом.
- [ ] 2.4 Реализовать активное семипольное сравнение и runtime gate: любой новый ID при
  оставшихся подходящих opaque даёт compatibility_pending без provider POST, локального
  draft, токена и чужого ID. Проверить отказ при присланном действительном токене; не
  расходовать его, не помечать чужую запись для сверки. Проверить конкурентные POST,
  webhook, отложенный ответ GET статуса, дополнение HMAC и отсутствие потерь свежих полей.
  Применять результат GET условно по наблюдённым status/providerId/confirmedAt: поздний
  pending/unknown после succeeded не снимает gate. Для legacy старше 14 суток проверить
  этот порядок и provider POST = 0; повторный succeeded не меняет первую дату подтверждения.
  Все автоматические writer-пути сохраняют терминальное состояние при устаревших ответах.
- [ ] 2.5 Проверить явную первичную инициализацию comparisonMode в payments.json, смену
  режимов и сохранение активного режима после рестарта: нулевой
  замер перед активацией не заменяет runtime gate. Позднее подтверждение истёкшего legacy,
  возвращение ключа и восстановление снимка снова включают отказ; произвольная смена
  режима или неизвестное состояние режима не разрешают старую защиту при новом UI.

## 3. Форма и восстановление

- [ ] 3.1 Проверить и реализовать форму без места: новая попытка с null, последовательные
  повторы старого ID, подтверждение дубликата, разные удержания, новая оплата после старой.
  Не терять место при пересохранении снимка и не выдавать снимок нового ID за точный старый
  payload после канонического переназначения по семи полям. Без снимка сохранять безопасную
  сверку, не угадывать место и не открывать новый платёж автоматически.
- [ ] 3.2 Добавить честный временный исход compatibility_pending: только предварительное
  удержание и снимок отправленного ID удалены, семь полей остались в живой форме до
  закрытия/перезагрузки/новой ручной отправки; отдельного черновика нет. Новый POST получает
  новый ID без переноса старого токена; чужие удержания сохранены. Проверить очистку и
  отсутствие ложного сообщения об оплате. Проверить старую кешированную форму и её generic-error/GET
  not_found/повтор: серверная защита сохраняется и без нового клиентского обработчика.
- [ ] 3.3 Пройти проверки API, формы, перезапуска и ротации, релевантные гейты web/payments,
  браузерную проверку узкого/широкого экрана и клавиатуры. Целевая негативная проверка:
  выключенная проверка opaque или venue-only обход обязаны сделать тест красным.

## 4. Приёмка и отдельный выпуск

- [ ] 4.1 Провести два независимых ревью реализации высокого риска и обязательный CI;
  провести отдельный проход на переусложнение по диффу: что удалить или заменить штатным
  средством; принятые замечания закрыть, отклонённые назвать с причиной.
- [ ] 4.2 Уточнить существующий runbook: подготовительный сервер → измеренный gate →
  активный сервер → новая форма. Проверить согласованную копию всех четырёх файлов и
  конфигурации/ключей при остановленных писателях, восстановление с обоими HMAC и токенами
  без реального провайдера. Доказать отказ старому backend-откату с открытым приёмом оплат;
  сохранить все записи после снимка, а не восстановить старую копию поверх них.
- [ ] 4.3 После отдельного разрешения на выпуск измерить фактический cohort без PII,
  предъявить нулевой gate и live-состояние режимов. Ненулевой gate означает отложенную
  активацию, а не формальную готовность через 14 дней. В этой поставке production не читать
  и не менять. Откат UI сохраняет активную серверную защиту; backend восстанавливать по
  проверенной процедуре с закрытым созданием до сверки.
- [ ] 4.4 После приёмки архивировать change; проверить применимость обновлённого picker
  и гейт ссылок. Наличие всех planning-файлов не означает выполнение задач или разрешение
  реализации/публикации.
