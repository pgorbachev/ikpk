## Context

See proposal.md for the operational gap. The repository already has the paired staging operator, a fixed one-time `initial-prod` profile, and a reusable production static-only profile. The paired host flow already prepares CMS artifacts before the fence, captures SQLite/media, migrates a candidate database, activates CMS, publishes static output, and has a pre-commit recovery path. Production has its own paths, units, and static rollback state; the new profile must not reuse staging paths or widen either existing production profile.

## Goals / Non-Goals

**Goals:** Reuse the current paired operator and its journal, backup, migration, acceptance, and recovery behavior for repeatable production operations; bind both releases to one admitted source; keep production content local to production.

**Non-Goals:** Do not introduce a deployment service or new framework; do not change production data in this proposal; do not copy staging194 content; do not change the target or CMS/data effects of the one-time initial install or static-only production profile; do not add post-commit database restore. Static-only publication joins the shared pointer-switch lock and matching pending-operation refusal protocol.

## Decisions

- Coordinate the staging194 `dev` to current-`main` source change in the existing `manual-publication-only` delta; this change defines the production behavior and does not duplicate staging admission.
- Add one separately configured reusable production-paired profile to the existing client and host helper. Bind it to the inventoried production host, CMS/static paths, service, writer gate, state directory, and off-host backup destination. Keep `production-static` read-only with respect to CMS.
- Reuse the paired `cms-update`, `static-publish`, and `recover` phases rather than creating a new launcher. A new operation requires the stable published Release, exact current canonical `main` SHA, successful required CI, and `release-preflight`; recheck them before each first-time CMS/static switch. If admission changes after fencing, make no next switch and use same-ID recovery. Recovery without a DB restore and committed finalization work offline; after local DB restore, remain fenced until the existing canonical restore-event write is pushed and verified, then reopen. A matching journal owner may pass its own valid marker only for recovery/finalization; unrelated operations remain blocked.
- Reuse the site destination's existing `.publication.lock` for every production paired, static-only, site-refresh, and CMS UI Restore pointer switch. The lock is currently created mode 0600 by the remote publisher, while CMS and publisher run as separate service principals; provision the same inode for only those two principals (for example through a dedicated group), never unrelated users. The remote publication session holds it across its complete worker run.
- Keep the existing CMS refresh state lock as the reservation/handoff record. The API acquires the destination lock first, then its local state lock, records the running reservation and spawns the existing detached worker while still holding the destination lock. The worker acquires the destination lock before capture/build/switch and verifies reservation ownership. The paired/static operators inspect refresh state under the destination lock and refuse a live/unreconciled refresh. Restore uses the same lock-first path before its existing local lock and pointer switch. This global-before-local order prevents lock inversion; interrupted API/worker handoff is reconciled from the existing PID/state record.
- At UI Restore, compare the target release `release.json.commit` with the currently installed `IKPK_INSTALLED_COMMIT` before switching `current`. This invalidates a pre-paired `previousReleaseId` after the paired CMS source changes while allowing a content-only release built by the installed source; do not add a second rollback mechanism.
- Persist the paired-operation marker and journal phase under the shared lock before the first live side effect, including the fence. Treat malformed/mismatched marker as global fail-closed. The marker is destination-visible and read by site-refresh, static-only, and Restore while holding the common lock. Keep it across the `cms-update`/`static-publish` process boundary; clear only on committed finalization or verified recovery. Retry only the next journal-owned phase for the same ID/source; after durable commit, retry only final health, writer reopen, and marker removal, never DB restore or pointer switch.
- For the first pair upgrade, the installed CMS predates the destination lock and marker. While holding the destination lock, use the existing write gate to block its refresh/Restore endpoints; while the service remains running, wait for accepted requests and recorded refresh PID, descendants, and `systemd-run --user --scope` unit to exit normally. Stop the service only after they finish, then recheck that no request or worker remains and verify CMS/static pointers and refresh state are terminal. Do not kill workers. If liveness or state cannot be proven, do not capture or activate and use only existing safe pre-acquisition recovery when DB and pointers are unchanged.
- Before CMS activation, record only the previous `IKPK_BUILD_WORKSPACE` and `IKPK_INSTALLED_COMMIT` values in the protected operation state. Atomically update those two keys in the existing service environment to the ready candidate workspace and exact admitted SHA; verify the workspace readiness before restart. Recovery restores only those two values, preserving every other environment entry and never logging secrets. Acceptance includes one subsequent CMS UI refresh using that installed workspace.
- Capture live production SQLite and uploads after verified writer closure. Use the existing migration runner on the candidate DB, and verify the sealed backup off-host before activation. Do not import the staging194 database or media.
- Complete dependency preparation and the CMS artifact before the fence. Prepare web dependencies with the existing `npm ci` in the extracted source tree. Prepare CMS dependencies with `npm ci` against the official npm registry, or reuse only a complete CMS lock-hash generation already verified by the existing helper; that fallback does not apply to web dependencies. If web preparation, CMS preparation, or the artifact build fails, refuse before the fence with writers open. Never use a third-party mirror or change persistent npm configuration.
- Reuse the canonical `state/cms-provenance` journal and its high-water mark for production content. Before writing the operation marker or fencing writers, read and validate the journal/HWM without mutation. After the fenced production capture, require `snapshot.fingerprint` to equal the latest entry's `fingerprint`, and require observed entry, content revision, and HWM to match that preflight lineage before migration. Recheck all four captured values before each first-time CMS/static switch. Bind the verified lineage to the production target, operation, Release/source evidence, and sealed database/media bytes. The journal remains outside the restored database; deployment does not initialize or reset it, and database recovery records the existing restore event without lowering its high-water mark. Do not reuse staging/initial-prod snapshot exceptions or the static-only proof.
- The existing `PublicationStateStore` exposes publication and `acceptState` writes but no restore-event write. Extend that store and the `cms-content-source` entry type with the smallest restore-event operation, reusing its `recordEvent` ledger, append-only commit/push path, and expected-observed-entry check. Keep the existing `checksum` payload unchanged for old CMS readers; add `pairedOperationId` and a separate checksum over the legacy entry fields plus marker and operation ID, which only the new reader verifies. This binding is required only for new paired-recovery restore entries; do not rewrite historical entries. A same-operation retry accepts only the exact next event matching operation ID, `restore` marker, fingerprint, and previous-entry number; the same fingerprint under another operation ID is not a match. Do not add a queue or separate service. If GitHub is unavailable after local byte restoration, keep the same operation journal and writer fence until the canonical event is pushed and read back; committed finalization and recovery with no DB restore remain offline.
- Build the paired production site's snapshot and static output with the existing production capture policy (`DEPLOY_MODE=prod`, production payment/form configuration, and configured production chat loader). Staging demo form stubs and `CHAT_LOADER_SRC=none` remain staging-only; browser acceptance avoids external write actions.
- Keep the durable paired journal and explicit pre-commit recovery. Commit only after CMS runtime proof and static candidate/browser acceptance; prohibit database restore after commit.
- Keep logs and receipts limited to non-secret identities, hashes, phase, and counts. Existing CMS users and grants are compared by the migration audit; only reviewed source changes may explain differences.

## Risks / Trade-offs

- **Risk:** Production fence can remain closed after an interrupted paired operation → **Mitigation:** Preserve operation ownership and the verified backup; allow retry of the same operation or explicit recovery only, with an acceptance test for both paths.
- **Risk:** A successful staging rehearsal may not expose production-specific path, permissions, or SQLite/media differences → **Mitigation:** Run the exact released source through the existing paired workflow on 194 first, test production behavior against an isolated production-like fixture, then perform read-only production preflight. Capture and verify the production-only backup as the first fenced operation phase before migration or live data mutation.
- **Risk:** Post-commit rollback could pair old code with a newer/incompatible schema or discard production writes → **Mitigation:** This change has no post-commit database, code, environment, or static-pointer rollback path. The committed pair may only be verified/finalized; any future rollback needs a separately admitted operation proving schema compatibility and preserving production writes.
- **Risk:** CMS Restore and the site-refresh worker use a CMS-local lock while the remote publisher uses a mode-0600 destination lock → **Mitigation:** Give only the fixed CMS and publisher service principals access to the same destination lock inode, acquire it first in every pointer-changing path, and test contention and the durable marker between paired commands.
- **Risk:** The old CMS does not honor the destination lock → **Mitigation:** Gate its refresh/Restore endpoints, wait for in-flight calls and detached/systemd workers to exit normally while the service still runs, stop it only after they finish, and recheck that none remain; do not kill or proceed on ambiguous state.
- **Risk:** Production static-only runs before the CMS understands the shared lock → **Mitigation:** Refuse static-only until the installed CMS is verified lock/marker-aware; the initial pair update performs legacy quiescence.
- **Risk:** GitHub is unavailable after local database restore → **Mitigation:** Keep the same operation journal and writer fence; retry the existing idempotent restore-event append and reopen only after remote verification. No separate queue is introduced.
- **Risk:** A process can stop between any two phase writes or after commit but before reopening writers → **Mitigation:** Durably write marker/journal before the first live side effect; test phase-by-phase recovery, safe pre-backup reopening only when live state is unchanged, same-ID post-commit finalization without database restore or pointer reswitch, and the fenced restore-event retry boundary.

## Migration Plan

1. Implement the profile by extending the current operator/config schema and tests; build neither a parallel tool nor a new host service.
2. Pass isolated profile/config/capture/build/recovery fixture tests, per-switch freshness, offline no-DB-restore recovery/finalization, restore-event outage/idempotency, crash-boundary, lock-contention, marker-gap, UI Restore, API/worker handoff, legacy-CMS quiescence, and next-site-refresh tests, and all canonical CI; independently review profile admission, target binding, backup, journal, fence, shared lock, environment update, retry, and recovery changes.
3. Merge to main, wait for its required CI, publish a stable Release for the exact SHA, and require `release-preflight` before packaging or installing it.
4. Deploy that exact released revision to staging194 through the existing paired workflow after the source-admission reconciliation in `manual-publication-only`. Verify content/user/grant preservation, CMS health/database proof, staging-only no-chat behavior, browser acceptance, and recovery. Separately run production-profile code against an isolated production-like fixture with temporary SQLite/media/config paths to verify production capture/build flags, lock refusal, crash recovery, and recovery without production data or credentials.
5. After the main-based 194 path succeeds, verify no consumer or active workflow still uses remote `dev`, then delete that branch only if its freshly observed SHA is unchanged and the reviewed deletion is accepted by the server.
6. For a later explicit production operation, repeat Release/CI preflight and perform a read-only check of production health, free space, lock, and operation state. The paired operation then acquires the common lock, writes its marker, fences writers, and creates/verifies the off-host production-only SQLite/media backup before migration or live database mutation. Run CMS activation, production-mode static acceptance, static publish, and commit. If a pre-commit phase fails before backup, use the existing safe recovery only when live SQLite and pointers prove unchanged; after destructive work, recover from the verified off-host backup before reopening writers.
