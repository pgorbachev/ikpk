## Context

See proposal.md for the operational gap. The repository already has the paired staging operator, a fixed one-time `initial-prod` profile, and a reusable production static-only profile. The paired host flow already prepares CMS artifacts before the fence, captures SQLite/media, migrates a candidate database, activates CMS, publishes static output, and has a pre-commit recovery path. Production has its own paths, units, and static rollback state; the new profile must not reuse staging paths or widen either existing production profile.

## Goals / Non-Goals

**Goals:** Reuse the current paired operator and its journal, backup, migration, acceptance, and recovery behavior for repeatable production operations; bind both releases to one admitted source; keep production content local to production.

**Non-Goals:** Do not introduce a deployment service or new framework; do not change production data in this proposal; do not copy staging194 content; do not change the target or CMS/data effects of the one-time initial install or static-only production profile; do not add post-commit database restore. Static-only publication joins the shared pointer-switch lock and matching pending-operation refusal protocol.

## Decisions

- Coordinate the staging194 `dev` to current-`main` source change in the existing `manual-publication-only` delta; this change defines the production behavior and does not duplicate staging admission.
- Add one separately configured reusable production-paired profile to the existing client and host helper. Bind it to the inventoried production host, CMS/static paths, service, writer gate, state directory, and off-host backup destination. Keep `production-static` read-only with respect to CMS.
- Reuse the paired `cms-update`, `static-publish`, and `recover` phases rather than creating a new launcher. A new operation requires the stable published Release, exact current canonical `main` SHA, successful required CI, and `release-preflight`; recheck them before each first-time CMS/static switch. If admission changes after fencing, make no next switch and use same-ID recovery. Recovery without a DB restore and committed finalization work offline; after local DB restore, remain fenced until the existing canonical restore-event write is pushed and verified, then reopen. The host journal/maintenance marker owns only paired-operation recovery; it is not a global marker consumed by CMS publishers.
- Require one manually coordinated operator window covering `cms-update` through `static-publish` or verified recovery. The operator excludes concurrent CMS/site publication and UI Restore for the duration. The existing destination `.publication.lock` protects each host command, but does not serialize the complete multi-command window and is not acquired by CMS site-refresh or UI Restore. State this as an operational requirement, not a technical concurrency guarantee.
- At UI Restore, compare the target release `release.json.commit` with the currently installed `IKPK_INSTALLED_COMMIT` before switching `current`. This invalidates a pre-paired `previousReleaseId` after the paired CMS source changes while allowing a content-only release built by the installed source; do not add a second rollback mechanism.
- Keep the paired operation journal and maintenance fence durable across the `cms-update`/`static-publish` process boundary. Malformed or mismatched operation state blocks continuation through this profile. Retry only the next journal-owned phase for the same ID/source; after durable commit, retry only final health, writer reopen, and finalization, never DB restore or pointer switch.
- For the first pair upgrade, use the existing Nginx write gate to reject new routed write and Restore requests, inspect existing refresh state/lock and recorded PIDs, wait for known workers to exit normally, and fail closed on active or unknown state. These checks do not prove an accepted Node handler exited after a client disconnect; record that race as an explicit residual and do not claim application-level in-flight drain or complete concurrency protection. Do not kill workers.
- Before CMS activation, journal the prior values and update the existing service environment for all paired build settings: `IKPK_BUILD_WORKSPACE`, `IKPK_INSTALLED_COMMIT`, `INITIAL_PROD_PROFILE=1`, `DEPLOY_MODE=prod`, `PAYMENT_ROLE=prod`, `PAYMENT_ENDPOINT_PROD`, and `CHAT_LOADER_SRC` from the validated production profile; clear `DEMO_FORMS` and `CHAT_OFFLINE_MESSAGE` for the production child build. Recovery restores the previous values of these nine keys while preserving every unrelated environment entry and never logging secrets. Acceptance includes a subsequent CMS UI refresh using the installed workspace and production build settings.
- Capture live production SQLite and uploads after verified writer closure. Use the existing migration runner on the candidate DB, and verify the sealed backup off-host before activation. Do not import the staging194 database or media.
- Complete dependency preparation and the CMS artifact before the fence. Prepare web dependencies with the existing `npm ci` in the extracted source tree. Prepare CMS dependencies with `npm ci` against the official npm registry, or reuse only a complete CMS lock-hash generation already verified by the existing helper; that fallback does not apply to web dependencies. If web preparation, CMS preparation, or the artifact build fails, refuse before the fence with writers open. Never use a third-party mirror or change persistent npm configuration.
- Reuse the canonical CMS provenance journal on the Git branch whose name is formed by joining `state` and `cms-provenance` with a slash, and its high-water mark for production content. Before writing the operation marker or fencing writers, read and validate the journal/HWM without mutation. After the fenced production capture, require `snapshot.fingerprint` to equal the latest entry's `fingerprint`, and require observed entry, content revision, and HWM to match that preflight lineage before migration. Recheck all four captured values before each first-time CMS/static switch. Bind the verified lineage to the production target, operation, Release/source evidence, and sealed database/media bytes. The journal remains outside the restored database; deployment does not initialize or reset it, and database recovery records the existing restore event without lowering its high-water mark. Do not reuse staging/initial-prod snapshot exceptions or the static-only proof.
- The existing `PublicationStateStore` exposes publication and `acceptState` writes but no restore-event write. Extend that store and the `cms-content-source` entry type with the smallest restore-event operation, reusing its `recordEvent` ledger, append-only commit/push path, and expected-observed-entry check. Keep the existing `checksum` payload unchanged for old CMS readers; add `pairedOperationId` and a separate checksum over the legacy entry fields plus marker and operation ID, which only the new reader verifies. This binding is required only for new paired-recovery restore entries; do not rewrite historical entries. A same-operation retry accepts only the exact next event matching operation ID, `restore` marker, fingerprint, and previous-entry number; the same fingerprint under another operation ID is not a match. Do not add a queue or separate service. If GitHub is unavailable after local byte restoration, keep the same operation journal and writer fence until the canonical event is pushed and read back; committed finalization and recovery with no DB restore remain offline.
- Build the paired production site's snapshot and static output with the existing production capture policy (`DEPLOY_MODE=prod`, production payment/form configuration, and configured production chat loader). Staging demo form stubs and `CHAT_LOADER_SRC=none` remain staging-only; browser acceptance avoids external write actions.
- Keep the durable paired journal and explicit pre-commit recovery. Commit only after CMS runtime proof and static candidate/browser acceptance; prohibit database restore after commit.
- Keep logs and receipts limited to non-secret identities, hashes, phase, and counts. Existing CMS users and grants are compared by the migration audit; only reviewed source changes may explain differences.

## Risks / Trade-offs

- **Risk:** Production fence can remain closed after an interrupted paired operation → **Mitigation:** Preserve operation ownership and the verified backup; allow retry of the same operation or explicit recovery only, with an acceptance test for both paths.
- **Risk:** A successful staging rehearsal may not expose production-specific path, permissions, or SQLite/media differences → **Mitigation:** Run the exact released source through the existing paired workflow on 194 first, test production behavior against an isolated production-like fixture, then perform read-only production preflight. Capture and verify the production-only backup as the first fenced operation phase before migration or live data mutation.
- **Risk:** Post-commit rollback could pair old code with a newer/incompatible schema or discard production writes → **Mitigation:** This change has no post-commit database, code, environment, or static-pointer rollback path. The committed pair may only be verified/finalized; any future rollback needs a separately admitted operation proving schema compatibility and preserving production writes.
- **Risk:** A second operator or CMS/site publisher runs between paired commands → **Mitigation:** Keep a manually coordinated single-operator maintenance window until commit or recovery. This is operational and is not enforced by a shared lock or marker.
- **Risk:** An accepted CMS handler continues after its client disconnects, after Nginx worker drain appears complete → **Mitigation:** Fail closed on known active/unknown worker state, do not kill workers, and explicitly retain the residual race; available host checks do not prove app-level request completion.
- **Risk:** GitHub is unavailable after local database restore → **Mitigation:** Keep the same operation journal and writer fence; retry the existing idempotent restore-event append and reopen only after remote verification. No separate queue is introduced.
- **Risk:** A process can stop between any two phase writes or after commit but before reopening writers → **Mitigation:** Durably write marker/journal before the first live side effect; test phase-by-phase recovery, safe pre-backup reopening only when live state is unchanged, same-ID post-commit finalization without database restore or pointer reswitch, and the fenced restore-event retry boundary.

## Migration Plan

1. Implement the profile by extending the current operator/config schema and tests; build neither a parallel tool nor a new host service.
2. Pass isolated profile/config/capture/build/recovery fixture tests, per-switch freshness, offline no-DB-restore recovery/finalization, restore-event outage/idempotency, crash-boundary, journal/fence refusal, UI Restore source-compatibility, recorded-worker drain, and next-site-refresh production-environment tests, and all canonical CI; independently review profile admission, target binding, backup, journal, fence, environment update, retry, and recovery changes. Do not claim that these tests prove cross-publisher serialization or app-level in-flight drain.
3. Merge to main, wait for its required CI, publish a stable Release for the exact SHA, and require `release-preflight` before packaging or installing it.
4. Deploy that exact released revision to staging194 through the existing paired workflow after the source-admission reconciliation in `manual-publication-only`, using a single-operator maintenance window and confirming recorded worker/state idleness. Verify content/user/grant preservation, CMS health/database proof, staging-only no-chat behavior, browser acceptance, and recovery. Separately run production-profile code against an isolated production-like fixture with temporary SQLite/media/config paths to verify production capture/build flags, refusal on active/unknown recorded workers, crash recovery, and recovery without production data or credentials. The rehearsal does not prove the disconnect race absent.
5. After the main-based 194 path succeeds, verify no consumer or active workflow still uses remote `dev`, then delete that branch only if its freshly observed SHA is unchanged and the reviewed deletion is accepted by the server.
6. For a later explicit production operation, repeat Release/CI preflight and perform a read-only check of production health, free space, per-command publication lock, and operation state. Open one manual single-operator maintenance window and keep it through paired commit or verified recovery. The operator fences writers and creates/verifies the off-host production-only SQLite/media backup before migration or live database mutation. Run CMS activation, production-mode static acceptance, static publish, and commit. If a pre-commit phase fails before backup, use the existing safe recovery only when live SQLite and pointers prove unchanged; after destructive work, recover from the verified off-host backup before reopening writers.
