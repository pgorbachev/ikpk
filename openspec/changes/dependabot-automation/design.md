## Context

Мотивация — в `proposal.md` («Why»); требования — в
`specs/dependency-update-automation/spec.md`. Здесь только то, что определяет реализацию.

Ограничения, из которых всё вытекает:

- **Публикация подписана ровно на один workflow.** Событие `workflow_run` не умеет
  требовать успеха нескольких workflow сразу, поэтому в условие выкладки входит только
  `Tests`. `Lint and Typecheck`, `Lighthouse CI`, `Security`, `Nightly full checks`
  выкладку не останавливают.
- **Обязательных для `main` проверок девять, и этот набор не совпадает с содержимым
  `Tests`.** Обязательны: `web checks`, `cms checks`, `scripts checks`, `Unit and build
  tests`, `Playwright smoke (desktop + mobile)`, `Secret scan`, `Runtime dependency
  audit (web)`, `Runtime dependency audit (scripts)`, `Lighthouse budgets (4 templates,
  median of 5)`. Внутри `Tests` живут три job'а — `Unit and build tests`, `Scripts unit
  tests`, `Playwright smoke`, — и **`Scripts unit tests` в обязательные не входит**.
  Значит его падение останавливает публикацию, но не останавливает слияние. Проверено на
  текущей настройке ветки.
- **`strict: false`** — актуальность базы PR не требуется, то есть PR сливается по
  проверкам, прогнанным на устаревшей вершине, и совместное состояние двух PR не
  проверяется никогда.
- **`allow_auto_merge` в репозитории выключен** — проверено: `enablePullRequestAutoMerge`
  отвечает «Auto merge is not allowed for this repository».
- **Runtime-зависимости есть во всех трёх пакетах.** `web` — `astro`,
  `@astrojs/sitemap`; `cms` — восемь, включая `@strapi/strapi`, `better-sqlite3`,
  `react`; `scripts` — `form-data`, `node-fetch`, `tsx`. Первая редакция этого документа
  утверждала обратное — что вне `web` всё является зависимостями разработки, — и это
  было неверно.
- **Уже был инцидент того же класса**, что и привилегированный контекст авто-слияния:
  деплой по `workflow_run` исполнял код чужого PR с правом записи в Pages.

## Goals / Non-Goals

**Goals:**

- Снять с ревьюера подъёмы, где суждение не требуется, не ослабив ни одной проверки.
- Сделать три инварианта («линтер что-то анализирует», «lockfile не потерял бинарник»,
  «тесты выполняются») машинно проверяемыми, блокирующими и публикацию, и слияние.
- Дать ревьюеру меньше PR на тот же объём обновлений.

**Non-Goals:**

- Не расширять гейт публикации на другие workflow — это отдельная работа (свод проверок в
  один workflow или вынос в reusable).
- Не автоматизировать мажоры ни при каких условиях, даже при зелёном CI: разбор #51 и #54
  показал, что мажор — это про совместимость peer-диапазонов, а не про прохождение тестов.
- Не трогать исключение `cms audit:prod` (report-only) — оно живёт своей причиной и
  меняется отдельно.

## Decisions

### Решение 1: судить по метаданным Dependabot, а не по заголовку PR

Заголовок PR (`chore(deps): bump X from A to B`) — вывод генератора, а не контракт: он
менялся между версиями Dependabot и не различает групповые PR. Тип подъёма и тип
зависимости берутся из метаданных, которые Dependabot публикует для своего же PR.

Недоступность метаданных трактуется как отказ, а не как повод к запасному способу
определения: разбор диффа `package.json` пришлось бы держать в синхроне с форматом
lockfile, а это ровно тот «список известных случаев», который отстаёт от предмета молча.

### Решение 2: право задаётся таблицей и работает fail closed

Класс разрешённых обновлений записан таблицей `экосистема × тип зависимости × тип
подъёма` (см. `proposal.md`), и решение принимается совпадением со строкой. Всё, что не
совпало, — ручное.

Так устранено противоречие первой редакции, где `github-actions` разрешались «любые», а
мажоры запрещались безусловно. Разрешён более узкий вариант: мажор не сливается
автоматически ни в одной экосистеме. Обоснование фактом: #44 (`setup-node` v4 → v7)
потребовал чтения релиз-нот трёх мажоров и проверки, что автокеш у нас задан явно, —
такое суждение автоматике не отдаётся.

Для PR с несколькими подъёмами берётся наименее разрешающая строка. Альтернатива —
разрешать, если разрешён каждый подъём, — эквивалентна, но формулировка через минимум
устойчивее к появлению новых строк.

### Решение 3: привилегированный шаг не видит кода PR, но права записи ему нужны

Шаг, решающий судьбу PR, запускается в контексте с правами записи. Поэтому в нём **нет**
шага checkout и **нет** установки зависимостей: он работает только с API GitHub.

Права — `contents: write` и `pull-requests: write`. Меньше не получается, и первая
редакция здесь ошибалась, требуя `contents: read`: пометка PR к автоматическому слиянию
является операцией записи, и официальный пример автоматизации Dependabot использует
именно эту пару. Права на публикацию (`pages`) и на изменение workflow не выдаются.

Отдельно: scope `workflow` у персонального токена, упомянутый в предусловиях, — это
**другая** модель прав, относящаяся к ручному слиянию PR, меняющих файлы workflow. Он не
заменяет permissions job'а и не выдаётся ему.

Альтернатива «checkout с последующей осторожностью» отвергнута: осторожность здесь не
проверяется ничем, а цена ошибки — исполнение чужого кода с правом записи.

### Решение 4: слияние поручается GitHub, но контур обязательных проверок расширяется

Workflow только **помечает** PR к слиянию; само слияние выполняет GitHub, когда сойдутся
все обязательные проверки. Так условие «после успеха всех обязательных проверок» не
дублируется в скрипте и не может разойтись с настройкой ветки.

Из этого следует то, что первая редакция упустила: **«внутри `Tests`» не означает
«обязательна»**. Auto-merge ждёт поимённый список защиты ветки, а не итог workflow.
Поэтому:

- три новых гейта либо выполняются шагами внутри уже обязательного job'а (`Unit and
  build tests`), либо оформляются отдельными job'ами и **вносятся в обязательные**;
- `Scripts unit tests` вносится в обязательные — сейчас его падение слияние не
  останавливает;
- включается требование актуальности базы (`strict`) либо merge queue. Без этого
  несколько PR сливаются по проверкам на устаревшей вершине, и их совместное состояние
  не проверяется никогда. Между двумя вариантами предпочтителен merge queue: `strict`
  заставляет пересобирать каждый PR при каждом слиянии, что при авто-слиянии даёт
  лавину прогонов.

### Решение 5: пороги — константы в репозитории **и** сравнение с базой

Для покрытия линтера и числа тестов проверка сравнивает измеренное значение и с числом,
записанным в репозитории, и с тем же измерением на базовой ветке. Нарушение любого из
двух — неуспех.

Почему оба, а не одно. Только сравнение с базой вырождается в «равно самому себе», если
оба прогона сломаны одинаково — а именно так выглядит поломка инструмента. Только
константа устаревает при росте: после роста со 128 до 180 файлов падение до 140 остаётся
зелёным при пороге 128. Первая редакция оставляла только константу и этот случай
пропускала.

Цена — второй прогон измерения на базе. Это принимается: измерение дешёвое (разбор
машинного отчёта), а пропущенное сокращение покрытия стоит дороже.

### Решение 6: кортеж (семейство, os, cpu, libc), а не множество платформ

Проверка lockfile сравнивает множество кортежей **(семейство пакета, ОС, архитектура,
разновидность libc)**. `os`, `cpu` и `libc` берутся из метаданных самого lockfile — они
там есть: в `web/package-lock.json` 131 запись с этими полями.

Первая редакция сравнивала множество платформ и опознавала платформу разбором имени
записи. Оба решения были неверны:

- разные пакеты закрывают одну платформу. `@esbuild/linux-x64` и
  `@img/sharp-libvips-linux-x64` дают один и тот же `(linux, x64)`. Удаление всех
  бинарников `sharp` для этой платформы оставило бы её представленной через esbuild, и
  гейт остался бы зелёным при неработающем `sharp`;
- разбор имени — не общий признак, а угадывание соглашения об именовании. Метаданные
  `os`/`cpu`/`libc` объявлены самим пакетом и являются тем, по чему npm принимает решение
  об установке.

Обоснование того, что исчезновение записей само по себе не дефект, остаётся прежним и
измерено: в #50 число платформенных записей упало с 50 до 45, но все пять исчезнувших
были вложенной копией `tsx/node_modules/@esbuild/*`, а кортежи остались представлены
верхним уровнем.

### Решение 7: посторонний коммит снимает пометку явным действием

Нативное поведение платформы снимает автоматическое слияние, когда изменения отправляет
участник **без права записи**. Коммит мейнтейнера с правом записи пометку не снимает —
то есть на нативное поведение как на полную защиту опираться нельзя. Первая редакция
формулировала требование через «автор коммита отличается от Dependabot» и полагалась на
платформу, что этому не соответствует.

Решение: при каждом обновлении ветки PR проверять происхождение вершины и, если она не
от Dependabot, снимать пометку явным вызовом. Нативное поведение остаётся как второй
слой, а не как единственный.

### Решение 8: пустой результат — это неуспех

Все три проверки различают «нарушений нет» и «измерить не удалось». Нулевой список
файлов у линтера, отсутствие записей с метаданными платформы в любом из двух lockfile,
отсутствие отчёта о прогоне — неуспех. Коды выхода разбираются по значению, а не по
признаку «не ноль».

### Решение 9: непубликация промежуточных коммитов — норма, молчание — нет

`Tests` объявляет `concurrency: cancel-in-progress`, поэтому при череде слияний
промежуточные прогоны отменяются, а выкладка на них пропускается. Наблюдалось
09.08.2026: из шести прогонов `Tests` на `main` четыре отменены, деплой на них
`skipped`, плюс один деплой упал на защите «проверенный коммит всё ещё вершина».

Это признаётся нормой и фиксируется требованием, а не оставляется на усмотрение
реализации, как было в первой редакции. Но отменённый прогон и не отработавшая выкладка
выглядят одинаково, поэтому вводится вторая половина: если вершина `main` не
опубликована за заданное время, подаётся сигнал.

### Решение 10: SHA-пины с версией в комментарии

`uses:` переводится на полный идентификатор коммита, рядом остаётся читаемая версия
комментарием. Без неё ревью подъёма превращается в сравнение двух сорокасимвольных строк.
Целостность (не осталось ли подвижных тегов) проверяется тем же способом, что и
целостность интеграции OpenSpec: поиском общего признака, а не списка известных действий.

## Risks / Trade-offs

- **Авто-слияние сливает подъём, который ломает то, что не покрыто ни одной проверкой** →
  класс сознательно узкий: только patch/minor зависимостей разработки и actions.
  Runtime-зависимости всех трёх пакетов и мажоры всех экосистем остаются ручными.
  Отключение — снятие одного workflow.
- **Расширение обязательных проверок замедляет и ручное слияние тоже** → принимается:
  проверка, которая не останавливает слияние, не является гейтом слияния, как бы она ни
  называлась.
- **Merge queue или `strict` при авто-слиянии дают дополнительные прогоны** → merge queue
  предпочтён именно поэтому: он пересобирает партию, а не каждый PR при каждом слиянии.
- **Три новых гейта повышают шанс, что публикация встанет из-за самой проверки, а не из-за
  дефекта** → каждая проверка обязана называть предмет и числа в сообщении об ошибке;
  негативная проверка каждой обязательна до слияния.
- **Сравнение с базой удваивает измерение** → принимается ради случая «покрытие упало, но
  выше устаревшего порога».
- **SHA-пины делают дифф обновления нечитаемым** → версия обязательна рядом комментарием.
- **Включение `allow_auto_merge` и правка обязательных проверок — изменения вне кода** →
  фиксируются задачами и проверяются в приёмке; иначе workflow будет молча падать на
  попытке пометить PR, а гейты — не влиять на слияние.
- **Мутация для негативной проверки может не затронуть предмет и дать ложный вывод о
  декоративности гейта** → для каждой проверки в отчёт идут два числа измеряемой
  величины, а не только цвет прогона.

## Migration Plan

1. Включить `allow_auto_merge`; получить токен со scope `workflow` для ручного слияния
   PR, меняющих workflow. Это разные вещи: первое нужно механизму, второе — человеку.
2. Сначала гейты (часть 2) с негативными проверками **и внесением их в обязательные**,
   затем группировка и SHA-пины (часть 3), и только последним — авто-слияние (часть 1).
   Обратный порядок означал бы период, когда PR сливаются автоматически на непроверенных
   или необязательных гейтах.
3. Откат: авто-слияние отключается удалением одного workflow; гейты — снятием шагов из
   `Tests` и из списка обязательных; SHA-пины откатываются обратной заменой.
