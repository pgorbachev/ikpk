## Context

Мотивация — в `proposal.md` («Why»); требования — в
`specs/dependency-update-automation/spec.md`. Здесь только то, что определяет реализацию.

Ограничения, из которых всё вытекает:

- **Публикация подписана ровно на один workflow.** Событие `workflow_run` не умеет
  требовать успеха нескольких workflow сразу, поэтому в условие выкладки входит только
  `Tests`. `Lint and Typecheck`, `Lighthouse CI`, `Security`, `Nightly full checks`
  выкладку не останавливают.
- **Обязательных для `main` проверок девять**, и это шире, чем гейт публикации: `web
  checks`, `cms checks`, `scripts checks`, `Unit and build tests`, `Playwright smoke
  (desktop + mobile)`, `Secret scan`, `Runtime dependency audit (web)`, `Runtime
  dependency audit (scripts)`, `Lighthouse budgets (4 templates, median of 5)`.
- **`allow_auto_merge` в репозитории выключен** — проверено: `enablePullRequestAutoMerge`
  отвечает «Auto merge is not allowed for this repository».
- **Единственные runtime-зависимости, уезжающие в прод, — `astro` и `@astrojs/sitemap`**
  в `web/package.json`. Всё остальное во всех трёх пакетах — зависимости разработки.
- **Уже был инцидент того же класса**, что и привилегированный контекст авто-слияния:
  деплой по `workflow_run` исполнял код чужого PR с правом записи в Pages.

## Goals / Non-Goals

**Goals:**

- Снять с ревьюера подъёмы, где суждение не требуется, не ослабив ни одной проверки.
- Сделать три инварианта («линтер что-то анализирует», «lockfile не потерял платформу»,
  «тесты выполняются») машинно проверяемыми и блокирующими публикацию.
- Дать ревьюеру меньше PR на тот же объём обновлений.

**Non-Goals:**

- Не расширять гейт публикации на другие workflow — это отдельная работа (свод проверок в
  один workflow или вынос в reusable).
- Не автоматизировать мажоры ни при каких условиях, даже при зелёном CI: разбор #51 и #54
  показал, что мажор — это про совместимость peer-диапазонов, а не про прохождение тестов.
- Не трогать исключение `cms audit:prod` (report-only) — оно живёт своей причиной и
  меняется отдельно.

## Decisions

### Решение 1: судить по метаданным Dependabot, а не по заголовку PR

Заголовок PR (`chore(deps): bump X from A to B`) — вывод генератора, а не контракт: он
менялся между версиями Dependabot и не различает групповые PR. Тип подъёма и тип
зависимости берутся из метаданных, которые Dependabot публикует для своего же PR.

Альтернатива — парсинг заголовка или диффа `package.json` — отвергнута: разбор диффа
пришлось бы держать в синхроне с форматом lockfile, а это ровно тот «список известных
случаев», который отстаёт от предмета молча.

### Решение 2: привилегированный шаг не видит кода PR

Шаг, решающий судьбу PR, запускается в контексте, имеющем права записи. Поэтому в нём
**нет** шага checkout и **нет** установки зависимостей: он работает только с API GitHub.
Права выдаются минимальные — чтение содержимого и операции с pull request; ни `pages`,
ни `workflow`.

Альтернатива — обычный контекст PR — не подходит: у него нет прав пометить PR к слиянию.
Альтернатива «checkout с последующей осторожностью» отвергнута: осторожность здесь не
проверяется ничем, а цена ошибки — исполнение чужого кода с правом записи.

### Решение 3: слияние поручается GitHub, а не workflow

Workflow только **помечает** PR к слиянию; само слияние выполняет GitHub, когда сойдутся
все обязательные проверки. Так условие «после успеха всех обязательных проверок» не
дублируется в скрипте и не может разойтись с настройкой ветки: список обязательных
проверок остаётся в одном месте.

Побочный эффект, который надо принять: это требует включить `allow_auto_merge` в
настройках репозитория — шаг вне кода, поэтому он вынесен в задачи явно.

### Решение 4: пороги — константы в репозитории, а не «сравнение с базовой веткой»

Для покрытия линтера и числа тестов проверка сравнивает измеренное значение с числом,
записанным в репозитории, а не с результатом того же измерения на базовой ветке.

Почему так: сравнение с базой требует второго прогона и молча вырождается в «равно
самому себе», если оба прогона сломаны одинаково — а именно так выглядит поломка
инструмента. Константа в репозитории заставляет изменение порога проходить через ревью:
если тестов стало меньше законно, это видно в диффе.

Цена: порог придётся поднимать вручную при росте кодовой базы. Это осознанный обмен —
шум от устаревшего порога заметен, а тихое падение покрытия нет.

Для платформенных записей lockfile сравнение идёт **с базовой веткой**, и это не
противоречие: здесь предмет — не абсолютная величина, а именно отсутствие сокращения, и
константы «сколько платформ должно быть» не существует.

### Решение 5: платформы, а не число записей

Проверка lockfile сравнивает **множество платформ**, для которых есть хотя бы одна
запись, а не число записей. Обоснование — измеренный случай: в #50 число платформенных
записей упало с 50 до 45, но все пять исчезнувших были вложенной копией
`tsx/node_modules/@esbuild/*`, а на верхнем уровне все 26 платформ остались. Проверка по
числу записей дала бы ложный отказ.

Платформа опознаётся по общему признаку в имени записи, а не по списку известных пакетов:
список `@esbuild/*`, `@img/sharp-*`, `lightningcss-*`, `rollup-*` отстанет от предмета
при первой новой зависимости.

### Решение 6: пустой результат — это неуспех

Все три проверки различают «нарушений нет» и «измерить не удалось». Нулевой список
файлов у линтера, отсутствие платформенных записей в обоих lockfile, отсутствие отчёта о
прогоне — неуспех. Коды выхода разбираются по значению, а не по признаку «не ноль».

### Решение 7: SHA-пины с версией в комментарии

`uses:` переводится на полный идентификатор коммита, рядом остаётся читаемая версия
комментарием. Без неё ревью подъёма превращается в сравнение двух сорокасимвольных строк.
Целостность (не осталось ли подвижных тегов) проверяется тем же способом, что и
целостность интеграции OpenSpec: поиском общего признака, а не списка известных действий.

## Risks / Trade-offs

- **Авто-слияние сливает подъём, который ломает то, что не покрыто ни одной проверкой** →
  класс сознательно узкий: зависимости разработки и actions. Runtime-зависимости сайта и
  мажоры остаются ручными. Отключение — снятие одного workflow.
- **Три новых гейта повышают шанс, что публикация встанет из-за самой проверки, а не из-за
  дефекта** → каждая проверка обязана называть предмет и числа в сообщении об ошибке;
  негативная проверка каждой обязательна до слияния.
- **Порог, заданный константой, устаревает** → при законном сокращении порог правится в
  том же PR и виден в диффе; это и есть механизм ревью.
- **SHA-пины делают дифф обновления нечитаемым** → версия обязательна рядом комментарием.
- **Включение `allow_auto_merge` — изменение вне кода** → фиксируется задачей и
  проверяется в приёмке; иначе workflow будет молча падать на попытке пометить PR.
- **Мутация для негативной проверки может не затронуть предмет и дать ложный вывод о
  декоративности гейта** → для каждой проверки в отчёт идут два числа измеряемой
  величины, а не только цвет прогона.

## Migration Plan

1. Включить `allow_auto_merge` и получить токен со scope `workflow` — без этого ни
   пометка к слиянию, ни слияние PR, меняющих workflow, не работают.
2. Сначала гейты (часть 2) с негативными проверками, затем группировка и SHA-пины
   (часть 3), и только последним — авто-слияние (часть 1). Обратный порядок означал бы
   период, когда PR сливаются автоматически на непроверенных гейтах.
3. Откат: авто-слияние отключается удалением одного workflow; гейты — снятием шагов из
   `Tests`; SHA-пины откатываются обратной заменой.

## Open Questions

- Нужно ли расширить класс авто-слияния на `semver-minor` runtime-зависимостей `web`
  после того, как гейты отработают некоторое время. Ответ не меняет ни спеку, ни
  разбивку задач: это отдельное решение с отдельным изменением класса.
