## Context

Мотивация — в `proposal.md` («Why»); требования — в
`specs/dependency-update-automation/spec.md`. Здесь только то, что определяет реализацию.

Ограничения, из которых всё вытекает:

- **Публикация подписана ровно на один workflow.** Событие `workflow_run` не умеет
  требовать успеха нескольких workflow сразу, поэтому в условие выкладки входит только
  `Tests`. `Lint and Typecheck`, `Lighthouse CI`, `Security`, `Nightly full checks`
  выкладку не останавливают.
- **Обязательных для `main` проверок девять, и этот набор не совпадает с содержимым
  `Tests`.** Обязательны: `web checks`, `cms checks`, `scripts checks`, `Unit and build
  tests`, `Playwright smoke (desktop + mobile)`, `Secret scan`, `Runtime dependency
  audit (web)`, `Runtime dependency audit (scripts)`, `Lighthouse budgets (4 templates,
  median of 5)`. Внутри `Tests` живут три job'а — `Unit and build tests`, `Scripts unit
  tests`, `Playwright smoke`, — и **`Scripts unit tests` в обязательные не входит**.
  Значит его падение останавливает публикацию, но не останавливает слияние. Проверено на
  текущей настройке ветки.
- **`strict: false`** — актуальность базы PR не требуется, то есть PR сливается по
  проверкам, прогнанным на устаревшей вершине, и совместное состояние двух PR не
  проверяется никогда.
- **`allow_auto_merge` в репозитории выключен** — проверено: `enablePullRequestAutoMerge`
  отвечает «Auto merge is not allowed for this repository».
- **Runtime-зависимости есть во всех трёх пакетах.** `web` — `astro`,
  `@astrojs/sitemap`; `cms` — восемь, включая `@strapi/strapi`, `better-sqlite3`,
  `react`; `scripts` — `form-data`, `node-fetch`, `tsx`. Первая редакция этого документа
  утверждала обратное — что вне `web` всё является зависимостями разработки, — и это
  было неверно.
- **Уже был инцидент того же класса**, что и привилегированный контекст авто-слияния:
  деплой по `workflow_run` исполнял код чужого PR с правом записи в Pages.

## Goals / Non-Goals

**Goals:**

- Снять с ревьюера подъёмы, где суждение не требуется, не ослабив ни одной проверки.
- Сделать три инварианта («линтер что-то анализирует», «lockfile не потерял бинарник»,
  «тесты выполняются») машинно проверяемыми, блокирующими и публикацию, и слияние.
- Дать ревьюеру меньше PR на тот же объём обновлений.

**Non-Goals:**

- Не расширять гейт публикации на другие workflow — это отдельная работа (свод проверок в
  один workflow или вынос в reusable).
- Не автоматизировать мажоры ни при каких условиях, даже при зелёном CI: разбор #51 и #54
  показал, что мажор — это про совместимость peer-диапазонов, а не про прохождение тестов.
- Не трогать исключение `cms audit:prod` (report-only) — оно живёт своей причиной и
  меняется отдельно.

## Decisions

### Решение 1: судить по метаданным Dependabot, а не по заголовку PR

Заголовок PR (`chore(deps): bump X from A to B`) — вывод генератора, а не контракт: он
менялся между версиями Dependabot и не различает групповые PR. Тип подъёма и тип
зависимости берутся из метаданных, которые Dependabot публикует для своего же PR.

Недоступность метаданных трактуется как отказ, а не как повод к запасному способу
определения: разбор диффа `package.json` пришлось бы держать в синхроне с форматом
lockfile, а это ровно тот «список известных случаев», который отстаёт от предмета молча.

### Решение 2: право задаётся таблицей и работает fail closed

Класс разрешённых обновлений записан таблицей `экосистема × тип зависимости × тип
подъёма` (см. `proposal.md`), и решение принимается совпадением со строкой. Всё, что не
совпало, — ручное.

Так устранено противоречие первой редакции, где `github-actions` разрешались «любые», а
мажоры запрещались безусловно. Разрешён более узкий вариант: мажор не сливается
автоматически ни в одной экосистеме. Обоснование фактом: #44 (`setup-node` v4 → v7)
потребовал чтения релиз-нот трёх мажоров и проверки, что автокеш у нас задан явно, —
такое суждение автоматике не отдаётся.

Для PR с несколькими подъёмами берётся наименее разрешающая строка. Альтернатива —
разрешать, если разрешён каждый подъём, — эквивалентна, но формулировка через минимум
устойчивее к появлению новых строк.

### Решение 3: привилегированный шаг не видит кода PR, но права записи ему нужны

Шаг, решающий судьбу PR, запускается в контексте с правами записи. Поэтому в нём **нет**
шага checkout и **нет** установки зависимостей: он работает только с API GitHub.

Права — `contents: write` и `pull-requests: write`. Меньше не получается, и первая
редакция здесь ошибалась, требуя `contents: read`: пометка PR к автоматическому слиянию
является операцией записи, и официальный пример автоматизации Dependabot использует
именно эту пару. Права на публикацию (`pages`) и на изменение workflow не выдаются.

Отдельно: scope `workflow` у персонального токена, упомянутый в предусловиях, — это
**другая** модель прав, относящаяся к ручному слиянию PR, меняющих файлы workflow. Он не
заменяет permissions job'а и не выдаётся ему.

Альтернатива «checkout с последующей осторожностью» отвергнута: осторожность здесь не
проверяется ничем, а цена ошибки — исполнение чужого кода с правом записи.

### Решение 4: слияние поручается GitHub, но контур обязательных проверок расширяется

Workflow только **помечает** PR к слиянию; само слияние выполняет GitHub, когда сойдутся
все обязательные проверки. Так условие «после успеха всех обязательных проверок» не
дублируется в скрипте и не может разойтись с настройкой ветки.

Из этого следует то, что первая редакция упустила: **«внутри `Tests`» не означает
«обязательна»**. Auto-merge ждёт поимённый список защиты ветки, а не итог workflow.
Поэтому:

- три новых гейта либо выполняются шагами внутри уже обязательного job'а (`Unit and
  build tests`), либо оформляются отдельными job'ами и **вносятся в обязательные**;
- `Scripts unit tests` вносится в обязательные — сейчас его падение слияние не
  останавливает;
- включается **`strict`** — запрет на слияние устаревшей ветки, — и вместе с ним
  механизм, который эти ветки **обновляет**. Одного запрета недостаточно, и этим
  решение отличается от второй редакции.

**Очередь слияния из рассмотрения исключена, и это не предпочтение, а ограничение
площадки.** Она доступна публичным репозиториям организаций, а `pgorbachev/ikpk`
принадлежит личному аккаунту: тип владельца — `User`, проверено через API. Третья
редакция назвала очередь основным вариантом, а `strict` с обновлением — запасным; порядок
перевёрнут, потому что «основной» вариант в этом окружении неисполним вовсе. Перенос
репозитория в организацию открыл бы очередь, но это решение об организации работ, а не
деталь автоматизации зависимостей: в scope этого change оно не входит и вносится только
явным решением владельца.

Почему одного `strict` мало — разбор второй редакции остаётся в силе: он **запрещает**,
но не **обновляет**. После первого автоматического слияния остальные PR становятся
устаревшими и остаются помеченными, но не сливаются, пока их кто-то не пересоберёт.
Dependabot пересобирает ветку по расписанию, при конфликте и по явной команде — но не
после каждого продвижения базы. При недельном расписании серия из шести PR продвигалась
бы по одному в неделю.

Отсюда конструкция из двух частей: `strict` держит запрет, а отдельный механизм после
каждого слияния приводит оставшиеся PR разрешённого класса к актуальной базе. Для
механизма рассматриваются два способа, в этом порядке:

1. **Попросить Dependabot пересобрать** — комментарием-командой к его же PR. Дёшево и не
   требует новых учётных данных; пересборку делает сам Dependabot, поэтому прогоны
   запускаются нормально. Работоспособность встроенным токеном я **не проверял** и не
   утверждаю: это эксперимент с предъявлением результата.
2. **Обновить ветку через API** от имени GitHub App, ограниченного этим репозиторием.
   Способ применяется, если первый не подтвердится. Здесь существенна тонкость, из-за
   которой встроенный токен не годится и на этом пути: события от встроенного токена
   не запускают workflow, то есть обновлённая вершина осталась бы без проверок и PR
   встал бы намертво. Субъект с собственной идентичностью этой проблемы не имеет.

Требования к субъекту второго способа: минимальный набор прав, хранение секретом,
ротация, и — существенно — он **не попадает в контекст, исполняющий код PR**, поскольку
workflow авто-слияния не делает checkout.

Если не подтвердится ни один способ, автоматическое слияние не вводится: требование о
продвижении серии остаётся невыполненным, а часть 1 без него превращается в очередь,
которая стоит.

### Решение 5: порог — всем, сравнение с базой — тем, кто сливается сам

Для покрытия линтера и числа тестов проверка сравнивает измеренное значение с числом,
записанным в репозитории (порог), — это применяется ко всем PR. Сравнение с тем же
измерением на базовой ветке применяется к PR, для которого верно **хотя бы одно** из
двух: он признан пригодным к автоматическому слиянию, либо он не меняет ничего, кроме
манифестов зависимостей и файлов блокировки.

Почему нужны оба условия. Только сравнение с базой вырождается в «равно самому себе»,
если оба прогона сломаны одинаково — а именно так выглядит поломка инструмента. Только
константа устаревает при росте: после роста со 128 до 180 файлов падение до 140 остаётся
зелёным при пороге 128.

Почему второе условие ограничено по области. Вторая редакция применяла его ко всем PR, и
это делало невозможным обычное удаление устаревшего исходника или теста: такой PR
неизбежно уменьшает измеряемое число, а правка порога в том же PR его не разблокирует —
сравнение идёт с базой, а не с порогом, и остаётся красным.

Почему область — объединение двух признаков, а не один файловый. Третья редакция
ограничивала её PR, меняющими только манифесты и файлы блокировки, и это оставляло дыру:
второй разрешённый класс авто-слияния — `github-actions` — меняет файлы workflow, а не
манифесты, и под сравнение не попадал. Минорный подъём действия способен сократить число
запущенных тестов, остаться выше устаревшего порога и слиться без человека. Поэтому
ведущий признак — **пригодность к автоматическому слиянию**: то, что сливается само,
обязано сравниваться с базой. Файловый признак оставлен вторым слагаемым, чтобы накрыть
PR с одними зависимостями, открытые человеком.

Ограничение не открывает ничего для автоматики: PR, меняющий исходники, по построению не
относится к разрешённому классу и слит автоматически быть не может.

Остаточный риск назван прямо: PR с изменением исходников может снизить покрытие, оставшись
выше порога, и второе условие его не поймает. Такой PR проходит человеческое ревью, а
порог продолжает работать нижней границей.

Цена — второе измерение на базе. Это принимается: измерение дешёвое (разбор машинного
отчёта), а пропущенное сокращение покрытия стоит дороже.

### Решение 6: кортеж (имя пакета, os, cpu, libc), а не множество платформ

Проверка lockfile сравнивает множество кортежей **(имя пакета, ОС, архитектура,
разновидность libc)**. Имя берётся из пути записи — часть после последнего
`node_modules/`; `os`, `cpu` и `libc` — из полей самой записи.

Первая редакция сравнивала множество платформ и опознавала платформу разбором имени.
Вторая ввела «семейство пакета» — и это тоже неверно, потому что понятия семейства формат
файла блокировки не содержит: поле с именем есть лишь у отдельных записей (на голове
этого change — у одной из 847 в `web`), а выделение «базовой части» из пути было бы тем
же угадыванием соглашения об именовании, против которого решение и вводилось. Полное имя
объективно и различает `@esbuild/linux-x64` и `@img/sharp-libvips-linux-x64` — чего и
требовалось.

Почему кортеж, а не платформа: разные пакеты закрывают одну платформу. `@esbuild/linux-x64`
и `@img/sharp-libvips-linux-x64` дают один и тот же `(linux, x64)`. Удаление всех
бинарников `sharp` для этой платформы оставило бы её представленной через esbuild, и
гейт остался бы зелёным при неработающем `sharp`.

Тупик, оставшийся от третьей редакции, снят. Монотонность множества кортежей на каждом PR
делала бы обязательную проверку вечно красной, если upstream законно прекратит поставку
бинарника под платформу, переименует платформенный пакет или сменит схему поставки, —
ручное ревью такой PR не разблокировало бы. Для порогов покрытия этот тупик снимался
правкой порога в том же PR; здесь аналог — запись о принятой потере конкретного кортежа с
причиной. Она меняет исходный файл, значит видна в диффе, проходит ревью и в класс
автоматически сливаемого не попадает. Запись обязана называть кортеж поимённо: «любые
потери в этом пакете» вернуло бы противоположную крайность — молчание.

Почему `os`/`cpu`/`libc` из полей, а не из имени: они объявлены самим пакетом и являются
тем, по чему npm принимает решение об установке. Записей с этими полями в
`web/package-lock.json` — **105** на голове этого change. Вторая редакция называла 131:
число было снято до слияния #50, которое дедуплицировало вложенную копию
`tsx/node_modules/@esbuild/*`, то есть измерялось на другом дереве.

Обоснование того, что исчезновение записей само по себе не дефект, остаётся прежним и
измерено: в #50 число платформенных записей упало с 50 до 45, но все пять исчезнувших
были вложенной копией `tsx/node_modules/@esbuild/*`, а кортежи остались представлены
верхним уровнем.

### Решение 7: происхождение вершины стережёт обязательная проверка, а не снятие пометки

Защитой служит **обязательная проверка**, которая на каждой вершине ветки PR отвечает на
вопрос «разрешено ли слить эту вершину без человека». Она падает **тогда и только
тогда**, когда автоматическое слияние для PR включено, а вершина не создана Dependabot
либо PR не попадает в разрешающую строку; недоступность метаданных при включённом
автоматическом слиянии тоже считается неуспехом. При выключенном автоматическом слиянии
проверка проходит.

Три предыдущие редакции ошибались по-разному, и каждая следующая ошибка тоньше:

- первая формулировала условие как «автор коммита отличается от Dependabot» и полагалась
  на платформу. Платформа же снимает автоматическое слияние только при пуше участника
  **без права записи**, поэтому коммит мейнтейнера пометку бы не снял;
- вторая добавила явное снятие пометки при обновлении ветки — но снятие само по себе
  fail-open. Обработчик не входил в обязательные проверки, поэтому его незапуск, падение
  или отмена оставляли пометку включённой; прочие обязательные проверки проходили, и
  платформа сливала изменённую вершину. Отказ механизма защиты приводил к слиянию;
- третья сделала проверку обязательной, но требовала падения на любой вершине не от
  Dependabot. Раз проверка обязательна для ветки, это запретило бы слияние **всех**
  человеческих PR и всех PR Dependabot, оставленных ручному пути по таблице. Гейт,
  вводившийся ради безопасности автоматического слияния, остановил бы вообще всё.

Отсюда разделение ролей: обязательная проверка — защита и работает fail closed в своей
ветви (автоматическое слияние включено); нативное поведение платформы и явное снятие
пометки — ускоряющие меры, которые закрывают PR раньше, но на которые нельзя опереться.
Ручной путь проверка не трогает вовсе.

Остаточная щель названа прямо: если проверка отработала при выключенной пометке, а затем
человек с правом записи включил автоматическое слияние вручную, не меняя вершину, новая
оценка не запускается. Это осознанное действие обладателя права записи, а не обход
автоматикой.

### Решение 8: пустой результат — это неуспех

Все три проверки различают «нарушений нет» и «измерить не удалось». Нулевой список
файлов у линтера, отсутствие записей с метаданными платформы в любом из двух lockfile,
отсутствие отчёта о прогоне — неуспех. Коды выхода разбираются по значению, а не по
признаку «не ноль».

### Решение 9: непубликация промежуточных коммитов — норма, молчание — нет

`Tests` объявляет `concurrency: cancel-in-progress`, поэтому при череде слияний
промежуточные прогоны отменяются, а выкладка на них пропускается. Наблюдалось
09.08.2026: из шести прогонов `Tests` на `main` четыре отменены, деплой на них
`skipped`, плюс один деплой упал на защите «проверенный коммит всё ещё вершина».

Это признаётся нормой и фиксируется требованием, а не оставляется на усмотрение
реализации, как было в первой редакции. Но отменённый прогон и не отработавшая выкладка
выглядят одинаково, поэтому вводится вторая половина: если вершина `main` не
опубликована за заданное время, подаётся сигнал.

### Решение 10: SHA-пины с версией в комментарии

`uses:` переводится на полный идентификатор коммита, рядом остаётся читаемая версия
комментарием. Без неё ревью подъёма превращается в сравнение двух сорокасимвольных строк.
Целостность (не осталось ли подвижных тегов) проверяется тем же способом, что и
целостность интеграции OpenSpec: поиском общего признака, а не списка известных действий.

## Risks / Trade-offs

- **Авто-слияние сливает подъём, который ломает то, что не покрыто ни одной проверкой** →
  класс сознательно узкий: только patch/minor зависимостей разработки и actions.
  Runtime-зависимости всех трёх пакетов и мажоры всех экосистем остаются ручными.
  Отключение — снятие одного workflow.
- **Расширение обязательных проверок замедляет и ручное слияние тоже** → принимается:
  проверка, которая не останавливает слияние, не является гейтом слияния, как бы она ни
  называлась.
- **Продвижение серии может оказаться нереализуемым в этом окружении** → очередь слияния
  недоступна (владелец типа `User`), остаются два способа обновления веток, и оба
  требуют проверки. Если не подтвердится ни один, часть 1 не вводится, а части 2 и 3
  сохраняют ценность сами по себе. Это названо заранее, чтобы отсутствие механизма не
  привело к соблазну ослабить `strict` и сливать на устаревшей базе.
- **Второй способ требует отдельного субъекта с правом на pull request** → митигация:
  GitHub App, ограниченное этим репозиторием, минимальные права, ротация, и отсутствие
  доступа к нему из контекста, исполняющего код PR.
- **Сравнение с базой не применяется к PR, меняющим исходники** → значит PR с
  изменением кода может снизить покрытие, оставшись выше порога. Ловится человеческим
  ревью и нижней границей порога; альтернатива — блокировать всякое удаление исходника —
  хуже.
- **Три новых гейта повышают шанс, что публикация встанет из-за самой проверки, а не из-за
  дефекта** → каждая проверка обязана называть предмет и числа в сообщении об ошибке;
  негативная проверка каждой обязательна до слияния.
- **Сравнение с базой удваивает измерение** → принимается ради случая «покрытие упало, но
  выше устаревшего порога».
- **SHA-пины делают дифф обновления нечитаемым** → версия обязательна рядом комментарием.
- **Включение `allow_auto_merge` и правка обязательных проверок — изменения вне кода** →
  фиксируются задачами и проверяются в приёмке; иначе workflow будет молча падать на
  попытке пометить PR, а гейты — не влиять на слияние.
- **Мутация для негативной проверки может не затронуть предмет и дать ложный вывод о
  декоративности гейта** → для каждой проверки в отчёт идут два числа измеряемой
  величины, а не только цвет прогона.

## Migration Plan

1. Включить `allow_auto_merge`; получить токен со scope `workflow` для ручного слияния
   PR, меняющих workflow. Это разные вещи: первое нужно механизму, второе — человеку.
2. Сначала гейты (часть 2) с негативными проверками **и внесением их в обязательные**,
   затем группировка и SHA-пины (часть 3), и только последним — авто-слияние (часть 1).
   Обратный порядок означал бы период, когда PR сливаются автоматически на непроверенных
   или необязательных гейтах.
3. Откат: авто-слияние отключается удалением одного workflow; гейты — снятием шагов из
   `Tests` и из списка обязательных; SHA-пины откатываются обратной заменой.
