## 6. Контур обязательных проверок

- [ ] 6.1 Внести три новых гейта в обязательные проверки ветки `main` — либо встроив их

- [ ] 6.3 Включить `strict` — запрет на слияние устаревшей ветки. Сам по себе он серию не
      двигает, поэтому обязателен механизм обновления из 6.4/6.5
- [ ] 6.4 Способ первый: после слияния PR просить Dependabot пересобрать оставшиеся PR
      разрешённого класса — командой-комментарием от встроенного токена. Вершину пишет
      Dependabot, правило происхождения расширять не нужно. Предъявить результат
      эксперимента — продвинулась ли серия без вмешательства
- [ ] 6.5 Способ второй, если команда от встроенного токена не распознана: та же команда
      от имени GitHub App, ограниченного этим репозиторием. Вершину по-прежнему пишет
      Dependabot; меняется только отправитель, расширение правила не требуется
- [ ] 6.5a Способ третий и последний: обновление ветки через API (`update-branch`) от
      имени GitHub App. **Только он требует расширения правила происхождения** — вершина
      будет merge-коммитом от механизма, а не от Dependabot. Реализовать проверку всех
      условий допустимости: два родителя; для первого — **отдельное положительное
      свидетельство происхождения из задачи 9.5e**, привязанное к его SHA и созданное
      ожидаемым субъектом. Результат гейта допустимости свидетельством **не является** и
      приниматься не может: при выключенном авто-слиянии он зелёный без всякой проверки
      происхождения. Далее: второй родитель — предок вершины базы; изменения относительно
      первого родителя совпадают с тем, что вносит второй; действующее лицо текущего
      события — объявленный механизм. Поля `author`/`committer` в условия не входят вовсе
- [ ] 6.5b **Негативная проверка происхождения после `update-branch`** — четыре мутации,
      каждая по отдельности: посторонняя правка в merge-коммите; **у первого родителя нет
      положительного свидетельства происхождения** (либо оно отрицательно, либо создано
      посторонним субъектом); второй родитель не предок вершины базы; обычный коммит с
      одним родителем от того же субъекта. Ожидание: все четыре красные. Для каждой
      записать, какое условие сработало, и имя покрасневшей проверки
- [ ] 6.5c Проверить положительную ветвь: корректное `update-branch` даёт **положительное
      свидетельство происхождения** и серия продвигается. Без этой проверки предыдущая
      задача не отличает «правило работает» от «правило запрещает всё»
- [ ] 6.6 Убедиться, что учётные данные механизма недоступны из контекста, исполняющего
      код PR, и что workflow авто-слияния по-прежнему не делает checkout

- [ ] 6.7 **Негативная проверка продвижения серии:** подготовить два PR разрешённого

      с подписью платформы от служебной учётной записи проходит. Без неё предикат легко
      написать так, что он отвергает все настоящие вершины — измеренный факт: у вершин PR
      #73 и #75 подписавшим значится служебная запись подписи, а не Dependabot
- [ ] 9.5c **Негативная проверка, две мутации по отдельности:** (а) коммит с полями автора
      Dependabot, отправленный из локального клона без подписи платформы; (б) коммит,
      созданный участником с правом записи **через API** с полями автора Dependabot — он
      будет подписан платформой наравне с настоящим, и отвергнуть его обязано действующее
      лицо события. Обе ожидаются красными; предъявить имя покрасневшей проверки и то,
      какое из двух условий сработало
- [ ] 9.5d Проверить ветвь «действующее лицо не определено» — она обязана быть красной, а
      не проходить по умолчанию
- [ ] 9.5e Реализовать **отдельное** свидетельство происхождения: результат, не совпадающий
      с гейтом допустимости, вычисляемый на каждой вершине независимо от состояния пометки
      и положительный только при фактически пройденных проверках подписи и действующего
      лица. В обязательные проверки его **не вносить** — иначе он запретит ручной путь.
      Для первого родителя читать именно его. Действующее лицо текущего события к родителю
      не применять: оно принадлежит механизму обновления и отвергло бы корректного родителя
      от Dependabot
- [ ] 9.5e1 **Негативная проверка ложного свидетельства:** запушить человеческий коммит в
      ветку PR Dependabot при выключенном авто-слиянии (гейт допустимости при этом
      обязан быть зелёным), затем обновить ветку механизмом. Ожидание: обновление
      **красное**, потому что свидетельство родителя отрицательно. Предъявить оба факта —
      зелёный гейт и красное обновление; при совмещённом свидетельстве этот путь проходил
      бы
- [ ] 9.5f **Живая проверка цепочки:** обновить ветку механизмом дважды подряд и убедиться,
      что проверка зелёная при сохранённых свидетельствах. Затем сделать свидетельство
      промежуточной вершины недоступным и убедиться, что проверка красная. Предъявить оба
      состояния — без второго неизвестно, читается ли свидетельство вообще
- [ ] 9.5g Определить, что делать при истечении срока хранения свидетельств: продвижение
      серии выполняется пересборкой ветки самим Dependabot, которая сбрасывает цепочку к
      одной вершине. Проверить этот путь
- [ ] 9.5a Проверить, что обязательная проверка **не блокирует ручной путь**: обычный
      человеческий PR и PR Dependabot с мажором сливаются вручную как прежде. Предъявить
      оба случая — это ровно то, что сломала бы формулировка «падать на любой вершине не
      от Dependabot»
- [ ] 9.6 Реализовать снятие пометки при обновлении ветки как **ускоряющую** меру поверх

- [ ] 9.7 Проверить на живом PR каждого класса: патч зависимости разработки — слился;

      разработки — остался открытым; runtime-зависимость `cms` — осталась открытой
- [ ] 9.8 Проверить, что при падении обязательной проверки помеченный PR не сливается
- [ ] 9.9 Проверить fail closed: отправить в ветку помеченного PR коммит от участника с
