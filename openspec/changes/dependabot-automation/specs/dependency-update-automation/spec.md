## Purpose

Определяет, какие обновления зависимостей репозиторий вправе принять без участия
человека, какие инварианты качества проверок обязаны быть доказаны перед этим, и в каком
виде обновления попадают к ревьюеру. Задача — снять с ревьюера механически проверяемое,
не сняв с него суждение.

## ADDED Requirements

### Requirement: Класс автоматически сливаемых обновлений задан таблицей

Право на автоматическое слияние SHALL определяться по совпадению трёх признаков —
экосистема, тип зависимости, тип подъёма — со строкой разрешающей таблицы. Отсутствие
совпадения SHALL означать отказ: правило работает fail closed.

Разрешены ровно две строки:

| Экосистема | Тип зависимости | Тип подъёма |
|---|---|---|
| npm в `web`, `cms`, `scripts` | прямая зависимость разработки | `semver-patch`, `semver-minor` |
| `github-actions` | — | `semver-patch`, `semver-minor` |

Система SHALL NOT сливать автоматически подъём мажорной версии ни в одной экосистеме,
включая `github-actions`.

Система SHALL NOT сливать автоматически подъём runtime-зависимости ни в одном из трёх
пакетов.

Если PR содержит несколько подъёмов, право на автоматическое слияние SHALL определяться
по наименее разрешающему из них.

Решение SHALL приниматься по метаданным, полученным от Dependabot, а не по разбору
заголовка PR или диффа: заголовок пишется генератором и не является контрактом.

#### Scenario: Патч зависимости разработки

- **WHEN** Dependabot открывает PR с подъёмом `semver-patch` зависимости, объявленной
  как прямая зависимость разработки
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Минорный подъём действия

- **WHEN** Dependabot открывает PR с подъёмом `semver-minor` в экосистеме
  `github-actions`
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Мажорный подъём действия

- **WHEN** Dependabot открывает PR с подъёмом `semver-major` в экосистеме
  `github-actions`
- **THEN** система не помечает PR к автоматическому слиянию и оставляет его ревьюеру

#### Scenario: Мажор зависимости разработки

- **WHEN** Dependabot открывает PR с подъёмом `semver-major` зависимости разработки
- **THEN** система не помечает PR к автоматическому слиянию

#### Scenario: Runtime-зависимость пакета cms

- **WHEN** Dependabot открывает PR, изменяющий runtime-зависимость пакета `cms`
- **THEN** система не помечает PR к автоматическому слиянию, независимо от типа подъёма

#### Scenario: Runtime-зависимость пакета scripts

- **WHEN** Dependabot открывает PR, изменяющий runtime-зависимость пакета `scripts`
- **THEN** система не помечает PR к автоматическому слиянию, независимо от типа подъёма

#### Scenario: Смешанный групповой PR

- **WHEN** сгруппированный PR содержит и подъёмы, попадающие в разрешающие строки, и
  хотя бы один, в них не попадающий
- **THEN** система не помечает PR к автоматическому слиянию

#### Scenario: Метаданные недоступны

- **WHEN** метаданные Dependabot для PR получить не удалось
- **THEN** система не помечает PR к автоматическому слиянию и не пытается вывести класс
  из заголовка или диффа

### Requirement: Автоматическое слияние ждёт весь релевантный контур проверок

Система SHALL выполнять автоматическое слияние не немедленно, а по факту успеха всех
проверок, обязательных для ветки `main`.

Набор обязательных проверок SHALL включать все проверки, чей отказ должен останавливать
слияние, — в том числе `Scripts unit tests` и три инварианта, вводимые этой
спецификацией. Размещения проверки внутри workflow `Tests` SHALL NOT быть достаточно:
защита ветки оперирует именами проверок, поэтому проверка внутри `Tests`, не внесённая в
обязательные, останавливает публикацию, но не останавливает слияние.

Система SHALL требовать, чтобы автоматически сливаемый PR был проверен на актуальной
базе: либо ветка PR обязана быть не старше вершины `main`, либо слияние проходит через
очередь, проверяющую совместное состояние.

#### Scenario: Проверки ещё идут

- **WHEN** PR помечен к автоматическому слиянию и часть обязательных проверок не
  завершена
- **THEN** слияние не происходит

#### Scenario: Обязательная проверка упала

- **WHEN** PR помечен к автоматическому слиянию и хотя бы одна обязательная проверка
  завершилась неуспехом
- **THEN** слияние не происходит и PR остаётся открытым

#### Scenario: Модульные тесты пакета scripts упали

- **WHEN** PR разрешённого класса затрагивает `scripts` и модульные тесты этого пакета
  завершаются неуспехом
- **THEN** слияние не происходит

#### Scenario: База PR устарела

- **WHEN** PR помечен к автоматическому слиянию, а вершина `main` продвинулась после
  прогона его проверок
- **THEN** слияние не происходит до повторной проверки на актуальной базе

### Requirement: Пометка к слиянию снимается при вмешательстве извне

Система SHALL снимать пометку к автоматическому слиянию, если в ветку PR приходит
коммит, не созданный Dependabot.

Требование существует потому, что нативное поведение платформы решает эту задачу лишь
частично: платформа отключает автоматическое слияние, когда изменения отправляет
участник **без права записи**, — то есть коммит человека с правом записи пометку не
снимает. Опираться на нативное поведение как на полную защиту нельзя, и разница SHALL
быть закрыта явной проверкой, а не подразумеваться.

Проверка SHALL выполняться при каждом обновлении ветки PR и SHALL определять
происхождение по вершине ветки, а не по составу PR целиком.

#### Scenario: Посторонний коммит без права записи

- **WHEN** в ветку PR отправляет изменения участник без права записи
- **THEN** пометка снята и слияние не происходит

#### Scenario: Коммит участника с правом записи

- **WHEN** в ветку PR, помеченного к автоматическому слиянию, приходит коммит участника
  с правом записи
- **THEN** система снимает пометку явным действием и слияние не происходит

#### Scenario: Обновление веткой самим Dependabot

- **WHEN** Dependabot пересобирает ветку PR (rebase или новая версия подъёма)
- **THEN** пометка сохраняется, а класс PR определяется заново по обновлённым метаданным

### Requirement: Механизм автоматического слияния не исполняет код проверяемого PR

Система SHALL принимать решение о слиянии в контексте, который не выполняет ни код из
ветки PR, ни его скрипты сборки и установки зависимостей.

Это требование существует потому, что контекст принятия решения обладает правами записи:
исполнение в нём содержимого PR даёт постороннему коду эти права.

Права контекста SHALL быть ограничены записью в содержимое репозитория и операциями с
pull request — минимумом, при котором пометка к слиянию выполнима. Права на публикацию
и на изменение workflow SHALL NOT выдаваться.

#### Scenario: Содержимое PR не попадает в привилегированный контекст

- **WHEN** выполняется шаг, решающий судьбу PR
- **THEN** рабочее дерево этого шага не содержит файлов из ветки PR, и ни одна команда
  шага не запускает скрипты из неё

#### Scenario: Права ограничены необходимым

- **WHEN** выполняется шаг, решающий судьбу PR
- **THEN** ему выданы права записи в содержимое репозитория и права на операции с pull
  request, и не выданы права на публикацию и на изменение workflow

### Requirement: Покрытие статического анализа не сокращается молча

Система SHALL проверять, что число файлов, фактически проанализированных линтером в
каждом из пакетов `web`, `cms`, `scripts`, удовлетворяет **обоим** условиям: оно не
меньше зафиксированного для этого пакета порога и не меньше числа, измеренного тем же
способом на базовой ветке. Нарушение любого из условий SHALL приводить к неуспеху.

Два условия нужны вместе, и ни одно не заменяет другое: порог ловит случай, когда база и
голова сломаны одинаково, а сравнение с базой ловит сокращение, оставшееся выше
устаревшего порога.

Проверка SHALL считать проанализированные файлы по машинному отчёту самого линтера, а не
по списку файлов в репозитории: расхождение между ними и есть предмет проверки.

Отсутствие отчёта, пустой отчёт или ошибка запуска линтера SHALL считаться неуспехом, а
не отсутствием проблем.

#### Scenario: Покрытие сохранилось

- **WHEN** линтер сообщает о числе проанализированных файлов не меньше порога пакета и
  не меньше измеренного на базовой ветке
- **THEN** проверка проходит

#### Scenario: Покрытие сократилось ниже порога

- **WHEN** обновление приводит к тому, что линтер анализирует меньше файлов, чем порог
  пакета
- **THEN** проверка завершается неуспехом и называет пакет, порог и фактическое число

#### Scenario: Покрытие сократилось, но осталось выше порога

- **WHEN** база анализирует 180 файлов, голова — 140, а порог пакета равен 128
- **THEN** проверка завершается неуспехом и называет число на базе и на голове

#### Scenario: Линтер не отработал

- **WHEN** линтер завершился ошибкой или не выдал разбираемого отчёта
- **THEN** проверка завершается неуспехом, а не считает это отсутствием нарушений

### Requirement: Платформенные записи lockfile не исчезают

Система SHALL проверять, что множество платформенных записей lockfile не сокращается
относительно базовой ветки, где записи различаются кортежем **(семейство пакета,
операционная система, архитектура, разновидность libc)**.

Семейством SHALL считаться идентичность пакета без платформенного различения, а
операционная система, архитектура и разновидность libc SHALL браться из метаданных
`os`, `cpu`, `libc` самого lockfile, а не выводиться разбором имени записи.

Требование именно к кортежу, а не к множеству платформ: разные пакеты поставляют
бинарники для одной и той же платформы, поэтому исчезновение всех записей одного пакета
для платформы остаётся незамеченным, если другой пакет эту платформу закрывает. Тогда
проверка была бы зелёной при неработающем пакете.

Исчезновение записи SHALL считаться допустимым только тогда, когда кортеж остаётся
представлен другой записью того же семейства.

#### Scenario: Дедупликация вложенной копии

- **WHEN** обновление убирает вложенную копию платформенных записей пакета, но те же
  кортежи остаются представлены записями того же семейства на верхнем уровне
- **THEN** проверка проходит

#### Scenario: Потеря бинарника одного пакета при сохранении платформы

- **WHEN** из lockfile исчезают все записи одного семейства для некоторой платформы, а
  сама платформа остаётся представлена записями другого семейства
- **THEN** проверка завершается неуспехом и называет потерянное семейство и платформу

#### Scenario: Потеря платформы целиком

- **WHEN** обновление приводит к тому, что для какого-либо ранее представленного кортежа
  в lockfile не остаётся ни одной записи
- **THEN** проверка завершается неуспехом и называет потерянные кортежи

#### Scenario: Нечего сравнивать

- **WHEN** в базовом или новом lockfile не удаётся обнаружить ни одной записи с
  метаданными платформы
- **THEN** проверка завершается неуспехом как невыполненная, а не проходит как «нарушений
  нет»

### Requirement: Число выполненных тестов не сокращается молча

Система SHALL проверять, что число фактически выполненных тестов удовлетворяет обоим
условиям — не меньше зафиксированного порога и не меньше измеренного на базовой ветке, —
отдельно для модульных тестов и для браузерных. Нарушение любого из условий SHALL
приводить к неуспеху.

Число SHALL браться из машинного отчёта прогона. Пропущенные тесты SHALL NOT
засчитываться как выполненные.

#### Scenario: Тесты выполнены в прежнем объёме

- **WHEN** прогон сообщает о числе выполненных тестов не меньше порога и не меньше
  измеренного на базовой ветке
- **THEN** проверка проходит

#### Scenario: Часть тестов перестала запускаться

- **WHEN** обновление приводит к тому, что часть тестов не запускается или помечается
  пропущенной, и число выполненных падает ниже порога либо ниже базового
- **THEN** проверка завершается неуспехом и называет ожидаемое и фактическое число

### Requirement: Новые инварианты входят в условие публикации и в условие слияния

Проверки покрытия линтера, платформенных записей lockfile и числа выполненных тестов
SHALL входить одновременно в набор проверок, успех которого является условием публикации
сайта, и в набор проверок, обязательных для слияния в `main`.

Требование двойное, потому что эти наборы не совпадают: публикация подписана на
завершение одного workflow целиком, а слияние — на поимённый список проверок. Проверка,
попавшая только в первый набор, не остановит автоматическое слияние; попавшая только во
второй — не остановит выкладку.

#### Scenario: Инвариант нарушен на ветке main

- **WHEN** любая из трёх проверок завершается неуспехом на коммите ветки `main`
- **THEN** публикация этого коммита не происходит

#### Scenario: Инвариант нарушен в PR

- **WHEN** любая из трёх проверок завершается неуспехом в PR
- **THEN** PR не сливается, в том числе автоматически

### Requirement: Вершина main публикуется или об этом сообщается

Система SHALL публиковать содержимое вершины ветки `main`. Непубликация промежуточных
коммитов SHALL считаться нормой: при быстрой череде слияний прогоны отменяются, и
выкладка идёт только для вершины.

Если вершина `main` не опубликована в течение заданного времени после её появления,
система SHALL подать сигнал, а не остаться молчаливой.

Требование существует потому, что отменённый прогон и не отработавшая выкладка выглядят
одинаково — их различает только явная проверка того, что опубликовано.

#### Scenario: Промежуточный коммит не опубликован

- **WHEN** несколько слияний происходят подряд и прогоны промежуточных коммитов
  отменяются
- **THEN** отсутствие публикации промежуточных коммитов нарушением не считается

#### Scenario: Вершина осталась неопубликованной

- **WHEN** вершина `main` не опубликована в течение заданного времени после появления
- **THEN** подаётся сигнал, называющий неопубликованный коммит

### Requirement: Каждый инвариант доказан негативной проверкой

Для каждой из трёх новых проверок SHALL быть предъявлено доказательство того, что она
краснеет при нарушении: записанная воспроизводимо мутация, значение измеряемой величины
до и после мутации, и имя покрасневшей проверки.

Проверка, для которой такое доказательство не предъявлено, SHALL NOT считаться выполненной
частью этого change.

#### Scenario: Доказательство предъявлено

- **WHEN** для проверки записаны точная мутация, два значения измеряемой величины и имя
  покрасневшей проверки
- **THEN** проверка считается доказанной

#### Scenario: Мутация не покраснела

- **WHEN** после внесения мутации проверка остаётся зелёной
- **THEN** результат SHALL трактоваться как «проверка декоративна либо мутация не
  затронула предмет», и оба варианта SHALL быть различены измерением до вывода

### Requirement: Одинаковые обновления приходят одним pull request

Система SHALL объединять в один pull request подъёмы одной и той же зависимости,
происходящие одновременно в нескольких пакетах репозитория.

#### Scenario: Общая зависимость трёх пакетов

- **WHEN** одна и та же зависимость обновляется в `web`, `cms` и `scripts` в одном цикле
- **THEN** Dependabot открывает один pull request, а не три

### Requirement: Внешние действия закреплены неизменяемой ссылкой

Все внешние GitHub Actions, используемые в workflow репозитория, SHALL быть закреплены
ссылкой на конкретный неизменяемый коммит, а не на подвижный тег версии.

Рядом с каждой такой ссылкой SHALL быть указана человекочитаемая версия, иначе состав
обновления невозможно прочитать при ревью.

#### Scenario: Действие закреплено

- **WHEN** workflow ссылается на внешнее действие
- **THEN** ссылка указывает на полный идентификатор коммита, а рядом стоит версия в
  читаемом виде

#### Scenario: Подвижная ссылка

- **WHEN** workflow ссылается на внешнее действие подвижным тегом
- **THEN** проверка целостности workflow завершается неуспехом и называет файл и строку
