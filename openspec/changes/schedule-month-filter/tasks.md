## 0. Порядок работы и обозначения

Порядок из `AGENTS.md` переносится сюда целиком, потому что нарушить его легко, а заметить
нарушение потом нечем:

```
спека → 2 независимых ревью (разные уклоны, только чтение) → approve владельца
      → МОКАПЫ контрола + выбор владельца
      → тесты ОТДЕЛЬНОЙ сессией с чистым контекстом (красный прогон предъявлен)
      → реализация (другой исполнитель)
      → негативные проверки каждого нового гейта
      → ревью кода (два независимых исполнителя) → приёмка → архив
```

Реализация не начинается ни до approve, ни до выбора мокапа: облик панели фильтров
меняется (пятый элемент в сетку на четыре колонки), и правило «мокапы до внедрения»
применяется в полном объёме — точечным исправлением дефекта это изменение не является.

**Обозначения у проверок:**

- **[RED]** — проверка обязана падать на текущем коде. Она и есть предъявляемое
  свидетельство: красный прогон по одному из двух способов из `AGENTS.md` — отдельный push
  коммита только с тестами (упавший check-run на этом SHA) либо приложенный к PR лог с
  точной командой и SHA. «Тесты лежат коммитом раньше» доказательством не является.
- **[GREEN-BY-DESIGN]** — проверка защищает **уже существующее** поведение и на текущем
  коде зелена по определению; красного прогона у неё быть не может. Для неё
  предъявляется **негативная мутация**: поведение временно нарушается, проверка обязана
  покраснеть. Записывается воспроизводимо — точная команда или патч плюс два числа, до и
  после; судить по **имени** покрасневшего теста, а не по цвету прогона.

Каждая мутация выполняется в своём worktree, фикс к моменту мутации закоммичен,
восстановление подтверждается постусловием, подобранным под предмет мутации: для
отслеживаемых файлов — пустой `git status --porcelain` и отсутствие diff относительно SHA
фикса; для мутаций внутри `web/dist/` — контрольная сумма дерева до и после
(`find . -type f -exec shasum {} + | sort | shasum`, из каталога, по относительным путям)
либо пересборка. `git status` внутри `dist` слеп: каталог в `.gitignore`.

## 2. Тесты по спеке — отдельной сессией, до реализации

Вход сессии: утверждённая спека и код репозитория. Обсуждение, которым спека рождалась, в
контекст не переносится. Пишутся только тесты; реализация не трогается.

**Где тесты обязаны оказаться.** Публикацию останавливает единственный workflow `Tests`, и
в нём исполняются: `web/tests/**/*.test.ts` через `npm test`, файлы из include-списка
`web/vitest.build.config.ts` через `npm run test:build`, `web/tests/site.spec.ts` через
`test:e2e:smoke` и `web/tests/a11y.spec.ts` через `test:e2e:a11y`
(`.github/workflows/test.yml:92,95`). **`web/tests/schedule-parity.spec.ts` не запускается
ни одним workflow** — ни `Tests`, ни `Nightly` (там только `test:e2e:compat`). Проверка,
положенная туда, будет зелёной потому, что её никто не выполняет.

Две ловушки при заведении нового файла проверок:

- новый `tests/*.test.ts` подхватывается `vitest.config.ts` автоматически (`tests/**/*.test.ts`);

  `vitest.build.config.ts`, и внести в exclude `vitest.config.ts` — иначе он либо не
  запускается вовсе, либо запускается до сборки и падает на отсутствующем `dist`.
