## Context

Мотивация — в `proposal.md`. Требования разнесены по двум возможностям:
`specs/request-form-transport/spec.md` — общий механизм форм-заявок,
`specs/payment-request/spec.md` — специфика оплаты. Здесь только то, что определяет
подход; решения 1–7 относятся к общему механизму, решение 8 — к размещению формы
оплаты.

Ограничения, из которых всё следует:

- сайт статический (`output: 'static'`), на демо-стенде за nginx лежит собранный
  `dist` — исполняемого кода на сервере нет;
- транспорт заявки не выбран и не может быть выбран сейчас: тестового портала
  Bitrix24 нет, своего бэкенда нет, API заказчика заменяется нашим при выходе в прод;
- в проекте уже есть режим сборки для форм (`DEMO_FORMS`, `web/src/lib/forms.ts`) и
  fail-closed гейт состава ссылок в `scripts/deploy-web.sh`. Новая форма обязана
  встроиться в них, а не завести вторую параллельную дисциплину.

## Goals / Non-Goals

**Goals:**

- спроектировать форму так, чтобы выбор адресата **не менял** ни разметку, ни спеку,
  ни тесты — только конфигурацию сборки;
- сделать невозможным молчаливое исчезновение заявки: ни в браузере, ни в сборке, ни
  в деплое;
- удержать страницу работоспособной в промежутке, когда транспорта ещё нет.

**Non-Goals:**

- выбор постоянного бэкенда — это решение уровня проекта, не этого change;
- хранение заявок на нашей стороне: адресат принимает и отвечает, мы не журналируем
  содержимое;
- капча и антибот-сервисы: внешний скрипт на странице стоит веса, приватности и
  зависимости от третьей стороны.

## Decisions

### Решение 1: транспорт — это конфигурация, а не код формы

Форма отправляет заявку в **один абстрактный адресат**, заданный на сборке. Что за
ним стоит — наш прокси, функция у провайдера, вебхук Bitrix24 — форму не касается.

*Альтернатива «сразу прибить к CRM-форме Bitrix24»* отвергнута: тогда собственная
форма не нужна вовсе (у Битрикса своя вёрстка и свои поля), спека про состав полей
теряет смысл, а мы теряем контроль над согласием на ПДн и над обратной связью об
успехе. *Альтернатива «прибить к `POST /api/payments` заказчика»* отвергнута по
решению владельца: этот API заменяется нашим при выходе в прод, то есть интеграция
была бы одноразовой.

### Решение 2: контракт запроса минимальный, скучный и записанный целиком

Словесного описания «POST с JSON и четыре исхода» недостаточно: по нему две сессии
построят несовместимые контракты, а тесты нельзя написать независимо от реализации.
Поэтому контракт фиксируется здесь дословно.

**Запрос.** `POST <адресат>`, `Content-Type: application/json`, тело:

| Поле | Тип | Обяз. | Ограничение |
|---|---|---|---|
| `requestId` | string | да | UUID v4; постоянен для одной попытки посетителя |
| `firstName` | string | да | 1–100 символов |
| `lastName` | string | да | 1–100 символов |
| `seminar` | string | да | 1–300 символов |
| `amount` | number | да | > 0 |
| `startDate` | string \| null | нет | `YYYY-MM-DD` |
| `venue` | string \| null | нет | до 300 символов |
| `email` | string | да | содержит `@` и доменную часть |
| `phone` | string | да | не менее 10 цифр |
| `consent` | boolean | да | только `true` |

**Ответ.** Тело `{ "status": "accepted" }` либо
`{ "status": "rejected", "errors": [{ "field": "<имя поля из таблицы>", "message": "<текст для посетителя>" }] }`.

**Отображение кодов на состояния формы:**

| Код | Состояние |
|---|---|
| `200`, `201` | отправлена |
| `409` с `status: accepted` | отправлена (повтор с тем же `requestId`) |
| `400`, `422` | отклонена по проверке; поля берутся из `errors[].field` |
| `401`, `403`, `404`, `5xx` | ошибка адресата |
| нет ответа за **10 секунд** | исход неизвестен |
| сетевой сбой | ошибка адресата |

`errors[].field` SHALL совпадать с именем поля из таблицы запроса — иначе требование
«показать, что именно исправить» неисполнимо: форме нечего подсветить.

Предел ожидания — **10 секунд**, число названо в design, а не оставлено реализации:
без конкретного значения сценарий «нет ответа» непроверяем.

Четыре исхода, а не три: отклонение по проверке отделено от ошибки, потому что
посетителю в этих случаях нужно разное — исправить поле либо связаться напрямую.

### Решение 2а: повтор безопасен по `requestId`

`requestId` генерируется один раз на попытку и **не меняется** при повторе после
неизвестного исхода. Меняются данные формы — генерируется новый.

Дедупликация лежит на принимающей стороне: только она знает, что уже приняла. Форма
может лишь дать ей возможность это определить. Отсюда следствие, которое надо
назвать вслух: **до появления адресата, умеющего дедупликацию, требование о повторе
исполнено наполовину** — форма шлёт стабильный идентификатор, но гарантии «дубля не
будет» нет. Это входит в условия выбора адресата, а не откладывается молча.

### Решение 3: конфигурация адресата имеет три значения, а не два

`боевой адресат` / `демонстрационный` / `не задан`:

| Значение | Отправка | Что видит посетитель |
|---|---|---|
| боевой | уходит адресату | состояния по спеке |
| демонстрационный | не уходит никуда | «в демонстрационном режиме заявка не отправлена» |
| не задан | не уходит | «отправка недоступна» + контакты |

Двух значений не хватает, и это была ошибка предыдущей редакции: демо-стенд обязан
показывать форму в работе, но «отправлена» на нём показывать нельзя, а «отправка
недоступна» нечего демонстрировать. Демонстрационный исход — отдельное наблюдаемое
состояние, не успех.

Сборка при `не задан` **проходит**, а не падает: иначе демо-сборку не собрать.
*Альтернатива «собирать молча»* отвергнута прямо — это и есть тихая заглушка.

### Решение 4: без JavaScript страница не предлагает недоступное действие

Отправка требует скрипта, а форма живёт в модальном окне, которое скриптом же и
открывается. Значит без скриптов кнопка открытия — обещание, заведомо невыполнимое.

Реализация: разметка кнопки открытия скрыта по умолчанию и раскрывается скриптом,
а рядом стоит `<noscript>`-блок со способом связаться напрямую. Так без скриптов
посетитель видит контакты, а не мёртвый контрол.

Это дешевле, чем поддерживать серверную обработку формы на статическом сайте, и
честнее, чем немая кнопка. **Требование переведено в спеку как нормативное**: пока
оно жило только здесь, все нормативные сценарии оставались зелёными на странице,
которая без скриптов не работает вовсе.

### Решение 5: гейт ловит общий признак — и признак назван конкретно

Сейчас `deploy-web.sh` сверяет ссылки по признаку `crm_form` и пути заглушки — форма
с отправкой под него не подпадает и прошла бы молча.

Механизм, а не намерение:

1. **адресат объявляется в HTML** — атрибутом на элементе формы, а не только внутри
   скрипта. Это обязательное следствие: адрес, зашитый в минифицированный бандл,
   гейту недоступен в принципе, и «общий признак» остался бы лозунгом;
2. **форма несёт опознавательный признак** — отдельный атрибут именно этой формы.
   Искать «все `<form>` в `dist`» нельзя: на сайте уже есть посторонние формы
   (`ArticleFilterBar`, `LeadMagnet`), и такой поиск потребовал бы объявленного
   адресата от них;
3. **форма присутствует в собранном HTML** скрытой, а не монтируется по клику — иначе
   в `dist` её нет и проверять нечего;
4. гейт находит формы по признаку и сверяет объявленный адресат с режимом сборки.

Гейт краснеет в пяти случаях: адресат не соответствует режиму; форма есть, а
объявления нет; объявление есть, а формы нет; **форма ожидается на странице, но не
найдена ни одной**; проверить не удалось (каталог не прочитан, ноль файлов).

Пятая ветка добавлена отдельно, потому что четырёх не хватало: «ноль файлов» — про
нечитаемый каталог, а не про нулевое число форм на странице, где форма обязана быть.
Именно этот зазор превратил бы гейт в декорацию — сборка зелёная, адрес транспорта не
проверен никогда.

**Способ сравнения — буквальное равенство, а не образец.** У существующего гейта по
ссылкам признак «боевого» узнаётся по форме URL (`crm_form_*` у всех форм Bitrix24). У
будущего транспорта такого образца нет и быть не может: за адресатом может стоять что
угодно. Поэтому `deploy-web.sh` сверяет значение, найденное в `dist`, **с тем самым
значением, которое он только что передал в сборку** — так же, как уже сверяется режим
демо-форм. Regex «по образцу хоста» здесь писать не по чему.

**Смежное ограничение:** преобразование импортированного контента вырезает голые
элементы формы (`html-cleaner.ts:187`). Форма обязана быть собственным компонентом
страницы; попытка внести её через контент приведёт к тихому удалению.

Перечислять известные адреса нельзя по прямому указанию `AGENTS.md`: список отстаёт
от предмета молча. Ровно на этом уже обжигались — первая редакция того же гейта
считала совпадения по одному хосту и отвергала законную боевую сборку, потому что
порталов у заказчика оказалось два. По той же причине спека формулирует проверку
позитивно («объявленный адресат соответствует режиму»), а не как поиск плохих адресов.

### Решение 6: защита от ботов — только поле-приманка, без измерения времени

Скрытое от глаз и от вспомогательных технологий поле, заполнение которого означает
бота.

*Измерение времени заполнения отвергнуто:* оно даёт ложные срабатывания на
автозаполнении браузера и у быстрых пользователей, то есть отсекает настоящие заявки.
Это была бы защита, работающая против цели change.

Срабатывание защиты — наблюдаемое состояние ошибки, а не молчание: требование внесено
в спеку, потому что иначе защита становится ещё одним способом потерять заявку тихо.
Защита заведомо слабая и на большее не претендует; серьёзная фильтрация — забота
стороны, принимающей заявку.

### Решение 7: содержимое заявки не журналируется у нас

Заявка содержит имя, фамилию, телефон и почту. В браузерных и сборочных логах
остаётся только факт отправки и исход, без полей.

Проверяется не «отсутствие логов вообще» (доказать невозможно), а конечный список
точек: код формы не передаёт значения полей в консоль, вывод сборки их не содержит.
Негативная проверка — добавить вывод поля и убедиться, что проверка краснеет.

### Решение 8: форма живёт в модальном окне

Паритет с замещаемым сайтом: там форма открывается по кнопке в модальном окне.

*Альтернатива «блок прямо на странице»* отвергнута дважды. По существу: страница
`/oplata` — справочная, форма из восьми полей в её середине разрывает чтение между
«способами оплаты» и «условиями возврата». По процессу: встроенный блок — изменение
раскладки, а правило проекта требует сначала мокапы в нескольких вариантах и выбор
владельца.

Модальное окно тоже новый заметный элемент, поэтому шаг мокапов остаётся в задачах —
но предметом выбора становится оформление окна, а не структура страницы.

**Ограничение реализации, которое нельзя терять:** окно скрывается, а не создаётся по
клику. Разметка формы присутствует в собранной странице всегда. Это не стилистическое
предпочтение: от этого зависит вся конструкция гейта (Решение 5), а у проекта уже есть
прецедент, когда содержимое, монтируемое по клику, оказалось недоступно инструменту,
работающему с готовой страницей. В коде сайта такой паттерн уже есть — скрытый элемент,
переключаемый инлайновым скриптом (`HeaderTools.astro`); фреймворковых островов в
проекте нет.

### Решение 9: красные тесты живут в ветке change и не вливаются в `main`

Тесты пишутся до появления транспорта и остаются красными неопределённо долго.

*Альтернатива «влить в `main`»* отвергнута: каждый последующий PR был бы красным, и
сигнал CI обесценился бы для всех задач. *Альтернатива «влить с `skip`»* отвергнута
прямее: пропускаемый тест — декорация, а появление реализации его не разбудит, то
есть он не поймает ровно тот момент, ради которого написан.

Цена решения названа честно: ветка стареет, и чем дольше нет транспорта, тем дороже её
слияние. Это принято сознательно; если ожидание затянется, вопрос выносится владельцу
повторно, а не решается тихо.

## Risks / Trade-offs

- **Контракт спроектирован под несуществующего адресата и не подойдёт выбранному** →
  контракт намеренно минимален (Решение 2); адаптер к любому получателю — небольшой
  и находится вне формы.
- **Гейт можно обойти, забыв объявить адресат в разметке** → гейт считает отсутствие
  объявления при наличии формы отказом, а не успехом (Решение 5).
- **Адрес транспорта виден в исходнике страницы — прямое следствие требования гейта**
  → Решение 5 обязывает держать адресат в открытом HTML, а не в бандле, значит адрес
  известен любому. Вместе с Решением 6 это означает, что и адрес, и имя поля-приманки
  доступны для чтения, то есть отправка в обход браузера тривиальна. Компромисс принят
  сознательно: проверяемость гейта важнее сокрытия, которое всё равно было бы мнимым
  (адрес извлекается из бандла за минуты). Следствие для принимающей стороны названо
  прямо — фильтрация и ограничение частоты обязаны быть на ней, а не на форме.
- **Форма, внесённая через контент, будет молча удалена** (`html-cleaner.ts:187`
  вырезает голые элементы формы) → форма реализуется собственным компонентом; проверка
  присутствия формы в собранной странице ловит нарушение.
- **Правка `normalizeLegacyControls` затрагивает не только `/oplata`** → правило
  переписывает любую кнопку без класса; перед изменением проверить все страницы, где
  оно срабатывает, и покрыть их тестом на сохранность.
- **Заявка уходит третьей стороне без нашего журнала — мы не докажем, что она была**
  → сознательный размен ради непревышения необходимого при обработке ПДн; поэтому же
  требование «данные не теряются при ошибке» лежит в спеке.
- **Сумму вводит человек, проверить её не с чем** → следствие принятого у заказчика
  порядка (сумму называет куратор); валидация ограничивается формой числа, ошибка
  ввода ловится только менеджером.
- **Отступление от паритета: согласие на ПДн, которого нет на боевом сайте** →
  названо в проекте и в спеке; отказ от него был бы сбором ПДн без основания.
- **Отступление от паритета: нет выбора кода страны у телефона** → названо в спеке;
  валидация принимает международные номера, требуя не менее десяти цифр.
- **Ветка с красными тестами стареет** → Решение 9; при затягивании вопрос выносится
  владельцу заново.
- **Дедупликация зависит от адресата, которого нет** → форма гарантирует стабильный
  `requestId`, но «дубля не будет» гарантирует только принимающая сторона. Входит в
  условия выбора адресата (Решение 2а), а не откладывается молча.
- **Раскрытие кнопки скриптом задерживает её появление** → кнопка скрыта до
  выполнения скрипта, значит на медленном соединении она появляется не сразу.
  Принято: альтернатива — показывать контрол, который какое-то время не работает.

## Migration Plan

1. Спека утверждается и тесты пишутся **до** появления транспорта — они красные и
   остаются красными в своей ветке, это ожидаемое состояние (Решение 9).
2. Реализация начинается, когда появляется любой из транспортов.
3. Выкатка: сначала демо-стенд (`DEPLOY_MODE=stand`), проверка состояний формы вживую,
   затем боевая сборка.
4. Откат: вернуть ссылку на расписание вместо кнопки формы — страница остаётся
   полностью работоспособной, так как всё информационное содержание от формы не
   зависит.

## Open Questions

- Какой адресат окажется первым — тестовый портал Bitrix24 или наш прокси. На спеку и
  разбиение задач не влияет, на выбор адаптера — да.
- Нужен ли институту онлайн-платёж на новом сайте вообще, или достаточно заявки и
  счёта от менеджера. Вопрос к заказчику; проведение платежа вынесено из объёма
  именно поэтому.
