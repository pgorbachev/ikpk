## MODIFIED Requirements

### Requirement: Класс автоматически сливаемых обновлений задан таблицей

Право на автоматическое слияние SHALL определяться по совпадению трёх признаков —
экосистема, **пакет**, тип подъёма — со строкой разрешающей таблицы. Отсутствие
совпадения SHALL означать отказ: правило работает fail closed. Совпадение является
необходимым, но для npm package `web` не достаточным условием: security-boundary override
ниже может только запретить автоматическое слияние и SHALL NOT разрешать иной класс.

Для строки `cms` трёх признаков недостаточно. Имя зависимости SHALL входить в закрытый
toolchain-список. Имя вне списка SHALL означать отказ, в том числе когда подъём
`semver-patch` или `semver-minor` и когда зависимость объявлена в секции разработки.

Toolchain-список ровно таков и относится только к `cms`:

- `@eslint/js`
- `eslint`
- `globals`
- `typescript`
- `typescript-eslint`
- `@types/node`

`@types/react` и `@types/react-dom` в список не входят: единственные импорты React в
`cms` лежат в `src/admin/`, а обязательный `tsc` этот каталог и файлы `.tsx` не
проверяет.

Пакет `payments` в таблицу не входит. Никакое его npm-обновление, включая имена из
списка выше и `tsx`, SHALL NOT получать автослияние. Обязательные контексты `main` на
21.11.2026 не содержат `payments checks`. Единственная обязательная проверка этого
пакета — `Runtime dependency audit (payments)`, и она вызывает `npm audit --omit=dev`.
Имена списка в `payments` стоят только в секции разработки, поэтому эта проверка их не
видит. Красный eslint или `tsc` слияние не останавливают.

| Экосистема | Пакет | Тип подъёма | Имя зависимости |
|---|---|---|---|
| npm | `web` | `semver-patch`, `semver-minor` | любое, кроме security-boundary override |
| npm | `scripts` | `semver-patch`, `semver-minor` | любое |
| `github-actions` | — | `semver-patch`, `semver-minor` | — |
| npm | `cms` | `semver-patch`, `semver-minor` | только toolchain-список |

Система SHALL NOT сливать автоматически подъём мажорной версии ни в одной экосистеме,
включая `github-actions` и имя из toolchain-списка.

Система SHALL NOT сливать автоматически обновление npm в `cms`, имя которого в
toolchain-список не входит, независимо от типа подъёма и от секции манифеста. Система
SHALL NOT сливать автоматически никакое обновление npm в `payments`.

**Тип зависимости признаком не является.** Секция манифеста — производственная против
секции зависимостей разработки — не описывает, что доходит до пользователя, и потому
решением быть не может: `astro` объявлен производственной зависимостью `web`, но это
сборщик, на выходе которого статический HTML; `tsx` объявлен зависимостью разработки
`payments` и при этом запускает процесс. Признаком для `web`, `scripts` и
`github-actions` служит пакет. Признаком для `cms` служит пакет вместе с именем из
списка, а не секция манифеста. Для `payments` секция тоже не является допуском: пакета
в таблице нет.

Если PR содержит несколько подъёмов, право на автоматическое слияние SHALL определяться
по наименее разрешающему из них.

Решение SHALL приниматься по метаданным, полученным от Dependabot, а не по разбору
заголовка PR или диффа: заголовок пишется генератором и не является контрактом.

Для `web` система SHALL дополнительно читать committed machine registry зависимостей
границы rich-content safety, созданный change `sanitize-rich-html-content`. Реестр SHALL
лежать по пути `web/tests/fixtures/rich-content-safety/security-dependency-registry.json`
и SHALL перечислять выбранные sanitizer, runtime DOM/parser, browser-oracle tooling и
точные direct/transitive parser lockfile nodes. PR SHALL оставаться на ручном пути, если
Dependabot metadata прямо называет зарегистрированный package (включая `parse5` и
`playwright`) либо если идентичность любого зарегистрированного node из
`runtime.lockfileNodes` или `oracle.lockfileNodes` различается между базой и головой.

Идентичность узла — это совокупность `version`, `resolved`, `integrity` и карт
`dependencies` и `optionalDependencies`. Отсутствующая карта и пустая карта совпадают.
Порядок ключей карты узлы не различает. Узел, который есть только на одной из сторон,
различается. Любой другой ключ записи, включая `peer`, `dev`, `optional`, `license`,
`engines`, `bin` и `funding`, сам по себе идентичность не меняет.

Классификация PR не отменяет требование группировки, и этот change его не ослабляет.
Конфиг Dependabot не меняется.

Lockfile diff здесь является только deny-only проверкой транзитивных изменений: он
SHALL NOT использоваться для выдачи разрешения, которое не следует из Dependabot
metadata и таблицы. Отсутствующий, нечитаемый либо несогласованный с lockfile registry
SHALL означать ручной путь для npm PR пакета `web`.

Пример остаточного риска в требовании о происхождении и сценарий «PR Dependabot,
оставленный ручному пути» после этой дельты применяются к обновлению `cms` только
когда эта таблица его не допускает. Обновление `cms` из toolchain-списка типа
`semver-patch` или `semver-minor` этими формулировками не описывается: для него
проверка допустимости завершается так же, как для разрешённого обновления `web` или
`scripts`. При расхождении со сценарием, который называет любое обновление `cms`
ручным путём, побеждает эта таблица. Сценарий «Общая зависимость разрешённого и
запрещённого пакетов» в требовании про один pull request этой дельтой заменён: позиция
`cms` остаётся отдельным PR, но для имени из списка это уже не запрещённый пакет.

#### Scenario: Патч зависимости пакета web

- **WHEN** Dependabot открывает PR с подъёмом `semver-patch` обычной зависимости пакета
  `web`, которая не названа security registry и не меняет идентичность его lockfile nodes
- **THEN** система помечает PR к автоматическому слиянию, независимо от секции манифеста,
  в которой зависимость объявлена

#### Scenario: Прямое обновление security-boundary package

- **WHEN** patch/minor PR пакета `web` прямо поднимает package из machine security registry
- **THEN** система не помечает PR к автоматическому слиянию и оставляет его для security
  review с maintenance/provenance и advisory evidence

#### Scenario: Транзитивный parser node изменён обычным подъёмом

- **WHEN** Dependabot metadata называет незарегистрированный package `web`, но
  идентичность зарегистрированного транзитивного parser node различается
- **THEN** deny-only override оставляет весь PR на ручном пути

#### Scenario: У зарегистрированного узла изменилась только книжная метаинформация

- **WHEN** patch/minor PR пакета `web` или `scripts` поднимает зависимость, не названную
  security registry, а у зарегистрированного узла между базой и головой различается
  только ключ, не входящий в идентичность, в том числе `peer`
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Security registry недоступен

- **WHEN** npm PR пакета `web` попадает в разрешающую строку, но machine security registry
  отсутствует, не читается либо расходится с lockfile subtree
- **THEN** система работает fail closed и оставляет PR на ручном пути

#### Scenario: Минорный подъём производственной зависимости пакета scripts

- **WHEN** Dependabot открывает PR с подъёмом `semver-minor` зависимости пакета
  `scripts`, объявленной в производственной секции манифеста
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Минорный подъём действия

- **WHEN** Dependabot открывает PR с подъёмом `semver-minor` в экосистеме
  `github-actions`
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Мажорный подъём действия

- **WHEN** Dependabot открывает PR с подъёмом `semver-major` в экосистеме
  `github-actions`
- **THEN** система не помечает PR к автоматическому слиянию и оставляет его ревьюеру

#### Scenario: Мажор в разрешённом пакете

- **WHEN** Dependabot открывает PR с подъёмом `semver-major` зависимости пакета `web`
  или `scripts`, либо с подъёмом `semver-major` имени из toolchain-списка в `cms`
- **THEN** система не помечает PR к автоматическому слиянию

#### Scenario: Patch toolchain-имени в cms

- **WHEN** Dependabot открывает PR с подъёмом `semver-patch` или `semver-minor` одного
  имени из toolchain-списка в пакете `cms` и других подъёмов в PR нет
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Runtime-зависимость cms

- **WHEN** Dependabot открывает PR, изменяющий в пакете `cms` зависимость, имени которой
  нет в toolchain-списке, в том числе `styled-components` или пакет Strapi
- **THEN** система не помечает PR к автоматическому слиянию, независимо от типа подъёма и
  секции манифеста

#### Scenario: Карты зависимостей совпадают без учёта порядка и пустоты

- **WHEN** patch/minor PR пакета `web` поднимает зависимость не из security registry, а
  у зарегистрированного узла карты `dependencies` и `optionalDependencies` совпадают по
  составу, отличаясь только порядком ключей, либо одна сторона карту не содержит, а
  другая содержит пустую
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Любое обновление пакета payments

- **WHEN** Dependabot открывает PR, изменяющий любую зависимость пакета `payments`, в
  том числе `typescript-eslint` или `tsx`
- **THEN** система не помечает PR к автоматическому слиянию, независимо от типа подъёма,
  числа зависимостей в PR и секции манифеста

#### Scenario: Смешанный групповой PR

- **WHEN** сгруппированный PR содержит и подъёмы, попадающие в разрешающие строки, и
  хотя бы один, в них не попадающий
- **THEN** система не помечает PR к автоматическому слиянию

#### Scenario: Метаданные недоступны

- **WHEN** метаданные Dependabot для PR получить не удалось
- **THEN** система не помечает PR к автоматическому слиянию и не пытается вывести класс
  из заголовка или диффа

### Requirement: Одинаковые обновления приходят одним pull request

Система SHALL запрашивать объединение в один pull request подъёмов одной и той же
зависимости, происходящих одновременно в `web` и `scripts`, если их version constraints
совместимы с общей целевой версией. Различие относительного типа подъёма между patch и
minor внутри этого разрешённого класса SHALL допускаться. При несовместимых constraints
Dependabot MAY открыть отдельные pull request.

Позиция `cms` SHALL приходить отдельным pull request, а не в группе с `web` или
`scripts`. Для имени из toolchain-списка и подъёма `semver-patch` или `semver-minor`
этот отдельный PR разрешён к автослиянию. Отдельность PR не делает позицию запрещённой.
Имя вне списка и мажор в `cms` остаются ручными и тоже приходят отдельно.

Наблюдённое основание: `@eslint/js`, `eslint`, `globals`, `typescript` и
`typescript-eslint` объявлены в `web`, `scripts` и `cms`. Минорный подъём любой из них
затрагивает все три пакета одновременно.

#### Scenario: Общая зависимость двух разрешённых пакетов с совместимыми constraints

- **WHEN** одна и та же зависимость обновляется в `web` и `scripts` в одном цикле и обе
  позиции совместимы с общей целевой patch/minor-версией
- **THEN** Dependabot открывает один pull request, а не два

#### Scenario: Общая зависимость web, scripts и cms

- **WHEN** в одном цикле обновляется `typescript-eslint` в `web`, `scripts` и `cms`
  подъёмом `semver-patch` или `semver-minor`
- **THEN** позиция `cms` приходит отдельным pull request и помечается к автослиянию, а
  совместимые подъёмы для `web` и `scripts` объединяются в другой pull request
