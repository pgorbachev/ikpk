## Context

См. `proposal.md`. Сайт собирается в статический HTML из снимка CMS. `getSnapshotReferenceDate()` используется как «сегодня» в расписании, страницах семинаров и подборках главной; уже опубликованный HTML не пересчитывается с ходом времени. `schedule-window.ts` различает последний день события и день начала, но точного времени не учитывает. CMS хранит `startAt` и `endAt` как datetime, но импортированные значения представляют календарные дни; у однодневного вебинара они равны. `additionalText` может содержать свободный текст о часе начала.

## Goals / Non-Goals

**Goals:** одна подтверждённая временная граница для записи; согласованное скрытие на всех поверхностях; воспроизводимые тесты с фиксированными часами; безопасный переход старых данных.

**Non-Goals:** удаление исторических страниц и записей CMS; автоматический разбор часа из текстовых примечаний; обновление содержания расписания из CMS без публикации нового снимка.

## Decisions

1. **Источник времени.** Сохранить `startAt`/`endAt` как прежние календарные границы и добавить `startsAtInstant` (UTC-момент) и `startTimeZone` (IANA-имя зоны ввода). Иначе присвоение реального часа `startAt` однодневному событию делает `endAt < startAt`, и действующая проверка CMS не пропустит запись. В снимок попадают новые поля. Только их подтверждённая пара определяет точное начало. Гейт сравнивает местную дату `startsAtInstant` в `startTimeZone` с датой `startAt`, которую сайт показывает после действующей нормализации; несовпадение отклоняется. Изменение любого из трёх значений снимает подтверждение и требует повторной сверки. Перед включением фильтра редактор сверяет все активные записи с датой сегодня или позже, а также записи без даты, с первоисточником. Гейт публикации отвергает неразрешённые записи без обоих новых полей или с невалидной зоной. Свободный текст не парсится: его формат и зона непредсказуемы. При вводе CMS показывает местное время и зону, чтобы оператор мог проверить конвертацию.

2. **Единый вывод.** `schedule-window.ts` получает чистую функцию `isBeforeStart(entry, now)` с границей `now < startsAtInstant`; `now` передаётся аргументом. Для браузера функция включается в обычный собранный модуль. Дата снимка остаётся опорной датой воспроизводимой сборки, как требует `cms-content-source`; браузер применяет текущий момент при первом открытии и последующих переходах. Скрипт фильтров расписания получает готовую текущую видимость, не вычисляя время.

3. **Статические страницы.** Сборка передаёт браузеру все активные записи снимка, которые могут стать ближайшими после исчезновения текущей, а не только первые три. Общий механизм пересчитывает ведущий анонс, карточки, анонсы дат на страницах программ, фильтры, месяцы и пагинацию при загрузке, по таймеру ближайшего начала и при `visibilitychange`/возврате фокуса. Для страницы семинара он убирает предложение записи на начавшийся сеанс, сохраняя сам маршрут и описание. Справочники курсов без дат остаются каталогом описаний. Перечень для новой оплаты использует ту же границу, но уже созданные платёжные попытки продолжают жить по прежнему контракту. Время сравнивается как UTC-момент, так что зона браузера не влияет на границу.

4. **Проверяемость.** Тесты сначала воспроизводят дефект при фиксированном времени до, в и после начала. Браузерный тест проверяет уже загруженную страницу, переход к следующему анонсу, фильтры/пагинацию и восстановление вкладки после пропущенного таймера. Негативная проверка временно возвращает старое правило в отдельном worktree и подтверждает, что именно регрессионные тесты краснеют.

## Risks / Trade-offs

- **Старый контент без подтверждённого времени → блокировка публикации.** До переключения собрать отчёт по всем активным записям с датой сегодня или позже и без даты, сверить часы с редактором и заполнить новые поля. Включать гейт только одновременно с готовыми данными.
- **Нет JavaScript или часы устройства неверны → статический HTML может оставаться устаревшим после публикации.** Начальный HTML воспроизводимо фильтруется по опорной дате снимка; для обычного браузера исправление происходит без выкладки. Это ограничение статической архитектуры должно быть явно принято владельцем при утверждении change. При требовании одинакового результата для посетителей без JavaScript нужна серверная динамика или публикация на каждой временной границе — отдельное архитектурное решение.
- **Снимок CMS не содержит новых или изменённых событий → клиент работает только с уже опубликованными данными.** Существующая процедура публикации остаётся источником новых событий; скрытие старых не требует новой публикации.
- **Переход через границу месяца → старый фильтр может показывать пустые месяцы.** Актуальный набор служит единственным источником карточек, опций и счётчиков.
- **Пересечение с активными changes → два правила видимости.** До реализации и merge обновить `cms-content-authoring-and-migration` (ближайшая дата) и `payment-seminar-picker` (список новых оплат) относительно новой границы; проверить применимость дельт после архивирования в одноразовом worktree.

## Migration Plan

1. Изолированно обновить схему CMS, импорт и захват снимка; получить отчёт обо всех активных будущих записях без подтверждённого времени. Заполнение данных проходит обычную редакторскую проверку.
2. Добавить гейт полноты, красные тесты, затем код, зелёные тесты и отдельное ревью. Релиз не допускается, пока отчёт не пуст и точный момент вебинара 22 октября проверен по исходному объявлению.
3. Провести сборку и браузерную приёмку на стенде до и после границы с управляемыми часами. Публиковать только через действующий release admission и штатный publication launcher.
4. Для отката вернуть предыдущий статический релиз штатной процедурой; изменения контента в CMS не удалять. При откате прежний релиз снова будет показывать событие по своему правилу, что фиксируется как ограничение отката.
