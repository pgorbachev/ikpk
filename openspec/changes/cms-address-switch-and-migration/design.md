## Context

Выделен из `cms-content-authoring-and-migration` 05.10.2026. Обоснования решений о плоской схеме,
истории адресов и переносе остаются в design.md исходного change и после его архива — в
`openspec/changes/archive/`. Здесь записано только то, что относится к разделению.

## Goals / Non-Goals

**Goals:** переключить канонический адрес целиком и перенести контент без потерь.

**Non-Goals:** схема системы управления, роли, медиа, формы — это исходный change.

## Предварительная SQL DEMO193-фаза

Предварительная фаза PR #186 (D4 + D23-data + D3-data) создаёт отдельную CMS-базу и data release
офлайн из неизменяемого SQL baseline и отдельно разрешённых публичных медиафайлов. DEMO193 —
только целевая демонстрационная база: её текущее содержимое не используется как источник,
поверхность для повторного импорта или overlay. Ручные изменения и три ручных семинара в DEMO193
не смешиваются с SQL baseline. У этой фазы нет backup/restore DEMO193.

Исходный SQL и приватный data release хранятся приватно в локальном Git. В публичный репозиторий
попадают только конвертер, синтетические фикстуры и очищенные спецификации. Приватный manifest
фиксирует source и target metadata ID, соответствие source→target и хеши кода, трансформации и
данных. Потеря любого согласованного поля, связи или отдельно разрешённого медиафайла всегда
завершает перенос ошибкой с ненулевым кодом. Неподдерживаемый элемент источника можно исключить
только по явному именному решению владельца; его перечисление в инвентаризации само по себе
разрешением не является. Документные файлы проходят отдельный allowlist и не
считаются растровыми медиа. Текущие количества для сверки: Institutes 3, Teachers 31, Programs 26,
Articles 68, Seminars 132. Срез Events на 2026-10-12: 280 active, из них 271 с active parent и
58 current/future; это инвентарные значения, а не фиксированный фильтр миграции. Значение 29 в
прежней подписи числа персон устарело; классификация персон остаётся
первичной и передаётся владельцу/заказчику на подтверждение.

SQL адаптера в репозитории пока нет; этот план описывает будущую поставку и не утверждает, что
адаптер или приёмка уже реализованы. Раздельный SQL data этап может быть выполнен до полной D7
поставки, не архивируя родительский change и не закрывая полную миграцию. Его зависимости — только
PR #186 на явно утверждённой точной ревизии, RED/GREEN-проверки, независимые code/security/pony
reviews, свежий CI и сверки точных пар кода и data snapshot. Требования полной поставки ниже,
включая защиту правок заказчика и атомарность источника, остаются в силе и не считаются
выполненными demo-прогоном. Изменения адресов и production не входят в эту фазу.

## Decision log

Зафиксированные ниже решения описывают применение уже принятых контрактов при переносе. Они не
разрешают DEMO193 overlay, не утверждают, что SQL покрывает данные, которых в нём нет, и не
свидетельствуют о выполненной реализации или production-приёмке.

- **Контакты и статические страницы.** Для SQL-отсутствующих публичных страниц использовать
  фиксированный принятый корпус и текущий код как явно перечисленные supplements с именами и
  версией в приватном manifest. Это не DEMO193 overlay. Для страниц с SQL-основанием сохранять
  SQL как базу; `OrganizationInfo` заменяет только соответствующие секции организации. У
  контактов Page задаёт SEO, а видимые контакты, реквизиты, карту и структурированные данные
  организации продолжают задавать `kontakty.astro`, константы навигации и props `ContactShell`;
  одного `Page.body` для этого недостаточно. Источники supplement следует раскрыть в manifest,
  не объявляя SQL владельцем данных, происходящих из кода или принятого публичного корпуса.
- **Семантические поля семинара.** `targetAudience` сохранять как именованный раздел внутри
  `full_text`, используя существующую композицию рендера тела. `learning_plan`, `learning_mode` и
  `recommendations` захватывать и отображать каждый один раз, не дублируя их устаревшей копией
  внутри тела. Сопоставление по значениям: `curriculum` → `learning_mode` → «Как проходит
  обучение»; `learningProcess` → `learning_plan` → «Учебный план». Сохранять точные утверждённые
  заголовки и пробелы; не добавлять в тело структурированные разделы или сырые сертификаты.
- **Даты, автор и порядок статей.** Сохранить текущие принятые сортировку по дате, отсутствие даты
  на карточках, условный показ даты статьи и JSON-LD; автора SQL и priority хранить только в
  приватной provenance. Не добавлять публичную byline-разметку или сортировку по legacy priority.
  Источник дня публикации остаётся единственным открытым выбором владельца: рекомендуются сутки
  SQL `createdAt`, подтверждённые captured JSON-LD `datePublished` для 68/68 точных identity.
  При этом дни существующего `published_at` совпадают с SQL `updatedAt` для 68/68 и лишь для 5/68
  совпадают с captured `datePublished`; переход на `createdAt` меняет 63 отображаемые даты. До
  ответа владельца не считать ни один источник даты утверждённым и не вводить fallback между ними.
- **Связи преподавателей событий.** Сохранять текущий публичный контракт `teachers[]`: переносить
  M2M `EventsAndTeachers` в существующую связь `teachers[]`. Пять расхождений с scalar
  `teacherId` у прошлых событий записывать как приватные именованные source exceptions; не
  объединять два источника. Сохранять принятые фильтры: исключаются 9 событий с удалённым
  семинаром и 18 связей с удалёнными преподавателями. Текущего подтверждённого конфликта для
  будущих/текущих событий нет; это решение о проекции, а не утверждение о восстановленной
  исторической precedence SQL backend.
- **Изображение и коллекция события.** Сохранение event-specific image и `isEventCollection` уже
  входит в принятый контракт/design G5. При реализации добавить отсутствующие CMS-поля и
  snapshot projection; сохранить существующего потребителя изображения в расписании. Флаг
  коллекции переносить в данные без нового UI.
- **Публичные документы.** Для 56 документов вести отдельный allowlist и проверять исходные байты,
  MIME и путь до материализации. Использовать существующую раздачу статических файлов и
  pass-through для нерaster-файлов; не загружать PDF через raster media pipeline Strapi. Наличие
  pipeline не означает, что байты всех 56 документов уже восстановлены или проверены.
- **Изображение института Барраля.** Использовать принятый branding asset
  `web/public/institutes/barral-logo.png`, SHA-256
  `8439ad1f965f71127795cbb93cc959db5b416a99fd55156d3449ffb4f81db5eb`, как замену отсутствующего
  исходного изображения. Зафиксировать отсутствие оригинала в provenance; не выдавать замену за
  восстановленные исходные байты и не подменять ею SQL image identity.
- **Видео.** Сохранить шесть активных playlist identity SQL IDs `31, 32, 33, 34, 36, 37`, каждая
  соответствует существующему approved playlist slug/mirror и SQL title. Хранить исходную
  playlist provenance приватно; не группировать записи и не выдумывать `Videos.type` (такого
  столбца в SQL нет). Байты трёх дополнительных thumbnail всё ещё требуют проверки; использовать
  принятые mirror thumbnails, не заявляя проверку этих байтов.

Первичная классификация персон и статей остаётся по фактическим active ID, но передаётся
владельцу/заказчику на подтверждение. Все решения сохраняют разделение публичного синтетического
CI и точной парной проверки: локально фиксировать полный SHA кода и хеш приватного data snapshot;
production, полная D7 и атомарность источника остаются отдельными воротами.

## Decisions

- **Переключение адресов неделимо.** Перенаправления, ссылки, `canonical`, карта сайта и снятие
  `noindex` выкладываются одной поставкой. Любой частичный порядок выводит записи из индекса либо
  оставляет два индексируемых адреса у одной страницы.
- **Красные тесты хранятся в каталоге change**, а не в `web/tests/`: PR с красными тестами в
  `main` не сливается, а удалить их значило бы выбросить оплаченную работу. При активации они
  возвращаются в `web/tests/` (задача 0.2).

## Risks / Trade-offs

- Дельта написана до появления основной спеки: при активации её надо пересобрать (задача 0.1),
  строгая валидация расхождения не покажет.
