## 2. Дефект D1: обязательный check не публиковался вовсе

**Наблюдение.** Первые же настоящие события после rollout (три PR, `synchronize`)
прогнали доверенный producer целиком — и упали в одном и том же месте.

| dispatcher run | source signal run | PR | результат |
|---|---|---|---|
| 32151344352 | 32151328732 | 134 | failure |
| 32151376093 | 32151355780 | 132 | failure |
| 32151397565 | 32151364146 | 136 | failure |

Состав jobs у 32151344352: `Authenticate source signal` — success,
`Policy / Authenticate dispatcher caller` — success, `Policy / Fresh pull-request
snapshot` — **failure**, `Policy / Eligibility gate` — failure, `Policy / Assessment`,
`Policy / Enable native auto-merge`, `Policy / Publish head-bound policy checks` —
skipped.

То есть доверенная двухступенчатая аутентификация сработала (это положительная находка:
signal → artifact → dispatcher → caller guard прошли на живом событии), а дальше политика
падала.

**Причина.** `jq -e` завершается кодом 1, когда последнее выведенное значение — `false`.
Шаг читал пометку выражением `.auto_merge != null`, а `auto_merge` у PR без включённого
авто-слияния равен `null`:

```
$ echo '{"auto_merge":null}' | jq -er 'if has("auto_merge") then (.auto_merge != null) else error("missing auto_merge") end'
false
exit=1
$ echo '{"auto_merge":{"enabled_by":{"login":"x"}}}' | jq -er '...той же записью...'
true
exit=0
```

**Следствие, измеренное на живом PR.** Публикация check'ов требует
`needs.snapshot.result == 'success'`, поэтому не публиковалось ничего:

```
$ gh api "repos/pgorbachev/ikpk/commits/3dfbdc0cb3789fd694f3e17092a69139574a8b20/check-runs?filter=all&per_page=100" \
    --jq '[.check_runs[]|select(.name|test("Dependabot auto-merge"))]'
[]
$ gh api repos/pgorbachev/ikpk/pulls/134 --jq '{mergeable,mergeable_state}'
{"mergeable":true,"mergeable_state":"blocked"}
```

Проверка `Dependabot auto-merge / Eligibility gate` уже была required, а отчитаться не
могла никогда — значит блокировались **все** открытые PR, и автоматизация не могла
включить авто-слияние даже правильному PR: job включения пометки живёт в том же прогоне и
тоже пропускался.

Дефект **fail closed** — лишнего слияния не произошло, — но автоматизация была
неработоспособна.

**Кто его исправил.** Параллельно с этой работой тот же дефект нашёл и закрыл другой
исполнитель: PR #138, слитый в `main` merge-коммитом `1f6140f`. Там `jq -er` заменён на
`jq -r` (отказ при отсутствии поля по-прежнему даёт `error`), пин переведён на engine v4
`b8797f132dc5f50600faaf6a16d537fb9be0701e`. Моя собственная правка того же места
(`| tostring`) **отброшена при слиянии** — переделывать уже сделанное незачем, а две
разошедшиеся редакции одного шага хуже одной. В ветке осталась только та часть, которой
не было ни у кого: дефект D2, обновление спеки и характеризующие тесты.

Тесты при этом сохранили силу и стерегут **слитую** редакцию: возврат `-e` в неё
(`s/jq -r 'if has\("auto_merge"\)/jq -er 'if has("auto_merge")/` над
`dependabot-auto-merge-policy.yml`) даёт 30 passed / 3 failed против контроля 33 / 0,
и краснеют «сообщает auto-merge-enabled=false, а не падает», «отличает устаревшую вершину
события от текущей» и — независимо — пришедший из #138 тест о совпадении дерева с
закреплённой ревизией.

Две проверки над одним предметом здесь **не дублируют друг друга, и расхождение названо**:
тест из #138 исполняет политику **по закреплённому SHA**, поэтому поломка рабочего дерева
без смены пина его не красит; мой тест исполняет **рабочее дерево**, поэтому не заметил бы
расхождения пина. Красит такую поломку третий — про совпадение дерева с пином. Ответы всех
трёх на этом дереве согласованы.

**Почему это не поймали 672 теста.** Предмет дефекта — shell внутри workflow. Все прежние
проверки смотрят либо на TypeScript-модуль решения, либо на структуру YAML; ни одна не
исполняла сам шаг. Новый тест исполняет **тот самый текст шага, взятый из YAML**, а не его
копию: разошедшаяся копия и была бы следующим таким же дефектом.

## 3. Дефект D2: продвижение не могло опознать слитый PR

Слияние PR #137 само породило событие `closed`, то есть механизм продвижения был проверен
живьём сразу же — и упал:

```
signal     run 32146430416  .github/workflows/dependabot-rebase.yml  pull_request_target  success
dispatcher run 32146446224  job «Authenticate merged source»         FAILURE (exit 1)
```

**Причина** — измеренное ограничение площадки, а не ошибка в предикате:

```
$ gh api repos/pgorbachev/ikpk/actions/runs/32146430416 --jq '{event,conclusion,pr_count:(.pull_requests|length)}'
{"event":"pull_request_target","conclusion":"success","pr_count":0}

$ gh api repos/pgorbachev/ikpk/actions/runs/32151328732 --jq '{event,pr_count:(.pull_requests|length)}'
{"event":"pull_request_target","pr_count":1}
```

Оба run — одного типа события, но у закрытого PR связь run→PR пуста, а у открытого
заполнена. Dispatcher требовал `pull_requests | length == 1`, то есть требовал
невыполнимого: опознать PR он не мог **никогда**.

Это дефект и **спеки**, а не только кода: требование «Dispatcher SHALL проверить exact
source run, workflow path, event, conclusion, actor, PR/head association …» для закрытого
PR неисполнимо. Спека обновлена через `/opsx:update`: связь требуется там, где площадка её
сохраняет; для закрытого PR она устанавливается типизированным artifact (номер PR) плюс
свежим authoritative снимком (факт слияния и вершина), а artifact доказательством слияния
не служит.

## 5. Негативная проверка гейтов

Опорный SHA фикса — `bae6af953e3370cd1fc7b7dd31d3fcd269251609`. После каждой мутации
дерево восстанавливалось и сверялось с этим SHA (`git diff --quiet <SHA> -- <файл>`);
расхождений не было. Прогон один и тот же:
`cd web && npx vitest run tests/dependabot-auto-merge-live-regressions.test.ts`.

Контроль без мутации: **20 passed / 0 failed**.

| мутация (perl-выражение над файлом) | числа | покраснел ИМЕННО |
|---|---|---|
| вернуть D1 — на моей тогдашней редакции: `s/\.auto_merge != null \| tostring/.auto_merge != null/` | 18/2 | «сообщает auto-merge-enabled=false…» + «отличает устаревшую вершину…» |
| вернуть D1 — на **слитой** редакции из #138: `s/jq -r 'if has\("auto_merge"\)/jq -er 'if has("auto_merge")/` | 30/3 (контроль 33/0) | те же два теста + «executes the exact policy revision pinned by the dispatcher» |
| снять `test "sha256:$(sha256sum …)" = "$ARTIFACT_DIGEST"` | 19/1 | «отвергает artifact с несовпадающим digest» |
| снять **обе** проверки количества artifact | 19/1 | «отвергает второй одноимённый artifact» |
| снять `test "$(jq -er '.schema' …)"` | 19/1 | «отвергает schema другого сигнала» |
| снять `test "$API_MERGED" = "$SIGNAL_MERGED"` | 19/1 | «отвергает противоречие между artifact и свежим снимком» |
| убрать `.head.sha == $head_sha` из свежего снимка | 19/1 | «отвергает свежий снимок с другой вершиной» |
| убрать `.artifacts[0].workflow_run.id == $run_id` | 19/1 | «отвергает artifact от другого run» |
| `.sourceRunAttempt == $run_attempt` → `(.sourceRunAttempt \| type == "number")` | 19/1 | «отвергает artifact от другой попытки того же run» |
| убрать сверку `.path` источника | 19/1 | «отвергает source run от другого workflow» |
| убрать `.event == "pull_request_target"` | 19/1 | «отвергает source run от другого события» |
| `.conclusion == "success"` → `(.conclusion \| type == "string")` | 19/1 | «отвергает source run с неуспешным исходом» |
| снять `test "$ARCHIVE_MEMBERS" = dependabot-rebase-signal.json` | 19/1 | «отвергает лишний файл в архиве» |

**Две мутации первого прогона остались зелёными, и причины у них разные — их обязательно
различить, иначе вывод о гейте делается по неудавшемуся эксперименту.**

1. Снятие одной строки `test "$(jq -er '.total_count' …)" -eq 1` дало **19/0**: предмет
   остался, потому что единственность artifact стерегут **две** строки, и вторая
   (`.artifacts | length`) поймала фикстуру с двумя artifact. Гейт не декоративен —
   при снятии обеих строк тест краснеет (строка в таблице выше).
2. Снятие `test "$ARCHIVE_MEMBERS" = …` дало **19/0** по настоящей причине: теста на
   лишний файл в архиве не было **вовсе**. Непройденная ветвь — такое же обещание, как
   непроверенный гейт, поэтому тест добавлен (коммит `3ee0d97`), и после этого та же
   мутация краснеет.

Отдельно: первая редакция мутации «снять привязку к `run_attempt`» вырезала кусок
jq-фильтра и **сломала его синтаксис**, из-за чего dispatcher отвергал всё подряд и
покраснели положительные тесты, а не целевой. Результат недействителен, мутация повторена
точечно — заменой предиката на всегда истинный. Красный цвет прогона сам по себе ничего
не доказывает: судить надо по имени покрасневшего теста.

## 6. Решение владельца: ruleset допустимости отменён (2026-08-18)

**Наблюдение, приведшее к решению.** После починки D1 конвейер заработал целиком — и стало
видно то, чего не было видно, пока он падал раньше публикации. Живой прогон 32159749333 на
человеческом PR #139:

```
Authenticate source signal            success
Policy / Authenticate dispatcher caller success
Policy / Fresh pull-request snapshot  success   ← до фикса здесь был отказ
Policy / Assessment                   success
Policy / Eligibility gate             failure   ← автор не Dependabot
Policy / Provenance evidence          failure
Policy / Enable native auto-merge     skipped
Policy / Publish head-bound policy checks (публикует оба check на head)
```

Проверка краснеет на **каждом** PR, автор которого не Dependabot, — так и было задумано
требованием 2.2. Но как **обязательная** она блокировала все человеческие PR: `#112`,
`#132`, `#134`, `#136` и сам `#139` стояли в `mergeable_state = blocked`, и каждый
пришлось бы сливать владельческим обходом. Требование, выполнимое только обходом,
декоративно.

**Что сделано.** Ruleset `20993209` удалён:

```
DELETE /repos/pgorbachev/ikpk/rulesets/20993209
```

Состояние после — проверено перечитыванием API:

- rulesets: остался только `14690936` «main protectioin», `active`, не изменялся;
- branch protection: `strict: true`, `enforce_admins: true`, **все 11** прежних required
  checks на месте;
- `mergeable_state` всех перечисленных PR сменился с `blocked` на `behind` — то есть
  блокировала именно эта проверка, а `strict` продолжает работать. PR #112 после этого был
  слит владельцем (`fa81c3b`), что подтверждает разблокировку на практике.

Полный снимок удалённого ruleset сохранён в разделе 1 этого файла и позволяет воссоздать
его дословно.

**Цена, названная прямо.** Ручное включение native auto-merge на недопустимой вершине
Dependabot (мажор, `cms`, пакет из security registry) больше **не останавливается ничем**:
платформа сольёт её по зелёному обычному CI. Прежде это перехватывала именно обязательность
gate. Риск принят владельцем и опирается на owner-only write boundary: единственный субъект
с правом записи — сам владелец, который и без пометки может слить что угодно. Автоматика
при этом по-прежнему не помечает недопустимую вершину: job включения пометки зависит от
успеха gate.

Возврат защиты требует **двух** вещей сразу, а не одной: воссоздать ruleset и сделать gate
выполнимым для человеческих PR. Иначе вернётся ровно та ситуация, из-за которой его сняли.

## 12. Итог приёмки: что подтверждено и что нет

### Подтверждено живьём

1. Двухступенчатый доверенный producer работает на настоящих событиях: сигнал read-only →
   типизированный artifact → dispatcher с проверкой source/artifact/attempt → caller guard →
   свежий снимок → оценка → публикация на head с ожидаемым App id 15368.
2. Механизм продвижения доходит до привилегированного job: **2 успеха из 2** прогонов после
   фикса D2 против **3 отказов из 3** до него, все на настоящих событиях закрытия. Латентность
   14–30 с.
3. Отрицательные классы отвергаются на настоящих вершинах, в том числе на свежих: мажоры
   Action (#143, #144), `cms` (#122, #130), мажоры `/payments` (#141, #142). Ни один PR не
   помечен и не слит.
4. Происхождение и допустимость независимы: на тех же вершинах `Provenance evidence`
   зелёное при красном `Eligibility gate`.

### Не подтверждено, и потому задача 3.5 остаётся открытой

Эксперимент «два подряд eligible PR» **не выполнен**: eligible PR под текущим конфигом не
существует ни одного. Прежние PR разрешённого класса осиротели после перестройки
`dependabot.yml` и закрыты, новые появятся либо по плановому запуску (понедельник), либо по
ручному «Check for updates». За 50 минут после закрытия новых PR не появилось; отличить
«кнопка не нажата» от «нажата, ничего не нашлось» по API невозможно — публичного API про
запуски обновлений у Dependabot нет, и это ограничение измерения, а не вывод.

Следствие: **два ключевых вопроса остаются без ответа.**

- распознаёт ли Dependabot команду `@dependabot rebase`, отправленную встроенным токеном
  (на обоих успешных прогонах помеченных PR не было, поэтому ни одного комментария
  отправлено не было);
- приходит ли событие `closed`, когда слияние выполняет сам `GITHUB_TOKEN`. Оба наблюдённых
  события закрытия породил человек своим токеном — это другой случай, и подменять им ответ
  нельзя.

Обойти это нельзя ни ручным включением пометки (тогда слияние приписывается владельцу, а
предмет проверки — пометка от `GITHUB_TOKEN`), ни синтетическим тестом.

### Что это означает для rollout

По правилу design'а «если не подтвердится ни один способ продвижения, автоматическое
слияние не вводится». Формально мы не в состоянии «способ проверен и провалился», а в
состоянии «способ не проверен», но для решения это одно и то же: оставлять включённым
механизм, чья несущая часть не подтверждена, нельзя.

Фактическая экспозиция прямо сейчас **нулевая**: ни одного eligible PR не открыто, поэтому
пометить и слить автоматика сейчас не может ничего. Но плановый запуск Dependabot в
понедельник создаст PR разрешённого класса, и тогда экспозиция появится без чьего-либо
участия. Значит решение о деактивации нужно принять до планового запуска, а не после.

Change **не архивируется**: открытыми остаются 3.1, 3.2–3.4, 3.5, 4.8, 4.10, 4.14, 6.5
(положительная половина), 6.6, 6.7, 6.9 и 7.6.

## 13. Решение владельца: rollout остаётся включённым, плановый запуск и есть эксперимент

Решение от 2026-08-20: `allow_auto_merge` **не** выключается, деактивация fail-closed не
выполняется. Обоснование — плановый запуск Dependabot в понедельник сам создаст PR
разрешённого класса, политика сама поставит пометку, и эксперимент пройдёт с настоящей
атрибуцией `GITHUB_TOKEN`, которую иначе получить нельзя.

Что этим принято, названо прямо:

- слияние произойдёт **без наблюдения**. Само слияние узкое и защищённое: класс —
  patch/minor `web`/`scripts`/Actions вне security registry, и все 11 обязательных проверок
  branch protection обязаны быть зелёными, `strict` включён;
- если продвижение не сработает, остальные PR встанут на `strict` и будут ждать человека.
  Это **застой, а не опасность**, и именно он остаётся неподтверждённым;
- отдельно остаётся принятый ранее риск отмены eligibility ruleset (§6): вручную включённая
  пометка на недопустимой вершине больше не перехватывается.

### Что снять в момент планового запуска — иначе событие пройдёт без доказательств

Событие одноразовое: пока PR не слит, наблюдать нечего, а после слияния часть состояния
исчезает. Поэтому перечень фиксируется здесь заранее.

1. По каждому свежему PR: номер, head SHA, класс, фактические `Eligibility gate` и
   `Provenance evidence` (conclusion + check id + app id), состояние marker и **кем**
   он включён (`auto_merge.enabled_by.login` обязан быть `github-actions[bot]`, а не
   человек — иначе атрибуция не та и эксперимент недействителен).
2. Момент слияния первого: `merged_at`, `merge_commit_sha`, кем слит.
3. **Ключевое:** появился ли прогон `dependabot-rebase.yml` (`pull_request_target: closed`)
   после слияния, выполненного `GITHUB_TOKEN`. Если прогона нет вовсе — событие подавлено,
   и способ 1 не работает по причине площадки, а не реализации.
4. Если прогон есть: прошёл ли dispatcher, и **отправил ли** `Policy / Request Dependabot
   rebases` комментарий `@dependabot rebase` (в отличие от прогонов 20.08, где помеченных PR
   не было и комментариев не отправлялось).
5. Ответ Dependabot на этот комментарий: распознана команда от встроенного токена или нет.
6. Получил ли второй PR новую вершину от Dependabot, прошли ли на ней сигнал/dispatcher/gate.
7. Слился ли второй автоматически, и **время между слияниями** — именно этот случай ломался
   на одном `strict`.

Если пункт 3 или 5 отрицателен, задача 3.1 закрывается как «способ не работает», и по
design'у следует переходить к способу 2 (команда от GitHub App), а не расширять допустимое
происхождение. Ослаблять `strict` нельзя ни в каком исходе.

## 15. Плановый запуск 24.08 состоялся, но пункт 1 чек-листа §13 вскрыл третий дефект

Dependabot создал партию из семи PR (#174–180) 2026-08-24T00:18–00:19Z — снимок вершины
`main` на тот момент включал #147 (`907cee9`). Сняты первые два измерения из §13:

- **Eligibility gate**: SUCCESS на шести из семи (#174–178, #180 — patch/minor), FAILURE на
  #179 (`astro` major bump, `web`) — ожидаемо по политике, не дефект.
- **`auto_merge.enabled_by`**: **не применимо ни к одному PR** — marker не включён ни разу,
  `autoMergeRequest` у всех семи `null` (проверено `gh pr view … --json autoMergeRequest`
  2026-08-25T07:1x UTC, PR всё ещё открыты).

Причина — не площадка и не логика политики, а третий живой дефект, найденный этим
измерением: репозиторий разрешает только squash (`allow_merge_commit: false,
allow_squash_merge: true` — `gh api repos/pgorbachev/ikpk`), а джоб `Policy / Enable native
auto-merge` вызывал `gh pr merge --auto --merge --match-head-commit`. GitHub отклоняет это на
этапе включения marker'а: `GraphQL: Merge method merge commits are not allowed on this
repository (enablePullRequestAutoMerge)` (run 32676345517, PR #180, job «Policy / Enable
native auto-merge», 2026-08-24T00:24:08Z).

**Это не единичный сбой партии 24.08.** Проверено по всей истории репозитория на момент
измерения (263 прогона dispatcher'а `dependabot-auto-merge.yml` до коммита `0f6a089`
включительно, 2026-08-18..2026-08-25 — число растёт с каждым новым пушем в любой PR,
пуш самого `0f6a089` уже добавил минимум один прогон сверху): джоб `Policy / Enable
native auto-merge` фактически исполнился (не `skipped`) ровно **6** раз, и все шесть —
2026-08-24T00:23:53Z..00:24:08Z, на всех шести eligible PR партии (#174–178, #180). Все шесть
упали той же ошибкой. За весь период 2026-08-18..2026-08-23, когда против этого движка
измерялись «15 успехов из 15» для цепочки продвижения (§9, §11, §14), джоб не выполнился ни
разу — те 15 событий проверяли только продолжение цепочки **после ручного слияния
человеком**, а не заявленную цель дельты (самостоятельное слияние Dependabot-PR без участия
человека). Эта цель **не подтверждена ни одним живым событием** за весь период с 18.08 по
25.08.

Хронология объясняется независимым решением: `allow_merge_commit` было `true` во время
слияний #137–147 (все шесть — настоящие двухродительские merge-коммиты, проверено
`git log --format=%P`). PR #150 (merge-коммит `e0c4d1d`, тоже двухродительский) стал
инцидентом, после которого принята конвенция «мержить только сквошем»: все PR начиная с
#151 (`f25b193`, `c128288`, `034e050`, …) — уже однородительские, проверено тем же
`git log --format=%P`. Это сделало `--merge` невалидным методом для всего репозитория
раньше, чем Dependabot успел создать первый PR, дошедший до `enable-auto-merge`. Спека и
дизайн дельты не называли метод слияния для PR Dependabot явно — он остался implementation
detail, разошедшимся с общерепозиторной конвенцией squash-only без предупреждения.

**Ответ уже лежал в репозитории до того, как появился дефект.** Проверка происхождения
из прероквизитов этой же дельты, `openspec/changes/dependabot-auto-merge/evidence/repository-prerequisites.md:45`, `"mergeMethod": "SQUASH"`
(раздел «Auto-merge mutation proof», зафиксирован 2026-08-18, раньше, чем в коде появился
жёсткий `--merge`), уже содержала живой ответ. Сверка реализации с этим файлом на этапе
кода предотвратила бы все шесть падений 24.08.

**Остаточный риск, а не закрытый вопрос.** Фикс меняет один жёстко зашитый литерал
(`--merge`) на другой (`--squash`) — тот же класс регрессии повторится, если политику
репозитория снова изменят (снова разрешат merge-commit, отключат squash), и обнаружится
это опять только по живому падению. Динамический запрос текущей политики репозитория
(`gh api repos/... --jq .allow_squash_merge`) снял бы этот класс регрессий насовсем, но это
расширение сверх минимального red/green-фикса найденного дефекта — заносится как остаточный
риск, а не решается здесь.
