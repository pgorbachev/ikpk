## 2. Тесты по спеке (отдельная сессия, до реализации)

- [ ] 2.1 Написать проверки классификации PR по таблице: патч зависимости `web`, минор

      отказ**, **обычная незарегистрированная производственная зависимость `web` при

      смешанный групповой PR (`web` вместе с `cms`), **недоступные метаданные**; для
      `web` отдельно: ordinary незарегистрированный patch разрешён, прямой package из
      security registry ручной, транзитивный registered node в lockfile diff ручной,
      missing/stale registry ручной
- [ ] 2.2 Написать проверки того, что обязательная проверка допустимости **не трогает
      ручной путь**: человеческий PR проходит, PR Dependabot с мажором проходит, PR с
      включённым авто-слиянием и вершиной без допустимого происхождения падает
- [ ] 2.3 Написать проверки на **две независимые мутации**, подпись и действующее лицо
      порознь: (а) подпись платформы есть, действующее лицо — участник с правом записи —
      падает; (б) действующее лицо допустимо, но подписи платформы нет — падает; (в) оба
      факта в порядке — проходит, причём подписавшим значится служебная запись платформы;
      (г) допустимое действующее лицо на однородительском коммите от механизма — падает
- [ ] 2.4 Написать проверки цепочки свидетельств: два последовательных обновления при
      сохранённых свидетельствах проходят; отсутствие свидетельства для промежуточной
      вершины падает; свидетельство от постороннего субъекта падает; **зелёный гейт
      допустимости без отдельного свидетельства падает**
- [ ] 2.5 Написать проверку разделения гейта и свидетельства: человеческий коммит при
      выключенном авто-слиянии даёт зелёный гейт и **отрицательное** свидетельство, а
      последующее обновление поверх него падает
- [ ] 2.6 Написать проверки условий слияния: проверки ещё идут; обязательная упала; база
      устарела; объединение с вершиной ломает проверки
- [ ] 2.7 Отметить явной записью сценарии без автоматической проверки, с причиной и
      способом ручной проверки. Кандидаты: фактический набор permissions

- [ ] 2.8 Предъявить красный прогон: отдельный push коммита только с тестами либо лог с

## 3. Механизм продвижения последовательности

- [ ] 3.1 Способ первый: после слияния PR просить Dependabot пересобрать оставшиеся PR
      разрешённого класса — командой-комментарием от встроенного токена. Вершину пишет
      Dependabot, правило происхождения расширять не нужно. Предъявить результат
      эксперимента — продвинулась ли последовательность без вмешательства
- [ ] 3.2 Способ второй, если команда от встроенного токена не распознана: та же команда
      от имени GitHub App, ограниченного этим репозиторием. Вершину по-прежнему пишет
      Dependabot; расширение правила не требуется
- [ ] 3.3 Способ третий и последний: обновление ветки через API (`update-branch`) от имени
      GitHub App. **Только он требует расширения правила происхождения.** Встроенный токен
      здесь не годится и по другой причине: его события не запускают workflow, обновлённая
      вершина осталась бы без проверок
- [ ] 3.4 Для способов 3.2–3.3 зафиксировать минимальный набор прав субъекта, хранение
      секретом и порядок ротации; убедиться, что учётные данные недоступны из контекста,
      исполняющего код PR
- [ ] 3.5 **Негативная проверка продвижения:** подготовить два PR разрешённого класса,
      слить первый, убедиться, что второй сливается сам без ручных действий. Записать время
      между слияниями — именно этот случай ломался на одном `strict`
- [ ] 3.6 Если не подтвердится ни один способ — **не вводить авто-слияние**: change
      закрывается как невыполнимый в текущем окружении. `strict` при этом не ослаблять

## 4. Обязательная проверка допустимости и свидетельство происхождения

- [ ] 4.1 Реализовать обязательную проверку допустимости: на каждом head SHA падает тогда и
      только тогда, когда авто-слияние включено, а вершина не имеет допустимого
      происхождения, класс не разрешён либо срабатывает security-boundary override
      (включая недоступность metadata/registry); при
      выключенном авто-слиянии — проходит. Внести её имя в обязательные
- [ ] 4.2 Проверить, что она **не блокирует ручной путь**: обычный человеческий PR и PR
      Dependabot с мажором или security-boundary dependency сливаются вручную как прежде.
      Предъявить все случаи
- [ ] 4.3 Реализовать определение происхождения двумя независимыми фактами: подпись
      платформы (способ создания) **и** действующее лицо события (субъект). Поля
      `author`/`committer` и выведенную по адресу учётную запись автора не использовать
      вовсе. Зафиксировать точный предикат и то, откуда берётся каждое поле
- [ ] 4.4 **Положительная проверка на настоящем PR Dependabot:** вершина с подписью
      платформы от служебной учётной записи проходит. Без неё предикат легко написать так,
      что он отвергает все настоящие вершины
- [ ] 4.5 **Негативная проверка подписи и лица, две мутации по отдельности:** коммит с
      полями автора Dependabot из локального клона без подписи платформы; коммит,
      созданный участником с правом записи через API с полями автора Dependabot — он будет
      подписан платформой наравне с настоящим, и отвергнуть его обязано действующее лицо
- [ ] 4.6 Проверить ветвь «действующее лицо не определено» — она обязана быть красной
- [ ] 4.7 Реализовать **отдельное** свидетельство происхождения: результат, не совпадающий
      с гейтом допустимости, вычисляемый на каждой вершине независимо от состояния пометки
      и положительный только при фактически пройденных проверках подписи и действующего
      лица. В обязательные проверки его **не вносить** — иначе он запретит ручной путь
- [ ] 4.8 **Негативная проверка ложного свидетельства:** запушить человеческий коммит в
      ветку PR Dependabot при выключенном авто-слиянии (гейт допустимости при этом обязан
      быть зелёным), затем обновить ветку механизмом. Ожидание: обновление **красное**.
      Предъявить оба факта — зелёный гейт и красное обновление
- [ ] 4.9 Реализовать чтение свидетельства для первого родителя merge-вершины. Действующее
      лицо текущего события к родителю не применять: оно принадлежит механизму обновления и
      отвергло бы корректного родителя от Dependabot
- [ ] 4.10 **Живая проверка цепочки:** обновить ветку механизмом дважды подряд и убедиться,
      что проверка зелёная при сохранённых свидетельствах. Затем сделать свидетельство
      промежуточной вершины недоступным и убедиться, что проверка красная
- [ ] 4.11 Реализовать проверку топологии merge-вершины: два родителя; второй — предок
      вершины базы; изменения относительно первого родителя совпадают с тем, что вносит
      второй; действующее лицо текущего события — объявленный механизм
- [ ] 4.12 **Негативная проверка топологии, четыре мутации по отдельности:** посторонняя
      правка в merge-коммите; у первого родителя нет положительного свидетельства; второй
      родитель не предок вершины базы; однородительский коммит от того же субъекта.
      Ожидание: все четыре красные, с указанием сработавшего условия
- [ ] 4.13 Положительная ветвь топологии: корректное `update-branch` даёт положительное
      свидетельство и последовательность продвигается
- [ ] 4.14 Определить, что делать при истечении срока хранения свидетельств: продвижение
      выполняется пересборкой ветки самим Dependabot. Проверить этот путь
