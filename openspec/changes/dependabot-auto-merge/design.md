## Context

Мотивация — в `proposal.md` («Why»); требования — в
`specs/dependency-update-automation/spec.md`. Здесь только то, что определяет реализацию.

**Этот change следует за `dependency-update-gates` и опирается на его результат.** Набор
обязательных для слияния проверок формируется там; здесь он используется как условие
слияния. Порядок обязателен: до доказанных и обязательных гейтов автоматическое слияние
превращает «зелёно» в «никто не смотрел».

Ограничения площадки, из которых всё вытекает:

- **`allow_auto_merge` в репозитории выключен** — проверено: `enablePullRequestAutoMerge`
  отвечает «Auto merge is not allowed for this repository».
- **Владелец репозитория имеет тип `User`** — проверено через API. Очередь слияния
  доступна публичным репозиториям организаций, поэтому этому репозиторию она недоступна, и
  запасным вариантом быть не может.
- **`strict: false`** сейчас; включение его запрещает слияние устаревшей ветки, но не
  обновляет её.
- **Производственные зависимости есть во всех трёх пакетах.** `web` — `astro`,
  `@astrojs/sitemap`; `cms` — восемь; `scripts` — `form-data`, `node-fetch`, `tsx`.
- **Секция манифеста не совпадает с тем, что доходит до пользователя.** `astro` объявлен
  производственной зависимостью `web`, но это сборщик, на выходе которого статический
  HTML; `tsx` объявлен производственной зависимостью `scripts`, который не
  разворачивается никуда. Поэтому секция признаком допуска быть не может — см. решение 2а.
- **Уже был инцидент того же класса**, что и привилегированный контекст авто-слияния:
  деплой по `workflow_run` исполнял код чужого PR с правом записи в Pages.
- **Подпись на вершинах Dependabot принадлежит платформе, а не Dependabot.** Измерено на
  вершинах двух PR: `state: VALID`, `wasSignedByGitHub: true`, `signer.login: web-flow`,
  при `author.name: dependabot[bot]`.

## Goals / Non-Goals

**Goals:**

- Снять с ревьюера подъёмы, где суждение не требуется, не ослабив ни одной проверки.
- Сделать так, чтобы отказ любого механизма защиты приводил к отказу в слиянии, а не к
  слиянию.

**Non-Goals:**

- Не вводить гейты-инварианты — они в `dependency-update-gates`.
- Не автоматизировать мажоры ни при каких условиях, даже при зелёном CI: разбор #51 и #54
  показал, что мажор — это про совместимость peer-диапазонов, а не про прохождение тестов.
- Не переносить репозиторий в организацию ради очереди слияния — это решение об
  организации работ, а не деталь автоматизации зависимостей.

## Decisions

### Решение 1: судить по метаданным Dependabot, а не по заголовку PR

Заголовок PR (`chore(deps): bump X from A to B`) — вывод генератора, а не контракт: он
менялся между версиями Dependabot и не различает групповые PR. Тип подъёма и тип
зависимости берутся из метаданных, которые Dependabot публикует для своего же PR.

Недоступность метаданных трактуется как отказ, а не как повод к запасному способу
определения: разбор диффа `package.json` пришлось бы держать в синхроне с форматом
lockfile, а это ровно тот «список известных случаев», который отстаёт от предмета молча.

### Решение 2: право задаётся таблицей и работает fail closed

Класс разрешённых обновлений записан таблицей `экосистема × пакет × тип подъёма`
(см. `proposal.md`), и решение принимается совпадением со строкой. Всё, что не
совпало, — ручное.

Так устранено противоречие первой редакции, где `github-actions` разрешались «любые», а
мажоры запрещались безусловно. Разрешён более узкий вариант: мажор не сливается
автоматически ни в одной экосистеме. Обоснование фактом: #44 (`setup-node` v4 → v7)
потребовал чтения релиз-нот трёх мажоров и проверки, что автокеш у нас задан явно, —
такое суждение автоматике не отдаётся.

Для PR с несколькими подъёмами берётся наименее разрешающая строка. Альтернатива —
разрешать, если разрешён каждый подъём, — эквивалентна, но формулировка через минимум
устойчивее к появлению новых строк.

### Решение 2а: признак — пакет, а не секция манифеста

Предыдущая редакция читала тип зависимости, то есть секцию `package.json`. Признак
оказался неверным, и обнаружилось это измерением, а не рассуждением: **на пачке
10.08.2026 из одиннадцати PR (#65–#77) таблица допускала ноль.** Восемь отказов дали
мажоры (по решению 2 — верно), один — пакет `cms` (верно), а два были ложными: `tsx` и
`astro` — сборочный инструментарий, объявленный производственными зависимостями.

Ноль — это не «осторожно», это «бесполезно»: Purpose требует снять с ревьюера механически
проверяемое, а при нулевой доле ревьюер разбирает всю пачку руками и вдобавок содержит
CI-конструкцию. Нынешняя таблица допускает на том же срезе два PR — #68 и #77.

Признаком выбран **пакет**, потому что пакеты различаются тем, чем проверен их вывод:

| Пакет | Чем покрыт вывод | Итог |
|---|---|---|
| `web` | сборка, `Playwright smoke`, `Lighthouse budgets`, dist-assertions, инварианты из `dependency-update-gates` | patch/minor автоматически, кроме machine security registry |
| `scripts` | `scripts checks`, `Scripts unit tests`, аудит | patch/minor автоматически — **после** задачи 6.2 в `dependency-update-gates` |
| `cms` | ничем: исполняется в рантайме, контуром не покрыт | всегда ручное |

**Отвергнуто: перенести `astro` и `tsx` в раздел зависимостей разработки.** Дёшево и
таблицу менять не пришлось бы, но гейт аудита исключает дерево разработки: перенос вывел
бы `astro` с поддеревом из области `Runtime dependency audit (web)`, а prod-дерево `web`
держится именно на нём (304 записи из 819). Обязательная проверка безопасности стала бы
зелёной декорацией. Смена признака даёт то же расширение автоматики, **не** платя эту
цену: `astro` остаётся производственной зависимостью, область аудита не меняется.

**Отвергнуто: поимённый список сборочного тулинга** отдельной строкой — список отстаёт от
предмета молча, новый сборочный пакет в него не попадёт, и отказ будет выглядеть работой
правила.

**Отвергнуто: оставить как есть.** Не потому, что доля мала, а потому, что мала она из-за
неверного признака, а не из-за осознанно узкого класса.

### Решение 2б: security-boundary registry является deny-only override

Change `sanitize-rich-html-content` вводит особую границу: sanitizer, runtime DOM/parser,
browser-oracle tooling и транзитивные parser nodes должны проходить maintenance,
provenance и полный advisory review. Обычная строка «`web` patch/minor» этого суждения не
выражает, поэтому совпадение с таблицей остаётся необходимым, но перестаёт быть
достаточным для этой узкой группы.

Machine registry хранит точные package identities и lockfile node selectors. Metadata
Dependabot остаётся единственным источником положительной классификации; registry и
lockfile diff работают только на запрет:

1. metadata прямо называет зарегистрированный package — ручной путь;
2. metadata называет иной package, но resolved lockfile diff меняет зарегистрированный
   direct/transitive node — ручной путь;
3. registry отсутствует, не читается или не совпадает с фактическим subtree — `web` PR
   остаётся ручным fail closed;
4. иначе действует исходная таблица.

Так транзитивное изменение не прячется за именем top-level package, но diff не становится
вторым способом выдать разрешение. Registry формируется и проверяется реализацией
`sanitize-rich-html-content`; этот change только потребляет его как committed deny input.

Committed path на реализации
`feat/sanitize-rich-html-content@e010e9dd8ad47b15b6b885ff52e01a1df6eca3e3`
(голова PR `3d10129265f183e2b746a5823012f42a0c115f73`):
`web/tests/fixtures/rich-content-safety/security-dependency-registry.json`.
Прямые package identities: runtime `parse5`, oracle `playwright`. Transitive lockfile
nodes — все строки `runtime.lockfileNodes` и `oracle.lockfileNodes` того файла
(`entities`, вложенный `parse5`, `playwright-core` и остальные перечисленные). Consumer
SHALL трактовать **каждый** listed package и listed node как deny-only; lockfile diff
SHALL NOT выдавать разрешение.

Отсюда жёсткий порядок поставки: `sanitize-rich-html-content` сначала реализуется,
принимается, архивируется и сливается вместе с registry и producer completeness gate.
Только на следующем состоянии `main` реализуется/включается consumer auto-merge и
проверяется положительный ordinary-`web` scenario. Fail-closed отсутствие registry
остаётся runtime-защитой, но не считается допустимым состоянием для live acceptance.

### Решение 3: привилегированный шаг не видит кода PR, но права записи ему нужны

Шаг, решающий судьбу PR, запускается в контексте с правами записи. Поэтому в нём **нет**
шага checkout и **нет** установки зависимостей: он работает только с API GitHub.

Права — `contents: write` и `pull-requests: write`. Меньше не получается, и первая
редакция здесь ошибалась, требуя `contents: read`: пометка PR к автоматическому слиянию
является операцией записи, и официальный пример автоматизации Dependabot использует
именно эту пару. Права на публикацию (`pages`) и на изменение workflow не выдаются.

Отдельно: scope `workflow` у персонального токена, упомянутый в предусловиях, — это
**другая** модель прав, относящаяся к ручному слиянию PR, меняющих файлы workflow. Он не
заменяет permissions job'а и не выдаётся ему.

Альтернатива «checkout с последующей осторожностью» отвергнута: осторожность здесь не
проверяется ничем, а цена ошибки — исполнение чужого кода с правом записи.

**Producer двухступенчатый: read-only `pull_request_target` signal, затем privileged
`workflow_run`.** GitHub принудительно оставляет `GITHUB_TOKEN` read-only и не выдаёт
secrets для `pull_request_target`, если PR создан Dependabot; явный блок `permissions`
этого не отменяет. Поэтому signal workflow из default branch только фиксирует
server-provided action, actor, PR number/head и вывод pinned `dependabot/fetch-metadata`
в одном строго типизированном JSON artifact. Он не делает checkout/download кода или
artifact из PR и не исполняет PR-содержимое.

Только signal с action `opened` или `synchronize` связывает actor с появлением нового
head и может создать либо заменить provenance. `reopened`, `auto_merge_enabled` и
`auto_merge_disabled` переоценивают policy для того же SHA по уже сохранённому
authenticated evidence; actor этих событий не считается создателем вершины и не может
перезаписать provenance.

Dispatcher слушает завершение только этого exact signal workflow через `workflow_run`.
До выдачи любого результата он через API проверяет source run id, repository, event,
path, conclusion, actor и связь с тем же PR/head; требует ровно один ожидаемый artifact,
проверяет его digest, состав архива, schema и совпадение полей с authoritative source run.
Source `run_id` и `run_attempt` входят в имя и schema artifact. Dispatcher также включает
собственные `run_id`/`run_attempt` и source `run_id`/`run_attempt` в machine identity
опубликованных checks; consumer читает jobs exact attempt и отвергает смешение попыток.
Лишь затем он вызывает reusable policy по полному SHA. Checkout собственного policy-кода
использует `repository: ${{ job.workflow_repository }}` и
`ref: ${{ job.workflow_sha }}` — moving `main` не является доверенной привязкой.

Прямая передача PAT/App token в signal отвергнута: secrets в этом Dependabot-контексте
недоступны, а долгоживущий credential добавил бы ротацию и более широкую границу доверия.
Schedule без signal отвергнут: он теряет authoritative actor события, необходимого для
проверки происхождения.

Permission matrix разделён по jobs, а не объединён на уровне workflow: signal получает
только `contents: read` и `pull-requests: read`; authenticator/snapshot — `actions: read`
и `pull-requests: read`; read-only assessment — `actions: read`, `checks: read`,
`contents: read`, `pull-requests: read`; publisher — только `checks: write`; marker/merge
job — `contents: write` и `pull-requests: write`; rebase commenter — только
`pull-requests: write`. Неуказанные scopes равны `none`.

Нативный check такого запуска относится к base-контексту, поэтому producer публикует два
отдельных check run на **свежо прочитанный текущий head SHA**: обязательный gate и
необязательное свидетельство происхождения. Этим занимается отдельный job с единственным
правом `checks: write`; право существует только у этого producer и контролируется
статическим inventory. Check содержит machine external id с типом результата, head SHA и
SHA reusable policy. Consumer принимает свидетельство только при совпадении всех этих
полей, ожидаемого GitHub App, доверенного dispatcher-caller и immutable reusable SHA.
Кроме того, он читает authoritative dispatcher jobs, извлекает из server-controlled run
title source run id и принимает результат лишь когда этот exact source run прошёл все
проверки связи с тем же PR head, а exact provenance job dispatcher run завершился
успешно: один лишь копируемый `details_url` доказательством не является.

Перед публикацией отдельный read-only job свежо читает `head.sha` и `auto_merge` через API.
Снимок из event payload не используется как доказательство текущего состояния. Если
свежий head/marker установить невозможно, положительный автоматический gate не
публикуется; отсутствие required check блокирует слияние. Сам результат gate от marker
не зависит: снимок нужен для точной привязки публикации и ускоряющего снятия marker.

### Решение 4: слияние поручается GitHub, но контур обязательных проверок расширяется

Workflow только **помечает** PR к слиянию; само слияние выполняет GitHub, когда сойдутся
все обязательные проверки. Так условие «после успеха всех обязательных проверок» не
дублируется в скрипте и не может разойтись с настройкой ветки.

Из этого следует то, что первая редакция упустила: **«внутри `Tests`» не означает
«обязательна»**. Auto-merge ждёт поимённый список защиты ветки, а не итог workflow.
Поэтому:

- три новых гейта либо выполняются шагами внутри уже обязательного job'а (`Unit and
  build tests`), либо оформляются отдельными job'ами и **вносятся в обязательные**;
- `Scripts unit tests` вносится в обязательные — сейчас его падение слияние не
  останавливает;
- включается **`strict`** — запрет на слияние устаревшей ветки, — и вместе с ним
  механизм, который эти ветки **обновляет**. Одного запрета недостаточно, и этим
  решение отличается от второй редакции.

**Очередь слияния из рассмотрения исключена, и это не предпочтение, а ограничение
площадки.** Она доступна публичным репозиториям организаций, а `pgorbachev/ikpk`
принадлежит личному аккаунту: тип владельца — `User`, проверено через API. Третья
редакция назвала очередь основным вариантом, а `strict` с обновлением — запасным; порядок
перевёрнут, потому что «основной» вариант в этом окружении неисполним вовсе. Перенос
репозитория в организацию открыл бы очередь, но это решение об организации работ, а не
деталь автоматизации зависимостей: в scope этого change оно не входит и вносится только
явным решением владельца.

Почему одного `strict` мало — разбор второй редакции остаётся в силе: он **запрещает**,
но не **обновляет**. После первого автоматического слияния остальные PR становятся
устаревшими и остаются помеченными, но не сливаются, пока их кто-то не пересоберёт.
Dependabot пересобирает ветку по расписанию, при конфликте и по явной команде — но не
после каждого продвижения базы. При недельном расписании серия из шести PR продвигалась
бы по одному в неделю.

Отсюда конструкция из двух частей: `strict` держит запрет, а отдельный механизм после
каждого слияния приводит оставшиеся PR разрешённого класса к актуальной базе. Для
механизма рассматриваются два способа, в этом порядке:

Порядок способов задан одним критерием — **кто пишет вершину ветки**. Предпочтительны те,
где её пишет Dependabot: тогда проверка происхождения работает без всяких исключений.

1. **Попросить Dependabot пересобрать** — комментарием-командой к его же PR, от встроенного
   токена. Дёшево и не требует новых учётных данных; вершину пишет Dependabot.
   Работоспособность встроенным токеном я **не проверял** и не утверждаю: это эксперимент
   с предъявлением результата.
2. **То же, но от имени GitHub App.** Применяется, если первый способ не сработал из-за
   того, что команда от встроенного токена не распознана. Вершину по-прежнему пишет
   Dependabot, поэтому правило происхождения расширять не нужно — меняется только
   отправитель команды.
3. **Обновить ветку через API** от имени GitHub App — последний способ, и он единственный
   требует расширения правила происхождения.

**Третий способ конфликтует с проверкой происхождения, и это надо было увидеть раньше.**
`update-branch` сливает вершину базовой ветки в ветку PR, то есть создаёт новую вершину,
автором которой является механизм обновления, а не Dependabot. Правило «вершина создана
Dependabot» остановило бы ровно тот PR, который механизм пытался продвинуть: ветка
обновилась, проверки запустились, происхождение не прошло, серия встала. Два механизма,
введённые в разных редакциях, противоречили друг другу.

Разрешение — узкое и проверяемое, а не «доверяем автору». Вершина от механизма обновления
принимается только при выполнении всех условий сразу: ровно два родителя; первый родитель
сам имеет допустимое происхождение (рекурсивно, иначе два подряд обновления разорвали бы
связь с Dependabot); второй родитель — предок вершины базовой ветки; изменения относительно
первого родителя совпадают с тем, что вносит второй, то есть слияние не привносит своего;
и — вместо прежнего условия про поля автора — **действующим лицом события, приведшего эту
вершину, является объявленный механизм**. Условие про совпадение изменений здесь несущее:
без него субъект с правом записи мог бы протащить произвольную правку под видом
обновления, и проверка бы её пропустила.

Про поля автора: предыдущая редакция ставила пятым условием «автор и коммиттер —
объявленный механизм». Это условие подделываемо и потому убрано целиком, а не заменено
подписью — см. решение 7а.

Требования к субъекту второго и третьего способов: минимальный набор прав, хранение
секретом, ротация, и — существенно — он **не попадает в контекст, исполняющий код PR**,
поскольку workflow авто-слияния не делает checkout. Для встроенного токена третий способ
не годится и по другой причине: его события не запускают workflow, то есть обновлённая
вершина осталась бы вообще без проверок.

Если не подтвердится ни один способ, автоматическое слияние не вводится: требование о
продвижении серии остаётся невыполненным, а часть 1 без него превращается в очередь,
которая стоит.

### Решение 7а: подпись отвечает за способ создания, действующее лицо — за субъекта

Прошлая редакция требовала «проверенную подпись с ожидаемой атрибуцией», подразумевая,
что подписавший и есть Dependabot. Измерение показало, что это не так. На вершинах двух
реальных PR Dependabot:

```
state: VALID   wasSignedByGitHub: true   signer.login: web-flow
author.name: dependabot[bot]   committer.name: GitHub
```

То есть подписывает платформа своей служебной учётной записью, а не Dependabot. Прямая
реализация прошлой формулировки отвергла бы все настоящие вершины Dependabot; обратная
крайность — доверять `web-flow` — приняла бы любой коммит, созданный через API кем угодно,
включая участника с правом записи, выставившего в поля автора Dependabot.

Отсюда разделение ролей между двумя разными фактами:

- **подпись платформы** отвечает на вопрос «как коммит создан» и отсекает вершину,
  отправленную из локального клона с произвольными полями автора;
- **действующее лицо события**, приведшего вершину в ветку, отвечает на вопрос «кто её
  привёл» и является authenticated-фактом платформы, а не содержимым коммита.

Допустимость требует обоих. Поля `author`/`committer` и выведенная по адресу учётная
запись автора из условий убраны совсем — не заменены подписью, а именно убраны: первые два
задаются создателем коммита, третья наследует подделываемость адреса.

**Рекурсия по родителю требует третьего факта — сохранённого свидетельства.** Действующее
лицо известно только для вершины, оценка которой вызвана текущим событием. Событие,
которым была введена предыдущая вершина, в полезной нагрузке текущего прогона
отсутствует. Прошлая редакция объявляла первого родителя «допустимым по этому же правилу»,
не заметив, что вычислить это в момент проверки нечем: применить текущее действующее лицо
к родителю — значит разобрать корректного родителя от Dependabot как обновление от
механизма и отвергнуть его, а восстанавливать историю из объекта коммита нельзя, там
подделываемые поля.

Решение: допустимость каждой вершины фиксируется в момент её оценки отдельным
результатом, который платформа хранит привязанным к SHA, — и для родителя читается этот
сохранённый результат. Свидетельство принимается только от ожидаемого субъекта: иначе его
создал бы кто угодно, имеющий право писать результаты проверок.

**Свидетельство обязано быть отдельным от гейта.** Гейт отвечает за полную пригодность к
автоматическому слиянию, свидетельство — только за происхождение. Даже зелёный гейт нельзя
читать как историческое свидетельство родителя: его producer, срок жизни и contract
отличаются, а класс зависимости способен измениться независимо от происхождения.

Поэтому это два разных результата с разными правилами:

| | гейт допустимости | свидетельство происхождения |
|---|---|---|
| когда вычисляется | на каждой вершине | на каждой вершине |
| при выключенной пометке | вычисляется по существу | вычисляется по существу |
| что означает зелёный | сливать без человека можно | подпись и действующее лицо проверены и пройдены |
| входит в обязательные | да | нет |

Свидетельство не делается обязательным намеренно: обязательным является полный gate, а
ручной путь проходит через узкий PR-only bypass отдельного ruleset.

Прошлая редакция делала gate зелёным при выключенном marker, чтобы не мешать ручному
слиянию. Это оставляло same-SHA race: после зелёного результата участник мог включить
auto-merge, и платформа могла слить PR раньше обработчика `auto_merge_enabled`. Никакой
повторный API-запрос после публикации не закрывает интервал. Поэтому gate больше не зависит
от marker: недопустимый класс или provenance всегда красные. `Eligibility gate` живёт в
отдельном ruleset, где только владелец репозитория имеет `pull_request` bypass. Остальные
required checks остаются в branch protection с `enforce_admins=true`; ручной bypass не
отключает тесты, линт или сборку.

Отсюда практическое ограничение, которое надо держать в голове при выборе механизма
продвижения: цепочка из нескольких последовательных обновлений живёт ровно столько,
сколько хранятся свидетельства промежуточных вершин. Это ещё один довод в пользу первых
двух способов из решения 4 — пересборка ветки самим Dependabot сбрасывает цепочку к одной
вершине и снимает вопрос о сроке хранения вовсе.

Практическое следствие для реализации: результат проверки подписи и личность подписавшего
доступны разными путями, и это надо учесть при выборе API. Ответ REST о верификации
содержит исход проверки, но не личность подписавшего; поля `signer` и
`wasSignedByGitHub` отдаёт GraphQL. Личность действующего лица берётся не из объекта
коммита вовсе, а из полезной нагрузки события, вызвавшего оценку данной вершины.

### Решение 7: происхождение вершины стережёт обязательная проверка, а не снятие пометки

Защитой служит **обязательная проверка**, которая на каждой вершине ветки PR отвечает на
вопрос «разрешено ли слить эту вершину без человека». Она падает **тогда и только
тогда**, когда вершина **не имеет допустимого происхождения**, PR не попадает в
разрешающую строку либо попадает под security-boundary override; недоступность metadata
или требуемого registry тоже считается неуспехом. Marker в предикат не входит.

Формулировка именно «не имеет допустимого происхождения», а не «не создана Dependabot»:
допустимых происхождений два, и через автора второе отвергалось бы. Это та же ошибка, что
описана в решении 4, — два механизма, введённые в разных редакциях, расходились по
формулировке, хотя предмет у них общий.

Три предыдущие редакции ошибались по-разному, и каждая следующая ошибка тоньше:

- первая формулировала условие как «автор коммита отличается от Dependabot» и полагалась
  на платформу. Платформа же снимает автоматическое слияние только при пуше участника
  **без права записи**, поэтому коммит мейнтейнера пометку бы не снял;
- вторая добавила явное снятие пометки при обновлении ветки — но снятие само по себе
  fail-open. Обработчик не входил в обязательные проверки, поэтому его незапуск, падение
  или отмена оставляли пометку включённой; прочие обязательные проверки проходили, и
  платформа сливала изменённую вершину. Отказ механизма защиты приводил к слиянию;
- третья делала проверку зелёной при выключенном marker, чтобы сохранить ручной путь.
  Marker меняется без SHA, поэтому после зелёного результата его можно было включить и
  попасть в окно до нового workflow run;
- четвёртая отделяет механизм ручного слияния от значения gate: gate всегда выражает
  auto-eligibility, а ручной путь — PR-only bypass отдельного ruleset владельцем.

Отсюда разделение ролей: обязательная проверка всегда работает fail closed; нативное
поведение платформы и явное снятие пометки — только ускоряющие меры. Узкий ruleset bypass
не затрагивает остальной обязательный контур, который остаётся под branch protection с
`enforce_admins=true`.

## Risks / Trade-offs

- **Авто-слияние сливает подъём, который ломает то, что не покрыто ни одной проверкой** →
  класс узкий: только patch/minor в `web` и `scripts` и в actions. Пакет `cms` и мажоры
  всех экосистем, а также direct/transitive dependencies из machine security registry,
  остаются ручными. Отключение — снятие одного workflow.
- **Транзитивный parser меняется под именем обычной top-level зависимости** → deny-only
  сравнение lockfile diff с exact node selectors; missing/stale registry оставляет `web`
  PR ручным, а не ослабляет правило.
- **Визуальная регрессия не покрыта ничем, а под нынешним признаком автоматически
  сливается минорный подъём сборщика** → названо прямо, иначе решение 2а утверждало бы
  покрытие, которого нет. `web/tests/visual-baseline.spec.ts` в CI **не запускается** — ни
  в `test.yml`, ни в `nightly.yml`; проверено поиском по `.github/`. Контур ловит отказ
  сборки, поведение в smoke, нарушения доступности, бюджеты и утверждения о составе
  `dist`, но не «вёрстка поехала»: сборка зелёная и на сломанной раскладке. Митигация в
  рамках этого change — сознательное принятие риска; закрытие требует визуального гейта и
  оформляется **отдельным change**, потому что эталоны снимаются исключительно в CI
  (локально невозможно: раннер `amd64`, под эмуляцией на Apple Silicon chromium падает, а
  набор шрифтов в docker-образе не совпадает с раннером).
- **Подъём в разрешённом пакете может сломать саму обвязку прогонов, а не продукт** →
  наблюдалось на #77: минорный подъём `astro` до 7.2.0 сделал `astro preview` фоновым, из-за
  чего локально переставали запускаться все прогоны с сервером, при зелёном CI. Починено в
  #80 обёрткой, но случай показывает границу: контур проверяет вывод продукта, а не
  работоспособность инструментов разработки, и такой подъём пройдёт автоматически.
- **Продвижение последовательности может оказаться нереализуемым в этом окружении** →
  очередь слияния недоступна (владелец типа `User`), остаются способы обновления веток, и
  все требуют проверки. Если не подтвердится ни один, change закрывается, а
  `dependency-update-gates` сохраняет ценность сам по себе. Это названо заранее, чтобы
  отсутствие механизма не привело к соблазну ослабить `strict` и сливать на устаревшей базе.
- **Способы, требующие отдельного субъекта с правом на pull request** → митигация: GitHub
  App, ограниченное этим репозиторием, минимальные права, ротация, и отсутствие доступа к
  нему из контекста, исполняющего код PR.
- **Обновление ветки через API расширяет правило допустимого происхождения** → самое
  опасное место: субъект с правом записи получает признание своей вершины. Митигация — не
  доверие автору, а проверяемые условия, из которых несущее «слияние не привносит своего»;
  порядок способов выстроен так, чтобы расширение применялось последним.
- **Цепочка обновлений живёт, пока хранятся свидетельства промежуточных вершин** → при
  истечении срока продвижение выполняется пересборкой ветки самим Dependabot, которая
  сбрасывает цепочку к одной вершине.
- **Человек с правом записи может включить пометку вручную на недопустимой вершине, не
  меняя её** → новая оценка не запускается. Это осознанное действие обладателя права
  записи, а не обход автоматикой; названо прямо, а не оставлено умолчанием.

## Migration Plan

1. Убедиться, что `dependency-update-gates` заархивирован и его требования переехали в
   `openspec/specs/`.
2. Дождаться реализации, приёмки, архива и merge `sanitize-rich-html-content`; проверить
   на `main` committed machine security registry и зелёный producer completeness gate.
3. Обновить дельту этого change относительно обеих основных спек и проверить её
   применимость.
4. Включить `allow_auto_merge`; включить `strict`.
5. Проверить механизмы продвижения последовательности в порядке предпочтения; при
   неудаче всех — закрыть change, не ослабляя `strict`.
6. Ввести обязательную проверку допустимости, deny-only machine security registry и
   отдельное свидетельство происхождения.
7. Только затем включить пометку к слиянию и выполнить ordinary-`web` live acceptance.
8. Откат: удаление одного workflow.
