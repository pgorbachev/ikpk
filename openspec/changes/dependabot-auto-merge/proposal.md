## Why

Обновления зависимостей приходят пачками: за один прогон Dependabot открыл 14 PR
(#44–#57) на одного ревьюера. Часть из них не требует суждения вовсе — патч зависимости
разработки читается механически, — и время ревьюера на них уходит зря.

Этот change снимает с человека узкий класс таких обновлений. Он **зависит** от
`dependency-update-gates` и `sanitize-rich-html-content` и вводится только после них:
гейты-инварианты должны быть доказаны негативной проверкой и внесены в обязательные, а
machine security registry — создан, проверен producer gate и перенесён в main вместе с
rich-content safety spec. Иначе автоматическое слияние превращает «зелёно» в «никто не
смотрел» либо оставляет всю строку `web` fail-closed и непроверяемой положительным сценарием.

Разделение сделано по факту: при десяти кругах ревью объединённого change семь блокирующих
находок из одиннадцати пришлись именно на автоматическое слияние — на согласование
механизмов между собой, на подделываемость атрибуции, на недоступность очереди слияния
личному аккаунту. Гейты закрылись раньше и не должны ждать этой части.

## What Changes

### Класс автоматически сливаемых обновлений

Право задаётся таблицей `экосистема × пакет × тип подъёма` и работает fail closed:
отсутствие совпадения означает ручной путь. Для `web` совпадение необходимо, но не
достаточно: machine registry границы rich-content safety задаёт deny-only исключение для
sanitizer/DOM/parser/browser-oracle packages и их транзитивных lockfile nodes.

| Экосистема | Пакет | Тип подъёма | Авто-слияние |
|---|---|---|---|
| npm | `web` | patch, minor | **да**, кроме security registry |
| npm | `scripts` | patch, minor | **да** |
| `github-actions` | — | patch, minor | **да** |
| любая | — | major | нет |
| npm | `cms` | любой | нет |
| любая | набор, где хотя бы одна позиция даёт «нет» | — | нет |

Мажор не сливается автоматически ни в одной экосистеме.

**Признак — пакет, а не тип зависимости.** Предыдущая редакция читала секцию манифеста, и
это оказалось неверным признаком — обнаружилось измерением: на пачке 10.08.2026 из
одиннадцати PR (#65–#77) таблица допускала **ноль**. Секции в этом репозитории не
описывают, что доходит до пользователя: `astro` — сборщик, на выходе которого статический
HTML, а `tsx` — раннер для скриптов, которые не разворачиваются никуда; объявлены оба
производственными. Нынешняя таблица допускает на том же срезе **два** — #68 и #77.

Пакеты различаются не тем, «уезжает ли в прод», а тем, **чем проверен их вывод**: `web` и
`scripts` покрыты обязательным контуром, `cms` исполняется в рантайме и им не покрыт вовсе.
Для `scripts` это опирается на внесение `Scripts unit tests` в обязательные — задача 6.2 в
`dependency-update-gates`; до неё строка `scripts` необеспечена.

Security-boundary override не пытается выдать право по lockfile diff: первичное
разрешение по-прежнему приходит только из Dependabot metadata и таблицы. Он может лишь
отозвать его, если metadata называет зарегистрированный package или diff меняет
зарегистрированный direct/transitive node. Отсутствующий либо несогласованный registry
оставляет npm PR пакета `web` ручным.

### Условия слияния

Слияние ждёт весь обязательный набор проверок — тот, что формируется в
`dependency-update-gates`. PR проверяется в объединении с вершиной `main`, а не на своей
базе, и механизм обязан продвигать последовательность готовых PR без человека: запрет на
слияние устаревшей ветки её не обновляет.

### Происхождение вершины

Обязательная проверка на каждой вершине отвечает на один вопрос — разрешено ли слить её без
человека, — независимо от текущего auto-merge marker. Для ручного пути она вынесена в
отдельный ruleset с PR-only bypass владельца; остальные обязательные проверки остаются в
branch protection с `enforce_admins=true` и bypass не получают.

Происхождение подтверждается двумя независимыми фактами: подпись платформы отвечает за
способ создания, действующее лицо события — за субъекта. Поля автора и коммиттера в условия
не входят вовсе: их задаёт создатель коммита. Допустимость каждой вершины фиксируется
отдельным свидетельством, привязанным к SHA, — результат гейта допустимости свидетельством
не является.

### Привилегированный контекст

Доверенный producer двухступенчатый. Read-only signal workflow из default branch
запускается через `pull_request_target`, не делает checkout кода PR и сохраняет только
строго типизированный metadata artifact. Privileged dispatcher запускается через
`workflow_run`, проверяет exact source run/path/actor/PR/head и artifact, после чего
вызывает policy-код по immutable SHA reusable workflow. Обязательный gate и отдельное
свидетельство публикуются на фактический head SHA через Checks API. Только шаг пометки к
слиянию получает `contents: write` и `pull-requests: write`; отдельный publisher получает
`checks: write`. Ни один из них не получает прав на публикацию или изменение workflow и
не исполняет содержимое PR. Долгоживущий PAT или GitHub App token этому producer не нужен.

## Impact

- `.github/workflows/` — новый workflow авто-слияния.
- Machine security dependency registry из `sanitize-rich-html-content` —
  `web/tests/fixtures/rich-content-safety/security-dependency-registry.json` — deny-only
  input классификации `web`; его direct (`parse5`, `playwright`) и transitive lockfile
  subtree обновляется только вручную. Lockfile diff отзывает разрешение, но никогда его
  не выдаёт. До появления registry на `main` и зелёного producer completeness gate
  auto-merge не включается.
- Настройки репозитория — требуется включить `allow_auto_merge` (сейчас выключено:
  `enablePullRequestAutoMerge` отвечает «Auto merge is not allowed for this repository»).
- **Механизм продвижения последовательности.** Включается `strict`, но одного его мало: он
  запрещает слияние устаревшей ветки, не обновляя её. Очередь слияния запасным вариантом
  **не является** — она доступна публичным репозиториям организаций, а владелец этого
  репозитория имеет тип `User`. Перенос в организацию в scope не входит.
- Возможно, GitHub App, ограниченное этим репозиторием, — если команду Dependabot не
  удастся подать встроенным токеном. Долгоживущий доступ на запись, требующий ротации.
- Область двух инвариантов из `dependency-update-gates` расширяется (`MODIFIED`).

## Предусловия и порядок

1. `dependency-update-gates` заархивирован, требования переехали в `openspec/specs/`.
2. `sanitize-rich-html-content` реализован, принят, заархивирован и слит; committed machine
   security registry существует, а его producer completeness gate зелёный на `main`.
3. Дельта этого change обновлена относительно появившихся основных спек и проверена на
   **применимость** — строгой валидации недостаточно, она не проверяет существование
   требования.
4. Только затем — реализация и live acceptance автоматического слияния.

Если ни один механизм продвижения последовательности не подтвердится, change закрывается
как невыполнимый в текущем окружении. Это не отменяет ценности `dependency-update-gates`:
он самодостаточен.
