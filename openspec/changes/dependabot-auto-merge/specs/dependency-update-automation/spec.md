## ADDED Requirements

### Requirement: Класс автоматически сливаемых обновлений задан таблицей

Право на автоматическое слияние SHALL определяться по совпадению трёх признаков —
экосистема, **пакет**, тип подъёма — со строкой разрешающей таблицы. Отсутствие
совпадения SHALL означать отказ: правило работает fail closed. Совпадение является
необходимым, но для npm package `web` не достаточным условием: security-boundary override
ниже может только запретить автоматическое слияние и SHALL NOT разрешать иной класс.

Разрешены ровно три строки:

| Экосистема | Пакет | Тип подъёма |
|---|---|---|
| npm | `web` | `semver-patch`, `semver-minor` |
| npm | `scripts` | `semver-patch`, `semver-minor` |
| `github-actions` | — | `semver-patch`, `semver-minor` |

Система SHALL NOT сливать автоматически подъём мажорной версии ни в одной экосистеме,
включая `github-actions`.

Система SHALL NOT сливать автоматически никакое обновление npm в пакете `cms` —
независимо от типа подъёма и от того, в какой секции манифеста зависимость объявлена.

**Тип зависимости признаком не является.** Секция манифеста — производственная против
секции зависимостей разработки — не описывает, что доходит до пользователя, и потому
решением быть не может: `astro` объявлен производственной зависимостью `web`, но это
сборщик, на выходе которого статический HTML; `tsx` объявлен производственной
зависимостью `scripts`, который не разворачивается никуда. Признаком служит пакет, потому
что пакеты различаются тем, чем проверен их вывод.

Если PR содержит несколько подъёмов, право на автоматическое слияние SHALL определяться
по наименее разрешающему из них.

Решение SHALL приниматься по метаданным, полученным от Dependabot, а не по разбору
заголовка PR или диффа: заголовок пишется генератором и не является контрактом.

Для `web` система SHALL дополнительно читать committed machine registry зависимостей
границы rich-content safety, созданный change `sanitize-rich-html-content`. Реестр SHALL
лежать по пути `web/tests/fixtures/rich-content-safety/security-dependency-registry.json`
и SHALL перечислять выбранные sanitizer, runtime DOM/parser, browser-oracle tooling и
точные direct/transitive parser lockfile nodes. PR SHALL оставаться на ручном пути, если
Dependabot metadata прямо называет зарегистрированный package (включая `parse5` и
`playwright`) либо если lockfile diff меняет любой зарегистрированный node из
`runtime.lockfileNodes` или `oracle.lockfileNodes`. Lockfile diff здесь является только
deny-only проверкой транзитивных изменений: он SHALL NOT использоваться для выдачи
разрешения, которое не следует из Dependabot metadata и таблицы. Отсутствующий,
нечитаемый либо несогласованный с lockfile registry SHALL означать ручной путь для npm
PR пакета `web`.

#### Scenario: Патч зависимости пакета web

- **WHEN** Dependabot открывает PR с подъёмом `semver-patch` обычной зависимости пакета
  `web`, которая не названа security registry и не меняет его lockfile nodes
- **THEN** система помечает PR к автоматическому слиянию, независимо от секции манифеста,
  в которой зависимость объявлена

#### Scenario: Прямое обновление security-boundary package

- **WHEN** patch/minor PR пакета `web` прямо поднимает package из machine security registry
- **THEN** система не помечает PR к автоматическому слиянию и оставляет его для security
  review с maintenance/provenance и advisory evidence

#### Scenario: Транзитивный parser node изменён обычным подъёмом

- **WHEN** Dependabot metadata называет незарегистрированный package `web`, но lockfile
  diff меняет зарегистрированный транзитивный parser node
- **THEN** deny-only override оставляет весь PR на ручном пути

#### Scenario: Security registry недоступен

- **WHEN** npm PR пакета `web` попадает в разрешающую строку, но machine security registry
  отсутствует, не читается либо расходится с lockfile subtree
- **THEN** система работает fail closed и оставляет PR на ручном пути

#### Scenario: Минорный подъём производственной зависимости пакета scripts

- **WHEN** Dependabot открывает PR с подъёмом `semver-minor` зависимости пакета
  `scripts`, объявленной в производственной секции манифеста
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Минорный подъём действия

- **WHEN** Dependabot открывает PR с подъёмом `semver-minor` в экосистеме
  `github-actions`
- **THEN** система помечает PR к автоматическому слиянию

#### Scenario: Мажорный подъём действия

- **WHEN** Dependabot открывает PR с подъёмом `semver-major` в экосистеме
  `github-actions`
- **THEN** система не помечает PR к автоматическому слиянию и оставляет его ревьюеру

#### Scenario: Мажор в разрешённом пакете

- **WHEN** Dependabot открывает PR с подъёмом `semver-major` зависимости пакета `web`
  или `scripts`
- **THEN** система не помечает PR к автоматическому слиянию

#### Scenario: Любое обновление пакета cms

- **WHEN** Dependabot открывает PR, изменяющий любую зависимость пакета `cms`
- **THEN** система не помечает PR к автоматическому слиянию, независимо от типа подъёма и
  секции манифеста

#### Scenario: Смешанный групповой PR

- **WHEN** сгруппированный PR содержит и подъёмы, попадающие в разрешающие строки, и
  хотя бы один, в них не попадающий
- **THEN** система не помечает PR к автоматическому слиянию

#### Scenario: Метаданные недоступны

- **WHEN** метаданные Dependabot для PR получить не удалось
- **THEN** система не помечает PR к автоматическому слиянию и не пытается вывести класс
  из заголовка или диффа

### Requirement: Автоматическое слияние ждёт весь релевантный контур проверок

Система SHALL выполнять автоматическое слияние не немедленно, а по факту успеха всех
проверок, обязательных для ветки `main`.

Набор обязательных проверок SHALL включать все проверки, чей отказ должен останавливать
слияние. Состав этого набора задаётся change `dependency-update-gates` — там же в него
вносятся `Scripts unit tests` и три инварианта; здесь фиксируется лишь то, что
автоматическое слияние ждёт именно обязательный набор, а не подмножество.

Система SHALL проверять автоматически сливаемый PR в объединении с вершиной `main`, а не
на той базе, на которой он был создан.

Механизм, обеспечивающий это, SHALL продвигать последовательность из нескольких готовых
PR **без вмешательства человека**: после слияния одного PR остальные обязаны быть
приведены к актуальному состоянию и перепроверены автоматически. Требование к результату,
а не к средству: конкретная реализация выбирается в `design.md` из доступных площадке.

Требование о продвижении обязательно, потому что запрет на слияние устаревшей ветки сам
по себе её не обновляет. Dependabot пересобирает ветку по расписанию, при конфликте и по
явной команде, но не после каждого продвижения базы, — значит один лишь запрет остановил
бы серию после первого слияния до следующего запуска по расписанию.

#### Scenario: Серия готовых PR

- **WHEN** несколько PR разрешённого класса одновременно готовы к слиянию
- **THEN** они сливаются один за другим, и каждый следующий перед слиянием проверяется в
  объединении с уже слитыми, без ручных действий

#### Scenario: База PR устарела

- **WHEN** PR помечен к автоматическому слиянию, а вершина `main` продвинулась после
  прогона его проверок
- **THEN** слияние не происходит до перепроверки в объединении с новой вершиной

#### Scenario: Объединение ломает проверки

- **WHEN** PR по отдельности зелёный, но в объединении с вершиной `main` обязательная
  проверка падает
- **THEN** слияние не происходит

#### Scenario: Проверки ещё идут

- **WHEN** PR помечен к автоматическому слиянию и часть обязательных проверок не
  завершена
- **THEN** слияние не происходит

#### Scenario: Обязательная проверка упала

- **WHEN** PR помечен к автоматическому слиянию и хотя бы одна обязательная проверка
  завершилась неуспехом
- **THEN** слияние не происходит и PR остаётся открытым

#### Scenario: Модульные тесты пакета scripts упали

- **WHEN** PR разрешённого класса затрагивает `scripts` и модульные тесты этого пакета
  завершаются неуспехом
- **THEN** слияние не происходит

### Requirement: Происхождение вершины PR подтверждается обязательной проверкой

Система SHALL иметь среди обязательных для слияния проверок такую, которая для **каждой
вершины** ветки PR отвечает на один вопрос: разрешено ли слить эту вершину **без участия
человека**.

Проверка SHALL завершаться неуспехом тогда и только тогда, когда вершина **не имеет
допустимого происхождения** в смысле правила «Допустимое происхождение вершины» ниже, PR
не попадает в разрешающую строку таблицы либо попадает под security-boundary override.
Текущее состояние auto-merge marker SHALL NOT влиять на результат. Невозможность получить
metadata или требуемый security registry SHALL считаться неуспехом.

Условие сформулировано через допустимое происхождение, а не через «создана Dependabot»,
потому что допустимых происхождений два, и второе из них — вершина от механизма обновления
ветки — по формулировке через автора отвергалось бы, останавливая ровно тот PR, который
механизм продвинул.

Для ручного пути `Eligibility gate` SHALL требоваться отдельным branch ruleset. Только
владелец репозитория SHALL иметь для этого ruleset PR-only bypass. Остальные обязательные
проверки SHALL оставаться в отдельной branch protection с `enforce_admins=true` и SHALL
NOT получать этот bypass. Поэтому ручной merge мажора, `cms`, security-boundary или
человеческого PR обходит только auto-eligibility, но не тесты, линт и сборку.

Требование сформулировано через обязательную проверку, а не через снятие пометки, потому
что снятие само по себе оставляет систему открытой при отказе: если обработчик обновления
ветки не запустился, упал или был отменён, пометка остаётся, остальные обязательные
проверки проходят, и платформа сливает изменённую вершину. Отказ механизма защиты SHALL
приводить к отказу в слиянии, а не к слиянию.

Нативное отключение автоматического слияния платформой и явное снятие пометки при
обновлении ветки SHALL применяться дополнительно, как ускоряющие меры, и SHALL NOT
считаться защитой: первое срабатывает только для участников без права записи, второе не
является обязательной проверкой.

**Происхождение подтверждается подписью, а не именами.** Поля автора и коммиттера — данные
самого объекта коммита; они задаются тем, кто коммит создаёт, и аутентификацией не
являются. Участник с правом записи способен выставить в них любое имя и адрес, включая
принадлежащие Dependabot.

**Подпись не удостоверяет субъекта, а удостоверяет способ создания.** Вершины PR
Dependabot в этом репозитории подписаны, но подписывающий — служебная учётная запись
подписи GitHub, а не Dependabot. Измерено на вершинах двух PR: `state: VALID`,
`wasSignedByGitHub: true`, `signer.login: web-flow`, при `author.name: dependabot[bot]` и
`committer.name: GitHub`.

Отсюда два запрета, каждый закрывает свою ошибку:

- признавать субъектом **подписавшего** нельзя: `web-flow` — это подпись платформы, и
  требование «подписавший есть Dependabot» отвергло бы все настоящие вершины Dependabot;
- принимать любую подпись платформы как достаточную тоже нельзя: участник с правом записи
  способен создать коммит через API с произвольными полями автора, и такой коммит будет
  подписан платформой наравне с настоящим.

Поля `author.name`, `author.email` и разрешённая по адресу учётная запись автора SHALL
NOT считаться подтверждением субъекта: первые два — данные объекта коммита, третья
выводится из адреса и наследует его подделываемость.

**Субъект подтверждается действующим лицом события, а не содержимым коммита.** Проверка
SHALL определять, кто привёл вершину в ветку PR, по authenticated-полю события,
вызвавшего оценку этой вершины, и SHALL требовать, чтобы это лицо принадлежало
объявленному множеству: Dependabot либо механизм обновления ветки. Проверка SHALL
завершаться неуспехом, если действующее лицо определить не удалось.

**Допустимое происхождение вершины.** Вершина SHALL считаться допустимой, если выполнены
оба общих условия и одно из двух частных.

Общие условия:

- подпись вершины действительна и поставлена платформой — это отсекает вершину,
  отправленную из локального клона с произвольными полями автора;
- автор pull request — Dependabot, и действующее лицо события, приведшего эту вершину в
  ветку, принадлежит объявленному множеству.

Частные условия — одно из двух:

1. вершина приведена в ветку самим Dependabot;
2. вершина приведена в ветку объявленным механизмом обновления и удовлетворяет **всем**
   перечисленным условиям одновременно:
   - у неё ровно два родителя;
   - для первого родителя существует **положительное свидетельство происхождения** —
     отдельный сохранённый платформой результат, привязанный к SHA родителя и созданный
     ожидаемым субъектом. Отсутствие свидетельства, отрицательное свидетельство,
     невозможность его получить или создание его иным субъектом SHALL приводить к
     неуспеху;
   - второй родитель является предком вершины базовой ветки либо равен ей;
   - изменения, которые вершина вносит относительно первого родителя, совпадают с
     изменениями, которые второй родитель вносит относительно точки ветвления, — то есть
     обновление не привносит ничего своего.

Совпадение полей автора и коммиттера с ожидаемым субъектом SHALL NOT входить в число
условий ни в одном из двух случаев — ни как достаточное, ни как необходимое: субъект
устанавливается действующим лицом события, а способ создания — подписью платформы.

**Почему для родителя нужно сохранённое свидетельство, а не повторное вычисление.**
Действующее лицо известно только для той вершины, оценка которой вызвана текущим событием:
полезная нагрузка описывает это событие и не содержит событий, которыми вводились
предыдущие вершины. Применить к родителю действующее лицо текущего события нельзя — оно
принадлежит механизму обновления, и правильный родитель от Dependabot был бы разобран как
обновление и отвергнут. Восстановить историческое действующее лицо из объекта коммита
тоже нельзя: там лежат подделываемые поля.

Поэтому допустимость каждой вершины SHALL фиксироваться в момент её оценки отдельным
результатом, который платформа хранит привязанным к SHA, — и для родителя SHALL читаться
этот сохранённый результат. Свидетельство SHALL приниматься только от ожидаемого субъекта:
иначе его мог бы создать посторонний.

**Свидетельство происхождения отделено от гейта допустимости, и смешивать их нельзя.**
Гейт выражает полный ответ «можно ли слить без человека», а свидетельство — только
исторический факт происхождения конкретного SHA. Разные contracts, producer identity и
срок хранения не позволяют использовать один результат вместо другого.

Отсюда требования к свидетельству:

- оно SHALL быть отдельным результатом, а не тем же, которым выражается гейт допустимости;
- оно SHALL вычисляться и записываться для **каждой** вершины ветки PR независимо от
  того, включено ли автоматическое слияние;
- оно SHALL иметь положительный исход **только** если для этой вершины фактически
  выполнены и пройдены обе проверки — подписи платформы и действующего лица, — а для
  вершины-слияния ещё и условия второго частного случая;
- зелёный результат гейта допустимости SHALL NOT приниматься как свидетельство ни при
  каких обстоятельствах;
- свидетельство SHALL NOT входить в число обязательных для слияния проверок: оно
  описывает происхождение, а не полное разрешение сливать.

При чтении сохранённого свидетельства consumer SHALL проверить не только поля check run,
но и authoritative workflow run: тот же PR head SHALL присутствовать в `pull_requests`,
а exact provenance job доверенного run SHALL завершиться `success`. Копируемый
`details_url` либо совпадающий external id без этой связи SHALL NOT приниматься.

Из этого следует ограничение, которое надо соблюдать при выборе механизма: цепочка из
нескольких последовательных обновлений допустима лишь пока для каждого промежуточного SHA
свидетельство сохранено и доступно. Если свидетельство недоступно — например, срок его
хранения истёк, — вершина SHALL считаться не имеющей допустимого происхождения, а
продвижение серии SHALL выполняться пересборкой ветки самим Dependabot, которая сбрасывает
цепочку к одной вершине.

Второй случай существует потому, что без него механизм продвижения серии противоречил бы
этой же проверке: обновление ветки слиянием актуальной базы создаёт вершину, автором
которой является механизм, а не Dependabot, и правило «создана Dependabot» остановило бы
именно тот PR, который механизм пытался продвинуть.

Расширение SHALL быть узким и проверяемым по перечисленным условиям, а не сводиться к
доверию имени автора: одного совпадения автора с доверенным механизмом недостаточно,
поскольку тот же субъект способен записать в ветку что угодно.

Если механизм продвижения серии не пишет ветку сам, а вынуждает пересборку выполнить
Dependabot, второй случай SHALL NOT применяться — такой механизм предпочтителен именно
потому, что не требует расширения правила.

#### Scenario: Вершина от Dependabot при включённом автоматическом слиянии

- **WHEN** для PR включено автоматическое слияние, вершина подписана платформой,
  действующим лицом приведшего её события является Dependabot, и PR попадает в разрешающую
  строку
- **THEN** проверка проходит

#### Scenario: Настоящая вершина Dependabot

- **WHEN** Dependabot приводит в ветку вершину, подписанную платформой, у которой
  подписавшим значится служебная учётная запись подписи, а не Dependabot
- **THEN** проверка проходит: субъект установлен действующим лицом события, а подпись
  подтверждает лишь способ создания

#### Scenario: Коммит с полями Dependabot, созданный человеком через API

- **WHEN** участник с правом записи создаёт через API коммит с полями автора Dependabot,
  и платформа подписывает его наравне с настоящими
- **THEN** проверка завершается неуспехом, потому что действующим лицом события является
  этот участник, а не Dependabot

#### Scenario: Коммит из локального клона с подделанными полями

- **WHEN** в ветку отправлен коммит с полями автора Dependabot, не подписанный платформой
- **THEN** проверка завершается неуспехом

#### Scenario: Действующее лицо не определено

- **WHEN** проверке не удалось установить, кто привёл вершину в ветку
- **THEN** проверка завершается неуспехом

#### Scenario: Обычный человеческий PR

- **WHEN** PR открыт человеком и автоматическое слияние для него не включено
- **THEN** auto-eligibility проверка неуспешна, а владелец может применить PR-only bypass
  только её ruleset после успеха остальных обязательных проверок

#### Scenario: PR Dependabot, оставленный ручному пути

- **WHEN** Dependabot открывает PR с мажорным подъёмом или с обновлением пакета `cms`, и
  автоматическое слияние для него не включено
- **THEN** auto-eligibility проверка неуспешна, и PR доступен владельцу для ручного
  слияния через тот же узкий bypass

#### Scenario: Коммит участника с правом записи

- **WHEN** в ветку PR, помеченного к автоматическому слиянию, приходит коммит участника
  с правом записи
- **THEN** проверка на новой вершине завершается неуспехом, и слияние не происходит даже
  при сохранившейся пометке

#### Scenario: Посторонний коммит без права записи

- **WHEN** в ветку PR отправляет изменения участник без права записи
- **THEN** проверка на новой вершине завершается неуспехом, и слияние не происходит

#### Scenario: Обработчик снятия пометки не отработал

- **WHEN** обработчик, снимающий пометку при обновлении ветки, не запустился, упал или
  был отменён, а прочие обязательные проверки прошли
- **THEN** слияние не происходит, потому что проверка происхождения на новой вершине не
  прошла

#### Scenario: Обновление веткой самим Dependabot

- **WHEN** Dependabot пересобирает ветку PR (rebase или новая версия подъёма)
- **THEN** проверка происхождения проходит, а класс PR определяется заново по обновлённым
  метаданным

#### Scenario: Ветка обновлена доверенным механизмом

- **WHEN** доверенный механизм обновления сливает вершину базовой ветки в ветку PR, и
  полученная вершина удовлетворяет всем условиям второго случая
- **THEN** проверка происхождения проходит, и продвижение серии не останавливается

#### Scenario: Обновление привнесло посторонние изменения

- **WHEN** вершина создана доверенным механизмом обновления, но вносит относительно
  первого родителя изменения, которых нет во втором родителе
- **THEN** проверка происхождения завершается неуспехом

#### Scenario: Для первого родителя нет сохранённого свидетельства

- **WHEN** вершина приведена механизмом обновления, но для её первого родителя
  сохранённого свидетельства происхождения не существует
- **THEN** проверка завершается неуспехом, а не считает родителя допустимым по умолчанию

#### Scenario: Человеческий коммит при выключенном автоматическом слиянии

- **WHEN** участник с правом записи отправляет коммит в ветку PR Dependabot, для которого
  автоматическое слияние выключено
- **THEN** гейт допустимости не проходит, а свидетельство происхождения для этой вершины
  записывается **отрицательным**

#### Scenario: Обновление поверх человеческого коммита

- **WHEN** после такого коммита ветка обновляется механизмом, и первым родителем новой
  вершины оказывается этот коммит
- **THEN** проверка завершается неуспехом, потому что свидетельство первого родителя
  отрицательно

#### Scenario: Зелёный гейт вместо свидетельства

- **WHEN** для первого родителя существует зелёный результат гейта допустимости, но
  отдельного положительного свидетельства происхождения нет
- **THEN** проверка завершается неуспехом

#### Scenario: Свидетельство создано посторонним субъектом

- **WHEN** для первого родителя существует результат проверки с ожидаемым именем, но
  созданный не тем субъектом, который выполняет эту проверку
- **THEN** проверка завершается неуспехом

#### Scenario: Два последовательных обновления

- **WHEN** ветка PR обновлена механизмом дважды подряд, и для каждой промежуточной вершины
  сохранённое свидетельство существует и получено от ожидаемого субъекта
- **THEN** проверка проходит, и связь с исходной вершиной Dependabot прослеживается через
  цепочку свидетельств

#### Scenario: Свидетельство промежуточной вершины недоступно

- **WHEN** ветка обновлена дважды подряд, но свидетельство для промежуточной вершины
  получить не удалось
- **THEN** проверка завершается неуспехом

#### Scenario: Второй родитель не из базовой ветки

- **WHEN** вершина создана доверенным механизмом обновления, но её второй родитель не
  является предком вершины базовой ветки
- **THEN** проверка происхождения завершается неуспехом

#### Scenario: Вершина от доверенного механизма без слияния

- **WHEN** субъект объявленного механизма обновления записывает в ветку обычный коммит с
  одним родителем, подписанный своей действительной подписью
- **THEN** проверка происхождения завершается неуспехом: подпись механизма признаётся
  только для вершины, удовлетворяющей всем условиям второго случая

### Requirement: Механизм автоматического слияния не исполняет код проверяемого PR

Система SHALL принимать решение о слиянии в контексте, который не выполняет ни код из
ветки PR, ни его скрипты сборки и установки зависимостей.

Это требование существует потому, что контекст принятия решения обладает правами записи:
исполнение в нём содержимого PR даёт постороннему коду эти права.

Права контекста SHALL быть ограничены записью в содержимое репозитория и операциями с
pull request — минимумом, при котором пометка к слиянию выполнима. Права на публикацию
и на изменение workflow SHALL NOT выдаваться.

Определения producer workflow SHALL читаться из default branch, а исполняемый policy-код
SHALL быть привязан к полному immutable SHA reusable workflow. Producer SHALL состоять из
read-only signal на `pull_request_target` и privileged dispatcher на `workflow_run`, потому
что GitHub принудительно понижает токен Dependabot-authored `pull_request_target` до
read-only. Signal SHALL NOT получать write-token или secrets и SHALL передавать только
строго типизированный metadata artifact, созданный без исполнения содержимого PR.

Dispatcher SHALL до использования artifact проверить exact source run, workflow path,
event, conclusion, actor, PR/head association, единственность artifact, digest, состав и
schema. Producer SHALL NOT исполнять workflow-определение из проверяемой ветки.
Обязательный gate и отдельное свидетельство SHALL публиковаться на свежо прочитанный
текущий head SHA отдельным job с `checks: write`; этот job SHALL NOT иметь
`contents: write` или `pull-requests: write`. Право `checks: write` SHALL NOT выдаваться
другим workflow этой автоматизации.

Event payload SHALL NOT считаться свежим доказательством marker. Если текущий head или
marker прочитать не удалось, система SHALL завершаться fail closed: положительный
обязательный результат для этого head не публикуется. Подтверждённое отсутствие marker
также SHALL NOT делать неразрешённый head зелёным.

#### Scenario: Содержимое PR не попадает в привилегированный контекст

- **WHEN** выполняется шаг, решающий судьбу PR
- **THEN** рабочее дерево этого шага не содержит файлов из ветки PR, и ни одна команда
  шага не запускает скрипты из неё

#### Scenario: Права ограничены необходимым

- **WHEN** выполняется шаг, решающий судьбу PR
- **THEN** ему выданы права записи в содержимое репозитория и права на операции с pull
  request, и не выданы права на публикацию и на изменение workflow

#### Scenario: GitHub понижает токен Dependabot signal

- **WHEN** `pull_request_target` запускается для PR, созданного Dependabot
- **THEN** signal остаётся полностью работоспособным с read-only `GITHUB_TOKEN`, а все
  операции записи выполняются только последующим доверенным `workflow_run` dispatcher

#### Scenario: Подменён source run или artifact

- **WHEN** dispatcher получает artifact от другого workflow/run/head, несколько
  одноимённых artifact, неверный digest, лишний файл либо несовпадающие actor/action/PR/head
- **THEN** положительный gate и свидетельство не публикуются и auto-merge не включается

#### Scenario: Ветка PR не может подменить producer

- **WHEN** PR меняет caller workflow или добавляет job с именем обязательного gate
- **THEN** это определение не исполняется доверенным producer, а результат без ожидаемых
  external id, dispatcher-caller, authenticated source run и immutable reusable SHA не
  принимается

#### Scenario: Event snapshot устарел

- **WHEN** payload показывает выключенное auto-merge, но свежий API-снимок текущего PR
  показывает включённый marker либо не может быть получен
- **THEN** сбой полной оценки не превращается в зелёный обязательный gate

#### Scenario: Marker включён после красного auto-eligibility

- **WHEN** на том же SHA участник включает auto-merge после результата для ручного пути
- **THEN** обязательный gate остаётся красным независимо от marker, и платформа не может
  слить PR до нового workflow run

#### Scenario: Подставлен URL настоящего producer-run

- **WHEN** same-name check на человеческом head копирует external id и `details_url`
  настоящего producer-run, но exact provenance job этого run неуспешен либо run относится
  к другому PR head
- **THEN** сохранённое свидетельство отвергается

## MODIFIED Requirements

### Requirement: Покрытие статического анализа не сокращается молча

Система SHALL проверять, что число файлов, фактически проанализированных линтером в
каждом из пакетов `web`, `cms`, `scripts`, не меньше зафиксированного для этого пакета
порога. Это условие SHALL применяться ко всем pull request без исключения.

Дополнительно система SHALL проверять, что это число не меньше измеренного тем же
способом на базовой ветке. Второе условие SHALL применяться к pull request, для которого
верно **хотя бы одно** из двух: он признан пригодным к автоматическому слиянию, либо он
не меняет ничего, кроме манифестов зависимостей и файлов блокировки. Для прочих pull
request сравнение с базой SHALL NOT применяться.

Первая часть области добавлена этим change и обязательна: PR экосистемы `github-actions`
сливается автоматически, но меняет файлы workflow, а не манифесты, — то есть по одному лишь
файловому признаку он выпал бы из-под сравнения. Минорный подъём действия способен
сократить число запущенных тестов или охват линтера, остаться выше устаревшего порога и
слиться без человека.

Вторая часть области нужна для PR, меняющих только зависимости, но открытых человеком:
они автоматически не сливаются, а сокращение покрытия ловить в них так же нужно.

Ограничение области обязательно, иначе условие запрещает законное удаление исходника или
теста: такой PR неизбежно уменьшает число файлов, и правка порога в том же PR его не
разблокирует — сравнение с базой останется красным. Порог при законном сокращении
меняется в том же PR и виден в диффе; такой PR меняет исходники, а не только манифесты,
поэтому под сравнение с базой не попадает.

Проверка SHALL считать проанализированные файлы по машинному отчёту самого линтера, а не
по списку файлов в репозитории: расхождение между ними и есть предмет проверки.

Отсутствие отчёта, пустой отчёт или ошибка запуска линтера SHALL считаться неуспехом, а
не отсутствием проблем.

#### Scenario: Покрытие сохранилось

- **WHEN** линтер сообщает о числе проанализированных файлов не меньше порога пакета и
  не меньше измеренного на базовой ветке
- **THEN** проверка проходит

#### Scenario: Покрытие сократилось ниже порога

- **WHEN** обновление приводит к тому, что линтер анализирует меньше файлов, чем порог
  пакета
- **THEN** проверка завершается неуспехом и называет пакет, порог и фактическое число

#### Scenario: Обновление зависимостей сократило покрытие выше порога

- **WHEN** pull request меняет только манифесты зависимостей и файлы блокировки, база
  анализирует 180 файлов, голова — 140, а порог пакета равен 128
- **THEN** проверка завершается неуспехом и называет число на базе и на голове

#### Scenario: Подъём действия сократил покрытие выше порога

- **WHEN** pull request экосистемы `github-actions` признан пригодным к автоматическому
  слиянию, меняет файлы workflow, и покрытие падает относительно базы, оставаясь выше
  порога
- **THEN** проверка завершается неуспехом, хотя манифесты зависимостей в нём не изменены

#### Scenario: Законное удаление исходника

- **WHEN** pull request удаляет устаревший исходник или тест, отчего число файлов падает
  относительно базы, но остаётся не меньше порога
- **THEN** проверка проходит, потому что сравнение с базой к такому pull request не
  применяется

#### Scenario: Удаление опускает число ниже порога

- **WHEN** pull request удаляет исходники так, что число файлов падает ниже порога, и
  порог в том же pull request не изменён
- **THEN** проверка завершается неуспехом

#### Scenario: Линтер не отработал

- **WHEN** линтер завершился ошибкой или не выдал разбираемого отчёта
- **THEN** проверка завершается неуспехом, а не считает это отсутствием нарушений

### Requirement: Число выполненных тестов не сокращается молча

Система SHALL проверять, что число фактически выполненных тестов не меньше
зафиксированного порога — отдельно для модульных тестов и для браузерных. Это условие
SHALL применяться ко всем pull request.

Дополнительно система SHALL проверять, что это число не меньше измеренного на базовой
ветке, с той же областью применения, что и для покрытия линтера: pull request признан
пригодным к автоматическому слиянию **либо** не меняет ничего, кроме манифестов
зависимостей и файлов блокировки. Область ограничена по той же причине — иначе законное
удаление теста блокируется навсегда.

Число SHALL браться из машинного отчёта прогона. Пропущенные тесты SHALL NOT
засчитываться как выполненные.

#### Scenario: Тесты выполнены в прежнем объёме

- **WHEN** прогон сообщает о числе выполненных тестов не меньше порога и не меньше
  измеренного на базовой ветке
- **THEN** проверка проходит

#### Scenario: Обновление зависимостей сократило число тестов

- **WHEN** pull request меняет только манифесты зависимостей и файлы блокировки, а часть
  тестов не запускается или помечается пропущенной, отчего число выполненных падает ниже
  порога либо ниже базового
- **THEN** проверка завершается неуспехом и называет ожидаемое и фактическое число

#### Scenario: Подъём действия сократил число тестов

- **WHEN** pull request экосистемы `github-actions` признан пригодным к автоматическому
  слиянию и число выполненных тестов падает относительно базы, оставаясь выше порога
- **THEN** проверка завершается неуспехом

#### Scenario: Законное удаление теста

- **WHEN** pull request удаляет устаревший тест, отчего число выполненных падает
  относительно базы, но остаётся не меньше порога
- **THEN** проверка проходит
