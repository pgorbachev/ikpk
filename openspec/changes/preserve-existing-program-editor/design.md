## Context

На staging194 операция `sitemap-cms-20261126-45404857` на ревизии `cms/scripts/audit-data-migration.mjs@454048574cee7e079a55263bc2e7bd33aa6811a7:474`, `function overlayProgramEditorConfiguration` отказала до commit; штатный recover завершён. Локальная сверка проверенного backup с сохранённым candidate обнаружила два отличия в `strapi_core_store_settings`: аудит `overlayProgramEditorConfiguration` отказывает при уже имеющемся `metadatas.editor_label`; сохранённая `strapi_content_types_schema` изменила `course-group.slug.required` с true на false в `attributes` и `__schema__.attributes`. Receipt содержит два отказа и последний stage совпадает по core-store с candidate, но не содержит финального candidate hash после отказа: это сильное свидетельство, а не полная привязка audit-момента к файлу. Backup и candidate содержат приватные данные и не входят в Git.

## Goals / Non-Goals

**Goals:** Узко выразить реальные преобразования и проверить неизменность остального. **Non-Goals:** Ручная правка БД, изменение содержимого сайта, снятие проверок, произвольное разрешение `strapi_core_store_settings` или доверие любому preimage.

## Decisions

1. `cms/src/seminar-management/forms.ts` применяет редакторское наложение к исходной конфигурации и сохраняет не затрагиваемые метаданные; при уже существующем `editor_label` проверка должна строить ожидаемый postimage из проверенного preimage тем же контрактом полей. Все существующие `metadatas.<field>`, `edit`, `list` перед наложением должны быть объектами, а не null, массивом или примитивом; отсутствие допустимо только там, где определён fallback. Существующий `editor_label` не входит в PROGRAM_FIELDS, но входит в hidden: сохраняются все исходные свойства метаданных и вложенных полей edit и list, поверх задаются edit.label=`editor_label`, edit.visible=false, edit.editable=false и list.label=`editor_label`. Подстановка стандартного объекта вместо исходного запрещена. При исходном отсутствии поля его добавление допустимо только после доказательства реального создания Strapi bootstrap и точного postimage. `overlay` возвращает только settings/metadatas/layouts, но Content Manager вызывает `updateConfiguration`; простое утверждение, что верхние ключи сохраняются, из этого кода не следует. На обнаруженной паре обе записи содержат uid и остальные три ключа; реальную семантику updateConfiguration требуется доказать изолированным bootstrap-тестом на допущенном Strapi. До этого разрешать лишь точно наблюдённую/доказанную форму и считать любые добавления, удаления или изменение остальных верхнеуровневых ключей отказом, не предполагать безусловный spread. Тестировать старый вариант отсутствия поля, обнаруженный вариант наличия и некорректные объекты. Утверждать допустимость точного перехода только после независимой сверки полного наложения с кодом и синтетических проверок.
2. Разрешить только симметричное `true → false` для `course-group.slug.required`, когда schema-файл из независимо проверенного admitted source/release SHA операции ровно задаёт false, не из candidate self-report; оставшуюся структуру сравнивать полностью. Сохранённый source отражает true, хотя как старый установленный schema source `7b4548d234710e0f0daacc2c8a46787b1e822e2f`, так и новый `454048574cee7e079a55263bc2e7bd33aa6811a7` указывают false. Фактический механизм появления true в старом core-store не доказан; учитывать это как допустимость нормализации к текущей допущенной схеме, не как доказанную историю изменения требования. Разные mirrored значения, absent/null, `false → true` и правки других полей остаются отказом; сравнение двух частей выполняется до наложения.
3. Тестовые базы создавать локально из искусственных JSON-структур, сохраняющих только нужную форму/перестановки; никакие реальные содержимое, имена, секреты, дампы или хеши приватных значений не коммитить. RED сначала для двух выявленных переходов при соблюдении других проверок; негативные мутации на каждом несвязанном пути, симметрии и исходной структуре обязаны падать. Проверить, что исходно поддержанный путь без `editor_label` остаётся зелёным.
4. Привязка target schema использует существующую цепочку допуска, без нового транспорта host↔runner: CI checkout и job привязаны к точному admitted main SHA/run/attempt; скрипт сборки копирует исходный `cms/src/api/course-group/content-types/course-group/schema.json` в фиксированный `src/api/course-group/content-types/course-group/schema.json` CMS artifact. Перед упаковкой проверяются байты этой копии относительно исходного файла; содержимое полной schema также сверяется с реально загружаемой схемой из собранного CMS-артефакта через строгий разбор обоих JSON с отказом на повторные ключи и полное canonical-сравнение (форматирование может отличаться). Ошибка, отсутствие или расхождение блокируют сборку.

   Оператор проверяет CI archive digest и связь run с SHA; host создаёт и повторно проверяет root-sealed execution artifact против допущенного payload. План внутри этого artifact обязан иметь единственную integrity entry фиксированного target-schema пути с SHA исходной копии, а runner обязан проверять наличие записи, regular file без ссылок, его hash и соответствие своего plan/artifact операции до чтения audit. Audit получает уже проверенный `plan.root` и использует только этот путь, никогда CMS-writable candidate/schema self-report. Сам plan hash не заменяет допуск CI artifact: старый незапечатанный fallback, произвольный CLI path или неподтверждённые provenance не могут авторизовать исключение. При отсутствии доверенной привязки или ошибке сравнения узкое исключение запрещено, без ослабления остальных проверок. Проверку artifact и schema повторять при prepare/resume и каждом применимом activation audit; тестовый контур не объявляет произвольный candidate доверенным.

   Изменения audit/runner и schema отражаются в соответствующих integrity hashes плана; исторические step ID, payload hashes и ledger остаются неизменными. Если artifact не содержит достоверной копии или schema расходится с compiled, ошибку нельзя обходить через candidate либо слепое обновление hash.
5. Связь с требованиями: действующий `cms-content-source` продолжает защищать содержимое и снимок; активный `production-migration-content-proof` требует закрытого независимого сравнения полного исходного и кандидатного состояния. Это ограниченное допустимое преобразование не заменяет и не ослабляет ни одно из них, а в production может использоваться только при тех же byte-bound доказательствах, полном аудите и совместимости дельт. Перед merge/archive проверить пересечение этих активных changes, применимость в одноразовом worktree и при необходимости обновить их в том же PR; никаких исключений для production по одному staging-примеру. Проверка применимости на базе `454048574cee7e079a55263bc2e7bd33aa6811a7`: strict для `production-migration-content-proof` проходит, но его архивирование отказывает из-за отсутствующего MODIFIED требования `Production paired recovery is bound to its operation backup` в основной `cms-content-source`; необходим принятый базовый change `repeatable-production-cms-deploy` и согласование порядка, а не обход проверки.

## Risks / Trade-offs

- [Предположенное наложение не совпадает со Strapi] → до реализации сверить форму и значения на изолированной фикстуре с применением реального bootstrap; не принимать по одному совпадению полей.
- [Послабление скрывает удаление чужой настройки] → точный ожидаемый postimage и отрицательные мутации, не исключение всей записи.
- [Подмена schema или привязки при resume] → exact-SHA CI provenance, обязательный plan hash, root-sealed artifact, проверка source→packaged bytes и полного JSON packaged→compiled, повторная проверка до audit и негативные тесты на каждую границу.
- [Сохранённый candidate не имеет хеш-привязки к моменту отказа] → явно оставить ограничение; при новой операции доказать полный audit на новом запечатанном кандидате.

## Migration Plan

После ревью и утверждения: отдельная сессия предъявляет RED, другой исполнитель делает минимальный фикс и GREEN, два независимых ревью и обычные гейты. Затем отдельный релизный процесс и штатная staging194 операция с новым ID, новым backup и прежними отказами; при ошибке явное восстановление. Никакого переноса старого кандидатного файла или обхода аудита.
