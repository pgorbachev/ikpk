## Context

На staging194 операция `sitemap-cms-20261126-45404857` на `origin/main@454048574cee7e079a55263bc2e7bd33aa6811a7` отказала до commit; штатный recover завершён. Локальная сверка проверенного backup с сохранённым candidate обнаружила два отличия в `strapi_core_store_settings`: аудит `overlayProgramEditorConfiguration` отказывает при уже имеющемся `metadatas.editor_label`; сохранённая `strapi_content_types_schema` изменила `course-group.slug.required` с true на false в `attributes` и `__schema__.attributes`. Receipt содержит два отказа и последний stage совпадает по core-store с candidate, но не содержит финального candidate hash после отказа: это сильное свидетельство, а не полная привязка audit-момента к файлу. Backup и candidate содержат приватные данные и не входят в Git.

## Goals / Non-Goals

**Goals:** Узко выразить реальные преобразования и проверить неизменность остального. **Non-Goals:** Ручная правка БД, изменение содержимого сайта, снятие проверок, произвольное разрешение `strapi_core_store_settings` или доверие любому preimage.

## Decisions

1. `cms/src/seminar-management/forms.ts` применяет редакторское наложение к исходной конфигурации и сохраняет не затрагиваемые метаданные; при уже существующем `editor_label` проверка должна строить ожидаемый postimage из проверенного preimage тем же контрактом полей. Все существующие `metadatas.<field>`, `edit`, `list` перед наложением должны быть объектами, а не null, массивом или примитивом; отсутствие допустимо только там, где определён fallback. Существующий `editor_label` не входит в PROGRAM_FIELDS, но входит в hidden: сохраняются все исходные свойства метаданных и вложенных `edit/list`, поверх задаются edit.label=`editor_label`, edit.visible=false, edit.editable=false и list.label=`editor_label`. Подстановка стандартного объекта вместо исходного запрещена. При исходном отсутствии поля его добавление допустимо только после доказательства реального создания Strapi bootstrap и точного postimage. `overlay` возвращает только settings/metadatas/layouts, но Content Manager вызывает `updateConfiguration`; простое утверждение, что верхние ключи сохраняются, из этого кода не следует. На обнаруженной паре обе записи содержат uid и остальные три ключа; реальную семантику updateConfiguration требуется доказать изолированным bootstrap-тестом на допущенном Strapi. До этого разрешать лишь точно наблюдённую/доказанную форму и считать любые добавления, удаления или изменение остальных верхнеуровневых ключей отказом, не предполагать безусловный spread. Тестировать старый вариант отсутствия поля, обнаруженный вариант наличия и некорректные объекты. Утверждать допустимость точного перехода только после независимой сверки полного наложения с кодом и синтетических проверок.
2. Разрешить только симметричное `true → false` для `course-group.slug.required`, когда schema-файл из независимо проверенного admitted source/release SHA операции ровно задаёт false, не из candidate self-report; оставшуюся структуру сравнивать полностью. Сохранённый source отражает true, хотя как старый установленный schema source `7b4548d234710e0f0daacc2c8a46787b1e822e2f`, так и новый `454048574cee7e079a55263bc2e7bd33aa6811a7` указывают false. Фактический механизм появления true в старом core-store не доказан; учитывать это как допустимость нормализации к текущей допущенной схеме, не как доказанную историю изменения требования. Разные mirrored значения, absent/null, `false → true` и правки других полей остаются отказом; сравнение двух частей выполняется до наложения.
3. Тестовые базы создавать локально из искусственных JSON-структур, сохраняющих только нужную форму/перестановки; никакие реальные содержимое, имена, секреты, дампы или хеши приватных значений не коммитить. RED сначала для двух выявленных переходов при соблюдении других проверок; негативные мутации на каждом несвязанном пути, симметрии и исходной структуре обязаны падать. Проверить, что исходно поддержанный путь без `editor_label` остаётся зелёным.
4. Привязка target schema: оператор допускает CI CMS artifact по точным source SHA, run/attempt и payload digest; host сверяет каждый файл root-protected execution artifact с допущенным payload. Отдельно оператор сверяет seminar proof с `git archive` этого SHA и связывает его digest с операцией; host проверяет proof по root journal. Из однократно прочитанных host байтов проверенного proof извлечь ровно regular member `cms/src/api/course-group/content-types/course-group/schema.json` без дубликатов и ссылок; сравнить его с `dist/src/api/course-group/content-types/course-group/schema.json` из защищённого CI artifact. Оба JSON строго разбирать с отказом при повторных ключах и сравнивать **полный canonical JSON**, а не байты или один `required`: сериализация при сборке может менять формат. Любое различие, отсутствие или неподтверждённая защита — отказ на рассматриваемое исключение.

   Host передаёт runner фиксированный canonical путь внутри root-protected artifact, digest schema и operation/source identity, полученные из доверенного допуска, а не из CMS-writable candidate или receipt. Runner проверяет тип, отсутствие ссылок, границы пути и digest, сопоставляет identity с операцией и передаёт проверенное значение в audit. Проверять binding на каждом prepare/resume и каждом применимом activation audit; сохранить root-owned доказательство либо каждый раз повторять защищённое чтение proof из тех же проверенных байтов. Нельзя полагаться на разовую проверку CMS-writable source_root, одни аргументы пользователя или legacy fallback без root-protected artifact. Старые пути, не использующие исключение, не расширяют доверие и остаются под прежними проверками.

   План миграции закрепляет hash audit-скрипта и runner: после изменения обновить соответствующие integrity hashes и другие явно необходимые защищённые входы; доказать, что исторические step ID и payload hashes не менялись, и повторно проверить состав/ledger. Не переписывать историю. Если потребуется включить source schema в пакет и plan integrity отдельно, доказать её соответствие proof и учесть изменения сборщика; одно совпадение plan hash не заменяет admitted SHA.

5. Связь с требованиями: действующий `cms-content-source` продолжает защищать содержимое и снимок; активный `production-migration-content-proof` требует закрытого независимого сравнения полного исходного и кандидатного состояния. Это ограниченное допустимое преобразование не заменяет и не ослабляет ни одно из них, а в production может использоваться только при тех же byte-bound доказательствах, полном аудите и совместимости дельт. Перед merge/archive проверить пересечение этих активных changes, применимость в одноразовом worktree и при необходимости обновить их в том же PR; никаких исключений для production по одному staging-примеру. Проверка применимости на базе `454048574cee7e079a55263bc2e7bd33aa6811a7`: strict для `production-migration-content-proof` проходит, но его архивирование отказывает из-за отсутствующего MODIFIED требования `Production paired recovery is bound to its operation backup` в основной `cms-content-source`; необходим принятый базовый change `repeatable-production-cms-deploy` и согласование порядка, а не обход проверки.

## Risks / Trade-offs

- [Предположенное наложение не совпадает со Strapi] → до реализации сверить форму и значения на изолированной фикстуре с применением реального bootstrap; не принимать по одному совпадению полей.
- [Послабление скрывает удаление чужой настройки] → точный ожидаемый postimage и отрицательные мутации, не исключение всей записи.
- [Подмена proof, schema или привязки при resume] → root-owned provenance, проверка одинаковых байтов proof и полного JSON CI artifact, повторное чтение до audit, негативные тесты на каждую границу.
- [Сохранённый candidate не имеет хеш-привязки к моменту отказа] → явно оставить ограничение; при новой операции доказать полный audit на новом запечатанном кандидате.

## Migration Plan

После ревью и утверждения: отдельная сессия предъявляет RED, другой исполнитель делает минимальный фикс и GREEN, два независимых ревью и обычные гейты. Затем отдельный релизный процесс и штатная staging194 операция с новым ID, новым backup и прежними отказами; при ошибке явное восстановление. Никакого переноса старого кандидатного файла или обхода аудита.
