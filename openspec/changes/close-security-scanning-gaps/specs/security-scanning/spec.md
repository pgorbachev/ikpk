## Purpose

Обеспечивает воспроизводимый анализ безопасности исходников и полного дерева зависимостей ИКПК, с явной обработкой исключений и запретом слияния непроверенных изменений.

## ADDED Requirements

### Requirement: Security-анализ исходников выполняется регулярно

Система SHALL анализировать поддерживаемые JavaScript/TypeScript исходники web, cms, scripts и payments, Python-скрипты и GitHub Actions при PR в main, push в main и не реже раза в неделю. Отчёт SHALL указывать анализируемую ревизию, языки, состояние анализа и найденные проблемы. Сбой либо отсутствие анализа SHALL NOT обозначаться как отсутствие уязвимостей. Не поддерживаемые анализатором шаблоны SHALL быть названы как ограничение; существующие source/build security-тесты SHALL сохраняться.

#### Scenario: PR меняет серверный TypeScript
- **WHEN** PR в main меняет CMS либо платежный сервис
- **THEN** анализ охватывает поддерживаемые исходники этих компонентов и публикует привязанный к проверяемому коммиту результат

#### Scenario: Обновление Dependabot
- **WHEN** PR Dependabot в main меняет зависимость или GitHub Action
- **THEN** анализ запускается без секретов приложения и имеет тот же обязательный результат, что PR человека

#### Scenario: Ошибка анализатора
- **WHEN** один из объявленных языков не проанализирован из-за ошибки запуска или выгрузки результата
- **THEN** проверка неуспешна; отсутствие alerts не считается успехом

### Requirement: Полное дерево зависимостей проверяется по единой политике

Система SHALL проверять все установленные по lockfile production и development зависимости каждого из web, cms, scripts, payments при PR в main, push в main и еженедельно. Найденные high/critical SHALL приводить к неуспеху, кроме совпадений с действующим индивидуальным исключением. Moderate/low SHALL оставаться видимыми в отчёте. Общее исключение для CMS SHALL отсутствовать. Существующие runtime-аудиты SHALL сохранять охват и пороги, за исключением явно утверждённого перехода CMS к указанной политике.

#### Scenario: Уязвимость только в инструменте сборки
- **WHEN** high advisory затрагивает исключительно devDependency web
- **THEN** полный audit web неуспешен, даже если runtime audit успешен

#### Scenario: Новая high в CMS
- **WHEN** CMS имеет high advisory, не покрытый действующим исключением
- **THEN** CMS security-проверка неуспешна, независимо от общего количества advisory и прежнего report-only состояния

#### Scenario: Не удалось измерить
- **WHEN** установка зависимостей, получение advisory либо разбор отчёта завершились ошибкой
- **THEN** проверка неуспешна и сообщает сбой измерения, а не нулевой состав уязвимостей

### Requirement: Исключения точечные и требуют принятия владельцем

Исключение SHALL идентифицировать advisory по GHSA/CVE либо канонической advisory URL, компонент, затронутый пакет, точные lockfile nodes и версии, максимальную принятую severity, обоснование применимости, компенсирующие меры, владельца решения и дату истечения. Исключения SHALL храниться в reviewable versioned документе и требовать явного принятия владельцем. Автоматическое принятие текущего отчёта целиком, wildcard пакетов/версий/advisory, увеличение допустимого числа проблем и бессрочные исключения SHALL быть запрещены. Истечение, нарушение структуры и неоднозначность исключения SHALL завершать проверку неуспехом. Новая версия/узел, новый advisory либо рост severity SHALL требовать нового решения. Approval в этом change SHALL NOT означать принятия ещё не перечисленных исключений.

#### Scenario: Ранее принятый риск
- **WHEN** advisory совпадает со всеми границами ещё действующего принятого исключения
- **THEN** он остаётся видимым как принятый риск и сам по себе не делает проверку неуспешной

#### Scenario: Риск изменился
- **WHEN** advisory существует в другом node, версии либо имеет severity выше принятой
- **THEN** прежнее исключение не подавляет его

#### Scenario: Исключение просрочено
- **WHEN** наступила дата истечения исключения по UTC
- **THEN** проверка неуспешна с указанием записи и срока

### Requirement: Результат анализа действительно блокирует merge

Слияние в main SHALL требовать успешных существующих обязательных проверок, runtime-аудита payments, полных dependency-аудитов всех четырёх компонентов и завершённого security-анализа объявленных языков без новых high/critical security alerts и error-level alerts в изменениях PR. Защита SHALL действовать для человека, администратора и автоматически сливаемого Dependabot PR, без bypass акторов. Отсутствующая, ошибочная, отменённая, пропущенная либо ещё выполняемая обязательная проверка SHALL NOT разрешать merge. Привязка результата к текущей проверяемой ревизии SHALL сохраняться после обновления PR; старый успешный результат не подтверждает новую голову. Исходные настройки защиты SHALL сохраняться при добавлении требований.

#### Scenario: Все функциональные проверки зелёные, security красная
- **WHEN** PR проходит функциональные проверки, но не проходит один из обязательных security-контекстов
- **THEN** merge заблокирован, включая попытку автоматического слияния

#### Scenario: Анализ отработал и нашёл проблему
- **WHEN** анализатор успешно выгрузил новый high security alert в изменениях PR
- **THEN** merge заблокирован; успешный технический запуск анализатора не подменяет результат проверки находок

#### Scenario: Проверка отсутствует
- **WHEN** обязательный security-контекст не создан на текущей ревизии PR либо отменён
- **THEN** PR остаётся заблокированным

### Requirement: Проверки не расширяют доверие к коду PR

Security-проверки SHALL использовать минимальные разрешения, неизменяемые ссылки на внешние Actions и ограниченное время выполнения. Код PR SHALL NOT исполняться в привилегированном pull_request_target/workflow_run контексте. Секреты приложения, CMS, SSH и платежного оператора SHALL NOT передаваться анализаторам. Установка и анализ кода PR SHALL выполняться в непривилегированном изолированном runner с read-only repository token; разрешение security-events:write допускается только для выгрузки результата анализа. Невозможность загрузить обязательный результат SHALL блокировать проверку.

#### Scenario: Враждебный lifecycle script
- **WHEN** PR добавляет lifecycle script в пакет
- **THEN** он не получает секретов приложения, токена с правами записи в исходники или доступа к deployment окружению

### Requirement: Приёмка подтверждает границы защиты

Перед объявлением security-контура действующим SHALL быть представлены positive и negative evidence для получения/разбора audit, каждой ветви политики исключений, полноты пакетов/языков и фактической блокировки merge при неуспехе/отсутствии проверки и при новом high alert. Контролируемые security fixtures SHALL NOT публиковаться в production. Находки первого полного CodeQL-прогона main SHALL быть рассмотрены поимённо: исправлены либо переданы владельцу для явного принятия риска, без заявления о чистоте всего main только по PR delta. Отчёт SHALL отдельно обозначать непроверенные live-приложение, ОС/инфраструктуру, аутентифицированные сценарии и неподдерживаемые шаблоны. Защита merge SHALL NOT объявляться защитой новой публикации.

#### Scenario: Первичный прогон нашёл существующий долг
- **WHEN** CodeQL обнаружил high в существующем коде main вне PR diff
- **THEN** находка фиксируется отдельно и не исчезает из отчёта из-за успешного PR delta-check

#### Scenario: Утверждение о завершении
- **WHEN** сформирован итоговый отчёт
- **THEN** он содержит ревизии и ссылки на прогоны, доказанную защиту merge, принятый долг и явно оставшиеся проверки живого контура
