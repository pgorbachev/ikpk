## ADDED Requirements

### Requirement: Staging193 rehearsal uses one sealed publication snapshot without production journal writes

Only an owner-designated rehearsal on staging193 (`193.124.115.99`, `https://193.124.115.99`, `deployMode=stand`, `paymentRole=ci`) may use `sourcePolicy=demo-publication-only`, profile `demo-dev`, `recordKind=publication-snapshot`, `sourceAge=untracked`, `origin=server-db`, and `sourceId=demo193-cms`. The source ID is a retained legacy machine identifier. For this frozen current-state snapshot, this scoped rule overrides generic provenance-journal observation and high-water-mark preconditions; it is not an edit, restore, or migration event and creates no edit, restore, initial-migration, acceptance, revision, or high-water-mark entry. All production publication, migration, and restore operations remain subject to the existing provenance journal contract.

Fix the destination and admitted full source SHA before executing candidate code. The operation manifest SHALL record its ID, old/new CMS code, DB, media, static and config identities, canonical ref, full SHA, exact CI run/attempt, and separate CMS/static payload digests. The CMS and static outputs SHALL derive from that one SHA. CI receives no host credentials. The first new command SHALL hold the host flock, check admission and operation availability, and refuse if a maintenance marker exists, an unfinished operation exists, or the operation ID has already been used. Journal-tail repair may occur during this check, but it does not start an operation. Before creating this operation's journal or marker, the command SHALL validate and extract the admitted source archive, install CMS and web npm dependencies, and build the CMS artifact as the configured unprivileged user while existing writers remain open. CMS build dependencies SHALL come from a complete immutable generation keyed by the source lock hash and build profile, using the existing lock-hash dependency layout; reuse requires compatible identity and completeness, and preparation SHALL NOT mutate or replace an existing generation. Build caches SHALL remain in the operation source tree. A preparation failure SHALL leave existing writers open and create no new journal or marker or change live DB/release state. After preparation, acquisition records the fresh old/new pair, appends `start`, creates the marker, then fences and verifies closure of CMS writers. The off-host-confirmed follow-up SHALL validate the same operation owner and structurally verify and reuse the complete prepared output bound to the same source and CI provenance; it SHALL NOT rerun npm or the CMS artifact build under the fence. After capture, build static output from the same SHA and sealed snapshot using the already prepared web dependencies. The snapshot proof SHALL bind a quiesced SQLite image, schema/content inventory, every referenced media byte, original media names and permissions, and one sealed bundle digest. REST reads alone are insufficient.

Each process SHALL acquire a host flock and verify the same persistent journal operation ID; the OS lock is process-scoped and is not held between commands. The durable journal and verified writer fence preserve operation ownership across commands. After prefence preparation, acquisition SHALL record the fresh old/new pair, append `start`, create the marker, fence and stop all CMS writers, and verify closure before any DB or live-code mutation; a persistent marker alone does not prove closure. The fence blocks admin, content-manager, upload, API write, and custom write routes while preserving payment/status routes and GET/HEAD media. Use existing Nginx locations; validate changes with `nginx -t` and restore the prior gate file on failure. If acquisition stops before verified closure, do not mutate DB or live release; recovery closes and verifies writers first. After closure, checkpoint SQLite WAL, prove no CMS process holds a DB handle, and make an integrity-checked DB/media backup whose actual bytes are verified off-host before migration or activation. Preserve media names, permissions, and DB references. CMS migration/audit and static snapshot/build run as `ikpk-cms`; root performs only bounded configured path, unit, gate, and atomic switch operations.

After CMS activation, poll health for up to 20 minutes and prove the running DB using process environment and open FD. After static activation verify served `/release.json`, required routes, and images against the same candidate. Keep one readable append-only journal file: success records are `start` (old bundle), `new-bundle`, `committed`. Commit follows CMS and static acceptance and precedes writer reopen. Before commit, explicit recovery may restore and verify the old pair; after commit, DB restore is forbidden.

#### Scenario: first release is accepted as one pair

- **WHEN** admitted source and run pass, off-host DB/media bytes verify, and CMS plus static candidate checks pass
- **THEN** health, process DB proof, media, and served release/routes/images identify the operation and source
- **AND** the three journal records end in durable commit before writer reopen, without production journal writes

#### Scenario: failure before commit is recovered explicitly

- **WHEN** acquisition stops early or CMS/static acceptance fails before commit
- **THEN** no mutation occurs before verified fence closure and the fence persists after closure
- **AND** retry uses the same operation ID or explicit recovery verifies/restores the old pair before reopening
- **AND** recovery refuses DB restore after commit

#### Scenario: second release retains an editor write

- **WHEN** a new editor record and media are saved after the first release and a second operation runs
- **THEN** that record and media remain served, migrations are not repeated, and mutable DB/WAL is checked by lineage and integrity rather than equality to the first backup
