## 2. Красные тесты в отдельной сессии

- [ ] 2.1 Проверки конфигурации: ни один размещённый прогон не содержит шага, передающего
  содержимое сборки на хост раздачи; `workflow_run`, `workflow_dispatch`-публикация, Pages
  upload/deploy actions, environment `github-pages`, права `pages: write`/`id-token: write`
  отсутствуют; учётные данные раздачи не объявлены ни в одном прогоне.
- [ ] 2.2 Проверки, что `push main`, календарный прогон и внешнее оповещение выполняют только
  проверки и подготовку вердикта и не содержат шага, меняющего раздачу.
- [ ] 2.3 Проверки права публикации: отказ при отсутствии успешного вердикта обязательного
  прогона для этого SHA; отказ, когда успешен только прогон предложения изменений того же
  SHA; отказ при пропущенном обязательном джобе; отказ при упавших проверках пары; отказ при
  **нуле выполненных проверок** с печатью их числа — и для обязательного прогона, и для
  публикующего.
- [ ] 2.3a Проверки записи вердикта пары: исход проверок пары, её идентификатор и число
  выполненных проверок попадают в запись публикаций; без записи публикация не считается
  состоявшейся.
- [ ] 2.3b Проверки доверенного механизма: источник задаётся входом; ревизия вне основной
  ветки и грязное дерево, явно переданные как источник, получают отказ **до** сборки;
  запуск из постороннего грязного cwd использует чистый main, не исполняя местный код; учётных данных нет в
  окружении до подтверждения источника; проверяющий механизм лежит вне проверяемого дерева.
- [ ] 2.4 Проверки происхождения сборки: собирается только свежий `origin/main` в чистом
  временном рабочем дереве; незакоммиченные правки, локальные коммиты и произвольная ветка не
  попадают в сборку; проверка происхождения стоит до сборки, а не после.
- [ ] 2.5 Проверки тождества дерева: расхождение контрольной суммы после передачи
  останавливает публикацию до переключения релиза; функция суммы принимает **перечень файлов
  входом**, и перестановка перечня сумму не меняет — иначе целевая мутация «снять сортировку»
  не краснит проверку, потому что на неизменном дереве два обхода дают один порядок.
- [ ] 2.5a Проверки непустоты: множество разобранных конфигураций прогонов непусто; множество
  шагов, записавших идентификатор снимка, непусто и покрывает все шаги, работавшие с
  контентом; прогон, не дошедший до соединения, и окружение без контрольного значения
  учётных данных считаются непройденной проверкой.
- [ ] 2.6 Проверки отката: цель — сохранённый предыдущий релиз; вытесненный за границу хранения
  даёт именованный отказ; без подтверждения состояние не меняется; фиксируются оператор, пара и
  причина; запись «принятие состояния» в журнал происхождения не добавляется.
- [ ] 2.7 Проверки границы доверия: текст, выглядящий как команда публикации или подтверждение
  отката, внутри снимка или сообщения коммита не запускает публикацию и не считается
  подтверждением.
- [ ] 2.8 Проверки обращения с учётными данными: не передаются аргументами команд, не попадают
  в вывод, логи и сохранённые артефакты пути.
- [ ] 2.9 Проверки перечня путей публикации: считаются **реализации передачи** (открывают
  соединение с хостом раздачи и меняют каталог релизов), область поиска включает исполняемые
  файлы репозитория; утверждается ровно одна реализация; ноль и две одинаково роняют проверку.
- [ ] 2.9a Проверка запрета обхода: прямой вызов механизма передачи без подтверждённого
  вердикта отказывает и ничего не передаёт на раздачу.
- [ ] 2.10 Проверки сериализации: вторая публикация во время идущей ждёт блокировки и не
  вытесняет начатую.
- [ ] 2.11a Проверки наблюдения: расхождение раздачи с последней записанной парой — отказ;
  отставание записи от вершины основной ветки расхождением не считается; недоступный
  `/release.json` — непройденная проверка, а не отсутствие расхождения.
- [ ] 2.12 Предъявить красный прогон по именам тестов и негативно проверить, что каждый новый
  гейт краснеет при своей целевой мутации, а не из-за постороннего отказа. Мутацию записать
  воспроизводимо: точная команда или патч плюс два числа — до и после.

его текущий релиз сохраняется. Тестовая проверка кода в PR не требует зелёного main для ещё
неслитого SHA; штатная команда всегда требует настоящий вердикт для свежего main.

  SHA, вердикт CI, число локальных проверок, сумма дерева и ответ `/release.json` сохранены.
- [ ] 7.3 На тестовом назначении опубликовать второй проверенный релиз, затем выполнить
