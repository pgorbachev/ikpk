## Проект серверного исполнения и приёмки на 193 — решение владельца 16.10.2026

Эта часть описывает выбранное продолжение существующего change. Source CI остаётся полным hosted workflow, но его допускает локальный операторский клиент через authenticated `gh`; серверный GitHub token удаляется. Для production до запроса серверу резервируется source tag точного main SHA. GitHub Releases не используются. Действующие проверки кода, candidate acceptance и происхождения сохраняются.

### Командный путь

Оператор запускает `deploy.sh demo|prod --sha <полный SHA>` из доверенного проверенного checkout/tooling version. Целевой SHA — отдельный параметр; его дерево не checkout-ится, не исполняется и не получает доступ к локальным credentials до source-CI admission. Это сохраняет принятое требование выполнять проверку механизмом вне проверяемого дерева без нового установленного локального framework. Доверенный локальный клиент проверяет закреплённый SSH-host и через authenticated `gh` получает полный evidence разрешённого source CI. Production дополнительно резервирует source tag для exact main SHA. Клиент передаёт ограниченный evidence bundle вместе с request ID через существующий SSH gateway; GitHub token и локальные GitHub credentials остаются на машине оператора. Установленный серверный исполнитель валидирует bundle, сохраняет request и результат и продолжает операцию при потере SSH-ответа. CMS-снимок, сборка, candidate checks и активация остаются серверными.

Сервер получает чистые исходники точного разрешённого SHA из канонического репозитория и проверяет их до исполнения кода с доступами. Нельзя запустить скрипт из произвольного локального checkout с SSH-правами. Поддерживаемый установленный исполнитель и SHA собираемого сайта фиксируются раздельно. Подготовка на одном VPS не требует переписывания существующего транспорта.

### Источник кандидата и порядок продвижения

Самый узкий предлагаемый путь для 193: релизный PR в dev → ревью/автотесты → merge в dev → обязательный CI для получившегося dev SHA → явный deploy demo. В этой поставке test.yml получает push для dev; защищённый допуск dev ограничен DEMO-профилем. До слияния поставки и успешного branch-CI выбранного SHA этот путь не считается доступным.

Если нужно испытать сам head PR до merge в dev, это отдельное изменение политики источника/CI и не входит по умолчанию. Production принимает только точный актуальный main после dev → main и полного обязательного CI получившегося main SHA. Нельзя выдавать проверку merge-ref PR за проверку другого SHA. Продвижение main/dev не меняет закреплённый источник операции незаметно; до принятия иной политики сохраняется отказ при изменении разрешённой вершины.

### Данные и проверки

Текущие CMS-данные назначения фиксируются одним согласованным снимком с медиа; прямое чтение произвольных таблиц сборщиком не предписывается. Выпуск кода может включить уже сохранённые правки контента, что соответствует последнему решению владельца. Одна операция, один активатор и один администратор; техническая проверка согласованности захвата остаётся обязательной. После фиксации снимка последующие правки CMS не подменяют байты готовящегося кандидата; заморозка редактирования на весь прогон CI/сборки не требуется.

Матрица проверок: полный тестовый набор SHA (включая E2E на фикстурах), полный релизный E2E и проверки кандидата на текущем снимке, затем внешняя проверка после активации. Каждый обязательный набор имеет проверяемый результат; skips/ноль/ошибка блокируют новую публикацию. Результат текущей операции можно использовать один раз, не дублируя идентичную работу на том же объекте. Существующий browser smoke не объявляется полным E2E; `npm run test:e2e` не исчерпывает все имеющиеся наборы. Demo и prod тестируются отдельно. Тестовые отправки не создают настоящие обращения/уведомления. После тестирования кандидат не пересобирается. По решению владельца от 15.10.2026 исторические compare/parity со старым сайтом исключены: сайта больше нет. Точный перечень закреплён в release-test-policy.mjs и манифесте. Меняющиеся production-данные не являются постоянным тестовым эталоном.

Сохраняются прежний рабочий релиз, ясные отказы до переключения, active-unindexed/pending после него, восстановление по прежнему ID и отдельный rollback. Аварийное восстановление проверяется однократно при приёмке механизма и при существенной его смене; перед каждым обычным выпуском ручная репетиция не повторяется.

### Зависимость от отдельного процесса обновления структуры БД в dev и на демо

Обновление структуры БД для `dev` и демостенда 193 выполняется отдельно. Не реализовывать его повторно и не запускать миграцию неявно из deploy.sh. Принятая модель описана в #330 и `docs/ops/production-data-migrations.md`. [PR #331](https://github.com/pgorbachev/ikpk/pull/331) слит в `dev` 16.10.2026 коммитом `d5f24c95f62579f261bc01ddc6e36cb1c6211e47`; дерево совпало с проверенной головой PR `b97145f606dab0ec0dfc3b0eef3c1d7c2eb37a28`. Перед merge подтверждены все 17 проверок этой головы. Закрытая репетиция проверила SIGKILL/retry, парный откат и запрет отката после новой записи; отдельная загрузка старой CMS сохранила схему и бизнес-данные, но не доказывает восстановление исходных секретов и авторизации. Диагностические пары репетиции не являются кандидатами публикации. Слияние runner не переключило CMS или публичный сайт 193 и не подтверждает готовность их новой рабочей пары.

Для живой репетиции на 193 требуется handoff этого процесса: версия CMS/схемы, совместимый SHA сайта, результат проверки целостности/сохранности данных, готовый способ восстановления БД и media при ошибке миграции. Нельзя выводить готовность схемы из одного зелёного CI сайта. Подготовку серверного механизма и изолированные проверки можно вести параллельно; живая репетиция на новой схеме выполняется после её отдельной приёмки.

Релизная ветка должна учитывать итоговую интеграцию DB-PR в dev до финального ревью и приёмки. Если он изменил ранее проверенный кандидат, проверки и ревью затронутой области повторяются; старые свидетельства не объявляются проверкой нового SHA. После handoff релизный механизм проверяет совместимость захвата текущих данных с выбранным SHA. Изменение структуры в ходе выпуска вызывает отказ, а не самостоятельную миграцию. Rollback статического сайта не откатывает БД: после миграции отдельно проверяется, допустимы ли прежний сайт и последующая публикация на нём. Непереносимость DEMO-миграции и её данных на production сохраняется; production требует собственного решения.

### Блокирующее решение по данным production

DEMO publication-only уже спроектирован как неизменяемый снимок без событийного журнала, но ещё не реализован. Legacy/prod в существующих specs всё ещё требуют TD-56. Нельзя назвать DEMO-приёмку разрешением того же ослабленного профиля для prod. Перед production выбрать: завершить старый событийный контракт либо отдельно согласовать его сужение с доказательствами согласованности и обнаружения смены/восстановления данных. План подготовки не выбирает эту политику молча. До решения production сохраняет отказ без журнала.

Результат исследования минимального одного VPS и БД из другой сессии — вход размещения и приёмки. Здесь не проводятся повторный аудит инфраструктуры, очистка или миграция. Отдельный технический план потребуется, если установка CMS #329 меняет схему/данные production: серверный выпуск статического сайта сам этого не делает.

## Context

См. `proposal.md` — Why. Сейчас `Tests` одновременно проверяет пару, сверяет её с раздачей и
через `workflow_run` запускает `Deploy to GitHub Pages`; ручная ветвь `deploy.yml` готовит
снимок заново, хотя принятая спецификация требует публиковать байты уже проверенного
состояния. Pages при этом не включён на уровне репозитория, а Astro-стенд раздаётся с VPS; публичный ikpk.su остаётся на другой площадке.

Существенное для решений состояние кода:

- джоб `publication-record` падает на каждом прогоне `main` (`exit 128`) и не записал ни одной
  пары: индекс `verified-pairs.json` пуст. Причина —
  `.github/workflows/test.yml@ba8cb6eefcc470d4ef0612b6fcdbbb5e84ce7edc:324`, `mkdir -p "$PROV/ledger"`: каталог наполняется до
  `git worktree add`, а тот отказывает на наполненном;
- шаг reconcile внутри `Tests` держится на пустом индексе пар:
  `web/scripts/publication-cli.ts@ba8cb6eefcc470d4ef0612b6fcdbbb5e84ce7edc:66`, `pairs.length === 0 && httpStatus === 404`.
  Поэтому сейчас он зелёный, а при первой же записанной паре начнёт отказывать;
- предыдущие релизы на раздаче сохраняются и доступны для возврата — это уже требование
  основной спеки, а не новая возможность.

**Актуализация контекста:** исторические ссылки выше сохранены для исходного инцидента.
В текущем main живой захват и доставка медиа уже есть; событийного писателя журнала всё ещё
нет. Скрипт VPS собирает текущее рабочее дерево, по умолчанию использует root и не проверяет
вердикт CI. Поэтому наличие работающей ручной команды ещё не означает выполнение этой спеки.

## Goals / Non-Goals

**Goals:**

- Убрать публикацию из системы непрерывной интеграции целиком — и событийную, и ручную.
- Оставить ровно один способ изменить боевую раздачу: локальный исполняемый entrypoint.
- Не хранить учётные данные раздачи в GitHub.
- Публиковать ровно то дерево, которое проверялось, доказывая это суммой, а не порядком шагов.
- Сохранить возможность отличить нормальное состояние от отката.
- Проверять полный source CI через локальный `gh`, передавать его attempt-bound evidence через bounded request и не хранить GitHub token на сервере.
- Перед каждой production-операцией требовать source tag с детерминированной привязкой к точному main SHA и отдельный publication receipt только после serving verification.

**Non-Goals:**

- Автоматическая свежесть сайта относительно `main`, CMS или календаря.
- Автоматический откат при неуспешной проверке раздачи.
- Публикация непроверенного содержимого, в том числе в аварийной ситуации.
- Включение или починка GitHub Pages.
- Перенос обязательных проверок с CI на машину оператора.
- Создание GitHub Releases, SemVer или датированных тегов.
- Криптографические подписи evidence между владельцем локальной машины и уже доверенным restricted SSH publisher.

## Decisions

### 1. Локальный `gh` проверяет source CI, сервер отдельно проверяет пару

Разделяются две вещи, которые прежде совпадали: **что разрешено публиковать** и **кто это
проверил**. Право на коммит даёт обязательный прогон — локальный путь читает его вердикт и без
успеха не работает. Пару «коммит и снимок» проверяет тот прогон, который её публикует, и
записывает свой исход вместе с парой.

Почему пару не может авторизовать CI. Идентификатор снимка вычисляется из отпечатка контента
**и опорной даты**, и принятая спека прямо утверждает сценарием, что снимки одного и того же
контента, снятые в разные дни, имеют разные идентификаторы. Отставание публикации от прогона
объявлено неограниченным. Значит «опубликовать ту пару, которую проверил обязательный прогон»
недостижимо в общем случае: снимок публикации не совпадёт со снимком прогона даже при
неизменном контенте. Отсюда два возможных выхода — тащить артефакт снимка прогона (возвращает
локатор артефакта и срок его хранения, то есть ограничивает окно публикации) либо признать
проверку пары обязанностью публикующего прогона. Выбран второй, и тогда цена — требование
аудируемости: исход проверок пары и число выполненных проверок записываются, иначе вердикт
публикующего прогона неотличим от его отсутствия.

Почему вердикт CI при этом нужен: он относится к коду и остаётся тем же вердиктом, который
стережёт слияние. Он не вычисляется локально: операторский `gh` читает authoritative run/jobs/
artifact данные из GitHub. Успех определяется строго — canonical repository, exact разрешённая
ветка и SHA, полный `Release source tests`, выбранная attempt, native обязательные jobs, policy
manifest и artifact digest. Локальный клиент не запускает и не перезапускает CI и не выбирает
старый success поверх более нового failure.

Для передачи используется один bounded evidence bundle внутри существующего SSH request: native
run identity, обязательные jobs, artifact metadata, исходный artifact размером до 4 MiB и его
GitHub-reported SHA-256. Полный serialized request SHALL укладываться в 8 MiB. Production tag
creation использует локальную auth оператора с правом записи refs; чтение Actions остаётся
read-only и не требует Actions write. Сервер повторно проверяет artifact SHA-256, имя единственного
manifest, ref/SHA/run/attempt/job identity, policy/profile/
report fields и связь с request ID и назначением. Он отдельно сверяет SHA с актуальной
разрешённой вершиной до запуска candidate code и выполняет проверки снимка/кандидата. GitHub
token отсутствует в server config, server process, SSH arguments, evidence и candidate
environment; server не обращается к GitHub API.

Сверка размера на `dev@91bbd36b52d1f367c8b42ce557111dff9b909804`: успешный run
`38940517004`, attempt 1, хранит artifact `release-source-tests-1` размером 4,256 байт по
GitHub artifact metadata. Это подтверждает запас для evidence manifest на выбранной голове;
CMS artifact в этом run не существует, поэтому его cap устанавливается только после измерения
нового CI payload.

Лимит 4 MiB относится только к небольшому CI-evidence ZIP. Контрольный JSON ограничен 8 MiB,
CMS archive имеет отдельный измеренный/versioned предел. Один restricted SSH stdin несёт атомарно
сформированный кадр из двух unsigned 64-bit big-endian lengths, за которыми следуют control JSON и
CMS archive в raw bytes (не base64 и не отдельный worker request). Server принимает оба полных
кадра в единственный incomplete private receive slot назначения, закреплённый за operation UUID,
проверяет declared lengths,
отсутствие trailing bytes, control identity, CMS outer GitHub ZIP digest и внутренний inventory;
только после полной проверки и durable фиксации canonical request он передаёт запрос worker под
существующей admission/flock. Worker никогда не запускается на частично принятых или ещё не
проверенных байтах. Размер archive cap SHALL быть выставлен по измеренному CMS ZIP полного
успешного CI run и зафиксирован версией; producer-only CI upload разрешён для измерения, а
server-side consumer и transport остаются закрыты до фиксации cap. Единственный receive
slot ограничивает совокупный incomplete ingress на destination суммой максимального 8 MiB control
и этого измеренного archive cap. До создания/записи staging сервер под существующей
сериализацией admission проверяет заявленные frame sizes и `statfs` для этих bounded bytes плюс
документированный free-space reserve. Reserve измеряется и задаётся при rehearsal; если он ещё
не определён, сервер fail-closed до записи. Превышение frame/aggregate bound или недостаток места
даёт отказ до создания/записи staging и без удаления старых данных.

Неполный приём остаётся в private staging как неисполняемое свидетельство и занимает единственный
incomplete slot до отдельного явно разрешённого операторского действия; повтор upload с тем же
UUID отвергается, а новый UUID сам по себе не обходит занятый slot. Это не требует нового status
API: неполный receive не считается принятой операцией; существующий readback не должен
представлять его как accepted. Автоматическая очистка/удаление прежних operational artifacts
не входит в протокол. После полного приёма и durable admission slot считается committed и его
bytes принадлежат обычному operation storage. Тот же ID идемпотентен только при
равенстве canonical control и обоих рассчитанных digest; отличное содержимое отвергается. Outer
GitHub ZIP digest передаётся только во внешнем control/evidence:
он не включается в CMS archive, иначе хеш был бы самоссылочным. Текущий stdin limit 2 KiB,
allowlist, framing, canonicalization/retry equality и клиентская сериализация должны быть
согласованно обновлены. Архив проверяется до распаковки на размер, безопасные пути, symlink,
точный inventory и обязательный output; существующие flock/admission semantics сохраняются.

### 1b. CMS build из полного source CI переиспользуется на сервере

`release-tests.yml` уже строит CMS и повторно использует этот admin build для CMS-to-site E2E,
но сейчас сохраняет лишь TAP отчёты. После успешных CMS unit/build и изолированного E2E тот же
run/attempt должен сохранить CMS release artifact без `node_modules`. Внутренний manifest
содержит source SHA/ref/run/attempt, digest `cms/package-lock.json`, Node/npm identity и точный
inventory файлов с digest каждого файла. GitHub ZIP digest остаётся только во внешнем native
artifact metadata/evidence/control request; сервер пересчитывает его при приёме архива. Локальный `gh`
загружает именно artifact текущего admitted run/attempt. Сервер проверяет manifest, native
artifact metadata, SHA/lock/runtime и архив, затем вызывает assemble-only режим
`build-cms-artifact.sh` на уже собранном `cms/dist`; `dist/build/index.html` обязателен.
Серверный CMS compile не повторяется. Astro site по-прежнему строится на сервере на текущей
паре БД/снимок/медиа; CMS artifact лишь заменяет повторную сборку CMS приложения. Нет артефакта,
неверная identity/digest, лишний файл, traversal/symlink или размер выше измеренного лимита —
отказ до candidate execution и activation, без fallback к server-side `npm run build`.

Минимальная граница доверия соответствует уже принятой модели доступа: authenticated `gh`
оператора получает native evidence, а restricted SSH publisher уже доверен принимать явные
операторские запросы. Структура, предел, identities и digest защищают от случайной подмены,
усечения и потери связи между evidence и операцией. Этот механизм не объявляется подписью,
которая доказывает происхождение против оператора с правом выкладки.

### 1a. Production tag резервирует код, publication receipt подтверждает выкладку

Предлагаемое имя source tag — `prod-src-<полный SHA>`. Оно детерминировано кодом и не
назначает релизу дату или версию. После admission source CI и проверки, что SHA остаётся точной
вершиной `main`, локальный entrypoint создаёт тег до отправки запроса, который может вызвать
серверные side effects. Если тег уже есть и разворачивается в тот же commit, его повторно
используют; несовпадающий или непроверяемый tag вызывает отказ. Если ответ GitHub на создание
потерян, клиент перечитывает ref: точное совпадение означает уже выполненную reservation,
любой другой исход даёт отказ. Force-update и удаление tag публикационным путем запрещены.

Tag reservation сохраняется при неудачной подготовке и не выглядит как опубликованный релиз.
Только после switch и serving readback сервер создаёт успешную квитанцию с request ID, tag,
source SHA, snapshot ID и release ID. Новая публикация того же SHA использует тот же tag и
получает новый operation ID и snapshot receipt. `/release.json` продолжает отвечать за пару
«commit + snapshot»; source tag не заменяет её и не является идентификатором CMS-данных.
DEMO/dev не создаёт production source tags.

Удаление `publication-record` устраняет TD-61, но не остальные падения `Tests`.
На срезе из proposal краснеют также dependency invariants и нестабильный тест провижининга.
Готовность определяется настоящим зелёным прогоном публикуемого SHA после merge, а не
предположением о единственной причине. Исправление этих дефектов — отдельная работа.

### 2. Требования формулируются на entrypoint, а не на исполнителя

Штатный путь — исполняемый скрипт (`scripts/deploy-web.sh` плюс команды
`scripts/publication-launcher.mjs`). Оператор, в том числе агент, является его исполнителем и
предъявляет вывод.

Причина не организационная, а про проверяемость: «агент берёт свежий `origin/main`», «агент
проверяет страницы» — утверждения, которые нельзя подтвердить тестом. Требование, адресованное
исполнителю, стало бы сценарием, который не может покраснеть, — ровно тот декоративный гейт,
которого этот проект уже набрал достаточно. Поведение скрипта проверяется, поэтому все `SHALL`
адресованы ему.

Отсюда же формулировка отката: подтверждение есть **отдельный вход** скрипта, а не намерение
исполнителя.

### 2a. Требования формулируются на исполняемый код — правило редакции, а не требование к системе

Все `SHALL` этой capability адресуются исполняемому коду: скрипту, программе, их входам и
выходам. Требование, адресованное человеку или агенту, стало бы сценарием, который не может
покраснеть, — тестом не подтверждается ни то, кто набрал команду, ни то, что исполнитель был
внимателен.

Правило живёт здесь, а не в тексте спецификации, и это осознанно: оно описывает, как мы пишем
требования, а не поведение системы. В спецификации оно было бы `SHALL`, который не краснеет ни
в одном состоянии мира, то есть ровно тем, против чего направлено.

**Граница правила названа, чтобы её не пришлось выводить.** Оно относится к требованиям, которые
этот change **пишет**. Текст, перенесённый в дельту дословно из уже принятой спецификации, форму
сохраняет — в `cms-content-source` есть `SHALL`, адресованные процедуре восстановления и тому,
кто восстанавливает базу. Переписывать их здесь было бы правкой чужого принятого требования под
видом переезда: у такой правки другой предмет и другая цена ревью. Приведение их к правилу —
отдельная работа, и она названа этим абзацем, а не оставлена умолчанием.

### 2b. Владение предусловиями

Событийный журнал и ревизию живого снимка для legacy и production поставляет
`cms-live-snapshot-capture` (задача 5.3). DEMO не ждёт событийную часть `TD-56`, но обязан
доказать согласованный неизменяемый захват данных и медиа; если средство захвата этого не
умеет, DEMO-публикация блокируется до ремонта. Для legacy/prod ручной путь читает журнал,
ведёт индекс публикаций и через общий протокол журнала записывает явное принятие
восстановленного текущего состояния CMS. В него не переносится получение событий
CMS и не добавляется запись события при чтении снимка: две правки между публикациями должны
остаться двумя событиями. Отсутствующая ревизия — отказ до передачи, а не режим bootstrap.
Интеграционные тесты используют управляемый журнал; настоящая приёмка требует живых событий.

Код launcher (fetch, сверка источника, чистое дерево, выдача учётных данных после проверки)
реализуется в этом change вместе с локальным путём. `server-hardening` устанавливает и
защищает этот артефакт на машине оператора, готовит ограниченные права выкладки; его
предшественник — приёмка `server-provisioning`. Код можно проверить до установки в
изолированной среде; настоящая публикация отказывает без защищённой установки.
Второй провижининг или второй launcher не создаётся. Порядок приёмки: provisioning →
установка и защита готового launcher средствами hardening;
живой захват и журнал могут завершаться параллельно; затем приёмка ручной публикации.
Слияние планов не равнозначно завершению этих работ.

### 3. Запись публикаций переезжает и получает третью роль

Индекс терял смысл как механизм **выбора**: между проверкой пары и её выкладкой больше нет
разрыва, публикуется текущая вершина, выбирать не из чего. Но ролей у записи оказалось три, а
не две: цели отката, аудит вердикта публикующего прогона (решение 1) и **опора наблюдения**
за опубликованным состоянием (решение 6). Поэтому запись остаётся, а писателем становится
локальный путь с учётными данными запускающего.

Это требует дельты к `cms-content-source`, и дельта разводит **двух** писателей, а не переносит
одного. Журнал пополняет прогон по событию изменения контента: правки происходят между
публикациями, и если бы журнал писал только публикующий путь, две быстрые правки дали бы одну
запись вместо двух — требование «на каждое изменение своя запись» стало бы невыполнимым.
Индекс опубликованных пар пополняет локальный путь: только он знает, что именно выложил.
Сериализация записи индекса — та же исключительная блокировка на хосте раздачи.

Отдельно назван исход «релиз переключён, запись не сделана». Переключение неделимо и
отменяться не может, поэтому такой исход возможен. Он завершает публикацию неуспехом и
**останавливает следующие штатные публикации** до восстановления записи: наблюдение опирается
на запись, и без неё оно не отличает подмену релиза от нормального отставания.

Цели отката — **сохранённые предыдущие релизы на раздаче**, а не артефакты прогона. Это тоже
дельта к `cms-content-source`: её требование связывало срок хранения снимка со сроком
повторной выкладки. Обещание сохраняется. Сохранённый снимок удерживает свою опорную дату и по принятому
контракту воспроизводит вывод даже в другой день; новую идентичность даёт новое снятие.
Готовый релиз выбран для отката потому, что не требует повторной сборки и доступной среды
сборки во время восстановления. Он возвращает опубликованные байты вместе с медиа. Срок
повторной выкладки называется вместе с глубиной хранения релизов.

Индекс и незавершённая запись разделены по стабильному идентификатору назначения.
Для stand и prod даже одинаковая пара может дать разные байты из-за режима сборки, поэтому
запись хранит назначение и сумму дерева. Проверка раздачи берёт последнюю запись только
своего назначения; откат проверяет и принадлежность назначения, и сохранённую сумму.

### 3a. Состав локального прогона

Для новой публикации одна команда `npm --prefix web run test:publication` исполняет группы из дельты
`deploy-gating`: снимок/журнал, сборка/содержимое, режим, browser smoke, платёжное назначение.
Это новая команда реализации, а не утверждение о её наличии в текущем main. Она принимает
один снимок и явную конфигурацию назначения, строит дерево один раз и проверяет именно его.
`release.json` записывается до измерения суммы и проверки готового дерева; отчёт с суммой
хранится вне этого дерева, чтобы не создавать самоссылку.
Существующие проверки медиа, режимов форм/чата и payment readiness переиспользуются;
браузерный smoke подключается к уже поднятому preview без повторной сборки. Запросы к
платёжному контуру для активных ролей ограничены read-only readiness/preflight; CRM-заявки
и реальные платежи не создаются. Роль оплаты задаётся отдельно от CRM и назначения: при `ci`
группа проверяет отсутствие формы/endpoint без запросов к API. Это позволяет публиковать
боевой сайт до включения оплаты, как требует основная online-payment. Проверки безопасности богатого содержимого и ссылок выполняются на живом
артефакте. Ожидания конкретной фикстуры и визуальные эталоны остаются в CI.

Команда выдаёт отчёт по фиксированному в коде составу групп; вызывающий не может выбрать
один удобный тест. Потребитель отчёта требует все группы, ненулевые результаты каждой,
совпадение назначения и суммы дерева. Отчёт другого запуска или назначения не подходит.
Нулевая группа или пропущенная проверка не превращаются в неприменимость. Перед передачей
сумма проверяется вновь; при изменении дерева нужен новый полный прогон.

Откат имеет отдельный набор: исходная запись с сохранённым свидетельством CI и локальных
проверок, принадлежность назначению, сумма сохранённого дерева, подтверждение/причина,
отсутствие незакрытой операции, проверки режимов, smoke и платёжного назначения по роли
этого релиза. Новый снимок и новая сборка не нужны. Удаление старого run или недоступность
CMS не отменяет сохранённое свидетельство. Откат выполняет установленный доверенный
механизм; неисправную вершину main ради отката не загружают и не исполняют. Launcher, build,
deploy и серверные скрипты сохранённого релиза не запускают. Его клиентский JavaScript
проверяется только в изолированном браузерном smoke без учётных данных выкладки.

### 4. Тождество выкладываемого дерева доказывается суммой

Прежде тождество держалось на передаче артефакта между джобами. Локально соблазн — считать
тождество следствием того, что «сборка и отправка идут подряд»; это не доказательство.
Контрольная сумма дерева считается после проверок, сверяется на хосте раздачи до переключения
релиза, и расхождение останавливает публикацию. Сумма считается по относительным путям и в
устойчивом порядке: на этом проекте несортированный обход уже давал ложное расхождение при
1756 побайтово совпадающих файлах.

После передачи и проверок выполняется последняя сверка вершины, последней записи журнала
и высшей отметки. Её значения сохраняются в записи операции; далее сразу следует атомарное
переключение. Общей транзакции с событийным писателем CMS нет: новое событие после этой
границы попадает в явно разрешённое остаточное окно, как новый коммит main. Оно не прерывает
переключение и не запускает следующую публикацию; обнаруженное до границы событие даёт отказ.

`release.json` с выбранными `commit` и `snapshotId` пишется внутрь каталога релиза до
переключения симлинка; после переключения путь читает `/release.json` с раздачи без смены
имени хоста и требует точного совпадения пары.

### 5. Привилегия не исчезает, а переезжает — и это меняет предмет требования о происхождении

Событийного пути публикации больше нет, поэтому класс «прогон, запущенный событием о
завершении другого прогона, получает секреты» исчезает целиком. Но право записи на боевой хост
не исчезает: оно становится постоянно доступным локальному пути. Поэтому требование о
происхождении не удаляется, а переформулируется на новый предмет: собирается только свежий
`origin/main` в чистом временном рабочем дереве, и проверка стоит **до** сборки — иначе код из
неподтверждённого источника уже исполнен.

Без этой переформулировки три из четырёх сценариев требования остались бы с условием
«получено событие о завершении прогона», которого не будет никогда, то есть стали бы
неопровержимыми. Требование о непривилегированной учётной записи выкладки сохраняется без
изменений: оно от триггера не зависело.

### 6. Перечень путей публикации должен искать и в скриптах

Проверка «ровно один путь публикации» прежде сверяла шаги размещённых прогонов. После переезда
таких шагов не остаётся ни одного, и проверка нашла бы ноль — а ноль в этом требовании есть
отказ, причём справедливый: «проверить не удалось». Поэтому область поиска расширяется на
локальные исполняемые entrypoint'ы репозитория, и «ровно один» утверждается по объединению.

Смягчать отказ до предупреждения нельзя: это вернуло бы слепоту, ради которой требование и
написано.

### 7. Pages удаляется как путь и как привилегия

Из workflow удаляются `workflow_run`, `workflow_dispatch`-публикация, Pages upload/deploy
actions, environment `github-pages`, Pages concurrency, права `pages: write` и
`id-token: write`. Конфигурационные тесты утверждают отсутствие любого пути публикации в
размещённых прогонах и отсутствие объявленных учётных данных раздачи.

Существующие проверки, выводящие обязательный прогон из наличия `workflow_run` у публикующего
workflow, теряют предмет. Измерено мутацией предмета — снятием
`.github/workflows/deploy.yml@ba8cb6eefcc470d4ef0612b6fcdbbb5e84ce7edc:11`, `workflow_run:` — 20 проверок в четырёх файлах:
`web/tests/demo-gate.test.ts` (9), `web/tests/browser-test-gating.test.ts` (5), `web/tests/deploy-gating.test.ts` (5),
`web/tests/social-accounts.test.ts` (1). Они намеренно выводят гейт из структуры, а не по имени, поэтому
переписываются под новый контракт, а не отключаются: `.skip` оставил бы обещание без предмета.
Семейство `dependabot-*` использует собственный `workflow_run` и к этому пути не относится —
в объём не входит.

Merge при этом не замерзает: `Deploy to GitHub Pages` не входит в обязательные контексты
защиты ветки, и имена джобов не меняются.

### 8. Доверенный launcher вне проверяемого дерева

Проверку происхождения нельзя поручить коду из целевого дерева: текущая публикационная
оболочка определяет корень по собственному расположению и подключает библиотеку проверок из
того же checkout (`scripts/deploy-web.sh@ba8cb6eefcc470d4ef0612b6fcdbbb5e84ce7edc:25`, `SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"`). Если
оператор запускает tooling из проверенного checkout и отдельно задаёт точный target ref/SHA,
проверка не зависит от файлов целевого SHA. До admission целевой checkout не создаётся и его
код не исполняется, поэтому кандидат не может подменить локальную проверку или прочитать
локальные credentials.

Поэтому локальная проверка source CI выполняется tooling из доверенного проверенного
checkout, отдельного от целевого дерева; сервер повторяет проверку SHA и evidence до
checkout/исполнения candidate code. Порядок несущий: сначала подтвердить источник, затем
исполнить код, и только подтверждённому коду дать доступ к учётным данным. До подтверждения
учётных данных в окружении candidate code нет вовсе — иначе непроверенный код успевает их
прочитать до всякого шага проверки.

Источник при этом SHALL быть **входом** проверяющего механизма, а не браться им молча. Оператор
передаёт полный target SHA отдельно от tooling checkout; ref выбирается только из политики
назначения. Это условие проверяемости: сценарии обязаны уметь предъявить и принять/отклонить
конкретную голову без молчаливого выбора источника.

### 9. Запрет обхода делается кодом, а не документацией

Механизм передачи содержимого на хост раздачи отказывается работать без подтверждённого
вердикта. Прежняя редакция ограничивалась тем, что документация назовёт прямой запуск
нештатным, — но требование «ровно один путь публикации» определяет путь по фактическому
поведению и прямо запрещает отбирать пути по нашему обозначению. Механизм, который передаёт
файлы и переключает релиз, есть путь публикации независимо от того, как мы его назвали.

Отсюда же уточнение счётного признака: считаются **реализации передачи**, а не способы вызова.
Один механизм, вызываемый из двух мест, — один путь; два независимых механизма — два, даже
если один объявлен диагностическим.

## Risks / Trade-offs

- **[Сайт может отставать неопределённо долго]** → принятое владельцем поведение;
  документация показывает последнюю опубликованную пару и команду публикации.
- **[Право записи на прод у рабочего места]** → непривилегированный deploy-user, закреплённый
  признак хоста, учётные данные вне аргументов команд и вне логов, исключительная блокировка на
  хосте. Взамен исчезает доступ у размещённых прогонов, где он выдавался и чужому коду.
- **[Оператором может быть агент, читающий контент заказчика]** → команда публикации приходит
  только от человека в сессии; содержимое трактуется как данные и не может быть ни командой,
  ни подтверждением. Отдельное требование, а не оговорка в документации.
- **[Публикация зависит от рабочего места]** → штатный путь есть скрипт, а не агент; он
  запускается человеком без агента и его поведение покрыто тестами.
- **[Evidence bundle повреждён или отвязан от запроса]** → общий serialized request ограничен
  8 MiB; сервер проверяет schema, identities, policy и digest до candidate execution и хранит
  evidence в защищённой квитанции с request ID.
- **[Production tag создан, а кандидат не опубликован]** → tag означает только source SHA;
  publication receipt появляется лишь после активации и serving readback. Retry того же SHA
  использует существующий tag и отдельный operation ID.
- **[Нет автоматического отката]** → возврат остаётся отдельной подтверждённой операцией; после
  неуспешной сверки раздачи путь называет действующий релиз.
- **[Два оператора публикуют одновременно]** → исключительная блокировка на хосте раздачи;
  ожидающая публикация не вытесняется.

## Migration Plan

**Первое известное назначение — существующий VPS-стенд 193.124.115.99.** Публичный
ikpk.su на срезе 19.09.2026 обслуживается другим сервером (158.160.147.32). Pages
не обслуживает ни одну из этих площадок. Его удаление не выключает nginx стенда и не
меняет его `current`; это доказывает непрерывность стенда, а не готовность production.
Production-назначение нового пути ещё не установлено: его адрес, доступ, права, раздача
и готовность должны быть подтверждены отдельно до задачи 7.5. Перенос трафика не входит
в этот change. Требование сначала подтвердить новую раздачу сохраняется для настоящего
переезда на другую площадку, но не требует первой выкладки новой командой до удаления
неиспользуемого workflow.

1. Начать реализацию от свежего интеграционного `dev`; production source policy при этом
   остаётся exact current `main`, DEMO — exact current `dev`. Проверить применение обеих дельт и
   предусловия отдельно; `server-provisioning` не ждёт архива этого change. Писатель CMS и
   права/защищённая установка launcher готовятся
   в соседних changes; код launcher реализуется здесь.
2. В отдельной сессии написать красные тесты конечного контракта. Для PR использовать
   временное тестовое назначение и управляемые ответы API CI; подмена вердикта не должна быть
   доступна через production-entrypoint. Это проверка реализации, не настоящая публикация.
3. В одном PR реализовать local `gh` source-CI admission, bounded evidence validation,
   production source-tag reservation/receipt semantics, локальный путь, запись пары и откат;
   удалить серверный GitHub token, `publication-record`, reconcile из `Tests` и Pages workflow
   с его правами. Переписать затронутые проверки под конечный контракт. До merge локальные и
   PR-проверки должны быть зелёными.
4. Перед merge подтвердить, что Pages не обслуживает публичный сайт и его отключение не
   изменит существующий релиз VPS. Если это неверно, остановить этот порядок внедрения:
   перенос действующей площадки требует отдельного плана и прежней защиты достижимости.
5. После merge дождаться полного успешного `Release source tests` для точного разрешённого
   SHA; local `gh` сверяет native run/attempt/artifact evidence перед запросом. При неуспехе
   новая команда отказывает; работающий релиз сохраняется. Зелёный PR не заменяет эту проверку,
   а посторонние падения CI не обходятся.
6. Подтвердить готовность живого журнала и среды запуска, затем выполнить явную публикацию
   на тестовое назначение штатной командой. Проверить пару, сумму дерева, повторную публикацию,
   подтверждённый откат и восстановление после неудавшейся записи индекса.
7. С подтверждением владельца выполнить публикацию на боевое назначение, проверить сайт и
   `/release.json`; убедиться, что последующий push без команды ничего не публикует.
   Только после этой приёмки возможен архив.

**Два разных отката.** До первой новой публикации неуспех запуска оставляет прежний релиз
нетронутым. После публикации штатный откат выбирает сохранённый проверенный релиз с записью
пары. Старые каталоги без такой записи не становятся проверенными автоматически: первый релиз
создаёт первую запись, а штатный откат становится возможен после появления следующего
проверенного релиза. При начальном вводе отсутствие проверенной цели явно сообщается
оператору до подтверждения публикации; оно не маскируется успешной проверкой отката.
Возврат событийной публикации из CI потребовал бы отдельного решения о правах и площадке.

## DEMO publication-only profile

Владелец утвердил профиль `demo-publication-only` для текущего stand на `193.124.115.99`.
Его разрешение задаётся защищённой конфигурацией, одновременно связывающей host
`193.124.115.99`, `siteUrl=https://staging.ikpk.su`, `deployMode=stand` и `paymentRole=ci`.
Неуказанный профиль сохраняет legacy
поведение; отсутствие журнала не включает DEMO-профиль автоматически.

Запись DEMO-публикации имеет явный дискриминатор `recordKind=publication-snapshot`, отдельный
от исторических событий журнала и legacy-записей. Она содержит `sourcePolicy`,
`sourceAge=untracked`, commit, неизменяемый content snapshot с байтами всех использованных
медиа, доказательство согласованности источника, результаты пяти существующих групп проверок,
сумму проверенного дерева и serving proof. Новая запись добавляется только после
подтверждённой раздачи; публикация добавляет пару в существующий verified-pairs индекс той же
ветви. Три прежних события, HWM 3, две stand-пары и историческая семантика ревизий остаются
неизменными; DEMO не создаёт синтетическую запись журнала или ревизию 4.

Захват должен доказать одно состояние для записей и медиа. Два совпавших последовательных
REST-запроса таким доказательством не являются. Если текущий интерфейс CMS не позволяет
получить согласованный захват либо выявить изменение во время захвата, публикация отказывает;
задача включает устранение этого пробела без предположения о конкретной реализации. После
захвата неизменяемые байты нельзя заменять данными последующего состояния.

Пять групп проверок, проверки кода и serving, атомарное переключение, блокировки,
идемпотентное восстановление и подтверждённый rollback остаются обязательными. Ограничение
legacy по `sourceAge` применяется к legacy/prod; DEMO подтверждает происхождение и
неизменность снимка, не заявляя свежесть относительно журнала CMS. Если переключение прошло,
а индекс не пополнен, состояние остаётся `active-unindexed`: новая публикация блокируется,
операция восстанавливается по тому же publication ID и никогда не заменяется прямой
альтернативной передачей.
