## Decisions

1. **Operator admission:** CI never publishes. Fix destination and source before executing candidate code. Require canonical exact-SHA `Tests` push run with all mandatory jobs successful and no skipped/cancelled job. One source SHA yields separate CMS/static digests. Browser checks and served verification use the same static bytes.
2. **Scoped capture proofs:** staging194 retains its demo publication proof. Initial-prod uses a separate truthful production server-DB proof bound to target, source, run, operation, database, schema, and media bytes. The normal publication snapshot reader continues rejecting server-DB proofs, including this one-off type; ordinary production journal/high-water-mark behavior is unchanged.
3. **Fence and backup:** the first CMS command holds the host flock, checks operation availability, and prepares the admitted source, CMS dependencies, and CMS artifact while current writers remain open. Any reused host dependency generation is complete, immutable and compatible with the lock hash and build profile; the staging194 CMS artifact is CI-built and verified under the CI-built CMS artifact requirements in this change; the fixed historical initial-prod operation retains its original build contract. Preparation failures create no new journal or marker and leave live data and releases unchanged. After preparation, existing acquisition records the old pair, starts the operation, writes the marker, and verifies writer closure before DB or live-code mutation. The off-host-confirmed follow-up validates ownership and the prepared output, reuses it without npm or CMS rebuild, and verifies the backup digest. Later commands reacquire the process-scoped flock; the journal and verified fence preserve ownership across process loss. After closure, checkpoint WAL and verify DB handles before capturing and confirming the DB/media backup. Migration and static snapshot/build run after the fence; static build uses the prepared web dependencies.
4. **Bound host work:** CMS migration/audit and static snapshot/build run on the server as the configured unprivileged user. Root is limited to configured gate/unit/release operations. Reuse Nginx locations, validate with `nginx -t`, and restore the previous gate file if validation fails. A closed fence survives process loss and reboot.
5. **Acceptance and commit:** poll health up to 20 minutes, prove the actual DB via process environment and open FD, and check media. Verify served `/release.json`, routes, and images against the same static candidate. Append `start`, `new-bundle`, and `committed`; write commit after both acceptances and before reopening writers. A pre-commit production fault keeps the fence closed; a forward fix may retry only the same admitted source and operation. DB restore or reopening from unknown/pre-journal state requires separate explicit owner approval. After commit DB restore is forbidden.
6. **Second release:** capture the current live DB/media and retain a new editor record. Check migration lineage and integrity, not equality with the first immutable backup hash.
7. **Static-only source selection:** staging194 retains its default of the exact current canonical `main` SHA with successful `Tests`, `Lint and Typecheck`, `Security`, and `Lighthouse CI` push runs and all required jobs successful. The shared tag-based production-static workflow (`--release-tag` plus validated in-memory Release admission) defaults to the green exact SHA on canonical `main` at operation start and allows an explicitly selected older stable GitHub Release only when the same four workflows pass for that exact SHA and existing compatibility checks pass. Record the selected source SHA, Release identity, and run/attempt evidence; this workflow does not cancel or replace its admitted SHA when `main` later advances. The legacy direct production-static `static-main` path without `--release-tag` retains its current-main pre-switch check. Reuse the read-only sealed CMS/content/media capture and static build checks; do not prepare or activate a CMS candidate, fence CMS writers, or change CMS code, service, environment, DB, uploads, roles, or users. Switch only `currentStatic` atomically, record the exact prior tree for explicit rollback, and keep paired staging194 admission and ordinary production admission separately scoped.

## Acceptance scenarios

- **First release:** exact staging source/run admitted; real DB/media backup bytes verified off-host; CMS and static health, provenance, process DB, media, and served candidate proofs pass; commit precedes reopen.
- **Initial production:** exact current main/run admitted; a truthful production-bound server-DB proof and prod/payment build use one fixed operation ID; offline browser checks and served release/routes/images match the frozen candidate; commit consumes the ID permanently before reopen.
- **Staging pre-commit recovery:** acquisition interruption changes no data/code; failures after closure leave the fence active; retry under the same operation ID or explicit recovery verifies/restores the old pair; post-commit DB restore refuses. This scenario applies to staging194 only.
- **Second release:** a new editor record/media remains served and migration ledger is unchanged.
- **Staging194 main static-only:** exact current `main` SHA and all four CI gates pass; the sealed current CMS capture and static candidate pass local and browser checks; only the static pointer changes, while CMS and its live data remain byte/state-identical; explicit rollback restores the exact old static tree.
- **Production static-only:** under the shared tag-based operator workflow, the green current `main` SHA is fixed at operation start or an operator explicitly selects an older stable GitHub Release whose exact SHA passes all four CI gates and compatibility checks; a fresh read-only production DB/media capture and static candidate pass local and browser checks; a later `main` advance does not change or cancel the tag-admitted SHA. The legacy direct no-tag `static-main` path continues requiring its source SHA to remain current through the pre-switch check; only the production static pointer changes, while CMS and its live data remain unchanged; the separate production-static journal supports explicit rollback.

## Risks

Current CI evidence is stale or failed, and disk inspection cannot prove loaded Nginx behavior. These facts block rehearsal admission; demo success will not establish production readiness.

8. **Shared site admission:** CMS refresh and restore, deployment, recovery, and cleanup use the existing destination flock. Under that lock they check existing unresolved operation evidence before changing site state; the existing operation journal lock remains internal. Preserve current and contract-protected rollback targets during cleanup.

9. **Explicit cancellation of an unclaimed refresh:** An authenticated content administrator can request `cancel-starting` with the exact `pid` and `refreshOperationToken` read from the protected local refresh state. Under the destination flock, the handler cancels only the matching unswitched record with status `running`, phase `starting`, and no worker PID; an acquired worker or a changed record is never cancelled. A worker still waiting for the lock must recheck its intent before capture and exit if it was cancelled. This action can cancel a live pending launch, so it is never automatic. The token stays out of GET responses, URLs and logs; do not expose it in shell history. A cancelled start is recorded as failed before a new attempt is admitted.
