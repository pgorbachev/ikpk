## Goals / Non-Goals

**Goals:** сохранение содержания и статусов, согласованные поля и предсказуемый редакторский сценарий, проверяемая миграция и возврат к прежней версии.

**Non-Goals:** изменение публичных URL, платёжного процесса, регистрационных ссылок и идентичности преподавателей; ручная редактура всего контента без участия владельца; изменение production в рамках подготовки предложения.

## Decisions

1. **Смысл, а не стили.** Сохранить отдельные смысловые поля, в них безопасный ограниченный rich text; сайт отвечает за CSS и заголовки. Новые поля и правила извлечения уточняются инвентаризацией всех фактических шаблонов, образец не считается универсальным. Не применять один regex или безусловное удаление HTML: 125 описаний обёрнуты legacy-разметкой, один iframe требует оценки, в эталоне внутри старые формы и полезный текст. Извлечение классифицирует элементы, сохраняет исходник и строит сопоставление текста, ссылок и медиа; неизвестные элементы блокируют автоматический перенос этой записи. Документы уже имеют отдельную модель: второй источник фактов не создаётся. Визуальные макеты и мобильные состояния согласовать до кода; действующая политика санитизации остаётся единственной.
2. **Продолжительность.** `seminar.duration` остаётся nullable text default, `schedule_entry.duration` nullable override. Публичный effective value: непустой override → опубликованный default → «Продолжительность не задана». Это presentation fallback; никогда не хранить её в БД или подменять ею snapshot value. Удалить только required-duration CMS guards и snapshot violation, сохранив проверки остальных полей/relations. Сайт должен применять один helper во всех existing consumers (seminar page, schedule/pricing, homepage modules, preview): сейчас `shortDuration` возвращает пустую строку, карточка скрывает значение, а schedule label строит `(... (-))`. Не выводить часы из дат и не назначать значения данным 321/404/409; их nullable значения сохраняются. Отдельная approved VM-4 запись о сохранении пустоты остаётся фактом решения, а не вычислением и не отменяется. В legacy migration сохранить непустые исходные overrides/defaults; неоднозначные значения не сводить к первому/последнему. Пустой duration не требует exception report, owner approval или registry entry.
3. **Исторический registry без rebind.** Не менять exact sealed registry bytes, SHA, root manifest, migration receipt, step hashes/ledger для действующей staging cohort. Для старого pinned snapshot/registry сначала сверять исходные полные bytes/digest и использовать прежний verifier без переписывания списка. Только его точные известные `missing-duration` элементы считаются tombstones; они не разрешают violations. Новые snapshot-contract v2 captures несут только активные exceptions и не генерируют duration entries. Неизвестные, повторные или подменённые entries остаются fail-closed. Это позволяет продолжить inherited cohort без отдельной registry rotation/rebind. `paid-zero-price` остаётся активным и по-прежнему требует точного доверенного исключения. Для нового snapshot/cohort генератор формирует только ещё нужные price exceptions; registry/source proof всё равно проверяются обычным механизмом.
4. **Платность и место.** Существующий переключатель бесплатности остаётся: платное проведение с незаполненной ценой можно сохранить и опубликовать, на сайте показывается «Цена уточняется»; цена больше нуля выводится как сумма. Ноль для платного проведения противоречив и отклоняется при сохранении и публикации; отрицательная цена недопустима. Бесплатное — 0; при переключении обратно на платное ноль очищается в пустую цену. Наличие исторических несоответствий не делает запись бесплатной и не снимает её с публикации. Реестр исключений и проверка цены остаются строгими и независимыми от optional duration. Неопубликованные преподаватели при съёме разрешаются по действующей спецификации. Признак онлайн — boolean `isOnline` у проведения с default false, `city='Онлайн'` преобразуется только при точной проверенной семантике; иные варианты — исключение. Административная подпись выводит «Онлайн», а не ошибку пустого города. Сроки и сертификаты из текста не интерпретируются автоматически.
4. **Преподаватели и связь.** Новые назначения проверяются сервером по логическим document ID, прежнее назначение разрешено сохранять без расширения списка доступных для выбора. Учесть изменения draft/published, порядок, удаление и прямой API. Фиксация семинара после первого сохранения обеспечивается сервером, включая обратную relation; миграционный оператор действует отдельным контролируемым путём, а не флагом в пользовательском запросе. Стандартный modal create и несохранённый родитель требуют технического прототипа; запрещено предполагать, что одно свойство схемы обеспечивает read-only и возврат. Временная несовместимость с импортом и прежними клиентами разрешается до включения нового правила; доверенный импорт должен соблюдать его либо быть специально ограниченным и проверенным миграционным путём.
5. **Соседние изменения.** Блокер реализации: выполнить изменения requirement-level пересечений с `seminar-management-ux` (перенос, fallback преподавателей, relation-create, имя) и `cms-content-authoring-and-migration` (обязательный город для всех форматов, пустой черновик проведения без семинара, поля и контент). Архивировать сначала `cms-content-authoring-and-migration`, затем `seminar-management-ux`, затем этот change; до реализации проверить этот порядок на изолированной копии и обновить соответствующие дельты так, чтобы после архивирования не появилось противоречивых требований. Самостоятельная новая capability не заменяет корректировку соседних изменений. Сохранять требования `rich-content-safety`, `cms-content-source`, адреса, обновление сайта и документы. Проверять применимость архивированием в отдельном одноразовом worktree после определения порядка.

## Risks / Trade-offs

- [Неизвестные шаблоны и вложения] → классификация всех записей, сохранение исходников, проверка человеком и повторяемая сверка; блокировать непроверенные преобразования.
- [Разные draft и published] → план и сверка по физическим версиям и логическим документам, никакой автоматической публикации черновиков.
- [Исторические аномалии против новых правил] → отдельный инвентарь и утверждённое решение на каждую; публикации и сайт не менять неявно, неизвестные состояния не трактовать как бесплатные.
- [Редакционные изменения после бэкапа] → свежий съём и сверка отпечатков непосредственно до выполнения; оговорённое окно без записи, повторный аудит при изменениях.
- [Откат потеряет новые правки] → проверенная резервная копия и обратимый план, откат базы допустим только в том же окне без новых записей; после возобновления редактирования нужен отдельный план согласования правок.

## Migration Plan

1. Подготовить воспроизводимый read-only аудит на свежем согласованном снимке: отдельные версии, связи, аномалии цен, городов и продолжительностей, вся rich-text разметка и документы. Идентифицировать и сохранить источник и хеш; не размещать БД или персональные данные в публичном репозитории.
2. Для каждой записи подготовить соответствие источника целевым полям, список неизвлечённых фрагментов, ссылок и медиа и отчёт расхождений. V2 не нормализует пустую строку duration в NULL и наоборот; byte/value-level сохранение этих вариантов проверяется отдельно. Получить решения редактора по неоднозначностям цены (сохранить подтверждённую неустановленную цену SER-1 как NULL), преподавателей и содержимого. По duration точно сохранять исходные значения: `""` остаётся пустой строкой, NULL остаётся NULL; не нормализовать их друг в друга, не требовать решений по пустоте, не выбирать часы по датам, не переводить это в exception workflow. Для 321/404/409 сохранить именно исходные представления (321 — пустая строка, 404/409 — NULL); прежнее решение оставить VM-4 пустым не трактовать как решение назначить ему часы.
3. При SQLite restore production DB на staging194 сохраняется исходный DB lineage ID; создать отдельные environment/cohort/operation identities, новый source snapshot digest, migration plan/proof/receipt и root-sealed cohort. Не переносить staging receipt/plan/registry и не считать совпадение lineage ID достаточной admission. Успех этой репетиции не доказывает production migration.
4. На изолированной свежей копии проверить миграцию с обеими версиями, сравнить связи, статусы, URL, тексты, ссылки, документы, медиа, цены и количества. Запустить тесты CMS publish/save, snapshot, render и data import; повторный запуск не перезаписывает поздние правки. Проверить все публичные duration consumers на точный fallback и убедиться, что fallback не попал в поле или JSON snapshot.
5. Для data migration versioning не переписывать и не переподписывать существующий `seminar-occurrence-model-v1`: его helper/auditor payload hashes входят в manifests и inherited receipts, и старый ledger SHALL оставаться неизменным без replay. Подтверждённый capture `20261118T100436Z` (source DB SHA-256 `1ace89a76345485cda6f47f7895d8ce95a3d23f6c702fec523b40d907d90d109`, как evidence текущего снимка, не постоянный pin; lineage ID `fed2d793a84b7ffe9425a4ec51a598687a4fed8283b06762ef4537a44c5d6e1c`) имеет ровно два шага: `institute-method-author-classification-v1` SHA-256 `5a824938c8075287c33925f00b4c22f168459031ed6336a4c75812790bcc2059` и `normalize-null-documents-state-v1` SHA-256 `4be74fe36c1117035344f35fb76d5426062e4a78ada0f3002740d70e214403d0`; occurrence-model-v1 отсутствует; для eligible operation по этой lineage подготовить отдельный `seminar-occurrence-model-v2` reviewed step с собственным versioned plan/auditor, который сохраняет NULL/blank и не создаёт `duration-needs-review`. Eligibility для v2 SHALL проверять exact DB lineage ID и полный history: допускается эта lineage `fed2d793a84b7ffe9425a4ec51a598687a4fed8283b06762ef4537a44c5d6e1c` с ровно двумя приведёнными выше migration-history строками и их SHA-256. Новый capture той же lineage допустим с новым snapshot digest только после повторной проверки exact history и создания нового operation-bound plan/proof/receipt; raw source SHA `1ace89…` не закрепляется навсегда; отсутствие v1 в произвольном источнике недостаточно. Любая неизвестная/частичная история, присутствие v1 или v2, дублированный ID и несовпадение hashes — fail closed. Для v2 зафиксировать distinct step ID/hash в новом receipt/cohort binding и проверить composition verifier и следующий inherited deploy; v1 cohort проходит прежнюю exact admission и сохраняет четыре applied step identities/hashes. Запрещены повторное применение v1, изменение его hash или перенос v1 decisions в новый source.
6. Для snapshot-contract versioning сначала проверить полный hash прежнего pinned registry и sealed manifest как есть. Старые trusted `missing-duration` строки остаются историческими tombstones только в старом pinned contract и не авторизуют нарушения; новые snapshots/plans/candidates не создают duration exceptions и не обязаны повторно согласовывать пустую duration. Новый contract version принимает отсутствие duration как валидное, но продолжает применять платёжные и остальные guards. SQLite-копия production DB на staging194 сохраняет исходный DB lineage ID, но получает новые environment/cohort/operation IDs, source snapshot digest, migration plan/proof/receipt, registry и manifest; прежние staging artifacts не наследуются автоматически. Это не доказывает production acceptance.
7. Порядок rollout: сначала доставить и проверить CMS-independent snapshot/build/import consumers и публичный UI fallback, включая выбранную web revision и refresh worker, на исходных NULL/blank данных. Только после успешного snapshot/build/site refresh разрешать CMS publish/removal для пустой duration. После первой публикации NULL откат допустим только с consumer, который уже корректно его читает, либо после восстановления DB из проверенной копии; нельзя возвращать старый rejecting consumer при сохранённых NULL. На изолированной копии протестировать этот порядок, failure points и recovery.
8. На изолированной свежей копии проверить v2 migration и contract v2, обе версии документов, данные, связи, статусы, URL, тексты, ссылки, документы, медиа, цены и количества. Тестами доказать: blank duration не превращается в часы; fallback не записывается в поле или JSON snapshot; v1 hashes/ledger неизменны; inherited source не запускает migration повторно; только точная допустимая history выбирает v2; все price checks и прочие guards остаются. Для будущего production rollout подготовить отдельный план совместимой доставки CMS, snapshot/import и сайта с контрольными точками и recovery. Свежий production backup, integrity, writer fence, CMS/site acceptance и production lineage отдельны от staging194 rehearsal; этот proposal не подтверждает production readiness.

## Open Questions

Точный механизм расширения стандартного relation-create и безопасного возврата выясняется прототипом до реализации; если он не обеспечивает контракт, требуется отдельная форма. Разрешение конкретных конфликтов данных и утверждение макетов выполняется владельцем до миграции и реализации соответственно.
