## 1. Набор записей, доступных к оплате

- [ ] 1.1 Модуль вывода набора рядом с `web/src/lib/schedule-window.ts`: основные записи
  плюс дополняющие с защитой от двойного учёта, состояние `active`, актуальность по
  **опорной дате аргументом**, и цена пригодна — **положительное целое** при снятом признаке
  бесплатности.
- [ ] 1.1d Горизонт берёт значение существующего клиентского срока удержания, а не объявляет
  своё; тест равенства всех копий срока (`payments/src/app.ts` и `web/src/scripts/payment-form.ts`
  уже держат его дважды независимо — третья копия нарушит довод, которым ограничение
  обосновано).
- [ ] 1.1a Тот же модуль отдаёт перечень для режима восстановления — без условий доступности,
  но **ограниченный горизонтом** (срок жизни удержания, выводится из той же константы, а не
  задаётся отдельным числом) и **проекцией из трёх значений**: семинар, дата, место. Отдельно
  от набора к оплате.
- [ ] 1.1b Отбор к оплате проверяет **непустоту каждого** из трёх значений по отдельности
  (семинар, дата начала, место). Источник этих полей не гарантирует: в схеме Strapi обязательно
  только имя записи.
- [ ] 1.1c Состояние сравнивается с `active` **положительно**, а не отсеиванием известных плохих
  значений: список известных плохих отстаёт от перечня молча. Фикстуры: пустое состояние и
  значение вне перечня. Умолчание `active` в схеме есть, но действует при создании через
  контракт, а не задним числом.
- [ ] 1.2 Условия 1–3 брать у страницы расписания дословно; правило актуальности — из
  `isCurrentOrFuture`, не выводить заново.
- [ ] 1.3 Unit-тесты фикстурами: доступная, законченная, идущая сегодня, неактивная,
  бесплатная, с нулевой ценой при снятом признаке, **с дробной ценой**, **с отсутствующей
  ценой**, **без семинара**, **без даты начала**, **без места**, **без состояния**, семинар без
  пригодной цены ни у одной записи, появление пригодной цены возвращает запись, дублирующая
  дополняющая, порядок, повторный вызов с той же опорной датой. Все перечисленные ветви
  отсутствия в текущих данных не встречаются вовсе — их проходят только фикстуры.
- [ ] 1.3a Тест-инвариант: любая запись из набора к оплате даёт форме три непустых значения.
- [ ] 1.3b Тесты перечня восстановления: запись внутри горизонта попадает, старше — не
  попадает; **неполная запись не попадает** (без семинара, без даты, без места) и вывод не
  отказывает; проекция содержит ровно три значения и не содержит цены, преподавателей,
  изображений, описания, ссылок.
- [ ] 1.4 Тест сравнения наборов: набор формы отличается от набора страницы расписания
  **ровно записями, не прошедшими собственные условия формы** (цена и полнота). Сравнивать с
  предикатом самих условий, а не со списком причин: перечисление отстаёт от предмета молча —
  так уже вышло дважды, с подписью «Бесплатно» и затем с добавлением условия полноты. Плюс
  обратная проверка: в разнице нет записи, которая прошла бы условия формы, — то есть форма не
  сужает набор по условиям, общим со страницей. Это гейт против расхождения двух источников, а
  не проверка чисел: по первому критерию числа совпадали с сырым снимком при неверном выводе.
- [ ] 1.4b Известное отклонение, проверкой не покрываемое: запись без связанного семинара
  уронила бы сборку страницы расписания — та разыменовывает связь без защиты. Сравнение
  наборов на таких данных не строить; хрупкость страницы — предсуществующая, отдельный дефект.
- [ ] 1.4a Тест: изменение подписи цены на странице расписания результат гейта 1.4 не меняет.
  Иначе запланированный фикс подписи покрасит гейт на верном коде.
- [ ] 1.5 Зарегистрировать отдельным дефектом: страница расписания подписывает «Бесплатно»
  пять платных семинаров с незаполненной ценой. Красный тест и фикс — вне этого change.

## 2. Разметка и выбор

- [ ] 2.1 Поле «Семинар» — выбор из перечня вместо текстового ввода. Запрет свободного ввода
  относится к **новой оплате**; в режиме восстановления ручной ввод трёх значений разрешён по
  действию посетителя — проверить обе половины, а не одну.
- [ ] 2.2 Данные набора встраиваются на сборке через то же средство доступа, что у
  страницы расписания, не по пути к файлу.
- [ ] 2.3 Сериализация встроенных данных экранирует `<` — приём из `web/src/lib/json-ld.ts:14`, `JSON.stringify(schema).replace(`.
- [ ] 2.4 Выбор даты для семинаров с несколькими доступными записями; до выбора дата и
  место пусты.
- [ ] 2.5 «Место проведения» и «Дата начала» — `readonly`, не `disabled` (design, Решение 1).
  Закрытость относится к значениям, подставленным системой; в режиме ручного ввода те же поля
  редактируемы — проверить оба состояния.
- [ ] 2.6 Место берётся из выбранной записи, а не из первой записи семинара.
- [ ] 2.7 Смена семинара: одна запись — заполнить оба поля; несколько — очистить и
  потребовать выбор даты.

## 3. Вырожденное состояние (роли `preview`, `stand`, `prod`)

- [ ] 3.1 Пустой набор: форма и скрипт присутствуют, отправка не предлагается, сообщение и
  способ связи показаны.
- [ ] 3.1a Роль `ci` при пустом наборе остаётся с нулём форм и без признака вырожденности —
  вырожденное состояние к ней не применяется.
- [ ] 3.2 Отдельный наблюдаемый признак вырожденности в статическом артефакте, отличимый
  от признака платёжной формы.
- [ ] 3.3 Проверка статуса и продолжение удержанной попытки работают в вырожденном
  состоянии — проверять на артефакте роли `stand`: у `preview` эндпоинт неразрешимый и
  удержаний не бывает, у `ci` формы нет.
- [ ] 3.4 Для ролей `stand` и `prod` пустой набор — **сборка проходит**, отказывает
  деплой-гейт с называнием причины. Отказ сборки недопустим: тогда артефакта, на котором
  проверяется продолжение удержания в вырожденном состоянии, не существует вовсе. Сверить с Requirement «Установленные платёжные контуры нельзя
  публиковать выключенными или перепутанными»: вырожденная форма несёт все четыре признака
  активности, поэтому существующий гейт её не отличит.
- [ ] 3.5 Для `preview` пустой набор отказом не является — иначе вырожденное состояние
  нечем проверить.

## 5. Отправка и восстановление

- [ ] 5.1 `payload()` отправляет закрытые поля в составе восьми значений — проверить, что
  блокировка их не выбросила.
- [ ] 5.2 Проверка семинара — совпадение с записью перечня, а не непустота; отправка без
  выбранной даты отклоняется, запись за посетителя не выбирается.
- [ ] 5.3 Сохранение полей попытки включает семинар, дату и место при любом элементе
  управления. Обход сегодня берёт только `input`: `web/src/scripts/payment-form.ts:266`, `querySelectorAll<HTMLInputElement>('input')` — и `select` выпал бы молча.
- [ ] 5.4 **Продолжение** начатой попытки: тройка восстанавливается дословно, без сверки с
  набором, поля закрыты, проверка перечня отправку не отклоняет. Проверять на записи,
  которой в наборе уже нет.
- [ ] 5.5 **Новая оплата** с предзаполнением из прежней попытки: сверка точной тройки;
  не совпало (записи нет, другая дата, другой город) — остальные поля сохранить, семинар не
  выбран, дата и место пусты, посетителю сказано выбрать заново.
- [ ] 5.6 Поле семинара умеет показать значение **вне перечня** — иначе продолжение по
  ушедшей записи нечем изобразить (design, Решение 6). Реализация только на `select` с
  опциями из набора это состояние не покрывает.
- [ ] 5.7 Ушедшая запись не предлагается для новой оплаты, хотя доступна для продолжения —
  проверить оба утверждения, а не одно.
- [ ] 5.8 **Режим восстановления** (design, Решения 6а, 8а, 9б): продолжение при утраченных
  значениях полей идёт по перечню **без условий доступности к оплате**, но ограниченному
  горизонтом удержания, проекцией из трёх значений и условием полноты; проверка «значение вне
  перечня» не применяется; отправка под тем же идентификатором попытки.
- [ ] 5.9 Запасной путь режима восстановления включается **действием посетителя** («не
  нахожу свою запись»), а не выводом формы из состояния данных. Отдельная фикстура: попытка по
  **неполной** записи — её в перечне нет, воспроизведение только ручным вводом. Причина: после потери значений от
  попытки остаются только идентификатор и время. Обратный переход к перечню, объявление смены
  способа ввода, перевод фокуса. Проверить, что это единственное место, где ручной ввод
  разрешён: при новой оплате он недоступен.
- [ ] 5.10 Несовпадение введённого вручную даёт серверный исход «нужна сверка», а форма
  собственного отказа не выносит.
- [ ] 5.10a Проверка заполнения не отклоняет ручной ввод за отсутствие выбранной записи —
  проверяется непустота трёх значений, а не факт выбора. Негативная проверка: вернуть проверку
  факта выбора и убедиться, что краснеет именно сценарий ручного ввода.
- [ ] 5.11 **В режиме восстановления сумма не подставляется** — историческая запись даёт
  только семинар, дату и место. Негативная проверка обязательна: вернуть автоподстановку и
  убедиться, что краснеет сценарий про изменённую посетителем сумму.
- [ ] 5.12 Сквозная проверка отпечатка, **три случая, а не один**: (1) есть идентификатор
  платежа оператора → возвращается существующая попытка; (2) платежа нет, окно дедупликации не
  истекло → повторное обращение к оператору по тому же ключу; (3) платежа нет, окно истекло →
  «нужна сверка», и это **верный** исход, а не дефект. Отдельный случай поверх этих —
  посетитель менял сумму при первой отправке.
- [ ] 5.13 Случай «запись в данных изменилась после первой отправки»: ручной ввод доступен по
  действию посетителя, распознавать изменение форма не обязана.

## 7. Гейты и приёмка

- [ ] 7.1 Тест сериализации с названием семинара, содержащим `</script>`, — **по каждому из
  двух блоков отдельно**: в наборе к оплате и в записи, присутствующей **только** в наборе
  режима восстановления. Проверка одного блока про второй не говорит ничего. Утверждать и по
  тексту артефакта, и по **разобранному** документу: совпадение по тексту говорит об
  экранировании, но не о целостности документа. На корректных данных безопасная и небезопасная
  сериализация дают одинаковый вывод, поэтому вредоносное значение обязательно.
- [ ] 7.2 Негативная проверка каждого нового гейта: нарушить поведение в своём worktree,
  убедиться, что покраснел **именно он** — судить по имени упавшего теста, не по цвету
  прогона; мутация записана командой или патчем плюс два числа.
- [ ] 7.3 Измерить вес `/oplata` до и после встраивания данных, сверить с бюджетами
  Lighthouse.
- [ ] 7.4 Локальные гейты в `web/`: `lint`, `typecheck`, `build`, `test`, `test:build`,
  `test:e2e:payment-stand`, `test:e2e:payment-preview`.
- [ ] 7.5 `./bin/check-spec-refs` локально — гейт требует фрагмент в кавычках рядом с любым
  номером строки, и на артефактах без кода он тоже применяется.
- [ ] 7.6 Ревью кода двумя независимыми исполнителями, не автором реализации.
- [ ] 7.7 `./bin/openspec validate --all --strict --no-interactive` плюс проверка
  применимости дельты применением в одноразовом worktree.
- [ ] 7.8 Архив change, требования переехали в `openspec/specs/online-payment/`.
