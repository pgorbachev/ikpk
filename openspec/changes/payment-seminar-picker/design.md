## Context

См. `proposal.md` — «Why». Здесь только то, что нужно для объяснения подхода.

Форма оплаты — статическая разметка Astro (`web/src/components/payment/PaymentForm.astro`)
плюс клиентский скрипт (`web/src/scripts/payment-form.ts`). Скрипт собирает тело запроса,
читая значения **по имени поля** (`payload()`) — не через `FormData`. Это существенно для
выбора способа блокировки: `disabled`-поля `FormData` не включает, а чтение по `.value`
включает. То есть неверный выбор здесь ломает контракт не в браузере, а в отпечатке
идемпотентности на сервере.

В текущем дереве `getScheduleEntries` загружает тип расписания из снимка
(`web/src/lib/data.ts:120`, `const records = loadSnapshot().content.types[type];`), нормализует
записи и добавляет имена преподавателей (`web/src/lib/data.ts:396`, `if (!_schedule) _schedule = loadJson<ScheduleEntry[]>('schedule_entries.json').map(normalizeScheduleEntry).map(withSeminarTeachers);`).
Страница расписания получает этот набор и фильтрует его по состоянию и актуальности
(`web/src/pages/raspisanie-i-tseny.astro:64`, `.filter((entry) => entry.status === 'active' && isBeforeStart(entry, todayDate))`).
Текущая реализация не объединяет основной список с отдельным списком дополнений. Исторический
замер 23.08.2026 описан отдельно в proposal и относится к составу данных и коду на ту дату.

## Goals / Non-Goals

**Goals.** Вывод набора — чистая функция с опорным моментом аргументом, проверяемая
фикстурами, дословно совпадающая с набором страницы расписания по общим условиям.
Блокировка полей, не выбрасывающая значения из запроса. Обязательный выбор конкретной
записи вместо догадки.

**Non-Goals.** Не меняется состав восьми полей запроса, не меняется состав полей
отпечатка, не вводится рантайм-запрос расписания из браузера, не трогается серверная часть
платежей.

## Decisions

### Решение 1: дата — `readonly`, а не `disabled`

`disabled` исключает поле из `FormData` и убирает его из порядка обхода клавиатурой, а
экранный чтец объявляет его «недоступным». Значение при этом остаётся в `.value`, то есть
наш `payload()` его прочитает — и дефект был бы невидим в тестах транспорта, но проявился
бы у любого, кто позже перепишет сборку тела на `FormData`. `readonly` сохраняет поле в
обходе, объявляется как «только для чтения» и не влияет на сериализацию.

Отвергнуто: `disabled` (см. выше); скрытое поле-дублёр рядом с показанным неизменяемым
текстом — два места хранения одного значения расходятся, и расходятся молча.

### Решение 2: перечень семинаров и записей встраивается в разметку как данные, а не как готовый список опций

Записи нужны скрипту после выбора семинара, поэтому связь «семинар → его доступные записи»
должна быть доступна в браузере целиком. Встраивается блок данных (семинар, его записи с датой,
ценой, без места), из которого скрипт строит и перечень семинаров, и выбор даты. Исторический размер по
снимку 23.08.2026 — 56 записей, доступных к оплате.

Режим восстановления требует **второго** блока, и подмешивать его в первый нельзя: иначе новая
оплата получила бы недоступные записи. Второй блок ограничен горизонтом (срок жизни удержания,
14 суток — исторический замер 23.08.2026: 64 записи из 65) и **проекцией двух значений**:
семинар и дата. Место не собирается, не показывается и не используется для различения записей.
Ограничения не косметические — без них это неограниченная публичная копия истории расписания в
разметке каждой страницы оплаты, растущая с каждым событием.

**Два блока — это две поверхности сериализации, а не одна.** Проверка экранирования на первом
про второй не говорит ничего: запись, попадающая только в набор восстановления, первым блоком
не покрывается. Отсюда отдельный интеграционный случай с `</script>` в такой записи, с
проверкой и текста артефакта, и разобранного документа: совпадение по тексту говорит об
экранировании, но не о целостности документа.

Отвергнуто: строить `<option>` на сборке и подтягивать записи отдельным запросом — вводит
рантайм-источник ради данных, которые уже есть на сборке.

Отвергнуто: класть в разметку все комбинации «семинар + дата» одним плоским перечнем —
посетитель выбирал бы из 56 позиций вместо 43 (исторический замер 23.08.2026), и решение владельца «сначала семинар, потом
дата» не выполнялось бы.

### Решение 3: вывод набора — отдельный модуль с опорным моментом аргументом

Новый модуль рядом с `web/src/lib/schedule-window.ts`; правило актуальности берётся из
`isBeforeStart(entry, now)` из согласованного `seminar-start-visibility`, а не выводится
заново. Граница — `now < startsAtInstant`; опорный момент — параметр. Причина не в чистоте:
проверка, сравнивающая с `new Date()`, краснеет от хода времени при исправном коде, и в
проекте это уже случалось дважды (гейт статуса семинара, гейт `catalog-data`).

Сборка встраивает данные из снимка, а общий механизм актуальности обновляет набор в
браузере при загрузке, наступлении начала и возвращении вкладки. Перед отправкой новой
попытки проверяется актуальность выбранной записи; истёкший выбор очищается с сохранением
остальных полей, другая дата автоматически не выбирается. Пустой набор включает
существующее вырожденное состояние. Восстановление, продолжение и проверка статуса
созданной попытки работают по прежнему содержимому, независимо от новой границы.

### Решение 4: подстановка суммы срабатывает на смену выбранной записи, а не на каждое событие формы

Иначе правка посетителя затирается при любой перерисовке. Признак — изменение выбранной
записи, а не «поле пусто».

### Решение 5: критерий — предикат над ценой, не подпись в интерфейсе

**Исправлено по находке повторного ревью.** Прежняя редакция различала `isFree === true`
(«платить нечего») и `newPrice === 0 && !isFree` («цена не указана») и допускала вторые к
оплате. В исторической production-ревизии до отдельного исправления подписи страница расписания обе подписывала одинаково: `web/src/pages/raspisanie-i-tseny.astro@52f17dece7a62c60cc1f9546cd5e9a25eda6668f:136`, `priceLabel: entry.isFree ? 'Бесплатно' :` — и вторая ветвь тернарника отдавала то же слово, потому что `web/src/lib/data.ts@52f17dece7a62c60cc1f9546cd5e9a25eda6668f:412`, `if (price === 0) return 'Бесплатно';`. Тернарник тогда был избыточен: на нуле обе ветви давали «Бесплатно», то есть страница
**не различала** эти случаи в принципе. Это свидетельство о прежнем дефекте, не описание текущего поведения после hotfix.

Значит форма, допускающая запись без цены, просила бы денег за то, что сайт объявляет
бесплатным.

**Третий круг ревью показал, что и это решение было сформулировано неверно — через подпись.**
Критерий «страница показывает цену» привязан к тексту, который change сам же требует
исправить: после исправления подписи проверка покраснела бы на верном коде. Признак проверки
не должен зависеть от предмета, который она требует изменить, — а именно так у нас уже
ломались гейты раньше.

Критерий переформулирован на своих основаниях: **цена — положительное целое число рублей при
снятом признаке бесплатности.** Основание не в подписи, а в том, что сумма платежа обязана
быть положительным целым, и запись с непригодной ценой в закрытом перечне — тупик: выбрать
можно, отправить нельзя. Fail-closed: как только данные исправлены, запись войдёт в перечень
без правки спеки.

**Дробная цена входит в тот же запрет, и это не предусмотрительность впрок.** Схема
хранилища объявляет цену типом `decimal`
(`cms/src/api/schedule-entry/content-types/schedule-entry/schema.json:43`, `"price": {`),
поэтому `1500.5` данными допускается, а форма принимает только целые рубли. В снимке на
23.08.2026 нецелых положительных цен ноль — то есть ветвь непройденная, и проверять её надо
фикстурами (дробная, отсутствующая), а не наблюдением над текущими данными.

Историческая цена решения по замеру 23.08.2026: уходили 5 записей, и два семинара исчезают из формы целиком (56/43
против 61/45 по первому критерию). Ветвь «цены нет — поле пустое» из требования о сумме
убрана как недостижимая, но запрет подставлять ноль оставлен: он проверяем на искусственных
данных, а доверие к смежному требованию — нет.

**Подпись «Бесплатно» у платного семинара — дефект страницы расписания, и он не в объёме
этого change.** Все пять записей — платные семинары института с незаполненной ценой.
Исправление подписи идёт отдельным дефектом через красный тест; здесь фиксируется только
непротиворечивость формы.

### Решение 6: продолжение попытки и новая оплата сверяются по-разному

Новая оплата сверяет пару «семинар + дата» с доступным набором. Другая дата не подставляется,
а изменение города на совпадение не влияет. Venue нового запроса всегда null; старое место
не наследуется. ID записи не добавляется в сохраняемые поля.

Продолжение прежнего ID берёт семинар и дату дословно из снимка, без сверки с расписанием,
включая прежнюю пустую дату. Доступный исторический venue остаётся внутренним значением
снимка `sessionFields` по ID; поля места, скрытого input и ручного ввода нет. Последовательные
повторы, подтверждение дубликата и переназначение канонического ID сохраняют точный снимок
своей попытки. Переключение удержаний не смешивает места. Полный восьмипольный серверный
HMAC сохраняется; новая миграция или серверный режим не вводится.

Историческая находка ревью сохраняется: запись уходит из набора раньше, чем истекает
удержание. Поэтому перечень не может блокировать продолжение. Поле семинара должно
показывать сохранённое значение вне набора — отдельным неизменяемым представлением
или опцией только для продолжения; для новой оплаты эта запись недоступна.

Граница разных ID с null и старым непустым местом принята владельцем 2026-10-21 в
remove-payment-venue. Остальные семь полей могут совпадать, но полные HMAC различаются,
включая запросы старой кешированной формы. Это не меняет защиту при совпадении полного
отпечатка или при повторе своего ID.

### Решение 6а: режим восстановления, когда значений полей нет

Историческая находка: закрытый перечень блокировал продолжение после утраты снимка,
хотя постоянное хранение полей запрещено. В восстановлении перечень не фильтруется
по доступности к оплате, но ограничивается горизонтом удержания и полнотой семинара и даты.
Проекция содержит только эти два значения. Место не требуется и не запрашивается.

Ручной ввод семинара и даты включается действием посетителя с обратным переходом,
объявлением смены режима и переносом фокуса. Дата старой попытки может быть пустой.
По одному ID и времени форма не определит, изменена или удалена запись расписания.
Отправка остаётся под прежним ID. При утраченном месте используется null; если старая
попытка имела непустое место, допустима прежняя безопасная сверка. Форма не снимает
удержание, не создаёт новый платёж автоматически и не обещает воспроизведения неизвестного HMAC.

### Решение 7: набор к оплате = набор страницы расписания минус не прошедшие собственные условия формы

**Историческая находка ревью 23.08.2026.** Тогда страница объединяла основной набор
с `scheduleSupplements` и фильтровала active; первая редакция picker это не учитывала.
Сегодня страница получает набор через `getScheduleEntries`, фильтрует и сортирует его
без отдельного списка дополнений. Требование — пользоваться текущим общим средством
доступа и теми же условиями, а не возвращать удалённый механизм объединения.

Поэтому условия 1–3 берутся у страницы дословно, а собственных условий формы **два**: цена
записи должна быть положительным целым числом рублей при снятом признаке бесплатности
(Решение 5) и семинар с датой должны быть непусты (Решение 9а). Слово «одно»
здесь оставалось от редакции до появления условия полноты — найдено седьмым кругом ревью. **След предыдущей редакции здесь был найден четвёртым кругом ревью:** стояло
«если страница объявляет у неё цену», то есть тот самый критерий через подпись интерфейса,
который Решение 5 и отменило.

**Числа первой редакции были верны случайно, и это важнее самой ошибки.** Там стояло «61
актуальная запись, 45 семинаров» — из сырого снимка. Видимое расписание даёт 63 и 47; две
добавочные записи обе бесплатные, поэтому после исключения бесплатных получалось снова 61 и
45. Верное число из неверного вывода: совпадение подтверждало бы неверный критерий, если бы
кто-то сверил только итог. После исправления критерия (Решение 5) набор — 56 и 43, то есть
совпадение с сырым снимком исчезло само. Проверка расхождения наборов введена затем, чтобы
аргументом было расхождение по составу, а не совпадение итога.

**Формулировать её надо предикатом самих условий формы, и я дважды написала перечисление.**
Сначала «расходятся ровно бесплатными» — устарело от смены критерия цены. Затем «ровно
записями с непригодной ценой или признаком бесплатности» — устарело от добавления условия
полноты (Решение 9а): исторически она включала город; по решению 2026-10-21
проверяются только семинар и дата. Правильная форма — «разница = записи, не прошедшие собственные условия
формы», плюс обратная проверка «в разнице нет записи, прошедшей эти условия». Тогда проверка
не отстаёт от предмета при следующем изменении условий.

**Сравнимость ограничена, и это надо знать до написания теста.** Запись без города страница
показывает («Уточняется»); после удаления места форма тоже допускает её при прочих
пригодных данных. А запись без
связанного семинара страница обработать не может: она разыменовывает связь без защиты, и такие
данные из будущего источника уронят сборку страницы раньше сравнения наборов. Хрупкость
предсуществующая — названа как известное отклонение, отдельный дефект, а не молча обойдена.

Все 63 записи исторического снимка 23.08.2026 имеют `status: 'active'`, то есть сегодня этот фильтр не
убирает ничего. Он всё равно нормативен: критерий не должен зависеть от того, что данные
сейчас однородны, иначе первая неактивная запись в CMS разведёт форму с расписанием молча.

### Решение 8: пустой набор — вырожденное состояние формы плюс отказ публикации установленного контура

**Исправлено по находке ревью.** Прежняя редакция говорила «отправка не предлагается», не
разбирая двух последствий.

Первое: убрать разметку формы нельзя. Скрипт останавливается целиком, если её нет —
`web/src/scripts/payment-form.ts:98`, `!actions || !panel) return;` — а восстановление попытки,
проверка статуса и продолжение удержанной оплаты идут тем же скриптом. Посетитель,
начавший платёж, потерял бы единственный способ узнать его исход. Значит форма и скрипт
остаются, а закрывается только путь новой оплаты.

Второе: для `stand` и `prod` такое состояние публиковать нельзя. Requirement
«Установленные платёжные контуры нельзя публиковать выключенными или перепутанными»
требует активную форму, а признак активности — наблюдаемый (признак формы, объявленная
база, равенство базы ожидаемой, роль `stand`/`prod`). Вырожденная форма все четыре условия
несёт, то есть гейт счёл бы её работающей. Поэтому пустой набор в этих ролях — отказ
**деплой-гейта** при успешной сборке (уточнено Решением 8а; первая редакция допускала и отказ
сборки, что делало вырожденное состояние непроверяемым). Для `preview` отказом он не является:
установленного контура у неё нет, а вырожденное состояние надо на чём-то проверять.

**Третье, найденное вторым проходом ревью: у роли `ci` формы нет вовсе.** Основной контракт
требует от неё ноль форм и ни одного объявленного эндпоинта, поэтому «сохранить форму при
пустом наборе» ей предписать нельзя — прежняя редакция требовала этого безусловно и тут же
называла пустой набор допустимым для `ci`, то есть противоречила себе и основной спеке.
Область требования сужена до ролей, у которых форма существует: `preview`, `stand`, `prod`.

Отсюда требование отдельного наблюдаемого признака вырожденности: без него «форма есть» и
«оплатить нечего» неразличимы в артефакте, и любая проверка активности отвечает не на тот
вопрос, что задан.

### Решение 9: сериализация встроенных данных экранирует `<`

Названия семинаров и даты приходят из CMS; место не входит в платёжную проекцию. `</script` внутри строкового значения
закрывает элемент раньше разбора, и остаток данных попадает в документ как разметка.
Берётся приём, уже применяемый для структурных данных сайта: `web/src/lib/json-ld.ts:14`, `JSON.stringify(schema).replace(`.

Проверка обязана содержать значение с `</script>`: на корректных данных безопасная и
небезопасная сериализация дают одинаковый вывод, и без такого значения проверка не
отличает их — тот же класс, что «гейт по выводу вместо гейта на проводку», уже
встречавшийся в этом проекте на JSON-LD.

### Решение 10: сохранение полей попытки читает не только `input`

Поле семинара становится select. Сохранение должно включать его и дату независимо от
типа элемента. Внутреннее место старой попытки сохраняется отдельно от обхода DOM в том же
сессионном снимке по ID, иначе повторное сохранение после удаления input его потеряет.
Проверяются именно последовательные запросы, а не только вид восстановленной формы.

### Решение 6б: в режиме восстановления сумма не подставляется

Даже после отдельного одобрения цены её подстановка относится только к новой оплате.
В восстановлении запись даёт семинар и дату, а сумму посетитель воспроизводит сам:
раньше он мог изменить предложенную цену. Подстановка поверх введённого изменила бы HMAC.
Проверка полного запроса включает семь воспроизводимых значений и venue: прежний null
либо доступное внутреннее место своей попытки. При утраченном непустом venue совпадение
не обещается. Исторические находки о цене и полноте отпечатка этим сохраняются.

### Решение 8а: сборка установленного контура при пустом наборе проходит, отказывает деплой-гейт

**Найдено пятым кругом ревью.** Решение 8 разрешало «отказ сборки **или** деплой-гейта». При
выборе отказа сборки требование «продолжение удержанной попытки работает в вырожденном
состоянии» оставалось без единого артефакта, на котором его можно предъявить: у `preview`
эндпоинт намеренно неразрешимый — `web/src/lib/forms.ts:78`, `export const PAYMENT_ENDPOINT_DEMO` — поэтому удержаний там не бывает; у `ci` формы нет; а `stand`/`prod` не
собрались бы. Обещание без предмета проверки.

Разделено: сборка `stand`/`prod` с пустым набором **проходит**, публикацию отказывает
деплой-гейт с называнием причины. Вырожденное состояние формы проверяется на `preview`,
продолжение удержания — на артефакте `stand`, где сервер есть.

### Решение 9а: полнота — семинар и дата

Схема Strapi требует имя записи, но не гарантирует связанные семинар и дату. Отбор
проверяет оба значения отдельно; неполная запись исключается без отказа вывода.
Историческая редакция требовала ещё город. Решение 2026-10-21 отменяет именно это условие:
запись без места пригодна при прочих условиях. Новые количества записей здесь не измерялись.

### Решение 6в: исход дословного повтора определяет сервер, а не форма

**Найдено пятым кругом ревью, и это была ошибка в обещании, а не в механике.** Сценарий
утверждал, что дословный повтор восьми значений даёт существующую попытку **без** «нужна
сверка». Но принятое требование о безопасном продолжении без известного платежа прямо
предписывает «нужна сверку», если у записи нет идентификатора платежа оператора и истекло окно
дедупликации по ключу идемпотентности (24 часа); так же устроен код
(`payments/src/app.ts:800`, `if (age > DEDUP_MS) {`). Удержание живёт 14 суток, то есть окно
истекает **внутри** срока, когда продолжение ещё законно, — случай достижим, а не гипотетичен.
Неизвестная версия ключа даёт сверку по тем же основаниям.

Сценарий разложен на три: с существующим платежом, без платежа внутри окна, без платежа за
пределами окна — и в третьем «нужна сверка» назван **верным** исходом. Форма отвечает за
возможность воспроизвести содержимое, за исход отвечает сервер.

### Решение 9б: полнота восстановления и состояние источника

Перечень восстановления тоже требует семинар и дату; неполную запись посетитель
воспроизводит вручную. Место в проекцию не входит и не влияет на полноту.

Историческая поправка ревью: схема имеет умолчание active. Оно действует при создании
через контракт, а не исправляет импортированные данные задним числом. В наборе новой
оплаты сохраняется положительное сравнение с active; неизвестное состояние не допускается.

### Решение 6г: исключение восстановления находится рядом с запретом

Историческая находка ревью: безусловный запрет свободного ввода конфликтовал с ручным
восстановлением. Теперь запрет и исключение стоят вместе в существующем требовании
«Выбор семинара и записи заполняет дату начала» и в проверке заполнения.

Picker больше не меняет полный блок «Состав полей формы оплаты»: его единственным
автором среди двух дельт остаётся remove-payment-venue. Поэтому архив picker не может
вернуть восьмое UI-поле, а архив удаления места — отменить выбор и восстановление picker.

## Risks / Trade-offs

**Оплата семинара вне расписания становится невозможной** → решение владельца от
23.08.2026, принятое при названном последствии. Обходной путь у института остаётся
нетехнический: куратор высылает ссылку на оплату, созданную иначе. Если это окажется
частым случаем, возврат свободного ввода — отдельный change, а не тихая правка.

**Исторический замер 23.08.2026: два семинара исчезали из формы целиком** → у них нет цены ни у одной записи, и страница
объявляет их бесплатными. Смягчение: заполнение цены в данных возвращает их без правки
спеки, а требование о расхождении наборов делает потерю измеримой, а не случайной. Долг
назван отдельно: подпись «Бесплатно» у платного семинара — дефект страницы расписания.

**Бесплатные события выпадают из формы совсем** → по замыслу: платить нечего. Риск в
другом — если у института появится бесплатное событие с обязательной регистрацией, форма
оплаты его не покажет, и связи между «запись» и «оплата» посетитель не увидит. Смягчение:
страница расписания их показывает.

**Ошибка в данных расписания становится непреодолимой для посетителя** → поля закрыты, и
исправить неверную дату он не может. Смягчение: набор строится на сборке из того же
источника, что страница расписания, то есть ошибка видна на странице раньше, чем в форме.

**Расписание к моменту оплаты устарело** → между сборкой и оплатой проходит время.
Общий механизм скрывает уже начавшиеся сеансы по текущему моменту даже в ранее
опубликованной странице. Изменённые или новые записи CMS требуют нового снимка и публикации;
без JavaScript или при неверных часах устройства ограничение статической архитектуры
сохраняется. Продолжение начатой попытки от исчезновения записи не зависит (Решение 6).
Серверная проверка расписания остаётся за границами этого change.

**Подставленная цена меняет бизнес-процесс** → согласование с заказчиком, до него
подстановка суммы отделима (`proposal.md`, «Impact»). Технически это одна задача из
списка, а не переплетённая с остальными.

**Рост веса страницы `/oplata`** → встроенные данные расписания. Смягчение: измерить в
`test:build` и сверить с бюджетами Lighthouse; при заметном росте — сократить состав полей
встраиваемой записи до используемых.

## Migration Plan

Отдельного развёртывания не требует: изменение целиком в статической сборке `web/`.
Откат — возврат коммита; серверная часть платежей не затрагивается, поэтому откат не
оставляет несовместимых записей в хранилище идемпотентности.

Порядок: красные тесты по спеке в отдельной сессии → реализация → ревью двумя
независимыми исполнителями → архив.

## Open Questions

Отдельное согласование автоподстановки цены (tasks 0.1) по-прежнему не получено.
Удаление места не является таким согласованием. Город не возвращается в форму или
платёжную проекцию для различения записей; прежний вопрос о подписи города снят решением
об удалении места. Он может оставаться контекстом исходных данных расписания.
