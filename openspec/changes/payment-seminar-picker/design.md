## Context

См. `proposal.md` — «Why». Здесь только то, что нужно для объяснения подхода.

Форма оплаты — статическая разметка Astro (`web/src/components/payment/PaymentForm.astro`)
плюс клиентский скрипт (`web/src/scripts/payment-form.ts`). Скрипт собирает тело запроса,
читая значения **по имени поля** (`payload()`, строки 536–550) — не через `FormData`. Это
существенно для выбора способа блокировки: `disabled`-поля `FormData` не включает, а
чтение по `.value` включает. То есть неверный выбор здесь ломает контракт не в браузере, а
в отпечатке идемпотентности на сервере.

Расписание доступно на сборке через `getScheduleEntries()` (`web/src/lib/data.ts:289`),
тип `ScheduleEntry` уже несёт `seminar.name`, `city.name`, `startAt`, `endAt`, `newPrice`,
`oldPrice`, `isFree`. Правило «событие ещё не закончилось» реализовано в
`web/src/lib/schedule-window.ts` (`lastDay`, `isCurrentOrFuture`) и повторно выводиться
здесь не должно.

## Goals / Non-Goals

**Goals.** Вывод перечня — чистая функция с опорной датой аргументом, проверяемая
фикстурами. Один источник правила актуальности. Блокировка полей, не выбрасывающая
значения из запроса.

**Non-Goals.** Не меняется состав восьми полей запроса, не меняется состав полей
отпечатка (Решение 3а архива), не вводится рантайм-запрос расписания из браузера, не
трогается серверная часть платежей.

## Decisions

### Решение 1: `readonly`, а не `disabled`

`disabled` исключает поле из `FormData` и убирает его из порядка обхода клавиатурой, а
экранный чтец объявляет его «недоступным». Значение при этом остаётся в `.value`, то есть
наш `payload()` его прочитает — и дефект был бы невидим в тестах транспорта, но видим
любому, кто позже перепишет сборку тела на `FormData`. `readonly` сохраняет поле в обходе,
объявляется как «только для чтения» и не влияет на сериализацию.

Отвергнуто: `disabled` (см. выше); скрытое поле-дублёр рядом с показанным
неизменяемым текстом — два места хранения одного значения расходятся, и расходятся молча.

### Решение 2: перечень семинаров и дат встраивается в разметку как данные, а не как готовый список опций

Даты нужны скрипту после выбора семинара, поэтому связь «семинар → его актуальные записи»
должна быть доступна в браузере целиком. Встраивается один блок данных (семинар, его
записи с датой, городом и ценой), из которого скрипт строит и перечень семинаров, и выбор
даты. Размер по текущему снимку — 61 запись, это десятки килобайт до сжатия.

Отвергнуто: строить `<option>` на сборке и подтягивать даты отдельным запросом — вводит
рантайм-источник ради данных, которые уже есть на сборке.

Отвергнуто: класть в разметку все комбинации «семинар + дата» одним плоским перечнем —
посетитель выбирал бы из 61 позиции вместо 45, и решение владельца «сначала семинар,
потом дата» не выполнялось бы.

### Решение 3: вывод перечня — отдельный модуль с опорной датой аргументом

Новый модуль рядом с `schedule-window.ts`; правило актуальности берётся из
`isCurrentOrFuture`, а не выводится заново. Опорная дата — параметр. Причина не в чистоте:
проверка, сравнивающая с `new Date()`, краснеет от хода времени при исправном коде, и в
проекте это уже случалось дважды (гейт статуса семинара, гейт `catalog-data`).

### Решение 4: подстановка суммы срабатывает на смену выбора, а не на каждое событие формы

Иначе правка посетителя затирается при любой перерисовке. Признак — изменение выбранной
записи, а не «поле пусто».

### Решение 5: отсутствующая цена — пустое поле, не ноль

`newPrice === 0` при `isFree === false` означает «цена не указана» (5 из 61 записи).
Подстановка нуля дала бы поле, которое не проходит собственную проверку суммы, — то есть
форму, которую нельзя отправить, и посетителю пришлось бы догадаться стереть ноль.
`isFree === true` в текущем снимке не встречается ни у одной актуальной записи, поэтому
поведение для бесплатных семинаров этим change не определяется — см. «Open Questions».

### Решение 6: сопоставление сохранённой попытки с перечнем — по названию семинара, и это названное ограничение

Сохранённая попытка хранит значения полей, а не идентификатор записи расписания. Значит
восстановление сопоставляет по названию, и переименование семинара в CMS будет
неотличимо от его исчезновения: посетитель получит «выберите семинар заново». Это
неприятно, но безопасно — противоположный выбор (восстановить название, которого в
перечне нет) дал бы платёж по несуществующей комбинации.

Отвергнуто: хранить в попытке идентификатор записи — потребовало бы менять состав
сохраняемого, а он уже описан принятым требованием о незавершённой попытке.

## Risks / Trade-offs

**Оплата семинара вне расписания становится невозможной** → решение владельца от
23.08.2026, принятое при названном последствии. Обходной путь у института остаётся
нетехнический: куратор высылает ссылку на оплату, созданную иначе. Если это окажется
частым случаем, возврат свободного ввода — отдельный change, а не тихая правка.

**Ошибка в данных расписания становится непреодолимой для посетителя** → поля закрыты, и
исправить неверный город он не может. Смягчение: перечень строится на сборке, то есть
ошибка видна на странице расписания раньше, чем в форме; плюс требование о пустом
перечне не даёт «форму без выбора» выдать за рабочую.

**Расписание к моменту оплаты устарело** → между сборкой и оплатой проходит время.
Смягчение частичное: требование о восстановлении попытки закрывает случай исчезнувшего
семинара, но посетитель, открывший давно закешированную страницу, увидит старый перечень.
Полное решение потребовало бы рантайм-проверки на сервере платежей, а он о расписании не
знает — это отдельный объём.

**Подставленная цена меняет бизнес-процесс** → согласование с заказчиком, до него
подстановка суммы отделима (`proposal.md`, «Impact»). Технически это одна задача из
списка, а не переплетённая с остальными.

**Рост веса страницы `/oplata`** → встроенные данные расписания. Смягчение: измерить в
`test:build` и сверить с бюджетами Lighthouse; при заметном росте — сократить состав
полей встраиваемой записи до четырёх используемых.

## Migration Plan

Отдельного развёртывания не требует: изменение целиком в статической сборке `web/`.
Откат — возврат коммита; серверная часть платежей не затрагивается, поэтому откат не
оставляет несовместимых записей в хранилище идемпотентности.

Порядок: красные тесты по спеке в отдельной сессии → реализация → ревью двумя
независимыми исполнителями → архив.

## Open Questions

- **Бесплатные семинары** (`isFree === true`). В актуальном снимке таких нет, поведение
  не определено. Ответ не меняет ни спеку остальных требований, ни разбивку задач:
  добавится одна ветвь подстановки. Спрашивать до тестов не обязательно.
- **Показывать ли город рядом с датой в выборе даты**, когда записи одного семинара идут
  в разных городах. Влияет на текст элемента выбора, не на контракт.
