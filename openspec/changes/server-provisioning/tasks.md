# Задачи

## 0. Способ проверки: что чем проверяется

Заполняется до написания тестов. Без этого сессия красных тестов не сможет начать: предмет
спеки — состояние живого хоста, и цель проверки выбрана в `design.md`, Решение 2.

- [ ] 0.1 Одноразовый контейнер как основная цель: образ, способ поднятия из теста, способ
      прогона провижининга внутри него. Цель считается готовой, когда на ней проходит хотя бы
      один сценарий.
- [ ] 0.2 Отметить у **каждого** требования спеки цель проверки. По умолчанию — контейнер.
      Исключения ниже, и их ровно два; всякое третье исключение обязано быть внесено сюда,
      а не решено на месте. Прежнее исключение про откат сетевых правил уехало в
      `server-hardening` вместе со своим требованием.
- [ ] 0.3 Исключение 1 — **сохранность TLS после провижининга** (сценарий «сертификаты
      переживают провижининг»). Причина: нужен настоящий домен и настоящий сертификат. Способ:
      ручная приёмка на проде, когда прод появится; до этого сценарий отмечается непроверенным
      явно, а не считается пройденным.
- [ ] 0.4 Исключение 2 — **объём данных при резервном копировании**. Причина: на контейнере
      данных нет. Способ: ручная приёмка на стенде со снятой копией и её объёмом.
- [ ] 0.6 Свести отметки в таблицу «требование → цель → способ» и предъявить её вместе со
      спекой. Требование без отметки — незакрытая задача, а не «проверим по ходу».

## 1. Характеризация текущего состояния

Без этого «не затирать постороннее состояние» не с чем сравнивать: неизвестно, что на стенде
поставлено провижинингом, а что руками.

- [ ] 1.1 Снять фактическое состояние стенда: пакеты, учётные записи, каталоги и их владельцы,
      юниты, правила доступа, слушающие сокеты, содержимое vhost.
- [ ] 1.2 Развести снятое на три части: соответствует тексту `scripts/bootstrap-vps.sh`;
      добавлено поверх него (в первую очередь 443-блок certbot); неизвестного происхождения.
- [ ] 1.3 Записать расхождение как факт с датой — оно и есть предмет TD-22
      (`docs/tech-debt.md:1197`, `## TD-22 — Текст`).
- [ ] 1.4 Зафиксировать, кто и чем подключается к стенду сейчас, каким пользователем, и есть ли
      консоль провайдера. Наличие консоли — предусловие задачи 5.

## 2. Красные тесты (отдельная сессия, чистый контекст)

- [ ] 2.1 Тесты по сценариям спеки на цели из задачи 0. Реализация не трогается.
- [ ] 2.2 Предъявить красный прогон: отдельный push коммита только с тестами либо лог с точной
      командой и SHA.
- [ ] 2.3 Каждый сценарий получает проверку либо явную отметку из таблицы 0.6.

## 3. Идемпотентность и обращение с посторонним состоянием

- [ ] 3.1 Повторный запуск на приведённом сервере: успех, ноль изменений, изменённое печатается
      отдельно от уже соответствовавшего.
- [ ] 3.2 Три входа вместо одного: чистая машина, прерванный запуск, машина приведённая не этим
      артефактом.
- [ ] 3.3 Отказ при обнаружении постороннего состояния в управляемом предмете; обход отказа —
      явным входом и только с резервной копией. Существующее поведение
      (`scripts/bootstrap-vps.sh@3a4164fffe48246f79d7d0b0d513af59d15de59a:62`, `exit 3`) распространить на остальные предметы, а не
      заменить.
- [ ] 3.3a **Политика обращения с посторонним** у каждого управляемого предмета: `merge`,
      `refuse` или `converge` — в объявленном состоянии, а не в коде. Конфигурация раздачи —
      `merge`, иначе на стенде с 443-блоком certbot нет ни одного исполнимого пути.
- [ ] 3.3b Слияние без замены целиком: объявленные директивы приводятся к объявленным
      значениям, названные посторонние включения остаются.
- [ ] 3.4 Запись применённой ревизии объявленного состояния на сервере; отказ при попытке
      применить более старую.
- [ ] 3.5 Снятие резервной копии не считается изменением состояния — иначе идемпотентность и
      бэкап противоречат друг другу.

## 4. Один артефакт, окружения, секреты

- [ ] 4.1 Значения окружений в `deploy/environments/`: несекретные значения и имена ожидаемых
      секретов.
- [ ] 4.2 Проверка «различие выражено значением»: перечислять фактические различия и падать на
      различии, не выраженном значением.
- [ ] 4.3 TLS: записать решение явно — вне объёма, владелец назван, провижининг его не ломает.
      Домен, закрытость стенда от индексации и доступ заказчика уехали в `server-hardening`
      вместе с требованием «один артефакт на стенд и прод».
- [ ] 4.4 Секреты: чтение из окружения процесса, запрет аргументов и формы, попадающей в
      историю оболочки; владелец и режим файла секрета на сервере; изменение секрета как
      изменение состояния, печатаемое без значения.
- [ ] 4.5 Согласовать с принятой конвенцией `payments/deploy/ikpk-payments@.service:36`, `EnvironmentFile=/etc/ikpk-payments/%i.env` — провижининг проверяет наличие и режим
      серверного файла, но не создаёт его содержимого.

## 5a. Инвентарь, база, непрерывность раздачи

- [ ] 5a.1 Инвентарь ПО в объявленном состоянии: дистрибутив, перечень пакетов, правило выбора
      версий. Без него «один артефакт» не даёт одинаковости двух серверов.
- [ ] 5a.2 Клиент базы данных системы управления и каталог её данных — по окружениям. Сегодня
      клиент выбирается умолчанием: `cms/config/database.ts:5`, `const client =`.
- [ ] 5a.3 Каталог данных входит в предмет резервного копирования.
- [ ] 5a.4 Развёртывание кода системы управления и миграции схемы — **вне объёма**, отнесены к
      change, который этой системой занимается. Записать отнесение, а не подразумевать.
- [ ] 5a.5 Непрерывность раздачи: адрес отвечает во время и после провижининга, содержимое не
      подменено. Прогон без предварительно опубликованного содержимого — непройденная проверка.
- [ ] 5a.6 Право записи в конфигурацию раздачи сузить до отдельного include-фрагмента.

## 5b. Служба системы управления

- [ ] 5b.1 Учётная запись службы, `unit`-файл, объявленный локальный адрес, проксирование через
      сервер раздачи, закрытость порта снаружи. Код системы управления и миграции схемы — вне
      объёма; проверяется **объявленная служба**, годится любая программа на объявленном адресе.
- [ ] 5b.2 Каталог данных службы: расположение, владелец, вхождение в резервную копию.
- [ ] 5b.2a **Доставка собранного артефакта системы управления на сервер.** Иначе служба не
      существует: `cms deploy` — команда облачного хостинга поставщика, а не выкладка на наш
      сервер. Атомарная смена с сохранением предыдущей версии, перезапуск, проверка ответа на
      объявленном локальном адресе, возврат назад при неответе.

## 6. Резервные копии

- [ ] 6.1 Признаки успешной копии: непустая, объём и состав соответствуют предмету, читается
      тем же средством, которым будет восстанавливаться.
- [ ] 6.2 Копия снимается в том же запуске, что и разрушающее действие.
- [ ] 6.3 Названный предикат сравнения при восстановлении вместо побайтового равенства.
- [ ] 6.4 Наследовать существующий механизм (`payments/deploy/ikpk-payments-backup.sh`) либо
      отклонить с причиной. Третий параллельный механизм не заводить. Автоматическое
      восстановление не вводить: `docs/runbook-payments-backup.md:71`, `Автоматического восстановления нет намеренно`.

## 7. Проверка результата

- [x] 7.1 Перечень объявленных свойств как данные, а не как список литералов в коде проверки.
- [x] 7.2 Сверка числа выполненных проверок с числом объявленных свойств; неравенство — неуспех
      с перечислением свойств без проверки.
- [ ] 7.3 Проверка отсутствия необъявленного уехала в `server-hardening` вместе с двусторонней
      сходимостью; здесь проверяется наличие объявленного.
- [x] 7.4 Корпус слушающих сокетов из данных хоста; пустой перечень — непройденная проверка.
      Предмет здесь — закрытость порта службы системы управления, а не сетевые ограничения
      целиком: те в `server-hardening`.
- [x] 7.5 Печать места выполнения проверки; сетевая закрытость, проверенная с самого сервера, —
      непройденная проверка.
- [x] 7.6 Три исхода проверки различимы кодом выхода: несоответствий нет; несоответствия
      найдены; измерить не удалось.
- [ ] 7.7 Негативная проверка каждого нового гейта. **Цель мутаций — одноразовый контейнер, не
      стенд**: мутации здесь меняют состояние машины (открыть порт, снять запись из перечня
      привилегий, остановить службу), а `git status` про состояние хоста не говорит ничего.
      Постусловие — пересоздание контейнера и повторная проверка состояния, дающая те же два
      числа, что до мутации. «Прогнать провижининг заново» постусловием не годится, когда
      мутируется сам провижининг.
- [ ] 7.8 Каждую мутацию записать воспроизводимо: команда или патч плюс два числа — до и после.
