# Задачи

Change в состоянии `queued`. Задачи ниже — свёрнутое backlog-описание, а не план к исполнению:
детализация делается при подъёме в `active`, после сверки спеки с `origin/main`.

## 1. Предусловия подъёма

- [ ] 1.1 `server-provisioning` заархивирован, требования переехали в `openspec/specs/`.
- [ ] 1.2 Стенд работает, обновление через CMS проверено.
- [ ] 1.3 Спека сверена с `origin/main` заново: за время в очереди могли появиться основные
      спеки, которым дельта противоречит, — строгая валидация этого не видит.
- [ ] 1.4 Проверена применимость дельты применением в одноразовом worktree, а не только
      валидацией.

## 2. Права выкладки

- [ ] 2.1 Собрать фактический перечень привилегированных действий выкладки по коду
      `scripts/deploy-web.sh`, а не по её описанию.
- [ ] 2.2 Правка `scripts/deploy-web.sh` под непривилегированную учётную запись.
- [ ] 2.3 Поимённый перечень запрещённых на запись предметов, включая собственные ключи доступа.
- [ ] 2.4 Судьба нынешнего root-пути: закрыть либо оставить с названной причиной и владельцем.

## 3. Сетевые ограничения

- [ ] 3.1 Запись о способе доступа помимо сети в объявленном состоянии — предусловие.
- [ ] 3.2 Подтверждение доступности каждого объявленного открытым порта до закрепления правил.
- [ ] 3.3 Автоматический откат при неподтверждённом соединении.

## 4. Двусторонняя сходимость

- [ ] 4.1 Третье значение политики — `converge` — в объявленном состоянии.
- [ ] 4.2 Снятие учётной записи только после резервной копии её домашнего каталога.

## 5. Доверенный механизм

- [ ] 5.1 Назвать машину и сверить с машиной активного пути публикации.
- [ ] 5.2 Владелец и режим механизма и его учётных данных; недоступность на запись проверяемой
      учётной записи.

## 6. Один артефакт на стенд и прод

- [ ] 6.1 Свойства, значением не выражаемые, — поимённо с решением по каждому: TLS, домен,
      закрытость стенда от индексации, доступ заказчика.
- [ ] 6.2 Сверка объявленных состояний двух окружений, а не двух живых серверов.

## 7. Незакрытые находки прежних кругов ревью

Перенесены вместе с требованиями и не потеряны:

- [ ] 7.1 Требования, сформулированные про объём change, а не про поведение продукта
      («SHALL NOT вводиться этим change») — после архивирования такие фразы означают не то, что
      задумано.
- [ ] 7.2 Две проверки над одним корпусом с разными перечнями и разными правилами счёта.
- [ ] 7.3 Сценарии требования о доверенном механизме непроверяемы на одноразовом контейнере —
      отметить цель проверки явно.

Код launcher (получение main, сверка источника, чистое дерево, выдача учётных данных)
поставляет `manual-publication-only`; задачи 5.1–5.2 устанавливают и защищают именно этот
артефакт. Его код и тесты могут быть слиты до установки. Приёмка установки не ждёт первой
публикации или архива manual-publication-only: проверяется уже поставленный код.

## 8. Админка системы управления: TLS и кеш (перенесено из `cms-content-authoring-and-migration` 05.10.2026)

Перенесено при сведении PR #186 с `main`: модель ветки (`ADMIN_DOMAIN` с отдельным сертификатом)
не пережила переписанный провижининг, а модель `main` требованию не удовлетворяет — снипет
`/admin` вставляется в блок `listen 80` (`add_proxy_include`, `merge_vhost_directives` в
`scripts/bootstrap-vps.sh`), без `no-store`, а на хосте, где certbot разделил vhost, попадает в
заглушку перенаправления. Сегодня это не задевает ни одно окружение: на стенде снипет выключен,
прод не провижинен. Открывать админку наружу — не раньше этих задач.

- [ ] 8.1 (бывшая 7.1a) **TLS для админки и её API:** имя **либо** сертификат на адрес (Let's Encrypt с 2026
      выдаёт и такие, Certbot поддерживает — домен рекомендуется, но безусловным предусловием не
      является), автоматическое обновление с учётом короткого срока действия, перенаправление с
      незащищённого протокола, признак «только по защищённому соединению» у cookie сессии.
      Отдельным пунктом, потому что нынешний bootstrap пишет vhost с одним `listen 80`
      (`scripts/bootstrap-vps.sh@3a4164fffe48246f79d7d0b0d513af59d15de59a:72`, `listen 80;`), а HTTPS в инструкции развёртывания —
      необязательный шаг; панель в таком vhost отдаёт пароль администратора открытым текстом
- [ ] 8.2 (бывшая 7.3) Адреса админки и API получают `no-store`; общее правило для адресов вне классов на них
      не распространяется — проверка по тексту конфигурации плюс свидетельство по живой раздаче
- [ ] 8.3 Cookie сессии `strapi::session` с признаком `secure`. В ветке PR #186 это было сделано в
      `cms/config/middlewares.ts` (`cookie: { secure: env.bool('SESSION_COOKIE_SECURE', true) }`) и
      при сведении снято: на стенде админка открывается ssh-туннелем по http, и безусловный
      `secure` без проверки входа там рискует закрыть доступ. Вернуть вместе с TLS и проверить вход
- [ ] 8.4 Красные тесты лежат в `openspec/changes/server-hardening/tests/` (написаны под модель
      `ADMIN_DOMAIN`): при активации переписать под принятую модель провижининга и вернуть в
      `web/tests/`; дельту `static-serving` сверить с текущей основной спекой — она написана
      относительно её прежней редакции
