## Context

The original paired release helper prepared CMS-user-owned workspaces with identity markers and symlinks to web and CMS dependencies. See `scripts/lib/rehearsal_host.py@cc03bf9ae84bb07032463f621bc65af8088418f1:2692`, `def _prepare_paired_site_workspace`. `_cleanup_after_commit` and `cleanup-site` currently remove site and CMS releases; the timer selects a profile from the site marker, and can run with no marker. The shared publication flock serializes cooperating writers, but is released between paired commands. The operation journal and admission state therefore remain essential. The separate unmerged dependency-generation-retention proposal explicitly excludes workspace cleanup and requires retaining dependencies of supported consumers.

## Goals / Non-Goals

**Goals:** Preserve reference closure and recovery across paired and static cleanup, provide an inspectable dry run, and keep retry behavior.

**Non-Goals:** Delete dependency generations, change rollback policy, or reclaim unrecognized legacy data. Do not expand deletion to static-main or other storage. Staging retains its own data, endpoints, credentials and admission rules.

## Decisions

Adopt the same workspace creation, identity, dependency-link, activation, retention and cleanup lifecycle on staging194 using fixed `/var/lib/ikpk-site-build/staging194-paired` and existing staging settings and admission. Preserve the pre-transition source-release workspace and recorded environment so an interrupted first operation can recover to the old layout. Future staging operations use the new layout. Do not select the production profile or endpoints on staging. Before activation, provision and verify the staging root and inspect the effective CMS unit and drop-ins; update them if required to allow the CMS user to write its workspace. The live staging unit was observed with ProtectSystem=full and empty ReadWritePaths on 2026-11-27, while the repository bootstrap includes a strict sandbox; do not assume either configuration remains unchanged. Verify actual write and build behavior, not merely directory readability. During transition retain sandbox access to the prior legacy workspace so interrupted recovery and refresh can use it; provide a tested rollback of unit configuration on failed installation. Also verify capacity and the separate cleanup unit sandbox before migration.
1. Add one shared workspace inventory/deletion path to post-commit and timer cleanup, routing by host environment: on production load fixed production-paired configuration and relevant production journals independently of the marker-selected profile; on staging194 load only the staging configuration and journal. Never require or create the other environment’s configuration. Use the appropriate explicitly fixed production or staging root; reject arbitrary roots and mismatched profiles. Profile selection alone is insufficient because static-only releases can invoke cleanup. Preserve existing cleanup behavior and retry on failure, including no-marker runs. Alternative: a new independent timer, rejected because it duplicates admission and retry handling.
2. Acquire the destination publication flock first, then the selected profile journal lock, then other relevant production profile journal locks in a documented deterministic order with bounded wait; reuse the existing state object for an identical lock inode, never recursively lock the same inode through a second instance. All participating host writers must use the publication flock before their operation lock; if validation or lock acquisition fails, defer. Under these locks, validate all journals and reservation/marker states; unfinished or ambiguous state defers workspace deletion. Inventory the actual running CMS process environment and its references, service unit and environment files for next start, current and previous paired release and recorded prior environment for rollback, plus every unfinished operation and recovery input. Resolve and validate paths and verify complete inventory, including absent or inaccessible processes/configuration. Do not infer a rollback workspace from recency. If complete closure cannot be proven, retain all. Match each marker exactly to the operation ID and SHA in its name and a unique, valid terminal journal operation; no heuristic ownership. The operation's completion must be established from the existing state machine, not merely its last arbitrary row. Inspect retained workspaces' dependency links and keep the existing CMS-release retention sufficient for those dependencies; if this cannot be proved, defer affected release deletion as well. Alternative: retain two newest, rejected because rollback and process references can diverge.
3. The CMS account owns workspace trees. Serialize supported publication, refresh and recovery with the existing publication flock and operation admission and journal locks. The refresh worker takes that flock while it builds. The owner accepts the residual risk of an external process mutating files without these locks; proving exclusion of every such writer is not a prerequisite for cleanup. Validate the root and candidate identities and recheck before removal; stop on detected replacement. Use symlink-resistant, descriptor-anchored deletion, reject nested mounts, never follow symlinks or mutate external hard-linked inodes, and handle interrupted deletion so a partial tree is not treated as a complete reusable workspace. A same-root quarantine alone does not prevent modification by the CMS user and is not presented as writer isolation. Alternative: stop all CMS-account processes to prove universal writer exclusion, rejected for this task because the owner accepts the residual risk.
4. A read-only preview uses existing validated lock files without creating them, reads journals without repair, never consumes a request or runs unrelated cleanup, and uses the same inventory and decisions, under the same gates, and reports per-child reasons and allocated-byte estimates without crossing links or counting external dependency targets. It is a point-in-time estimate; execution re-evaluates. Output must identify errors separately from eligible/retained. Per-child outcomes and failures go to persistent operational logs without leaking environment secrets. Service sandbox gets only the exact required writable root; test actual systemd execution rather than unit text alone.

The ten-minute timer must inventory workspaces even when neither marker nor request exists. Cleanup failures are logged and retried by that independent periodic pass, including when site cleanup has already consumed a request or cleared a marker. Do not claim the marker remains present after every failure.

## Risks / Trade-offs

- [A non-cooperating process can change CMS-owned trees outside the locks] → Owner accepts this residual risk. Serialize supported workflows, recheck identities, stop on detected changes, and use symlink-resistant removal and mount checks; these measures do not prove universal writer exclusion.
- [Incomplete historical journal or rollback metadata] → Retain affected data and report; do not manufacture ownership from names.
- [CMS release cleanup breaks a retained workspace's web dependency] → Compute retention before either deletion path and protect corresponding targets; verify refresh after pre-commit recovery.
- [Preview differs from application] → Fresh locked re-evaluation on application; never turn preview into deletion authority.

The owner confirmed that post-commit CMS rollback is not required. Acceptance exercises the existing pre-commit recovery of an interrupted paired operation. Retention of the previous release and its workspace remains governed by the existing cleanup and recovery contract; this decision does not authorize deleting them.

Reassess under locks when activated. No production cleanup is implied by creating this proposal.

## Staging data seed

The verified production snapshot and referenced uploads are already staged under a private directory on 194. The existing cohort manifest binds the active SQLite inode and CMS release, and the current staging migration receipt binds its exact ledger. The source and staging schemas match, but their migration ledgers and administrative data differ. Directly swapping the database breaks the active cohort and inherited migration admission. The import requires an explicit staging seed operation that admits the source data, preserves staging accounts and integration settings, and produces fresh, verified cohort evidence with a recoverable prior baseline. Keep the staged copy private until that operation passes offline validation.
