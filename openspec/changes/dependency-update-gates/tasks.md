## 4. Инвариант: платформенные записи lockfile

- [ ] 4.1 Реализовать извлечение кортежей `(имя пакета, os, cpu, libc)`: имя — часть пути
      записи после последнего `node_modules/`, платформа — поля `os`/`cpu`/`libc` записи;
      без выделения «базовой части» имени
- [ ] 4.2 Реализовать сравнение с lockfile базовой ветки по множеству кортежей
- [ ] 4.3 Реализовать неуспех при отсутствии записей с метаданными платформы в любом из
      двух lockfile
- [ ] 4.4 Реализовать узаконивание потери: файл в репозитории, где принятая потеря
      записывается **поимённым** кортежем с причиной; запись класса кортежей («любые
      потери в пакете») не допускается
- [ ] 4.5 Сделать разрешение **одноразовым**: учитывать только записи, добавленные
      относительно базовой ветки; запись, уже присутствующая в базе, разрешения не даёт
- [ ] 4.6 Реализовать инвалидизацию: наличие записи для кортежа, присутствующего в
      lockfile головы, — неуспех с требованием убрать устаревшую запись
- [ ] 4.7 Разместить проверку в условии публикации и в обязательных проверках для всех
      трёх пакетов (см. 6.1)
- [ ] 4.8 Негативная проверка на трёх мутациях: удалить все записи одного имени пакета для
      платформы, оставив её представленной другим именем (ожидание — **красное**);
      удалить кортеж целиком (красное); удалить вложенную копию, оставив верхний уровень
      (зелёное). Для каждой записать множества кортежей до и после
- [ ] 4.9 Проверить обе ветви узаконивания: потеря с записью — зелёное; та же потеря без
      записи — красное
- [ ] 4.10 Проверить одноразовость на полном цикле: узаконить потерю и слить; вернуть
      кортеж (ожидание — **красное**, запись противоречит lockfile); убрать запись
      (зелёное); потерять кортеж снова без новой записи (**красное**). Предъявить все
      четыре состояния — именно этот цикл бессрочная запись пропускала бы молча

## 8. Форма подачи обновлений и SHA-пины

- [ ] 8.1 Перевести `.github/dependabot.yml` на `directories:` с общей группой так, чтобы
      одинаковый подъём в трёх пакетах приходил одним PR — **но только когда все позиции
      имеют одинаковый тип зависимости и одинаковый тип подъёма**. Иначе разделять: `tsx`
      объявлена runtime в `scripts`, но зависимостью разработки в `web`
- [ ] 8.2 Сделать группы однородными по типу зависимости и типу подъёма средствами
      конфигурации группировки (разделение по типу зависимости Dependabot поддерживает)
- [ ] 8.3 Проверить на живых PR, что однородность достигнута: runtime и мажоры приходят
      отдельно от патчей зависимостей разработки. Наблюдалось на #70 — `astro` (runtime
      minor) и `tsx` (dev patch) вместе
- [ ] 8.4 **Не переклассифицировать зависимости ради однородности.** Если перенос между
      runtime и разработкой делается по независимой причине — измерить объём
      runtime-аудита до и после и предъявить оба числа. Ориентир: prod-дерево `web` — 304
      записи из 819 и держится на `astro`; его перенос оставил бы гейту почти пустоту при
      зелёном цвете
- [ ] 8.5 Заменить во всех workflow `uses: owner/repo@vN` на полный идентификатор коммита
      с версией в комментарии рядом
- [ ] 8.6 Добавить проверку целостности: подвижная ссылка на внешнее действие — неуспех;
      ловить общий признак, а не список известных действий
- [ ] 8.7 Негативная проверка проверки целостности: вернуть один подвижный тег, убедиться,
      что проверка называет файл и строку
- [ ] 8.8 Обновить `docs/tech-debt.md`: долг про мажорные теги actions закрыт
