## Context

Мотивация — в `proposal.md` («Why»); требования — в
`specs/dependency-update-automation/spec.md`. Здесь только то, что определяет реализацию.

Ограничения, из которых всё вытекает:

- **Публикация подписана ровно на один workflow.** Событие `workflow_run` не умеет
  требовать успеха нескольких workflow сразу, поэтому в условие выкладки входит только
  `Tests`. `Lint and Typecheck`, `Lighthouse CI`, `Security`, `Nightly full checks`
  выкладку не останавливают.
- **Обязательных для `main` проверок девять, и этот набор не совпадает с содержимым
  `Tests`.** Обязательны: `web checks`, `cms checks`, `scripts checks`, `Unit and build
  tests`, `Playwright smoke (desktop + mobile)`, `Secret scan`, `Runtime dependency
  audit (web)`, `Runtime dependency audit (scripts)`, `Lighthouse budgets (4 templates,
  median of 5)`. Внутри `Tests` живут три job'а — `Unit and build tests`, `Scripts unit
  tests`, `Playwright smoke`, — и **`Scripts unit tests` в обязательные не входит**.
  Проверено на текущей настройке ветки.
- **Производственные зависимости есть во всех трёх пакетах.** `web` — `astro`,
  `@astrojs/sitemap`; `cms` — восемь, включая `@strapi/strapi`, `better-sqlite3`,
  `react`; `scripts` — `form-data`, `node-fetch`, `tsx`. Секция манифеста при этом не
  описывает риск: `astro` — сборщик, `tsx` — раннер для скриптов, которые никуда не
  разворачиваются, и оба объявлены производственными.
- **Одни и те же зависимости объявлены во всех трёх пакетах** — `@eslint/js`, `eslint`,
  `globals`, `typescript`, `typescript-eslint`, причём `typescript-eslint` одной версией.
  Отсюда ограничение на объединение между пакетами в решении 6.
- **`Tests` объявляет `cancel-in-progress`.** При череде слияний промежуточные прогоны
  отменяются, деплой на них пропускается. Наблюдалось 09.08.2026: из шести прогонов на
  `main` четыре отменены, плюс один деплой упал на защите «проверенный коммит всё ещё
  вершина».

## Goals / Non-Goals

**Goals:**

- Сделать три инварианта («линтер что-то анализирует», «lockfile не потерял бинарник»,
  «тесты выполняются») машинно проверяемыми, блокирующими и публикацию, и слияние.
- Отличить «вершина не опубликована» от «промежуточный коммит не опубликован».
- Дать ревьюеру меньше PR на тот же объём обновлений, не смешивая в одном PR изменения
  разного риска.

**Non-Goals:**

- **Автоматическое слияние в этот change не входит.** Оно вынесено в
  `dependabot-auto-merge` и вводится после того, как гейты доказаны негативной проверкой
  и внесены в обязательные.
- Не расширять гейт публикации на другие workflow — это отдельная работа (свод проверок в
  один workflow или вынос в reusable).
- Не трогать исключение `cms audit:prod` (report-only) — оно живёт своей причиной.

## Decisions

### Решение 1: «внутри `Tests`» не означает «обязательна»

Проверка внутри `Tests` останавливает публикацию, потому что выкладка подписана на итог
workflow. Слияние она не останавливает: защита ветки оперирует поимённым списком. Живое
доказательство — `Scripts unit tests`, который лежит внутри `Tests` и в обязательные не
внесён.

Поэтому три новых гейта либо выполняются шагами внутри уже обязательного job'а (`Unit and
build tests`), либо оформляются отдельными job'ами и **вносятся в обязательные**; вместе с
ними вносится `Scripts unit tests`.

### Решение 2: порог — всем, сравнение с базой — только PR, меняющим одни зависимости

Для покрытия линтера и числа тестов проверка сравнивает измеренное значение с числом,
записанным в репозитории (порог), — это применяется ко всем PR. Сравнение с тем же
измерением на базовой ветке применяется только к PR, не меняющим ничего, кроме манифестов
зависимостей и файлов блокировки.

Почему нужны оба условия. Только сравнение с базой вырождается в «равно самому себе», если
оба прогона сломаны одинаково — а именно так выглядит поломка инструмента. Только
константа устаревает при росте: после роста со 128 до 180 файлов падение до 140 остаётся
зелёным при пороге 128.

Почему область второго условия ограничена. Без ограничения оно запрещает обычное удаление
устаревшего исходника или теста: такой PR неизбежно уменьшает измеряемое число, а правка
порога в том же PR его не разблокирует — сравнение идёт с базой, а не с порогом.

Признак берётся из состава изменённых файлов, а не из автора PR: это свойство содержимого
и проверяемо на любом PR. Остаточный риск назван прямо: PR с изменением исходников может
снизить покрытие, оставшись выше порога, — ловится человеческим ревью и нижней границей.

**Change `dependabot-auto-merge` расширяет эту область** на PR, признанные пригодными к
автоматическому слиянию: у экосистемы `github-actions` меняются файлы workflow, а не
манифесты, и по файловому признаку такой PR выпал бы из-под сравнения. Расширение живёт
там, потому что до появления автоматического слияния понятия пригодности не существует.

### Решение 3: кортеж (имя пакета, os, cpu, libc), а не множество платформ

Проверка lockfile сравнивает множество кортежей **(имя пакета, ОС, архитектура,
разновидность libc)**. Имя берётся из пути записи — часть после последнего
`node_modules/`; `os`, `cpu` и `libc` — из полей самой записи.

Почему кортеж, а не платформа: разные пакеты закрывают одну платформу.
`@esbuild/linux-x64` и `@img/sharp-libvips-linux-x64` дают один и тот же `(linux, x64)`.
Удаление всех бинарников `sharp` для этой платформы оставило бы её представленной через
esbuild, и гейт остался бы зелёным при неработающем `sharp`.

Почему имя целиком, а не «семейство»: понятия семейства формат файла блокировки не
содержит — поле с именем присутствует лишь у отдельных записей (в `web` — у одной из 847),
а выделение «базовой части» из пути было бы угадыванием соглашения об именовании.

Почему `os`/`cpu`/`libc` из полей, а не из имени: они объявлены самим пакетом и являются
тем, по чему npm принимает решение об установке. Записей с этими полями в
`web/package-lock.json` — **105**.

Что исчезновение записей само по себе не дефект — измерено: в #50 число платформенных
записей упало с 50 до 45, но все пять исчезнувших были вложенной копией
`tsx/node_modules/@esbuild/*`, а кортежи остались представлены верхним уровнем.

Тупик снят узакониванием: потеря кортежа допустима, если она **поимённо** записана в
репозитории с причиной. Разрешение одноразовое — учитывается только запись, добавленная
относительно базы; запись для кортежа, который в lockfile присутствует, даёт неуспех и
подлежит удалению. Иначе кортеж мог бы вернуться и снова исчезнуть, а старая запись
разрешила бы вторую потерю молча.

### Решение 4: пустой результат — это неуспех

Все три проверки различают «нарушений нет» и «измерить не удалось». Нулевой список
файлов у линтера, отсутствие записей с метаданными платформы в любом из двух lockfile,
отсутствие отчёта о прогоне — неуспех. Коды выхода разбираются по значению, а не по
признаку «не ноль».

### Решение 5: непубликация промежуточных коммитов — норма, молчание — нет

`Tests` объявляет `cancel-in-progress`, поэтому при череде слияний промежуточные прогоны
отменяются, а выкладка на них пропускается. Это признаётся нормой требованием, а не
оставляется на усмотрение реализации. Но отменённый прогон и не отработавшая выкладка
выглядят одинаково, поэтому scheduled-проверка сравнивает вершину `main` с последним
успешным Pages deployment. Если вершина не опубликована за **30 минут**, проверка падает
и называет её полный SHA; `workflow_dispatch` даёт воспроизводимый ручной запуск.

### Решение 6: один PR на одну зависимость через разрешённые пакеты

Для общей записи `directories: [/web, /scripts]` используется
`group-by: dependency-name`. Поэтому одна зависимость обновляется одним PR через оба
разрешённых пакета, а разные зависимости приходят разными PR. Внутри одной зависимости
группа однородна по классу допуска пакетов репозитория и типу подъёма.

Прежняя редакция брала признаком тип зависимости, то есть секцию манифеста. Признак
заменён вместе с таблицей допуска в `dependabot-auto-merge` (решение 2а там): секция не
описывает риск — `astro` и `tsx` объявлены производственными, хотя оба сборочный
инструментарий, — и группировка по ней разделяла бы по различию, которого нет.

Объединение между пакетами выполняется только для позиций одного класса допуска: `web` со
`scripts` объединять можно, `cms` с ними нельзя. Иначе требование о группировке само
создавало бы смешанную группу — пять зависимостей объявлены во всех трёх пакетах сразу.

Цена решения принята владельцем: прежний пакетный PR с несколькими разными
patch/minor-зависимостями распадается на один PR на зависимость. Это необходимо для
гарантированного cross-directory обновления общей зависимости средствами Dependabot.

**Почему перенос между секциями всё равно ограничен.** Достигать однородности переносом
больше нельзя по построению — признак секцию не читает, — но защищаемое прежним запретом
свойство осталось. Гейт runtime-аудита исключает дерево зависимостей разработки, поэтому
перенос вывел бы из-под проверки и `astro`, и всё его поддерево. Измерено: prod-дерево
`web` — 304 записи из 819, и держится оно на `astro`; после переноса аудиту остался бы
`@astrojs/sitemap` с поддеревом. Гейт остался бы зелёным, проверяя почти ничего.

Поэтому правило нынешней редакции: перенос между секциями не сокращает область
runtime-аудита, независимо от мотива, и объём измеряется до и после.

### Решение 7: SHA-пины с версией в комментарии

`uses:` переводится на полный идентификатор коммита, рядом остаётся читаемая версия
комментарием. Без неё ревью подъёма превращается в сравнение двух сорокасимвольных строк.
Целостность (не осталось ли подвижных тегов) проверяется поиском общего признака, а не
списка известных действий.

## Risks / Trade-offs

- **Расширение обязательных проверок замедляет ручное слияние** → принимается: проверка,
  которая не останавливает слияние, не является гейтом слияния, как бы она ни называлась.
- **Три новых гейта повышают шанс, что публикация встанет из-за самой проверки, а не из-за
  дефекта** → каждая проверка обязана называть предмет и числа в сообщении об ошибке;
  негативная проверка каждой обязательна до слияния.
- **Сравнение с базой удваивает измерение** → принимается ради случая «покрытие упало, но
  выше устаревшего порога».
- **Сравнение с базой не применяется к PR, меняющим исходники** → такой PR может снизить
  покрытие, оставшись выше порога. Ловится ревью и порогом; альтернатива — блокировать
  всякое удаление исходника — хуже.
- **Порог, заданный константой, устаревает** → при законном сокращении правится в том же
  PR и виден в диффе; это и есть механизм ревью.
- **SHA-пины делают дифф обновления нечитаемым** → версия обязательна рядом комментарием.
- **Мутация для негативной проверки может не затронуть предмет и дать ложный вывод о
  декоративности гейта** → для каждой проверки в отчёт идут два числа измеряемой
  величины, а не только цвет прогона.

## Migration Plan

1. Гейты с негативными проверками **и внесением их в обязательные**; вместе с ними
   `Scripts unit tests`.
2. Наблюдаемость публикации вершины.
3. Группировка и SHA-пины.
4. Откат: гейты снимаются шагами из `Tests` и из списка обязательных; SHA-пины
   откатываются обратной заменой.

Автоматическое слияние (`dependabot-auto-merge`) вводится только после шага 1, и это не
предпочтение, а условие: до доказанных и обязательных гейтов оно превращает «зелёно» в
«никто не смотрел».
