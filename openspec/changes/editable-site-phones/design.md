## Goals / Non-Goals

Контракт охватывает HTML, который публикует ИКПК, включая SEO-разметку. Внешнее сообщение об отсутствии оператора задаётся в кабинете Битрикс24 и обслуживается отдельно согласно действующей спецификации external-widgets. Остальные контактные данные ведутся по существующим правилам.

## Decisions

1. Добавить в существующий тип Page два строковых атрибута. Запись определяется по принадлежности странице /kontakty (у перенесённой записи slug и legacy_id равны kontakty), независимо от заголовка и локального ID базы. В интерфейсе этой записи показать отдельные русские подписи. Для остальных Page атрибуты необязательны, их значения не участвуют в выборе контактов. Проверять оба номера на сервере при публикации контактов, включая частичное обновление и публикацию уже сохранённого черновика. Для пользователей с действующими правами на эту запись проверить доступ к новым полям, сохранив ограничения на остальные типы и записи.
2. Из одного ввода получать видимый номер и международный номер для ссылок и JSON-LD. Принимать цифры ASCII с префиксом +7, пробелы, скобки и дефисы. После удаления разделителей требовать ровно +7 и десять цифр. Показывать номера в принятой на сайте форме по роли, например +7 (812) 646-54-50 и +7 981 038-77-97. Для ссылок добавлять tel: к международному значению. Для доступного имени использовать отображаемый номер.
3. Включить оба поля в проекцию static_pages и её отпечаток, обновить тип данных, закреплённый снимок и ожидаемые метаданные. Astro получает пару один раз из снимка. Вычисление принадлежит серверной сборке, включая страницы, импортирующие общую навигацию. На странице контактов сохраняются отдельные роли каждого городского номера. При отсутствии или неоднозначности записи либо ошибке значения текущая публикация завершается до переключения сайта.
4. Для сведений об организации связать конкретные строки восстановленных панелей с ролями и подставлять данные до штатной санитизации. Проверить вывод и при наличии тех же строк в теле CMS. Привязать подстановку к назначению строки, чтобы вторая замена работала так же, как первая, и посторонние телефоны в редакционном тексте сохранялись. Общая замена цифр по всем HTML-файлам может затронуть чужой контакт.

## Migration Plan

Сначала добавить два допускающих NULL столбца. При первом переходе заполнить только отсутствующие значения в существующих опубликованной и черновой версиях контактов. Выполнить заполнение атомарно, сохранив остальные поля, состояние публикации и более свежие пользовательские значения. Это даёт корректную пару первой сборке и позволяет повторить переход. При отсутствии ожидаемой записи оператор получает причину остановки. Для проверки перехода прогнать существующий путь допуска схемы и сравнения данных на копии старой базы с черновиком, ограничив разрешённые расхождения двумя колонками и их начальным заполнением. После проверки публиковать обычным способом.

Для исторических снимков без полей воспроизводить прежний выпуск его сохранёнными артефактами и версией сборщика. Закреплённый снимок для текущего сборщика обновляется вместе с контрактом. При откате вернуть предыдущую проверенную версию сайта штатным механизмом, сохранив введённые номера в CMS для повторного выпуска.

## Risks / Trade-offs

Проверка шапки на всех страницах может пройти при устаревшем телефоне внутри конкретной секции. Проверять элементы внутри каждой секции, включая раскрытые панели, условный блок программы без даты и значения JSON-LD. Проверить два последовательных изменения с разными номерами и поиск остатков старых значений в собранном HTML. Пользовательские документы и произвольный редакционный текст не подвергаются массовой замене.
