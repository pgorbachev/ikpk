## Goals / Non-Goals

Контракт охватывает HTML, который публикует ИКПК, включая SEO-разметку. Внешнее сообщение об отсутствии оператора задаётся в кабинете Битрикс24 и обслуживается отдельно согласно действующей спецификации external-widgets. Остальные контактные данные ведутся по существующим правилам.

## Decisions

1. Добавить в существующий тип Page два строковых атрибута. Запись определяется по принадлежности странице /kontakty (у перенесённой записи slug и legacy_id равны kontakty), независимо от заголовка и локального ID базы. В форме контактов показать отдельные русские подписи и подсказку о том, что телефоны для сайта задаются здесь, а унаследованный текст Body не выводится на /kontakty. Сохранить имеющиеся заголовок и Body. У закреплённой записи заголовок «Контакты», в редакторе пользователь называет её «Контакты сайта». В остальных формах Page скрыть оба атрибута по записи и отклонить непустые значения для другой Page на сервере. Проверять оба номера на сервере при публикации контактов, включая частичное обновление и публикацию уже сохранённого черновика. Обновить сопоставление полей в lifecycle статической страницы и условную проверку для kontakty в CMS и в парном проверочном контракте. Черновик контактов допускает незаполненные поля. При отказе в публикации сообщить имя ошибочного поля и ожидаемый формат, включая начальное +7. Для content-admin предоставить в меню Page → Контакты сайта узкую форму двух полей существующей записи. Серверная операция определяет роль по учётной записи, сама выбирает канонические контакты и принимает только center_phone и manager_phone. Не выдавать collection-wide права Page. Сохранение меняет только телефонные поля черновика. Публикация обновляет только телефоны опубликованной версии и согласует их с черновиком в одной транзакции, сохраняя прочие поля обеих версий. При одновременных правках сохранить независимое изменение другого номера либо сообщить о конфликте устаревшей версии. Право «Обновить сайт» уже есть у content-admin. Супер-администратор сохраняет полный редактор. Приёмка проверяет реальную роль content-admin и отдельную учётную запись без этого права.
2. Из одного ввода получать видимый номер и международный номер для ссылок и JSON-LD. Принимать цифры ASCII с префиксом +7, пробелы, скобки и дефисы. После удаления разделителей требовать ровно +7 и десять цифр. Показывать номера в принятой на сайте форме по роли, например +7 (812) 646-54-50 и +7 981 038-77-97. Для ссылок добавлять tel: к международному значению. Для доступного имени использовать отображаемый номер.
3. Включить оба поля в проекцию static_pages и её отпечаток, обновить тип данных, закреплённый снимок и ожидаемые метаданные. Astro получает пару один раз из снимка. Вычисление принадлежит серверной сборке, включая страницы, импортирующие общую навигацию. На странице контактов сохраняются отдельные роли каждого городского номера. При отсутствии или неоднозначности записи либо ошибке значения текущая публикация завершается до переключения сайта.
4. Для сведений об организации связать конкретные строки восстановленных панелей с ролями и подставлять данные до штатной санитизации. Проверить вывод и при наличии тех же строк в теле CMS. Привязать подстановку к назначению строки, чтобы вторая замена работала так же, как первая, и посторонние телефоны в редакционном тексте сохранялись. Общая замена цифр по всем HTML-файлам может затронуть чужой контакт.

## Migration Plan

Штатная синхронизация схемы Strapi добавляет два допускающих NULL столбца. Заполнение включить в план миграций как шаг after-sync с проверкой результата. При первом переходе заполнить только отсутствующие значения в существующих опубликованной и черновой версиях контактов. Выполнить заполнение атомарно, сохранив остальные поля, состояние публикации и более свежие пользовательские значения. Это даёт корректную пару первой сборке и позволяет повторить переход. При отсутствии ожидаемой записи оператор получает причину остановки. Для проверки перехода прогнать существующий путь допуска схемы и сравнения данных на копии старой базы с черновиком, ограничив разрешённые расхождения двумя колонками и их начальным заполнением. После проверки публиковать обычным способом.

В чистой CMS штатный импорт при создании Page сразу публикует её. Передать начальные значения для контактов при первом создании. При повторном импорте сохранить значения, которые уже выбрал редактор. [Импорт Page](https://github.com/pgorbachev/ikpk/blob/107a41c571a64e804cc71e2a65b81b49bea734db/scripts/import.ts#L581-L594)

Первую сборку выполнить из свежего снимка после заполнения полей. Повторное использование старого снимка без полей должно дать понятную причину отказа. Первый парный выпуск меняет публичную проекцию static_pages относительно проверенной резервной копии. Штатный допуск обычного выпуска требует прежнего отпечатка, а текущая проверка миграции знает изменения семинаров и расписания. Для перехода расширить проверяемый путь миграции: из старой проекции независимо построить ожидаемую новую, добавив только согласованные поля телефонов к контактам и учитывая выбранное представление пустых полей у остальных Page. Сверить весь результат с кандидатом, связав резервную копию, источник, запуск, снимок и статическую сборку. На репетиции принять ожидаемый переход и отклонить любое постороннее изменение до переключения. После первого выпуска замена телефонов идёт обычной кнопкой CMS. [Допуск первого выпуска](https://github.com/pgorbachev/ikpk/blob/107a41c571a64e804cc71e2a65b81b49bea734db/scripts/rehearsal/staging193.py#L1639-L1663)

Для исторических снимков без полей воспроизводить прежний выпуск его сохранёнными артефактами и версией сборщика. Закреплённый снимок для текущего сборщика обновляется вместе с контрактом. При откате вернуть предыдущую проверенную версию сайта штатным механизмом, сохранив введённые номера в CMS для повторного выпуска.

## Risks / Trade-offs

Проверка шапки на всех страницах может пройти при устаревшем телефоне внутри конкретной секции. Проверять элементы внутри каждой секции, включая раскрытые панели, условный блок программы без даты и значения JSON-LD. Проверить два последовательных изменения с разными номерами и поиск остатков старых значений в собранном HTML. Пользовательские документы и произвольный редакционный текст не подвергаются массовой замене.
