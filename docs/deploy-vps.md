# Ручная публикация сайта на VPS

Штатный путь — установленный `publication-launcher.mjs` вне любого checkout.
Оператор запускает этот инструмент; проверки, выбор источника и переключение выполняет
код. Push, расписание CI, событие CMS и зелёный PR сайт не публикуют. GitHub Pages удалён.
Свежесть сайта не имеет SLA: новая версия появляется только после явной команды.

## Готовность назначения

До настоящей публикации нужны все предусловия задач 1.4–1.7 change
`manual-publication-only`: непривилегированный deploy-user, закреплённый known_hosts,
исключительная блокировка, защищённая установка launcher и его runtime, учётные данные
через брокер/SSH-agent, событийный журнал CMS с проверенной ревизией снимка. Установку
и права поставляют `server-provisioning`/`server-hardening`; событийный писатель —
`cms-live-snapshot-capture`. Наличие REST API CMS не доказывает готовность журнала.

На 19.09.2026 эти операционные предусловия ещё не приняты. Примеры ниже описывают
подготовленную установку, а не подтверждают её наличие на машине оператора или VPS.
Production `ikpk.su` разрешается в `158.160.147.32`; `193.124.115.99` — отдельный стенд.
DNS эта процедура не меняет. [Проверка площадки](testing/manual-publication-only/site-topology-readonly.md)
подтвердила `has_pages: false`, HTTP 200 главной и отсутствие `/release.json` на production.
Поэтому прежний production-релиз пока не является проверенной целью отката.

Nginx назначения должен раздавать `<webRoot>/current` и явно включать
`<webRoot>/shared/nginx-redirects.conf` только для этого назначения. Файл не должен
использоваться другим сайтом, в том числе через wildcard или промежуточный include.
Публикация проверяет действующую конфигурацию через `nginx -T`, проверяет новую через
`nginx -t` и перезагружает nginx фиксированной разрешённой командой. Право на эти команды
и права записи каталога готовятся отдельно; launcher их не устанавливает.

## Защищённая конфигурация

`config.json` лежит рядом с установленным launcher. Пример для стенда без оплаты:

```json
{
  "canonicalRepository": "git@github.com:pgorbachev/ikpk.git",
  "sshTarget": "deploy@193.124.115.99",
  "destinationId": "stand",
  "deployMode": "stand",
  "demoForms": "stub",
  "paymentRole": "ci",
  "siteUrl": "https://staging.ikpk.su",
  "actor": "<учётная запись оператора>",
  "webRoot": "/var/www/ikpk",
  "knownHostsFile": "/opt/ikpk-publication/stand/known_hosts",
  "keepReleases": 5,
  "chatLoaderSrc": "none",
  "credentialBroker": ["/opt/ikpk-publication/stand/credentials"]
}
```

Адрес `siteUrl` должен соответствовать фактически настроенной раздаче. Файлы установки
защищены от подмены и групповой/общей записи; runtime имеет собственные зависимости и
`runtime.json` с `version: 1` и полным SHA установленного кода. Runtime используется для
отката и обслуживания состояния, поэтому доступ к свежему `main` для них не нужен.

CRM-режим и оплата независимы. `deployMode: prod` направляет формы в CRM заказчика;
`demoForms: stub` допустим только на стенде. `paymentRole: ci` означает отсутствие формы
оплаты и запросов к платёжному API, в том числе на production. Активные роли требуют
`payment` с endpoint, mode, shopId и siteOrigin. Роль `stand` требует `test`/`1440249`,
роль `prod` — `prod`/`409285`. Readiness читается через SSH с loopback VPS, preflight —
без создания оплаты. Чат объявляется явно: `none` либо согласованный адрес загрузчика.

## Новая публикация

```bash
node /opt/ikpk-publication/stand/publication-launcher.mjs publish \
  --config /opt/ikpk-publication/stand/config.json \
  --source-url git@github.com:pgorbachev/ikpk.git --source-ref main
```

Launcher подтверждает канонический `refs/heads/main` до выдачи учётных данных и запускает
его чистую копию. Допустимый локальный `--source-dir` также должен точно соответствовать
этому источнику; ветка PR, tag `main`, dirty checkout и произвольный worker не подходят.

Обязательный CI — `.github/workflows/test.yml` основного репозитория для **этого SHA**,
события push/schedule основной ветки. Все пять джобов должны завершиться успехом:
Capture content snapshot, Unit and build tests, Dependency update invariants,
Scripts unit tests, Playwright smoke (desktop + mobile). Пропущенный джоб и зелёный PR
не заменяют этот вердикт.

Worker снимает один живой снимок, строит одно дерево и выполняет пять групп:
снимок/журнал, сборка/содержимое, режим назначения, browser smoke desktop/mobile,
платёжное назначение. Ноль проверок, пропуск, изменившееся дерево, устаревший журнал
или несоответствие платёжного магазина дают отказ. Готовое дерево содержит `release.json`
и свой файл редиректов; сумма охватывает оба. Перед переключением повторно сверяются
`main` и журнал CMS. После переключения проверяются фактический `/release.json` и HTTP
главной, затем добавляется неизменяемая запись в индекс назначения.

Вывод содержит только ограниченный аудит: полный commit, snapshotId, treeDigest,
идентификатор операции, числа проверок и вердикт. Секреты и необработанный вывод дочерних
процессов туда не попадают. Код завершения ненулевой — публикация не принята.

Прямой вызов `scripts/deploy-web.sh` без защищённого контекста отказывает. Ручные `scp`,
`rsync` или смена `current` не создают свидетельство проверенной публикации.

## Отдельная проверка без публикации

Для уже снятого живого снимка и отдельной копии журнала, из каталога `web`:

```bash
npm run test:publication -- \
  --snapshot-dir /absolute/captured-snapshot \
  --ledger-dir /absolute/provenance-state \
  --config /opt/ikpk-publication/stand/config.json \
  --commit <полный-SHA> --report /absolute/reports/publication.json
```

Команда один раз собирает `web/dist`, выполняет фиксированные пять групп и сохраняет
новый отчёт вне снимка, журнала и сборки. Произвольный набор проверок выбрать нельзя.
Она не снимает снимок повторно и не переключает раздачу; для активной платёжной роли
разрешён только read-only readiness назначения. Этот отчёт сам по себе не выдаёт право
публикации: установленный launcher выполняет полный протокол самостоятельно.

## Откат

```bash
node /opt/ikpk-publication/stand/publication-launcher.mjs rollback \
  --config /opt/ikpk-publication/stand/config.json \
  --release-id <сохранённый-releaseId> --confirm --reason '<причина отката>'
```

Цель должна иметь полную запись именно этого назначения и сохранённые неизменные байты.
Откат использует установленный код, первоначальное свидетельство CI и свежие проверки
сохранённого дерева: режим, browser smoke, платёжное назначение. CMS, старый Actions run,
снимок и свежий `main` не требуются. При несовместимой текущей платёжной конфигурации
откат отказывает. Оператор и причина записываются отдельной операцией; журнал CMS не
меняется. Глубина хранения — минимум пять релизов вместе с текущим; автоматического
отката при ошибке нет. Перед первой боевой публикацией отсутствие проверенной цели
отката сообщается владельцу отдельно.

**Восстановление из резервной копии не публикует.** `scripts/restore-server-state.sh <env>`
(объявлен как `RESTORE_CMD`) кладёт последнюю копию `current-*` в
`${WEB_ROOT}/restored/restore-<время>` — рядом с релизами, а не внутри окна удержания, чтобы не
вытеснять цели отката, — сверяет её побайтно и печатает `restored=<id>`, `path=…` и
`activation=launcher-only`. Действующий релиз и симлинк раздачи он не трогает: путь публикации
у сайта один, и восстановленное дерево становится видимым посетителям только решением
оператора через launcher. Восстановленный каталог не лежит в `releases/` и не является проверенной парой индекса,
поэтому `rollback` на него невозможен; выбирать можно между откатом на сохранённый
проверенный релиз и новой публикацией из `main`.

## Незавершённая запись и принятие состояния CMS

Если сайт переключён, но проверка раздачи/запись индекса не завершилась, команда выдаёт
`active-unindexed` и действующую пару. Pending сохраняется и блокирует следующую
публикацию. После устранения причины:

```bash
node /opt/ikpk-publication/stand/publication-launcher.mjs recover \
  --config /opt/ikpk-publication/stand/config.json
```

Восстановление сверяет действующий релиз и раздачу перед записью индекса. Подготовленная,
но не переключённая операция может быть отменена с восстановлением прежнего файла
редиректов. Неожиданное ручное изменение конфигурации или неоднозначный сбой переключения
сохраняет pending и требует отдельного разбора. Удалять pending вручную для обхода отказа
нельзя: сначала надо восстановить согласованность раздачи и учёта.

Принятие восстановленного состояния CMS — другое действие, применимое только к явно
наблюдённым номеру записи и отпечатку:

```bash
node /opt/ikpk-publication/stand/publication-launcher.mjs accept-state \
  --config /opt/ikpk-publication/stand/config.json \
  --observed-entry <номер> --fingerprint <отпечаток> --confirm
```

Новое событие во время подтверждения делает старое подтверждение недействительным.
Эта команда добавляет acceptance в журнал и сама ничего не публикует. После успешного
принятия нужна новая явная публикация.

## Приёмка после merge

Сначала предъявить зелёный `Tests` актуального `main`. Затем, после готовности установки
и событийного журнала, на стенде выполнить две публикации и подтверждённый откат, сохранить
аудит и ответы раздачи. Production принимается отдельно после готовности его назначения
и подтверждения владельца. Результаты временных fixtures не считаются этой приёмкой.
