### `web/tests/external-widgets-deploy.test.ts`

Источник — `scripts/lib/deploy-checks.sh` через `source` в bash-подпроцессе (см.
`sh()` в самом тестовом файле). Два узла:

1. **`form_links_match_mode` меняет внутреннее устройство, не сигнатуру.** Текущая
   реализация (`scripts/lib/deploy-checks.sh:494`, `all_links=$(grep -rohiE '(href|src|action)[[:space:]]*='...`)

   уничтожается раньше отбора. Тест требует ОБРАТНОГО на двух примерах сразу:
   - `data-form-link="…crm_form_ve1op/"` (имя НЕ кончается на href/src/action) обязан
     быть пойман (`external-widgets-deploy.test.ts:174`, `'ссылка формы в АТРИБУТЕ ДАННЫХ гейту видна'`);
   - `data-chat-loader="<bitrix-адрес>"` на элементе с `data-chat-facade` обязан быть
     **пропущен**, даже если переименовать атрибут в `data-chat-src`
     (`external-widgets-deploy.test.ts:128`, `'загрузчик в атрибуте, чьё имя кончается на \`src\`, боевую выкладку не отвергает'`).
   Единственный путь, где оба условия выполняются одновременно, — разбор **разметки**
   (элемент + все его атрибуты + сосед-атрибут `data-chat-facade` на том же теге), а
   не регулярка по имени атрибута. Дословно того же требует спека:
   `openspec/changes/external-widgets/specs/external-widgets/spec.md:1020`,
   `**Выбор сделан здесь: назначение SHALL определяться разбором разметки — элементом, его атрибутом и`.
   Вызов остаётся трёхаргументным — это проверяется отдельно (см. ниже, реестр).
2. **Новая функция `chat_widget_matches_mode <dist> <mode> <raw-config>`** — нужна
   рядом с `payment_endpoint_matches` (`scripts/lib/deploy-checks.sh:93`). В отличие
   от (1), здесь парсер НЕ обязателен: все 13 сценариев теста удовлетворяются, если
   функция (а) разбирает `raw-config` в три состояния тем же правилом, что и
   `readChatLoaderConfig` (`'none'` → declared-absent; валидный URL со схемой →
   address; иначе → unspecified), (b) считает «несёт чат» = находит литеральную
   подстроку `data-chat-facade` в файлах `$dist/**/*.html` (для declared-absent/
   unspecified) либо литеральную подстроку самого адреса (для address), и (c) по
   режиму `prod` даёт 5 исходов (2 положительных: address+несёт совпадающий адрес;
   declared-absent+не несёт), по `stand` — 2 (оба states кроме unspecified дают
   «не несёт» = проходит, «несёт» = не проходит), unspecified — всегда отказ с
   текстом `не объявлена`/`не объявлено` независимо от режима и вывода.
   Вызывающая сторона — `scripts/deploy-web.sh`: добавить вызов сразу за существующим
   `if ! form_links_match_mode "$DIST_DIR" "$DEPLOY_MODE" "$DEMO_FORMS"; then` и
   **экспортировать `CHAT_LOADER_SRC`** туда же, где сейчас экспортируется
   `PAYMENT_ROLE` (строка `export PAYMENT_ROLE="$DEPLOY_MODE"`), иначе артефакт,
   который проверяет гейт, не будет тем артефактом, который получил `npm run build`.

## 2. Контринтуитивные находки — дорого не знать заранее

1. **`parse5` по умолчанию не разбирает `<noscript>` как разметку.** Проверено
   выполнением на этом дереве: `parse(html)` с содержимым
   `<noscript><a href="https://yandex.ru/x">link</a></noscript>` даёт единственный
   узел `#text` со значением `"<a href=\"...\">link</a>"` — сам `<a>` элементом не
   становится. `web/tests/helpers/dom.ts:15`, функция `children()`, сегодня
   разворачивает только содержимое `<template>` (`n.content?.childNodes`). Красный
   тест `external-widgets-dist.test.ts` («в статической разметке секции нет iframe,
   а в noscript есть ссылка…») требует находить `<a>`-элемент ВНУТРИ `<noscript>`
   через `subtree()`/`walk()`. Без правки `dom.ts` это структурно невыполнимо —
   никакая разметка компонента этого не даст. Нужно расширить `children()`: если у
   узла `nodeName === 'noscript'` и его единственный childNode — `#text`, разобрать
   этот текст `parseFragment()` и вернуть результат вместо текстового узла (не
   вместе с ним — иначе `textOf()` посчитает содержимое дважды). Проверено, что
   `helpers/dom.ts` использует ровно 5 тестовых файлов
   (`payment-characterization.test.ts`, `site-copy.test.ts` и три новых
   external-widgets), и ни один из них не ходит по `<noscript>` за пределами этой
   возможности — единственные два места `<noscript>` в проде сегодня
   (`web/src/components/Analytics.astro:61-62`, счётчики; `ContactShell.astro:131`,
   карта) — риск регрессии низкий, но не нулевой, стоит перепроверить после правки.
2. **`applyBackgroundInert` метит только прямых детей `<body>`.**
   `web/src/scripts/payment-form.ts:207`, `function applyBackgroundInert(on: boolean) { for (const node of [...document.body.children])…`
   — ставит/снимает `inert` на каждом `document.body.children`, кроме диалога, и
   переустанавливает это через `MutationObserver` на `childList` body. Значит фасад
   чата ОБЯЗАН быть смонтирован как прямой сосед `<body>` (рядом с `<Footer />` /
   `<Analytics />` в `BaseLayout.astro`), а не внутри `<main>` — иначе при открытом
   диалоге оплаты кнопка чата останется кликабельной и/или видимой поверх затемнения,
   воспроизводя ровно тот класс дефекта, который уже правили на PR #151
   (`web/tests/payment-transport.spec.ts:96`, `'фон исключён из фокуса и чтения'`).
3. **Риск столкновения с формой оплаты — не в позиции кнопки, а в z-index диалога.**
   Продовый `<PaymentForm />` подключён только в `web/src/pages/oplata.astro`
   (`grep -rl PaymentForm src/pages` даёт единственный файл); его собственный триггер
   не зафиксирован в углу экрана. `.payment-dialog` несёт `z-index: 200`
   (`web/src/components/payment/PaymentForm.astro:132`); фасад чата обязан иметь
   z-index **ниже** — design.md прямо называет это задачей 7.3g. Дырка, которую
   design называет отдельно (7.3e/7.3f): actuation-клики по кнопке оплаты **до**
   открытия диалога, когда `inert` ещё не выставлен, — своей проверки на это в
   существующих платёжных спеках нет, стоит добавить вручную после того, как фасад
   появится, а не считать риск закрытым автоматически.
4. **`scripts/lib/deploy-checks.sh` — регулярка не спасает уточнением.** См. раздел
   1, узел про `form_links_match_mode`: сегодняшнее извлечение слепо к
   `data-form-link` (не кончается на href/src/action) и одновременно не различает
   «загрузчик чата на бирикс-хосте» от «ссылка формы на том же хосте» никаким
   способом, кроме контекста элемента. Любая правка регулярки уточняет один случай и
   портит другой — нужен разбор по элементам, реализуемый node-скриптом, вызываемым
   из bash (в среде выкладки node уже требуется сборкой).
5. **Preview-порт делится между worktree.** По памяти проекта
   (`worktrees-share-tcp-ports.md`, `mutation-run-that-measured-nothing.md`)
   параллельный Playwright-прогон в разных worktree на одном порту (обычно 4322) даёт
   не ошибку, а тихое «0 тестов выполнено» — перед тем как доверять локальному
   `npm run test:e2e:*` в этом worktree, стоит убедиться, что другой сессии сейчас
   не занят тем же портом (либо задать свой `PREVIEW_PORT`).
6. **Проверки датозависимого фрагмента читают исходник прогона, а не манифест.**
   `external-widgets-guard.test.ts:328` («датозависимый фрагмент назван в самой
   проверке») и соседние — это grep по тексту `visual-baseline.spec.ts`, ищущий
   литералы `SEL_AWARD_ROW`, `data-chat-hours`, `SEL_REVIEWS_SECTION`,
   `SEL_CHAT_TRIGGER`, `SEL_CHAT_MOUNT`. Манифеста покрытия в репозитории нет
   (`visual-regression-gate` его не занёс), поэтому эти тесты проверяют присутствие
   строк в комментариях/коде файла, а не фактическое покрытие — лечится правкой
   текста `visual-baseline.spec.ts`, а не логики.

## 5. Рекомендуемый порядок швов

**Независимо, можно отдельными сессиями/коммитами:**

1. `web/src/lib/external-widgets.ts` + `web/src/lib/award-badges.ts` — чистые модули,
   не требуют компонентов; закрывают весь `external-widgets.test.ts` самостоятельно.
2. Правка `web/tests/helpers/dom.ts` (носитель `<noscript>`) — инфраструктурная,
   не зависит от остального; несколько red-тестов (dist/demo) станут ИЗМЕРИМЫМИ
   только после неё, независимо от вида компонента.
3. `a11y.spec.ts` → импорт общего `TEMPLATES` — не зависит ни от чего другого.

**Обязаны идти вместе, в указанном порядке — общий символ или общий артефакт:**

1. `external-widgets.ts`/`award-badges.ts` (lib) →
   `ChatFacade.astro`/`Reviews.astro` (компоненты потребляют lib) →
   `BaseLayout.astro`/`index.astro` (подключают компоненты) →
   регенерация фикстур `rich-content-safety` (после того как компоненты существуют
   и подключены, на чистом дереве, `generate-baseline` **до** `generate-occurrences`,
   при обоих собранных деревьях). Перестановка любого шага даёт ровно тот дефект,
   который спека называет сценарием «Инструменты запущены в обратном порядке»
   (`spec.md:943`).
2. `chat_widget_matches_mode` + переписанный `form_links_match_mode` в
   `scripts/lib/deploy-checks.sh` обязаны попасть в тот же коммит, что вызов в
   `scripts/deploy-web.sh` и экспорт `CHAT_LOADER_SRC`: `external-widgets-registry.test.ts:294`
   сверяет буквальный трёхаргументный текст вызова `form_links_match_mode`, и
   изменение вызова без функции (или наоборот) оставляет несогласованный, наполовину
   работающий гейт.
3. Вставка `installThirdPartyGuard` в 15 существующих `*.spec.ts` можно отдельным
   коммитом, но должна лечь до правки текста покрытия `visual-baseline.spec.ts` (или
   вместе с ней) — тест-хранитель сканирует один и тот же файл на оба предмета.
4. `docs/tech-debt.md` и `docs/handoff/external-widgets-acceptance-evidence.md` можно
   писать в любой момент после того, как существуют соответствующие гейты, но файл
   свидетельств приёмки динамически импортирует `chatLoaderConfig()`,
   `chatOfflineMessage()` и `DECLARED_AWARD_BADGES` — значит после шага 1 из
   «обязаны идти вместе», не раньше.
5. Документ о персональных данных и приёмочные записи по двум блокированным пунктам
   (раздел 4) не встают в очередь реализации вовсе — ждут ответа заказчика.

## 6. Открытая находка: кнопка чата на мобильном перекрывает контент на пяти шаблонах — не закрыто

Добавлено сессией верификации (owner-review шага 4→5, не сабагентом реализации).

Отчёт сессии, писавшей `ChatFacade.astro`/`Reviews.astro`, назвал мобильный e2e
непроверенным и предположил единственную причину: «`.topnav-drawer` в `TopNav.astro`
не клипует геометрию потомков — баг стороннего компонента». Предположение **отчасти
верно, но неполно**, и его нельзя было принимать без проверки: `git diff main --
web/src/components/topnav/TopNav.astro` действительно пуст (файл этой веткой не
тронут), и это ЧАСТЬ причины — `.topnav-drawer` использует `position: absolute`, из-за
чего его геометрия не схлопывается вместе с закрытым `<details>` (замерено:
`detailsOpenAttr: false`, `drawerDisplay: "block"`, реальный `getBoundingClientRect`).
Фикс — в `web/tests/external-widgets.spec.ts`, хит-тест перекрытия теперь проверяет
предка `details:not([open])`, не только собственный `display`/`visibility` элемента.
Это устранило 6 из 11 ложных падений (`institute`, `oplata`, `svedeniya`, `seminar`,
`video`, и один из финального списка — числа считаны по прогону `--project=mobile`).

**Оставшиеся 5 падений — не тестовый дефект и не сторонний баг: настоящее перекрытие.**
Измерено на 375×812 (та же ширина, что спека называет проверяемой, `spec.md`, раздел
«Кнопка чата не перекрывает содержимое страницы»):

| Шаблон | Путь | Перекрывает |
|---|---|---|
| home | `/` | карточка «Ближайший семинар» (`rect.top=608, rect.bottom=804.4` — почти вся высота вьюпорта 812) |
| kontakty | `/kontakty` | ссылка `tel:` с номером телефона (`rect.top=761.5, rect.bottom=787.1`) |
| statyi | `/statyi` | две карточки статей |
| raspisanie-i-tseny | `/raspisanie-i-tseny` | `<select>` выбора города (`rect.top=782, rect.bottom=822.6`) |
| course (ИКПК) | `/institut-klinicheskoy-prikladnoy-kineziologii/…` | карточка модуля программы |

Кнопка занимает `x:[327,359], y:[764,796]` на этой ширине (32×32 CSS px + отступ 1rem —
уже уменьшена с 68px до 48px предыдущей правкой для десктопа, `widgets.css:22`
комментарий). На мобильном этого недостаточно: у нескольких шаблонов контент у нижнего
края вьюпорта при скролле 0 занимает почти всю оставшуюся высоту (у карточки семинара
— 196px из 204px свободных), и никакой размер кнопки в разумных пределах не даёт
безопасного угла без изменения самого контента.

**Почему это не чинится точечным CSS и не должно чиниться здесь без решения владельца.**
Правило `AGENTS.md`, раздел «Изменения облика»: перекрывающая кнопка — дефект
(аналогично «невидимая кнопка»), и точечный фикс позиции допустим без мокапов. Но здесь
нет узкого фикса позиции: смещение кнопки требует либо (а) отдельного поведения на
мобильном — скрывать/сдвигать кнопку до прокрутки мимо героя, что не описано ни одним
сценарием спеки и меняет наблюдаемое поведение, либо (б) правки высоты/отступов
ПРЕДСУЩЕСТВУЮЩИХ компонентов (карточка семинара, `<select>` города, карточки статей —
их эта ветка не касалась и не должна), что уже редизайн чужой раскладки, а не фикс
кнопки чата.

**Статус:** красный прогон `test:e2e:widgets --project=mobile` — 5 названных случаев,
воспроизводимо (см. таблицу). Спека называет требование безусловным для 375px без
исключения по scroll-позиции; тест написан по требованию верно. Нужно одно из: мокап
поведения кнопки на мобильном (владелец), либо `/opsx:update` спеки с явным исключением
и его обоснованием. Ни то, ни другое не сделано этой сессией. **Не считать шов
компонентов закрытым по мобильному e2e, пока это не решено.**
