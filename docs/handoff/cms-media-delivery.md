# Передача: медиа CMS не доходят до сайта

Документ для исполнителя, который продолжит работу без моего контекста. Всё, что здесь
написано, измерено; где измерено — сказано чем.

Дата снятия фактов: 06.09.2026. Опорная ревизия: `origin/main@70106210ad93cebeb370ff0d0be00c22aa8c6a84`.
Рабочая ветка: `fix/cms-media-delivery` в отдельном worktree
`/Users/pgorbachev/projects/private/ikpk-wt-media` (создана от свежего `origin/main`,
зависимости `web/node_modules` установлены).

## 1. Задача

На стенде `http://193.124.115.99` не отображаются изображения преподавателей и акций.
Довести до состояния, когда изображения, загруженные редактором в CMS, доходят до сайта, и
закрыть гейтом класс дефекта, а не конкретный симптом.

## 2. Как воспроизвести

```bash
curl -s http://193.124.115.99/aktsii-i-skidki | grep -o '<img[^>]*>'
curl -s -o /dev/null -w '%{http_code}\n' http://193.124.115.99/uploads/1_1732538413910_61932bccdb.webp
curl -s http://193.124.115.99/ | grep -o '<img class="teacher-photo"[^>]*>' | head -3
```

Наблюдается: адреса вида `/uploads/**` отдают 404; у преподавателей `src="[object Object]"`.

## 3. Корневая причина: файлы никогда не переносятся

Снятие снимка забирает записи и не забирает файлы.

- поле для медиа в снимке объявлено — `web/scripts/lib/content-snapshot.ts:24`, `media: SnapshotMedia[];`
  — и в живом снимке пусто: `capture-content-snapshot.ts` создаёт содержимое как
  `const content: SnapshotContent = { types, media: [] };` и больше к `media` не возвращается;
- живой снимок ссылается на **287 уникальных** файлов по `/uploads/**`, всего **313**
  вхождений. Распределение по типам: `articles` 221, `course_groups` 53, `teachers` 29,
  `news` 4, `promotions` 4, `institutes` 2. Внешних (не наших) адресов картинок — 0.
  Пересчитывается на снимке своим выражением:

  ```bash
  node -e "
  const s=JSON.parse(require('fs').readFileSync(process.argv[1],'utf8'));
  const txt=JSON.stringify(s.content.types);
  const refs=[...txt.matchAll(/\/uploads\/[A-Za-z0-9_.\-]+/g)].map(m=>m[0]);
  console.log('вхождений',refs.length,'уникальных',new Set(refs).size);
  " <путь к snapshot.json>
  ```

  Снимок, на котором это измерено, лежит в `/private/tmp/snapshot-main2/snapshot.json`
  (каталог временный — при его пропаже снять заново, см. п. 9);
- в самой CMS файлы на месте и скачиваются: через ssh-туннель
  `http://127.0.0.1:11337/uploads/1_1732538413910_61932bccdb.webp` отдаёт `200`, 6238 байт,
  `image/webp`. На сервере это `/opt/ikpk-cms/shared/uploads` — **533 файла, 26 МБ**, каталог
  вынесен из релиза и подключён симлинком `current/public/uploads → /opt/ikpk-cms/shared/uploads`,
  то есть смену артефакта переживает (проверено `ls -l` на сервере).

Вывод: дефект целиком на нашей стороне конвейера, чинить в CMS нечего.

Легаси-картинки при этом работают, и это сбивает с толку: они пришли **другим путём** —
скачаны в репозиторий (`media-originals/`, git-tracked) и разложены в `web/public/media/`
генератором производных. К CMS этот путь отношения не имеет.

## 4. Второй дефект, независимый: форма поля `photo`

`web/src/lib/data.ts:194`, `  photo: string;` — сайт читает адрес строкой. Соответствие
полей кладёт туда объект:

`web/scripts/lib/content-field-map.ts:122`,
`{ type: 'teachers', field: 'photo', source: 'photo', transform: 'mediaRef' }`

`mediaRef` возвращает `{ url, id }`, поэтому в разметку попадает `[object Object]`.

У акций и новостей форма поля другая и **правильная**: `Promotion.image` и `NewsItem.image`
объявлены объектом (`web/src/lib/data.ts:238` — `NewsItem`, `web/src/lib/data.ts:248` — `Promotion`; обе строки `  image: { url: string; id: string };`), и
компоненты берут `.url`. Там дефект только корневой (п. 3). Не «исправляйте» их заодно —
сломаете.

В закреплённой фикстуре `discovery/entities/teachers.json` у всех 29 записей `photo` —
строка вида `https://storage.yandexcloud.net/ikpk-image/media/...`, которую
`localizeAssetUrls` превращает в `/media/...`. То есть строка — это принятая форма, а
объект в живом пути — расхождение с ней.

## 5. Почему молчали гейты

Гейт ровно на этот класс существует: `web/tests/media-migration.test.ts`, тест
`every image reference resolves locally — no external image hosts`. Он не сработал по двум
причинам, и обе про **условия измерения**, а не про сам гейт.

1. Он в наборе `test:build` и запускается по **закреплённой фикстуре**, где медиа — легаси
   `/media/**`, лежащие на диске. Сборка из **живого** снимка идёт через
   `scripts/deploy-web.sh`, и этот гейт там не прогоняется вовсе: деплой проверяет ссылки
   форм (`form_links_match_mode`), виджет чата (`chat_widget_matches_mode`) и платёжный
   контур — проверки изображений среди них нет.
2. `[object Object]` он не увидел бы и на живом снимке: ссылка, не начинающаяся с `/`,
   отбрасывается как относительная — `if (!ref.startsWith('/')) continue;`. Это тишина
   вместо исхода: «не путь и не схема» — само по себе расхождение, а не повод пропустить.

Отсюда две обязательные части работы, помимо самой доставки: деплой обязан прогонять
проверку разрешимости изображений по собранному `dist`, и отбрасывание «относительных»
ссылок должно стать расхождением.

## 6. Где это специфицировано

Работа **не новая**: она лежит в активном change `cms-content-authoring-and-migration`
(9/91 задач), спека `openspec/changes/cms-content-authoring-and-migration/specs/cms-media-pipeline/spec.md`.
Оттуда два требования:

- «Изображения отдаются с сайта, а не из системы управления» — адреса изображений на
  странице статические адреса сайта, ни один не указывает на хост системы управления;
- «У каждого отдаваемого изображения есть производные и известные размеры» — набор
  производных ширин и запись размеров обязательны, адаптивный набор ссылается только на
  существующие файлы, **отсутствие производных или размеров останавливает сборку**.

На контент-адресуемое хранилище медиа уже написаны красные тесты —
`web/tests/cms-snapshot-media.test.ts`, задача 3.7 не сделана. Их не переписывать: они часть
предмета. Контракт будущего модуля объявлен в
`web/tests/helpers/cms-content-publication-contract.ts` (`MediaStoreModule`: `contentIdOf`,
`readFromStore`, исходы `content-id-mismatch` и `missing` различены).

## 7. Замысел реализации: переиспользовать существующий тракт

Ключевое решение — **не строить второй медиа-тракт**. У проекта уже есть трёхуровневая
схема: оригинал (не отдаётся) → производные в `web/public/media/` → манифест размеров
`web/src/lib/media-manifest.json`, из которого берутся `width`/`height` и `srcset`. Медиа CMS
встраиваются в неё, а не рядом с ней.

Швы:

1. `web/scripts/lib/content-media-store.ts` — новый модуль, контент-адресуемое хранилище
   (`contentIdOf`, `readFromStore` с проверкой прочитанного по идентификатору);
2. `web/scripts/capture-content-snapshot.ts` — при живом съёме скачивает каждый медиафайл,
   кладёт байты в хранилище по идентификатору содержимого, заполняет `content.media`.
   Недокачанный файл — **отказ съёма**, а не тихий пропуск: это тот же принцип, что уже
   принят для пустого съёма;
3. `web/scripts/prepare-snapshot.ts` — материализует медиа снимка на диск сборки, читая из
   хранилища с проверкой идентификатора;
4. `web/scripts/make-derivatives.ts` — второй корень оригиналов помимо `media-originals/`,
   чтобы медиа CMS получили производные и записи манифеста;
5. `web/src/lib/media.ts`, `localizeAssetUrls` — переписывает `/uploads/<файл>` в
   `/media/uploads/<файл>`. Место выбрано потому, что рерайт применяется к **сырому тексту
   снимка до разбора** (`web/src/lib/data.ts:81`, `  _snapshot = JSON.parse(localizeAssetUrls(raw)) as SnapshotFile;`),
   то есть одним изменением накрывает и поля-строки, и поля-объекты, и картинки внутри
   HTML-тел статей. Рерайт обязан быть привязан к границе (кавычка, `=`), иначе зацепит
   внешний адрес, содержащий `/uploads/`;
6. `web/tests/media-migration.test.ts` — ссылка изображения, не являющаяся ни схемой, ни
   root-relative путём, становится расхождением;
7. `scripts/deploy-web.sh` — прогон проверки разрешимости изображений по собранному `dist`
   перед выкладкой.

Почему целевой префикс именно `/media/uploads/`: `srcsetFor` в `web/src/lib/media.ts`
собирает адрес варианта как `/media/_w/<ширина><путь без префикса /media>`, а генератор
производных кладёт вывод в `web/public/media/<путь относительно корня оригиналов>`. Любой
другой префикс потребует править обе эти механики.

## 9. Ловушки стенда, на которых уже терялось время

- **Туннель к CMS.** Админка и REST доступны только через ssh-туннель на порт **11337**
  (`ssh -L 11337:127.0.0.1:1337`). Порт 1337 снаружи закрыт намеренно, `/admin` отдаёт 404 —
  это требование владельца, не чинить. Проверять туннель **только**
  `lsof -nP -iTCP:11337 -sTCP:LISTEN`: `pgrep` показывает живой процесс ssh и при мёртвом
  пробросе. Упавший туннель в прошлый раз привёл к тому, что запросы ушли в локальный dev-Strapi
  на 1337 и вернули чужие 401 — час разбирательства на ровном месте.
- **Память.** На машине 948 МБ плюс своп, Strapi в пике 493 МБ. Любой `du`/`find /` по всему
  диску держит I/O в потолке минутами, и Strapi при этом выглядит зависшим. Не запускать
  обходы всего диска; спрашивать конкретные каталоги.
- **Готовность после смены артефакта** измерена в 142 с на свободной машине и 370 с под
  давлением памяти; `SERVICE_HEALTH_TIMEOUT=600` в `deploy/environments/stand.env`.
  Гейт готовности платёжного контура может дать ложное красное сразу после старта —
  зарегистрировано как TD-62 (PR #233, открыт).
- **Пустой съём.** Снятие сразу после перезапуска CMS однажды дало снимок с нулём записей во
  всех типах, и контракт его принял: на пустоте нарушать нечего. Отказ на пустом съёме
  добавлен, PR #234 — **открыт, не слит**. Пока он не слит, после смены артефакта
  пересчитывать число записей руками (здоровый снимок — 338 записей).
- **Ключ доступа** к серверу: `~/.ssh/id_ed25519_ikpk_vps`, пользователь `root`. Без `-i`
  ssh отвергается по publickey.

## 10. Обязательные ограничения владельца

Действуют без срока, нарушать нельзя:

- не публиковать комментарии, ревью и PR в GitHub без прямого разрешения в текущем диалоге;
- не делать `push` без явного разрешения;
- секреты стенда не выводить в команды, логи и артефакты (маска — минимум 16 символов;
  значения секретов стенда 24 символа). Один раз они уже утекли в вывод и были перевыпущены;
- секреты VPS не хранить в GitHub;
- rich HTML из CMS обязан идти через уже принятую единую границу `rich-content-safety`;
  второй санитайзер или второй sink не создавать;
- медиа CMS не должны отдаваться с хоста Strapi — это и есть причина, по которой файлы
  переносятся в сборку, а не проксируются;
- CMS не должна быть доступна заказчику до появления журнала происхождения.

## 11. Как проверять

Локальные гейты `web/`: `npm run lint`, `npm run typecheck`, `npm run build`, плюс
`npm run test:build` — работа затрагивает сборочный вывод и медиа, так что он обязателен.
`./bin/check-spec-refs` прогонять локально: он блокирует merge, и узнавать о его красноте из
CI — узнавать позже всех. Перед выводом «у меня зелено» — `git fetch --prune`.

Негативная проверка обязательна для каждого нового гейта: вернуть дефект и убедиться, что
гейт покраснел, записав **точную мутацию и два числа — до и после**. Судить по имени
покрасневшего теста, а не по цвету прогона: у проекта уже был случай, когда мутация красила
прогон падением соседних тестов, а проверяемый гейт оставался зелёным.

Приёмка по существу — та же, что владелец уже принимал для CMS: правка в админке доходит до
сайта. Здесь дополнительно: изображение, **загруженное через админку**, видно на собранной
странице, и его адрес не указывает на хост CMS.

## 12. Push и приёмочный деплой на стенд

Это отдельный финальный этап после реализации, двух code review, ponytail-review и локальных
гейтов. Push и выкладка выполняются только после явного разрешения владельца в текущем
диалоге; до этого можно подготовить команды и проверить их локально.

1. Зафиксировать итоговую ревизию: ветка должна быть перебазирована на свежий
   `origin/main`, все находки ревью закрыты, рабочее дерево чистое. Перед коммитом проверить
   `git status --short --branch` и `git diff --cached --name-status`; после коммита записать
   полный SHA (`git rev-parse HEAD`).
2. После разрешения владельца отправить именно эту ветку:

   ```bash
   git push -u origin fix/cms-media-delivery
   ```

   В журнале приёмки сохранить полный SHA, который ушёл на `origin`, а не только имя ветки.
   Push ветки сам по себе не является выкладкой на стенд.
3. Перед live-съёмом проверить туннель **только** так:

   ```bash
   lsof -nP -iTCP:11337 -sTCP:LISTEN
   ```

   Если слушателя нет — сначала восстановить `ssh -L 11337:127.0.0.1:1337`; не подменять
   CMS локальным портом 1337 и не продолжать съём.
4. Снять свежий снимок из CMS через туннель. `CMS_TOKEN` должен быть заранее передан в
   окружение из секретного хранилища и не попадать в команду, лог или артефакт:

   ```bash
   CMS_URL=http://127.0.0.1:11337 \
   CONTENT_SNAPSHOT_DIR="$PWD/web/.snapshot" \
   npm --prefix web run snapshot:capture
   ```

   Отсутствие файла, ошибка HTTP или пустой/неполный съём — отказ этапа; к деплою не
   переходить. Зафиксировать `snapshotId` и число записей. Снимок должен содержать медиа,
   а не только ссылки на `/uploads/**`.
5. Выполнить ручной деплой ровно из того же worktree и SHA:

   ```bash
   SSH_KEY=~/.ssh/id_ed25519_ikpk_vps \
   DEPLOY_MODE=stand \
   CHAT_LOADER_SRC=none \
   SITE_URL=http://193.124.115.99/ \
   ./scripts/deploy-web.sh 193.124.115.99
   ```

   Скрипт сам пересобирает сайт, прогоняет медиа-гейт по собранному `dist` и только затем
   загружает релиз. Ненулевой код, провал media-gate или health-check — неуспешный деплой,
   даже если symlink уже был переключён.
6. После успешного health-check проверить стенд по фактическому HTML и файлу:

   ```bash
   curl -fsS http://193.124.115.99/aktsii-i-skidki | grep -E '/media/uploads/|/media/_w/'
   curl -fsS http://193.124.115.99/ | grep -qv '\[object Object\]'
   curl -fsS -o /dev/null -w '%{http_code}\n' \
     http://193.124.115.99/media/uploads/<имя-файла-из-снимка>
   ```

   Для приёмки нужен именно файл, загруженный/изменённый в CMS до live-съёма: проверить,
   что он доступен через `/media/uploads/...`, в HTML нет `/uploads/...` и
   `[object Object]`, а адрес не указывает на хост CMS. Записать commit SHA, `snapshotId`,
   release ID и результаты curl-проверок.
7. Если live-проверка провалилась, выкладку считать не принятой: сохранить вывод гейта и
   health-check, не удалять предыдущий релиз и отдельно принять решение об откате. Откат —
   переключение `/var/www/ikpk/current` на предыдущий каталог релиза с последующим
   `nginx -t` и `systemctl reload nginx`; после него повторить smoke-проверки и записать
   причину.
