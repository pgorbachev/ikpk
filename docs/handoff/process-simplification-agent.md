# Задание агенту: упростить процесс разработки IKPK

## Цель и границы

Владелец хочет быстрее довести демо до рабочего состояния и сократить повторные
согласования, ревью и расход контекста. OpenSpec нужен для согласования новых
пользовательских возможностей и изменений их поведения. Обычные технические задачи
должны выполняться без полного цикла OpenSpec; глубина проверок зависит от риска.

Результат этой задачи — небольшой согласованный PR с изменениями инструкций процесса.
Приведённая ниже политика — постановка владельца на реализацию. Не создавай отдельный
OpenSpec change для изменения самого процесса и не запускай старый полный конвейер
ради этой правки документации. Для этого PR достаточно проверки согласованности,
релевантных действующих гейтов и одного независимого ревью перед приёмкой владельцем.
Новые продуктовые или инфраструктурные решения в эту задачу не входят.

## 1. Разделить задачи по изменению поведения и риску

Вместо «всё значительное требует полного цикла» зафиксируй следующие пути.

| Тип задачи | Достаточный процесс |
| --- | --- |
| Новая пользовательская возможность или изменение доступного пользователю поведения | Короткий OpenSpec change с поведением и критериями приёмки → согласование владельцем → реализация с проверками → независимое ревью и приёмка → архив |
| Техническая задача, сохраняющая пользовательское поведение и контракты | Цель и ожидаемый результат в задаче/PR → реализация → релевантные проверки → одно независимое ревью; без нового OpenSpec change |
| Исправление отклонения от принятого поведения | Воспроизведение → регрессионная проверка и исправление → независимое ревью; без новой спеки |
| Простая правка текста, перевода или настройки формы без изменения возможностей | Правка → соразмерная проверка результата; отдельный автотест и согласование спеки не обязательны |

Пользователь — также администратор сайта. Название «техническая задача» не позволяет
скрыть изменение его возможностей. Например, кнопка обновления сайта — продуктовая
возможность, а рефакторинг её внутреннего кода при прежнем поведении — техническая задача.

Риск оценивается отдельно. Изменения прав доступа, денег, персональных данных,
миграций, внешних контрактов, выкладки и защитных гейтов требуют краткого описания:
что может сломаться, как это проверить, как восстановиться при неудаче. Оно может
жить в задаче/PR; само по себе не требует четырёх новых документов OpenSpec.
Риск определяется изменением поведения системы, а не одним фактом касания файла.

Существующие принятые спецификации остаются источником требований. Нельзя молча
нарушить их под видом технической задачи. При изменении закреплённого контракта
явно согласуй его дельту и обнови затронутые требования; не создавай дублирующую
спеку, если изменение уже покрывается существующим change. Документирование
существующего поведения не должно блокировать исправление или поставку функции.

## 2. Сократить согласования и артефакты

- Владелец согласует пользовательское поведение, объём и существенные риски.
  Выбор внутренней реализации в этих границах исполнитель делает самостоятельно.
- Уже согласованные решения повторно не предъявляются как открытые вопросы.
  Повторное согласование нужно при изменении поведения, объёма или существенного риска.
- Исправления формулировок, ссылок и приведение артефактов к принятому решению
  не требуют поштучного утверждения перед каждой записью.
- Одному пользовательскому сценарию соответствует цельная постановка. Не создавай
  отдельные changes для каждой технической подзадачи внутри неё.
- Не меняй схему OpenSpec и его CLI ради этой задачи. Если схема требует proposal,
  design, specs и tasks, оставь их краткими, без повторения требований во всех файлах.
- Категорию и риск задачи исполнитель коротко обосновывает в описании PR.
  Вопрос владельцу нужен при содержательной неопределённости, влияющей на результат
  или риск, а не автоматически при любом сомнении о названии категории.

## 3. Сделать тестирование соразмерным

- Нет обязательной отдельной сессии для написания всех тестов. Исполнитель может
  писать тесты и код в одной сессии; независимость сохраняется на этапе ревью.
  Отдельный автор тестов полезен для рискованных или неоднозначных контрактов.
- Для воспроизводимого программного дефекта по умолчанию нужен регрессионный тест,
  падающий на исходном дефекте и проходящий после исправления. Для простой правки
  документации, перевода или настройки не требуй искусственного RED.
- Если автотест не даёт полезной проверки или требует несоразмерной инфраструктуры,
  допускается воспроизводимая ручная/стендовая проверка с краткой причиной и результатом.
  Критичный инвариант нельзя объявить проверенным одной визуальной оценкой формы.
- Не требуй мутации для каждого нового теста. RED на исходном дефекте уже доказывает
  чувствительность соответствующего теста; повторять ту же проверку мутацией незачем.
- Для нового или существенно изменённого защитного гейта нужна целевая негативная
  проверка: нарушить именно охраняемое условие и убедиться, что оно обнаружено.
  Это может быть тестовая фикстура или воспроизведение дефекта; отдельное временное
  повреждение рабочего кода не обязательно. Ошибку запуска теста не считать таким доказательством.
- Для критичных инвариантов выбирай негативные сценарии по конкретным рискам:
  например, чужие права, потеря связи, сбой активации релиза. Не вводи универсальный
  процент mutation coverage или новый обязательный тестовый инструмент.
- Если временная мутация всё же нужна, сохрани правила её изоляции и восстановления.
- Запускай проверки, относящиеся к изменению. После успешного прогона повторение
  нужно при новых изменениях, сбоях или оставшемся конкретном вопросе.

## 4. Упростить ревью и выбор исполнителей

- По умолчанию одно независимое ревью; автор не принимает собственную реализацию.
- Для высокого риска — два независимых ревью. Критерий: ошибка может привести
  к потере/раскрытию данных, неправомерному доступу, неверным платежам или остановке
  сайта без простого проверенного восстановления. Число файлов и наличие change
  сами по себе не делают задачу высокорисковой.
- Проверка переусложнения входит в обычное ревью: что удалить, где использовать
  штатный механизм. Отдельный обязательный третий проход /ponytail-review отменить;
  инструмент может оставаться доступным по необходимости.
- Проверять исправленные находки и их последствия; полный повторный проход нужен
  при существенном изменении предмета, а не после любой редакционной правки.
  Ревью всегда привязано к ревизии; для новой головы явно указывать, что перепроверено.
- Завершение ревью: требования выполнены, блокирующие находки закрыты, оставшиеся
  ограничения названы и приняты соразмерно их влиянию. Не требовать бесконечных
  полных кругов ради отсутствия любых новых замечаний.
- Выбирать модель по сложности и риску. Убрать универсальное требование самой
  сильной модели для всех спек и ревью, обязательные названия моделей и инструментов.
  Сильная модель уместна для сложного анализа и высокого риска; независимость
  проверяющего сохраняется при любом выборе инструмента.

## 5. Устранить противоречия, сохранив полезные ограничения

Заменяй старые требования, не добавляй поверх них раздел «можно проще».
Проверь таблицу конвейера, раздел тестов, правила дефектов, baseline, стоп-правило
ревью, критерии готовности и инструкции propose/update/apply/archive в обеих
системах агентов. Базовые правила должны иметь один источник; в skills — ссылка
и только необходимые особенности команды, а не копия всего процесса.

Истёкший 24.09.2026 эксперимент не продлевать автоматически. Убери его из действующих
обязательств, сохрани ссылку на историю и сам журнал переходов. Полезные части,
которые остаются действующими, сформулируй явно в постоянных правилах, согласованно
с этой постановкой. Старые журнал, backlog и согласованные решения не удаляй.

Сохрани изоляцию worktree, защиту чужих изменений, проверки полномочий, честность
отчётов, требования к секретам и ограничения публикации от имени владельца.
Сохрани действующие продуктовые и технические инварианты. Не меняй CI workflows,
branch protection, исполняемый код гейтов, runtime, инфраструктуру или секреты.
Упрощение инструкций не разрешает обходить существующий обязательный CI.
Если найдено противоречие с CI, предъяви его отдельно с минимальным предложением.

Не превращай задачу в полную переработку всей документации или новый реестр рисков.
Убирай дубли и устаревшие обоснования в затронутых разделах. Не переписывай архивные
свидетельства и отзывы так, будто новые правила действовали раньше.

## Проверка результата и поставка

Предъяви короткую таблицу «было → стало» и примеры классификации:

1. Перевод кнопки CMS — без OpenSpec и обязательного нового автотеста.
2. Добавление проведения из семинара — пользовательская возможность с критериями приёмки.
3. Рефакторинг helper без изменения контракта — технический путь, существующие проверки.
4. Исправление порядка дат — регрессионная проверка; новый change не нужен, если правило уже принято.
5. Миграция БД или изменение активации релиза — план риска и восстановления;
   глубина ревью зависит от последствий, а не от наличия UI.
6. Новый гейт прав доступа — негативный сценарий обязателен; мутации всех прочих тестов не нужны.

Проверь поиском, что старые универсальные требования не остались в действующих
инструкциях. Различай действующее правило, условное правило и историческую цитату.
Не добавляй тест, проверяющий буквальную формулировку текста AGENTS.md.

Запусти git diff --check и релевантные существующие проверки документации/интеграции.
Если затронуты артефакты OpenSpec, проверь их штатной валидацией и check-spec-refs.
Не запускай полный build/browser suite только ради правки инструкций локально;
обязательные CI jobs пусть выполняются как настроено.

Отчёт: файлы и краткий diff, команды и результаты, оставшиеся противоречия,
объём корневого AGENTS.md до/после в символах или байтах. Экономию токенов и времени
не выдавай за измеренную без замера. Проведи одно независимое ревью и подготовь PR
для владельца. Самостоятельно не merge. Не публикуй комментарии/ревью от лица
владельца без его явного разрешения.
