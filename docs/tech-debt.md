## TD-1 — Дублирование логики пагинации в statyi/index.astro

**Файлы:** `web/src/pages/statyi/index.astro`
**Метки в коде:** `TODO(TD-1)` (2 места — серверная `buildPaginationTokens` и клиентская `getPaginationTokens`)

**Проблема:**
Алгоритм построения токенов пагинации продублирован дважды: серверная функция для SSG initial render и клиентская для динамической перестройки при фильтрации. При изменении алгоритма нужно обновлять оба места.

## TD-2 — Все статьи как `<template>` в HTML на странице /statyi

**Файлы:** `web/src/pages/statyi/index.astro`
**Метки в коде:** `TODO(TD-2)`

**Проблема:**
Клиентская фильтрация/поиск работает через скрытые `<template>` теги — все статьи рендерятся в HTML при сборке. При росте каталога страница будет тяжёлой (сейчас 68 статей — приемлемо).

**Решение (на выбор):**
1. Статические пагинированные страницы `/statyi/page/2` — нет JS-поиска.
2. JSON-индекс `/statyi-index.json` — клиент грузит один раз, рендерит карточки динамически. Сохраняет поиск/фильтрацию без раздутого HTML.

**Когда актуально:** при росте каталога свыше ~200 статей.

## TD-3 — Пагинация /statyi без fallback при отключённом JS

**Файлы:** `web/src/pages/statyi/index.astro`
**Метки в коде:** нет (архитектурный долг)

**Проблема:**
Пагинация реализована через `<button>` + клиентский JS. При отключённом JavaScript или ошибке загрузки скрипта пользователь и поисковый бот видят только первые 6 статей — нет ни ссылок, ни URL для остальных страниц.

**Решение (на выбор):**
1. Статические страницы `/statyi/page/2`, `/statyi/page/3` — работают без JS, индексируются поисковиками.
2. `<a href="?page=2">` с прогрессивным улучшением через JS — сохраняет URL-навигацию и работает без скриптов.

**Когда актуально:** сейчас некритично (SEO покрывается SSG), но желательно до роста каталога.

## TD-7 — Откат релиза выполняется руками

**Метки в коде:** `scripts/deploy-web.sh` (сообщение при провале health-check)

**Проблема:**
Провал health-check теперь роняет деплой ненулевым кодом, но symlink `current` к этому
моменту уже переключён: сломанный релиз остаётся активным, и восстановление — ручное
(перевести symlink на предыдущий каталог в `releases/`, перезагрузить nginx).

**Решение:** автоматический откат — запомнить предыдущую цель symlink до переключения,
при провале health-check вернуть её и перезагрузить nginx, затем завершиться ненулевым
кодом. Отдельная работа, потому что требует решения, что считать провалом (одна
страница или набор) и как отличать провал релиза от недоступности сети.

**Когда актуально:** до первого боевого деплоя.

## TD-8 — Импорт в CMS сообщает об ошибках и завершается нулём

**Метки в коде:** `scripts/import.ts`

**Проблема:**
`report.errors` и `report.missingRelations` печатаются в итоговом отчёте (`TOTALS: … ❌ N
errors`), после чего `main()` завершается нормально — код выхода 0. Импорт с потерянными
сущностями и оборванными связями выглядит успешным. Отдельно: `catch` при загрузке файла
(`import.ts:246`) создаёт сущность без изображения, не увеличивая никакого счётчика.

Тот же класс, что закрыт для `make-derivatives`, `gen-redirects`, `refresh-catalog`,
`recover-collapsibles`, `download-media` и `localize-upload-links`, но здесь ставка выше:
пишется в CMS заказчика, и повторный запуск не идемпотентен.

**Решение:** ненулевой код выхода при непустых `errors`/`missingRelations`, счётчик
неудачных загрузок файлов, осознанный обход отдельным флагом.

**Когда актуально:** до следующего запуска импорта в CMS заказчика.
