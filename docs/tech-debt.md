## TD-1 — Дублирование логики пагинации в statyi/index.astro

**Файлы:** `web/src/pages/statyi/index.astro`
**Метки в коде:** `TODO(TD-1)` (2 места — серверная `buildPaginationTokens` и клиентская `getPaginationTokens`)

**Проблема:**
Алгоритм построения токенов пагинации продублирован дважды: серверная функция для SSG initial render и клиентская для динамической перестройки при фильтрации. При изменении алгоритма нужно обновлять оба места.

**Решение:**
Вынести в `web/src/lib/pagination.ts` как чистую функцию и импортировать из обоих мест (Astro компилирует `<script>` с поддержкой ESM).

## TD-2 — Все статьи как `<template>` в HTML на странице /statyi

**Файлы:** `web/src/pages/statyi/index.astro`
**Метки в коде:** `TODO(TD-2)`

**Проблема:**
Клиентская фильтрация/поиск работает через скрытые `<template>` теги — все статьи рендерятся в HTML при сборке. При росте каталога страница будет тяжёлой (сейчас 68 статей — приемлемо).

**Решение (на выбор):**
1. Статические пагинированные страницы `/statyi/page/2` — нет JS-поиска.
2. JSON-индекс `/statyi-index.json` — клиент грузит один раз, рендерит карточки динамически. Сохраняет поиск/фильтрацию без раздутого HTML.

**Когда актуально:** при росте каталога свыше ~200 статей.

## TD-3 — Пагинация /statyi без fallback при отключённом JS

**Файлы:** `web/src/pages/statyi/index.astro`
**Метки в коде:** нет (архитектурный долг)

**Проблема:**
Пагинация реализована через `<button>` + клиентский JS. При отключённом JavaScript или ошибке загрузки скрипта пользователь и поисковый бот видят только первые 6 статей — нет ни ссылок, ни URL для остальных страниц.

**Решение (на выбор):**
1. Статические страницы `/statyi/page/2`, `/statyi/page/3` — работают без JS, индексируются поисковиками.
2. `<a href="?page=2">` с прогрессивным улучшением через JS — сохраняет URL-навигацию и работает без скриптов.

**Когда актуально:** сейчас некритично (SEO покрывается SSG), но желательно до роста каталога.

## TD-6 — Браузерные проверки не сверяют код ответа

**Метки в коде:** нет

**Проблема:**
Измерено на этой ветке: из переходов `page.goto` в `web/tests/*.spec.ts` **81 не
захватывает ответ вовсе** — `a11y.spec.ts` 2 из 2, `site.spec.ts` 19 из 20,
`compare.spec.ts` 58 из 60, `compat.spec.ts` 2 из 3. Проверка, выполненная на странице
404, при этом не падает: страница маленькая, нарушений axe на ней нет, DOM-утверждения не
находят элементов и молчат либо ждут таймаут, а причина в отчёте выглядит как поломка
компонента.

Это не гипотеза. На ветке `feat/demo-mode-and-hero-photo` (PR #27) ровно так проверялись
**10 шаблонов доступности из 14**: адреса шли со слэшем на конце при
`trailingSlash: 'never'`, и «36 проверок доступности» в описании PR означали одну
проверенную главную. Там это закрыто обязательной сверкой кода ответа; здесь, в `main`,
проверки остались прежними — сборка отдаёт обе формы адреса, поэтому дефект пока не
проявляется, но зависит от конфигурации, а не от самих проверок.

Часть набора уже устроена иначе и переделки не требует: `compare.spec.ts` и
`parity-compare.test.ts` сверяют `status < 400`, а `web/tests/helpers/navigation.ts`
распознаёт неотданную страницу по разметке — слабее кода ответа (не отличит 500 с иной
разметкой), но не молча.

**Решение:**
Захватывать ответ у каждого перехода и сверять с ожидаемым кодом: `200` там, где
проверяется содержимое; ожидаемый `301`/`404` там, где предмет — сам ответ, без следования
редиректу. Правило записано в `AGENTS.md`, раздел «Дефекты: red/green и негативная проверка
гейтов»; оно действует на новые проверки и на те, которых касается работа, поэтому долг
закрывается постепенно, а не одной переделкой набора.

**Когда актуально:** при слиянии PR #27 (там появляется `trailingSlash: 'never'`, и любой
адрес со слэшем начинает отдавать 404) — то есть до него, иначе часть проверок станет
вакуумной молча.
