# Релизы и допуск к деплою

Правило владельца от 20.10.2026: код сайта и CMS разворачивается только из
**опубликованного GitHub Release `vX.Y.Z` с зелёным CI на точном SHA тега**.
Draft, Prerelease, ветка, произвольный SHA и один Git-тег допуском не являются.
Это техническое правило поставки; отдельный OpenSpec change для него не требуется.

## Выпуск версии

1. Слить изменения в `main`. Выбрать полный SHA; для новой публикации существующий
   launcher требует, чтобы это была текущая голова канонического `main`.
2. Дождаться успешного CI именно этого SHA в `pgorbachev/ikpk`: `Tests`,
   `Lint and Typecheck`, `Security`, `Lighthouse CI`. Для каждого workflow нужен
   последний канонический main-прогон (`push` или `schedule`), завершённый с `success`,
   и успех всех обязательных jobs. Красный, отсутствующий, выполняющийся,
   отменённый или пропущенный обязательный результат блокирует выпуск и деплой.
   Зелёный PR и локальные тесты не заменяют CI после merge.
3. Создать тег `vX.Y.Z` на этом полном SHA и опубликовать GitHub Release с этим тегом,
   без Draft/Prerelease. В описании указать изменения, SHA, ссылки на CI и условия
   восстановления. Версия — три неотрицательных числа без ведущих нулей;
   `-rc`, `+build` и тег `prod-2026-10-19` под это правило не подходят.
4. Перед упаковкой или установкой кода выполнить проверку (Node 24, `GH_TOKEN`
   предоставляется защищённым окружением с правами чтения Contents и Actions):

   ```bash
   node web/scripts/release-preflight.ts --release-tag v1.0.0 --commit <полный-SHA>
   ```

   Нужен код выхода 0 и `status: admitted`. Команда только читает GitHub API;
   сама не создаёт релиз, не устанавливает код и не публикует сайт. Проверка
   разыменовывает настоящий тег, включая annotated tags: `target_commitish: main`
   в GitHub Release не является доказательством SHA.
5. Разворачивать код и собирать payloads из той же чистой ревизии. Для публикации
   сайта указывать `--release-tag v1.0.0` в штатном launcher; остальные параметры —
   по [runbook деплоя](deploy-vps.md). Launcher повторяет допуск через GitHub API;
   отдельный preflight его не заменяет. После активации проверить фактически
   отдаваемый `/release.json`, health и пользовательский сценарий, сохранить
   версию, SHA, CI run IDs и результат в записи поставки.

Тег и опубликованную версию не переносить и не переиспользовать. Исправление — новая
версия. Если `main` ушёл вперёд до запуска или во время подготовки, существующий
launcher откажет: дождаться CI новой головы и выпустить новую версию. Зелёный CI
не отменяет проверки снимка CMS, миграций, резервных копий и назначения.

Обязательные jobs `Tests` и проверки количества тестов сохраняются. Дополнительно
проверяются все package checks и `OpenSpec integration` в `lint.yml`, Secret scan,
runtime audits web/scripts/payments и исправность CMS audit report в `security.yml`,
а также Lighthouse budgets в `lighthouse.yml`. CMS audit остаётся report only по
найденным advisory; сбой самого измерения блокирует допуск. Ночные и Dependabot
workflow не являются релизным CI для коммита; их цвет не заменяет эти четыре workflow.

## Обновление контента и восстановление

Кнопка CMS «Обновить сайт» публикует новый снимок контента на уже установленном коде
допущенного релиза. Она не является разрешением установить новую ревизию кода.
Для репетиции с нерелизным кодом нужен отдельный изолированный стенд и явно
согласованная задача; это не production-деплой и не принятие релиза.

Откат выбирает ранее принятую публикацию из индекса назначения и проверяет её
сохранённые байты штатным механизмом. Старые записи сохраняют первоначальное
свидетельство CI: добавление нового правила не лишает действующий сайт пути
восстановления и не требует задним числом создавать релизы. `recover` завершает
уже начатую операцию, а не даёт допуск новой ревизии. Ручной перенос файлов и смена
`current` не заменяют допуск новой версии.

## Ввод правила в эксплуатацию

Изменение репозитория само не обновляет установленный launcher или CMS на VPS.
Перед использованием нового процесса установить согласованную версию launcher
и worker, проверить защищённую конфигурацию и выполнить репетицию на стенде.
Установочные и старые trial-скрипты не получают собственного обхода правила:
оператор обязан выполнить preflight перед установкой кода. Проверка внутри
launcher автоматически блокирует новую публикацию без допущенного релиза;
это не утверждение, что все исторические установочные скрипты уже имеют такой гейт.

Риск изменения — отказ ранее допустимого деплоя из `main` без релиза или при
красном дополнительном workflow. Проверка — негативные сценарии для release/tag/SHA
и каждого обязательного workflow плюс существующие publication/rollback suites.
Восстановление действующей раздачи — штатные `rollback`/`recover`; обход допуска
для новой версии ради устранения отказа запрещён.

Технические основания: [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name),
[GitHub workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow).
