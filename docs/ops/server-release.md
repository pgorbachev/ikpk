# Серверный выпуск одной командой

Статус: реализация в разработке, живая установка и приёмка не выполнялись. Владелец разрешил продолжить интеграцию и приёмку на 193 после проверок; production требует отдельного разрешения. Проверять окончательный SHA и результаты ревью PR. Миграции CMS/БД выполняются отдельным процессом по `production-data-migrations.md`, а не командой ниже.

## Операторский путь

После установки доверенных компонентов и принятия назначения:

```sh
./deploy.sh demo --sha FULL_40_CHARACTER_SHA
./deploy.sh prod --sha FULL_40_CHARACTER_SHA
```

Оператор запускает deploy.sh из доверенного проверенного checkout/tooling. Целевой SHA задаётся отдельно; скрипт до admission не checkout-ит и не исполняет целевой код. Локальный GitHub CLI (`gh`) аутентифицирован в каноническом аккаунте и только читает точный последний eligible run, его jobs и ZIP artifact для указанного SHA/ref. Demo принимает dev, prod — main. Для prod перед SSH резервируется неизменяемый `prod-src-<полный SHA>` tag; совпадающий tag переиспользуется. Ноутбук закрепляет SSH-ключ, сохраняет и показывает request ID до отправки. Сервер без GitHub token проверяет связанность source identity, SHA, manifest и digest, затем отдельно строит кандидат на сервере. Команда ждёт итог, но разрыв SSH не прекращает принятую systemd-операцию.

```sh
./deploy.sh demo status REQUEST_UUID
./deploy.sh demo --request-id REQUEST_UUID
./deploy.sh demo recover
./deploy.sh demo rollback RETAINED_RELEASE --reason 'Причина возврата'
```

Повтор известного UUID возвращает ту же операцию. Параметры уже принятого запроса не меняются; новый UUID означает новый запрос. При потере ответа сначала запросить status известного UUID. `not-found` означает, что сервер не нашёл квитанции; `unknown` — что менеджер процессов недоступен либо приём запроса ещё не подтверждён; это не доказательство остановки. `interrupted`/неопределённый результат требуют проверки current/pending и штатного recover. Нельзя вручную удалять pending или незавершённые квитанции ради следующего запуска.

На одном VPS один общий flock допускает только одну тяжёлую операцию demo/prod. При занятости другая операция завершается busy, без очереди и без второй сборки. Существующая блокировка активации назначения также сохраняется.

## Однократная установка (отдельная разрешённая операция)

Требуются Linux, systemd user manager с linger, util-linux flock, Node не ниже 22.16 с `node:sqlite`/backup, Git, unzip и зависимости существующего publisher. Использовать результат отдельного исследования ресурсов, а не ставить всё на production без проверки.

На сервере вне Git checkout установить `scripts/server-deploy.mjs`, `scripts/release-test-policy.mjs` и `scripts/release-test-reports.mjs` с сохранением их соседней структуры в каталоге назначения с защищёнными правами. Источник CI проверяется локальным доверенным операторским tooling до отправки; `release-ci.mjs` и GitHub credential на сервере не устанавливаются. `server-deploy.mjs` повторно проверяет переданный run/attempt и ZIP-доказательство, сохраняет его в приватном `operations/<request-id>/tests.json` и передаёт доверенному launcher только путь к этому файлу. Launcher сверяет доказательство офлайн и отдельно подтверждает канонический branch/SHA; он не обращается к GitHub и не читает `ciTokenFile`. Существующие publication-launcher, config, broker и runtime устанавливаются штатным способом из deploy-vps.md. Исполнитель не должен запускаться root. Каталог установки/файлы не доступны для записи другим пользователям; операции хранятся в приватном `operations/` этого каталога.

**DEMO и production — разные сервисные учётные записи и SSH-доступы.** DEMO-пользователь не читает production config/broker и не может менять production webRoot/current. На одном VPS это проверяется реальными отказами доступа, а не полем JSON. Оба пользователя получают только доступ к общему regular lock-файлу, например `/var/lock/ikpk-build.lock`; файл не world-writable, родительский каталог не позволяет его заменить. Изоляцию проверить до допуска dev-кода. Для SSH-ключа использовать `restrict` и forced command:

```text
command="/absolute/node /opt/ikpk-publication/demo/server-deploy.mjs gateway",restrict ssh-ed25519 PUBLIC_KEY
```

Gateway принимает только точную команду submit или status с UUID; execute запускается локально systemd. Пути Node/entry клиента должны совпадать с установленными путями на сервере. Ключ не должен открывать произвольную shell, forwarding или другой путь переключения сайта.

Пример серверного `server.json` рядом с server-deploy.mjs (реальные пути подтвердить при установке):

```json
{
  "version": 1,
  "destination": "demo",
  "sourceRef": "dev",
  "repository": "pgorbachev/ikpk",
  "launcher": "/opt/ikpk-publication/demo/publication-launcher.mjs",
  "buildLockFile": "/var/lock/ikpk-build.lock",
  "timeoutSeconds": 14400
}
```

Существующий publisher config этого примера должен задавать `canonicalRepository=https://github.com/pgorbachev/ikpk.git`, sourceRef=dev, sourceProfile=demo-dev, stand/ci и защищённые host/siteUrl 193.124.115.99 / https://staging.ikpk.su. Production config использует main/prod и отдельные доступы. Ни адрес из исторического документа, ни этот пример не подтверждают фактическую установку.

Локальный `gh` credential нужен только доверенному операторскому процессу; он не передаётся на сервер, в SSH environment, candidate process или логи. Сервер принимает только proof для точных repository/workflow/ref/SHA и пересчитывает digest bounded ZIP artifact. Actions write, dispatch и rerun не используются этим deploy path. Сам publisher работает под доверенным UID, собирает кандидат из принятого SHA и имеет только broker-доступы своего назначения. Код канонического SHA после CI входит в доверенную границу, установленный server executor — уже доверенный.

Клиент: каталог `~/.config/ikpk-deploy` с demo.json/prod.json, без групповой/общей записи; ключ 0600 и отдельный known_hosts. Переменная IKPK_DEPLOY_HOME может указать другой абсолютный каталог конфигурации.

```json
{
  "version": 1,
  "destination": "demo",
  "sshTarget": "deploy-demo@193.124.115.99",
  "identityFile": "/Users/OPERATOR/.ssh/ikpk-demo",
  "knownHostsFile": "/Users/OPERATOR/.ssh/ikpk-demo-known-hosts",
  "serverNode": "/absolute/node",
  "serverEntry": "/opt/ikpk-publication/demo/server-deploy.mjs"
}
```

Локальные квитанции запросов: `~/.local/state/ikpk-deploy/DESTINATION/UUID.json`. Они не содержат ключей или данных CMS.

### Привилегированный захват DEMO

Root устанавливает `scripts/server-capture.mjs` и его `scripts/lib/server-capture-*.mjs` в `/opt/ikpk/capture/` с сохранением структуры; файлы и предки принадлежат root и не доступны для групповой/общей записи. Фиксированный `/etc/ikpk/demo-capture.json` имеет права 0600 и связывает конкретные CMS units, SQLite, uploads, статический `/media/`, доверенные CMS schemas и каталоги результата. Источники задаются разрешёнными реальными путями, без симлинков; путь `current` разрешается при установке, а не принимается от кандидата. Схемы копируются из принятого CMS SHA в отдельный защищённый каталог. Обновление схем и выбора рабочей CMS-пары — отдельная административная операция.

Шаблон `scripts/deploy/ikpk-demo-capture@.service` устанавливается в системный manager. `/usr/bin/node` в шаблоне должен совпадать с проверенным root-owned runtime. `ExecStopPost` всегда выполняет независимое восстановление ранее работающих CMS после завершения, ошибки или SIGKILL capture. Не применять `RemainAfterExit`: успешный `systemctl start` должен вернуть управление после возобновления CMS. Приёмка проверяет реальный сбой unit, а не только прямой вызов JavaScript.

`scripts/deploy/ikpk-demo-capture-recovery.service` устанавливается и включается на старте сервера. Он восстанавливает незавершённые leases после полного reboot/power loss, когда `ExecStopPost` не исполнялся. Не задавать `Before=` восстанавливаемым CMS units: recovery сам ждёт их запуска. Перед каждым новым capture helper также восстанавливает старые leases; неудачное восстановление блокирует новый снимок.

`scripts/server-capture-request.sh` устанавливается как root-owned `/usr/local/sbin/ikpk-demo-capture-request`, режим 0755. Единственное право sudo пользователя публикации — этот wrapper, без SETENV; он принимает ровно один UUIDv4 и запускает только соответствующий capture unit с очищенным окружением. Не выдавать wildcard-доступ к `systemctl`: wildcard аргументов sudo может включить дополнительные службы. Пример правила для заранее созданной отдельной учётной записи:

```sudoers
deploy-demo ALL=(root) NOPASSWD: NOSETENV: /usr/local/sbin/ikpk-demo-capture-request *
```

Правило проверяется `visudo -cf`; имя пользователя сверяется с фактической установкой. Невалидные ID, лишние аргументы и имя другой службы должны отказать. У deploy-пользователя нет sudo на прямой `capture`, `resume`, редактирование конфигурации или остановку произвольной CMS.

`captureBundleRoot` принадлежит root с выделенной группой чтения publisher (0750); запечатанные каталоги/файлы — 0550/0440. Lease-каталог восстановления доступен только root (0700). `publicationEvidenceRoot` принадлежит publisher и имеет 0700: там сохраняются ID, снимок, отчёты и доказательства восстановления вне временного checkout. Внешний server-deploy удерживает общий build flock; root helper повторно его не захватывает. Отдельный короткий root flock сериализует capture/resume/recovery: root unit может пережить смерть внешнего user unit, поэтому новый UUID не должен принять ещё живой capture за незавершённый после аварии. Весь список писателей источников должен быть учтён: остановка одной CMS при второй службе с доступом к тем же медиа не доказывает согласованность.

## Тестовый допуск и данные

Локальный доверенный операторский tooling с GitHub CLI выбирает последний eligible run `release-tests.yml` канонического репозитория для точной ветки и SHA, ждёт завершения уже запущенного прогона и проверяет native metadata/jobs и attempt-specific artifact; новый run не запускается и старый успех не подменяет более новый failed/running run. Серверный адаптер офлайн перепроверяет bounded manifest/ZIP-доказательство, связывает его с request ID и назначением, сохраняет в приватной операции и передаёт установленному launcher. Сдвиг ветки после проверки не подменяет закреплённый SHA; для production локальный клиент проверяет текущий `main` перед резервированием source tag и перед отправкой запроса.

release-tests.yml автоматически создаёт исходный tests-only run на push dev/main, поэтому для DEMO не требуется сначала размещать новый workflow в main ради workflow_dispatch. До появления этого workflow на выбранном SHA новый путь ожидаемо отказывает. Никакого автоматического deploy по успеху CI нет.

Полные source-проверки выполняются на контролируемой фикстуре. Исторические compare/parity к старому сайту исключены по сообщению владельца, что сайта уже нет; перечень и основание входят в manifest. Регулярные изменения production-данных не требуют менять fixture-ожидания: текущий кандидат отдельно проверяется с его собственным снимком. Визуальные фикстурные эталоны проверяются на macOS, для которой они приняты; baseline не обновляется автоматически ради зелёного релиза.

Снимок/медиа фиксируются один раз, проверяется и активируется одно и то же дерево. Пробы форм не создают настоящие заявки. До активации отказ сохраняет прежний сайт, после неё возможен active-unindexed — нужны recover и при необходимости отдельный rollback. Статус accepted/running не означает published.

## Ограничения до первой живой приёмки

- DEMO snapshot-only профиль реализован внутри существующего publisher и сохраняет отдельные доказательства захвата/проверок. Живая цепочка установки, sudo, актуальных данных, сборки и публикации ещё не принята. Разрешение dev CI не заменяет эту приёмку и не создаёт событийную ревизию искусственно.
- Production сохраняет требования TD-56 и всех существующих гейтов. Их отказ не обходится этой командой.
- Процесс структуры БД для dev/193 отдельный: #330 документирует подход, [PR #331](https://github.com/pgorbachev/ikpk/pull/331) слит в dev как `d5f24c95f62579f261bc01ddc6e36cb1c6211e47` после зелёных 17 проверок головы `b97145f606dab0ec0dfc3b0eef3c1d7c2eb37a28`. Закрытая репетиция не переключала рабочую CMS или публичный сайт. Для выпуска нужна свежая рабочая CMS-пара с проверкой совместимости и восстановления; диагностические пары репетиции не продвигать.
- После независимого ревью требуются установка на испытательное назначение, две публикации, rollback/recover, обрыв SSH/ответа и перезапуск сервера. Реальные systemd/flock и ограничения прав не подтверждаются одними mocked unit tests на Mac.
- Production — отдельное разрешение, собственный полный прогон, конкретная первая пара и проверенный временный план восстановления прежнего ручного выпуска. Из демо не переносить БД, media bytes или настройки.

Изолированные проверки SSH-запросов, CI-допуска и политики подтверждают отказы при подмене SHA/ветки/назначения, пропавшем результате, повторах и запоздалом исполнении. Независимое Astra High ревью операционной части нашло потерю stderr-audit, блокировку аварийным временным файлом и неполную долговечную CI-квитанцию; все три исправлены с регрессионными проверками. Отдельное независимое Astra High ревью тестовой полноты завершено; исправления reusable workflow, отчётов и кандидатных проверок перепроверены. Последний полный нативный scripts-прогон: 252 PASS, один timeout транспортной проверки, один Linux-only skip на Mac. Транспортная проверка повторена отдельно с исходным лимитом и CI=true/GITHUB_ACTIONS=true: PASS. Capture: 19 PASS, один Linux-only skip; реальный flock должен пройти Linux CI. Scripts lint и typecheck зелёные.

Кандидатная матрица содержит 113 проверок, сохранённый rollback — отдельные 8 smoke. Первый полный локальный прогон Chromium/Firefox/WebKit на фикстурном артефакте дал 112 PASS / 1 FAIL, без skips/flaky: длинный мобильный H1 расширял документ с 375 до 403 px. Дефект исправлен вместе с TD-4/TD-5, без отключения проверок: 26 целевых браузерных сценариев прошли, включая 200% текста и широкие окна; обычный вид главной на 375/768/1280/1601 px совпал с базой. Полный результат на новой живой DEMO-паре ещё требуется; старый прогон не подтверждает её готовность.

Нативный успешный полный run нового release-tests.yml на GitHub пока не предъявлен. После слияния в dev проверяются реальные имена jobs, все машинные отчёты и результаты полного набора. TD-4/TD-5 больше не `fixme`. Сборка и ожидания календарных блоков исправлены на общую опорную дату снимка. Для TD-52 действует решение владельца от 29.08.2026: семь конкретных mobile-отклонений остаются видимыми принятыми ограничениями при обязательном PASS соответствующего desktop-сценария. Это не прохождение mobile-проверки и не разрешение новых пропусков. Неприменимая комбинация viewport допускается только по точному перечню и при успешном исполнении соответствующей проверки на применимом project. Черновики preview B/C/D отсутствуют в обычной сборке: пропуски по роли разрешены только с точными именами и причиной в закреплённом source-профиле. Они не подтверждают E2E демоверсии.

DEMO publisher реализован; source policy проверяется до credentials, recovery сохраняет исходный ID и проверяет приватные снимок/медиа/отчёты, статический rollback не откатывает БД. Независимое ревью выявило и проверило исправления восстановления capture после reboot, пересечения root/user операций и синхронизации evidence перед активацией. Финальные дельты дополнительно проверены Sol без блокеров. До полного CI новой головы и живой приёмки это не готовый выпуск на 193. Ограничения production и отдельная приёмка перечислены выше.

До установки требуется оценить объём зависимостей и пик ресурсов сборки/проверок с работающей CMS. Эти ограничения относятся к demo, не к исследованию production в другой сессии.
