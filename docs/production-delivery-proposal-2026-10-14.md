# Процесс поставки IKPK в production

Дата: 14 октября 2026. Редакция по ревью Grok: 15 октября 2026. Цель — обычная поставка кода или контента без ручного повторения аварийных команд. Владелец выбрал один явный запуск оператором или из CMS; последующие этапы должны выполняться автоматически. Merge, сохранение контента и расписание CI сами не публикуют сайт.

Уточнение владельца: целевой процесс работает без его участия и без его локальной машины. Для контента администратор сохраняет данные и нажимает «Опубликовать» в CMS; постоянно доступный исполнитель сам получает снимок и медиа, собирает сайт, проверяет, доставляет и активирует релиз, возвращая статус в CMS. Владелец не переносит файлы, не запускает терминальные команды и не подтверждает каждый штатный выпуск. Выбор постоянной площадки исполнения ещё открыт; независимость от персонального компьютера уже является требованием.

Предлагается развить существующий launcher/worker для двух процессов, принять их на production и подключить действия CMS. История выпуска нужна для выбора защит; подробная хронология не является основным результатом. Реализация, изменения production/CMS, очистка и перенос каталогов в этот этап не входят. Остальные решения и приоритеты ниже — предложение для согласования.

## Что мешает штатной поставке

| Подтверждённое условие | Следствие для будущего процесса |
| --- | --- |
| В коде уже есть launcher, worker, проверки пары код/снимок, блокировка назначения, transport, rollback и recover [S1–S3] | Нужна эксплуатационная связка и приёмка; второй framework публикации не нужен |
| Кнопка CMS снимает и собирает сайт из собственного workspace, затем переключает релиз; «Восстановить» также активирует каталог напрямую [S4] | Оба действия должны обращаться к штатным publish/rollback; одного обновления файлов кнопки недостаточно |
| Писатель событий контента существует, но его подключение к правкам CMS остаётся TD-56 [S5] | Разрешить контракт свежести и происхождения контента до штатной приёмки, не имитировать журнал записью при съёме |
| `Tests` на текущем remote `main@09347070ceb5634cf4b46774934238c0eac306d1` завершился failure; browser smoke skipped [S6] | Текущий SHA не имеет полного успешного вердикта штатного гейта. Решение владельца об аварийном выпуске не становится постоянным обходом |
| В handoff описана внешняя приёмка вручную доставленного релиза, а production-конфигурация штатного прогона отсутствовала [S7] | Работоспособность сайта и готовность штатного механизма поставки — разные результаты |
| Совместимость фактических CMS media/relations исправлена, но четыре ограничения переноса данных остаются именованным долгом [S8] | Схемы и преобразователь поставляются совместно; изменение заполненного неподдерживаемого поля останавливает публикацию |
| Handoff сообщает пустой production-файл редиректов при наличии правил в Git [S7] | Принимать релиз вместе с конфигурацией раздачи: маркер сайта не доказывает работу старых URL |
| Handoff фиксирует ограничения VPS по диску и памяти; локальную сборку владелец называет исключением, в том числе из-за опасений дефицита ресурсов [S9, S12] | Проверить ресурсы серверной сборки и влияние на CMS; выбрать размещение по замерам. Необходимость отдельной машины пока не доказана |

Причины первоначального расхождения установленных версий и полное влияние на посетителей пока не установлены. Эти неизвестные не мешают определить проверяемые границы следующей поставки.

## Два процесса поставки и общий механизм исполнения

CMS — источник редакторских данных. На переходном этапе владелец меняет их через REST API CMS; в целевом процессе администратор работает через UI CMS. Оба входа сохраняют данные в одной CMS и проходят её серверные проверки, права доступа и учёт изменений. Снимки и файлы сборки — производные данные, их ручная правка не является способом обновления контента. Обычная редакторская правка не требует PR с данными.

| Вид изменения | Подготовка | Явный запуск и результат |
| --- | --- | --- |
| Выпуск сайта: изменения исходников | PR, проверки и независимое ревью; успешный обязательный CI выбранного SHA `main` | Оператор явно запускает выпуск нового кода со снимком текущего активного принятого релиза этого назначения, включая результат rollback. Неопубликованные правки CMS автоматически не включаются |
| Публикация данных: редакторские изменения в базе | Сейчас владелец сохраняет изменения через REST API CMS, затем администратор — через UI CMS; видно, что они ещё не опубликованы | Сейчас оператор, затем кнопка CMS запускает сборку нового снимка на точном SHA активного принятого релиза. Новые исходники из `main` не подхватываются |
| Схема или версия CMS | Проверить схему, importer и преобразователь на копии данных; подготовить бекап, план обновления и восстановления | Отдельная контролируемая установка CMS, readback данных и связей; после подтверждения совместимости — обычная публикация сайта |

Обновление CMS и миграция базы не прячутся внутри команды публикации статического сайта. Откат сайта возвращает прежний проверенный артефакт и не откатывает CMS. Возврат схемы или данных CMS требует собственного проверенного плана.

Таким образом, два обычных процесса — публикация данных и выпуск сайта. Изменение схемы/версии CMS относится к согласованному техническому выпуску, а не к редакторской публикации. Сохранение в базе и публикация на сайте остаются разными действиями. При статической генерации оба процесса требуют серверной сборки; общий исполнитель не означает общий выбор входов или общие полномочия.

Каждый результат фиксирует пару «полный SHA кода + идентификатор и digest снимка», включая медиа, а также вид операции, инициатора и исходный активный релиз. Для выпуска сайта необходимо хранить снимок текущего активного принятого релиза каждого назначения вместе с медиа и доказательствами происхождения. Если новый код с ним несовместим, обычный выпуск блокируется; согласованное обновление кода и данных требует явно подтверждённого состава и проверок обоих процессов. Использование снимка текущего активного принятого релиза для выпуска сайта принято владельцем 15.10.2026.

Это изменение существующего контракта: текущий worker требует актуальный `main` и live-снимок [S1, S2]. Два режима ещё не реализованы. До реализации нужен согласованный OpenSpec change для выбора источников, повторного использования снимка, CI-свидетельств и повторной сверки перед активацией. Старый активный SHA допускается только с проверяемыми CI-свидетельствами и по действующей политике безопасности. Отсутствие допуска блокирует публикацию данных до восстановления проверяемого допуска того же SHA либо отдельного выпуска сайта; это не повод молча обновить код.

Rollback возвращает целиком ранее проверенную пару кода и данных; интерфейс показывает обе версии. Он не возвращает базу CMS к старому состоянию. Сочетание старого кода с новым снимком требует новой сборки и проверки, а не называется готовым rollback.

## Исполнитель, версии и полномочия

Постоянный исполнитель поставки работает на отдельно установленной поддерживаемой ревизии. SHA сайта — вход сборки, а не способ выбрать старый worker. В записи операции фиксируются версия исполнителя и SHA сайта. Сборка и преобразователь данных привязаны к выбранному SHA сайта; захват выполняется совместимой с ним версией инструмента, явно указанной в операции. Если этот набор не понимает установленную схему CMS, публикация данных блокируется до согласованного технического выпуска. Подмена преобразователя кодом нового `main` без проверки совместимости недопустима.

OpenSpec должен заменить проверки равенства вершине `main` в launcher/worker, чтении CI и повторной сверке runner правилами выбранного процесса. Сохраняются проверки канонического репозитория, точного SHA, целостности исходников, доверенного CI, совместимости снимка и ожидаемого активного релиза. Простое удаление отказов `untrusted-source`/`head-moved` не является решением [S13].

CI-свидетельства необходимо сохранять с проверяемым происхождением, SHA, run/attempt, составом обязательных проверок и версией политики на весь срок поддержки опубликованной версии. Сейчас `publication-ci-counts` хранится 90 дней, а истёкший артефакт отвергается [S13]. Срок хранения не означает срок разрешения: сохранённый успех заново оценивается по действующей политике. Если доказательства утрачены или недостаточны, требуется доверенная повторная проверка того же SHA либо отдельный выпуск сайта; до этого публикация блокируется. Способ архива и повторного CI старого SHA ещё предстоит определить в OpenSpec — текущий workflow не объявляется уже поддерживающим такой путь.

Владелец 15.10.2026 принял разделение полномочий:

| Действие | Допуск |
| --- | --- |
| Публикация данных | Администратор контента; временно назначенный оператор |
| Выпуск кода | Отдельно назначенный оператор выпуска |
| Rollback всей пары | Отдельно назначенный оператор восстановления |
| Recover незавершённой операции | Отдельно назначенный оператор восстановления |

Один человек может иметь несколько явно выданных прав. Право редактировать или публиковать контент само по себе не даёт трёх остальных прав. Сервер проверяет действие, инициатора и назначение для UI, REST и CLI; скрытая кнопка не заменяет проверку. Сервис CMS передаёт подтверждённую личность инициатора и не расширяет её полномочия своими credentials. Текущее разрешение refresh/restore для `content-admin` не считается целевой матрицей [S13]. Конкретных операторов и отображение прав на роли нужно назначить до приёмки.

## Предлагаемый ход операции

1. **Запрос.** Назначение production, оператор, идентификатор операции и вид операции «публикация данных» либо «выпуск сайта» и выбранная пара кода и данных. Один активный запрос допускается до начала сборки; повторное нажатие показывает текущую операцию или именованный отказ. Серверный допуск проверяется по принятой матрице для CLI, CMS publish, выпуска кода, rollback и recover. Remote-lock сейчас берётся после сборки, поэтому сам по себе этого не обеспечивает [S1]. Очередь на несколько запросов добавлять только при подтверждённой потребности.
2. **Предварительная проверка.** Защищённая установка launcher, runtime, доступы, ожидаемый текущий релиз и свободные ресурсы. Для принятого назначения — пригодная цель отката; для первого подключения — отдельно согласованный переход и способ восстановления, описанный ниже. Выбор точного SHA по виду операции: активный принятый SHA для данных; выбранный проверенный SHA `main` для сайта. Проверить действительность допуска CI для этого SHA. Отказ возникает до затратной сборки и загрузки.
3. **Снимок.** Для данных — новый согласованный live-снимок с медиа, связями, опорной датой и идентификатором, проверка журнала. Для сайта — сохранённый снимок текущего активного принятого релиза назначения, включая результат rollback, с медиа и проверкой происхождения/digest. Закрепить исходный release ID и snapshot ID/digest; отсутствие сохранённого снимка блокирует выпуск. В обоих случаях проверить совместимость с выбранным кодом и закрепить версию контента.
4. **Сборка и проверки.** Один изолированный workspace на серверном исполнителе. Размещение на VPS с CMS допустимо после проверки запаса ресурсов и защиты работающих служб; отдельная машина выбирается при недостаточности такого размещения. Сборка один раз; `release.json` до проверок готового дерева. Проверить контент, URL, режим назначения, браузерные сценарии и принятую конфигурацию форм/платежей. Подтвердить неизменность снимка и дерева после проверок.
5. **Доставка.** Под блокировкой назначения доставить именно проверенное дерево; сверить полный состав и суммы. Файл редиректов и его применение входят в тот же контракт поставки.
6. **Активация.** Повторно сверить ожидаемый текущий релиз и допустимость закреплённой пары. Для данных продвижение `main` не влияет на выбранный активный SHA, но изменение CMS после снимка останавливает операцию. Для сайта новые правки CMS не подменяют опубликованный снимок; продвижение `main` не подменяет выбранный SHA, но его допуск должен оставаться действительным. Любая другая активация делает запрос устаревшим: остановить его и потребовать новый явный запуск с актуальной парой. Атомарно переключить релиз по протоколу transport.
7. **Приёмка.** Через внешний HTTPS проверить только чтение: версию, страницы, медиа, старые URL, 404 и доступность формы. До активации браузерный smoke проверяет взаимодействие с формой с изолированным тестовым получателем. Проверка всей цепочки доставки заявки требует отдельно подготовленной тестовой интеграции и её доказательств; проверки только на чтение этого не подтверждают. Штатные пробы не создают реальные обращения в CRM и не отправляют уведомления клиентам. Запись успешной операции связывает SHA, snapshot, digest, назначение и результаты проверок. Статус «опубликовано» появляется после этой приёмки.
8. **Восстановление.** Отказ до переключения сохраняет прежний релиз. Ошибка внешней проверки или записи индекса после переключения может оставить новый релиз активным: показать его пару, сохранить pending и запретить следующую публикацию до recover или отдельно согласованного восстановления. Pending не удалять вручную. После восстановления согласованного состояния оператор при необходимости запускает проверенный rollback.

Это целевой порядок. В существующем runner уже реализована значительная часть шагов 2–8 [S1–S3]; полный набор внешних проверок и пригодность production-назначения ещё нужно принять. Разделение выбора входов и сверок по двум процессам ещё не реализовано. Автоматический откат в текущем решении отсутствует [S3]. Если он понадобится, это отдельное изменение поведения после проверки восстановления.

Платежи этим предложением не включаются. До установки production API уже принят профиль `DEPLOY_MODE=prod`, `PAYMENT_ROLE=ci`: реальные формы заявки и отсутствие платёжной формы/endpoint. Этот профиль поддерживается конфигурацией launcher и отдельной проверкой отсутствия оплаты [S11]. Новая роль `disabled` не нужна. При подготовке назначения сверить фактический артефакт и применить принятый профиль; не переносить автоматически `PAYMENT_ROLE=prod` из аварийной команды handoff. Успешный полный платёжный гейт выпуска handoff не предъявлен [S7].

## Первое подключение production

Владелец 15.10.2026 принял отдельный первый переход: явно согласованная пара проверенного кода и названного снимка CMS. Это не обычная публикация данных на старом SHA и не обычный выпуск кода с ещё не принятой исходной парой. Перед запуском назначенный оператор подтверждает полный SHA с успешным допустимым CI, snapshot ID/digest, состав данных и медиа и ожидаемый текущий ручной релиз. Если используются новые данные CMS, их включение подтверждается явно; отсутствие исторического снимка не разрешает незаметно взять live-данные.

Наличие пригодного сохранённого снимка старого выпуска пока не установлено; пустой индекс сам по себе не доказывает его отсутствия. Перед первым переходом сохранить выбранные байты снимка и медиа в защищённом хранилище и проверить восстановление и digest. Запись операции должна ссылаться на эти байты; один `release.json`, digest или индекс не заменяет снимок. Хранение сохраняет снимки активного релиза и поддерживаемых целей rollback, чтобы после отката выпуск кода мог использовать их данные. Это добавляемый контракт, а не подтверждённая возможность текущего индекса [S13].

Первая пара проходит проверки совместимости, происхождения, сборки, доставки и внешней приёмки; изменение CMS после согласованного нового снимка либо смена ожидаемого релиза отменяют запуск. После её успешной приёмки работают два обычных процесса. Принятие этого порядка не является разрешением на выкладку сейчас; конкретные SHA, снимок и план временного восстановления ещё не выбраны.

Сначала прочитать индекс назначения и проверить допустимые цели. Наличие `release.json` и ручного каталога не создаёт запись проверенного релиза: rollback требует исходных CI и локальных проверок того же назначения [S3]. Не импортировать ручной выпуск как проверенный и не подменять его свидетельства.

Если индекс пуст, первая штатная публикация создаёт первую запись, но не даёт штатного отката на старый ручной релиз. Это отдельный переход, который владелец должен принять вместе с временным способом возврата до переключения. Ручная команда handoff — исторический кандидат: пригодность каталога, его байты, редиректы и действие команды необходимо подтвердить перед использованием. Две публикации и откат на стенде не закрывают этот production-разрыв. После первой успешной индексированной публикации её можно принять как цель следующей операции; после второй проверить штатный production-rollback.

Первый переход также применит Git-файл редиректов и правила удержания каталогов. Заранее показать изменение старых URL и список каталогов, которых коснётся автоматическая очистка. До завершения перехода согласованная аварийная цель и её доказательства должны оставаться доступными: текущий retention защищает current и непосредственно предыдущий current, а произвольный исторический hotfix может удалить [S10]. Очистка и изменение production в нынешнем этапе не разрешены.

## Где выполнять сборку

По уточнению владельца, на демостенде 193 сборка уже выполнялась на сервере. Сборка на Mac при последнем выпуске была исключением, в том числе из-за опасений нехватки ресурсов [S12]. Поэтому целевая основа — автоматическая серверная сборка. Опыт стенда подтверждает существование такого способа работы, но не достаточность ресурсов нынешнего production.

| Вариант | Польза | Условия и цена |
| --- | --- | --- |
| Серверный исполнитель на VPS с CMS | Меньше обслуживаемых узлов; снимок и сборка могут оставаться на сервере | Измерить пики RAM, CPU, I/O и диска, предусмотреть запас, ограничение нагрузки и сериализацию; подтвердить доступность CMS во время сборки |
| Выделенная машина с защищённым launcher | Разделение ресурсов сборки и работающей CMS; публикация не зависит от ноутбука | Дополнительная площадка, доступы и автоматическая передача данных; выбрать, если совместное размещение не обеспечивает нужный запас и доступность |
| Mac оператора | Временное исключение при инфраструктурных ограничениях | Зависит от владельца и доступности ноутбука; не удовлетворяет целевой приёмке |
| CI собирает и сохраняет пакет, явная команда активирует | Возможность использовать постоянные раннеры и готовые артефакты | Требует решить доступ к live CMS, передачу snapshot/provenance и доказательство идентичности артефакта. Это расширение принятого пути, а не готовая возможность текущего `Tests` |

Целевой вариант — постоянно доступный серверный исполнитель, принимающий запрос публикации из CMS и автоматически выполняющий весь путь. Сначала проверить уже применявшуюся серверную сборку на стенде и измерить ресурсы подходящей production-конфигурации. По результату выбрать совместное размещение, увеличение ресурсов VPS или отдельного исполнителя. Отдельная машина не является заранее принятым требованием. Ручная активация после сборки на CI не удовлетворяет целевому сценарию: одного запроса администратора должно хватать до внешней приёмки и возврата статуса. Mac остаётся временным исключением.

Критерий целевой приёмки: Mac владельца выключен, владелец не участвует; администратор меняет данные через UI CMS и одним запуском получает опубликованный результат либо понятную ошибку. Снимок и артефакты передаются между серверными компонентами автоматически. Аналогичный запуск доставки кода выполняет уполномоченный оператор через постоянного исполнителя, без зависимости от компьютера владельца. Обслуживание и разбор исключительных сбоев остаются отдельной эксплуатационной обязанностью.

## Как сделать процесс быстрее

Разделить цену проверки кода, проверки конкретного выпуска и проверки инфраструктуры. CI кода работает с закреплённой фикстурой [S6]; он не проверяет сегодняшний live-контент. Новый снимок требует проверки пары даже при том же SHA кода. При неизменном SHA использовать допустимый успешный CI без полного повторения кодовых проверок на постоянном серверном исполнителе; обязательные проверки конкретного выпуска сохраняются.

TD-75 устранить через отдельный явный набор provisioning-проверок с собственной площадкой исполнения и политикой обязательности. Перенос из основного unit-набора не означает удаление: изменения provisioning и его контрактов должны оставаться заблокированы при отказе соответствующего набора. Согласованно обновить workflow, обязательность checks и чтение CI-свидетельства: отдельный workflow сам по себе не становится гейтом. Отдельно предъявить успешный полный новый вердикт для сайта. Переиспользовать решение из `dev` только после сверки с текущим `main` [S6].

Для первого штатного выпуска записать длительность ожидания, снимка, установки зависимостей, сборки, каждой группы, загрузки и внешней приёмки. Оптимизировать измеренный критический путь. Кэш зависимостей и производных медиа имеет смысл при проверяемых ключах; кэш не является доказательством успешного выпуска. Не назначать обещание «публикация за N минут» до этих измерений.

Повторную доставку проверенного пакета после сетевого сбоя стоит поддерживать через тот же протокол, сохраняя проверки destination, SHA, контента, digest и pending. Произвольный прежний `dist` или CI-артефакт не становится допустимым релизом. Штатный новый publish сейчас снова выполняет сборку и проверки; отдельный путь повторной активации нового пакета без сборки не подтверждён. Rollback сохранённого проверенного релиза уже выделен отдельно [S3].

## Решение по изменениям контента

TD-56 — существенная незавершённая граница, а не основание создать ещё один журнал. Существующий контракт требует событий каждой правки и различения восстановления; записывать только отпечаток при публикации недостаточно. В частности, две правки A → B → A должны оставаться двумя событиями [S5].

Учёт изменений должен охватывать и REST API, и UI CMS на серверной границе изменения данных. Обработчика только в интерфейсе администратора недостаточно. Приёмка включает одинаковую правку обоими способами: данные сохранены, изменение учтено, до явной публикации сайт прежний, после успешной публикации отражает принятую правку.

Вариант подключения CMS к существующему журналу в TD-56 предполагает полный захват на событие: исторически указаны 1–3 секунды на прогретой CMS и 102 секунды на холодной. Это старые замеры, не текущий SLA [S5]. Не включать такой синхронный расход в сохранение контента без проверки. Нужно согласовать место писателя, порядок событий, fingerprint, обработку параллельных правок и сбоев; либо явно пересмотреть контракт, если его цена превышает нужную защиту. Отдельная новая архитектура событий пока не выбрана.

На время съёма и активации должно быть проверяемое согласование состояния: для публикации данных изменение после снимка вызывает отказ; следующий явный запуск получает новый снимок. Выпуск сайта использует закреплённый опубликованный снимок независимо от последующих редакторских правок. Простое HTTP 200 съёма не доказывает согласованность нескольких коллекций. До приёмки событийного пути временное окно без редакторских изменений остаётся операционным условием, а не заменой журнала.

Шаги 1 и исследование предусловий 2–3 можно вести независимо. Реальная приёмка 3 зависит от успешного CI, принятого контракта контента и готового назначения. Шаг 4 зависит от 3. Предлагаемые ответственные — исполнитель CI, исполнитель CMS/контракта, исполнитель инфраструктуры, владелец для приёмки; конкретные люди и сроки назначаются при согласовании.

Не включать всю уборку каталогов в критический путь следующего выпуска. Сначала обеспечить место и восстановимость выбранного builder. Позднее согласовать единый контейнер локальных worktree, артефактов, снимков, бекапов и временных данных; перед размещением внутри checkout исключить его из Git. Перенос только после проверки владельцев, изменений, уникальных коммитов, ignored-файлов, процессов и абсолютных путей, штатными средствами Git. Исторические пути доказательств сохраняются.

Хранение согласовать с существующим механизмом: remote требует минимум пять релизов [S10], хотя аварийный handoff оценивал два. Бюджет считать для принятого retention, текущей операции, бекапа, отката и пиков, а не переносить приблизительные 1/3 GB из handoff как норматив. Бекап вне VPS, но только на том же почти заполненном Mac, ещё не является независимо принятой схемой восстановления.

## Обязательные вопросы будущего OpenSpec

Финальное ревью выделило три незавершённых контракта. Они не блокируют закрытие анализа, но должны быть решены и проверяемо описаны до утверждения спецификации и начала реализации. Ниже не утверждается ещё не выбранное владельцем поведение.

1. **Состав публикации данных.** Определить, публикуется ли всё подготовленное состояние CMS или выбранный набор записей, как отделяются черновики и что именно подтверждает инициатор. Сценарий: один редактор подготовил цену, другой сохранил незавершённый текст; публикация цены не должна неожиданно выпускать неподтверждённый состав. Спецификация должна определить набор, момент его фиксации, отображение пользователю и правила при параллельной правке; последовательное изменение нескольких коллекций не считать согласованным снимком без доказательства.
2. **Сбой до переключения.** Определить восстановление допуска и статуса после падения исполнителя на снимке, сборке или доставке. Сценарий: перезапуск сервера не оставляет вечную «операция выполняется», а освобождение допуска не позволяет прежнему исполнителю позднее активировать устаревший результат. Нужны проверка фактического состояния, защита от поздней активации и наблюдаемый итог прерванного запроса. Конкретный механизм выбирается в OpenSpec; таймер сам по себе не доказательство завершения.
3. **Конфигурация выпуска.** Определить, какие несекретные параметры назначения влияют на артефакт/раздачу, как фиксируется их версия или digest, кто вправе их менять и что возвращает rollback. Сценарий: публикация только данных не должна незаметно менять настройки форм, чата или редиректов; одинаковая пара SHA/снимок не является полной идентичностью при изменении конфигурации. Секреты не сохранять в публичном маркере релиза. Изменения конфигурации и границы её отката должны быть видимы как отдельный технический состав выпуска.
