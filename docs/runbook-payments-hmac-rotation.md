# Runbook: ротация ключа отпечатка (HMAC)

Задача 4.1e, Решение 3б. **Это не тот runbook, что для секрета ЮKassa** — тот в
`docs/runbook-payments-secret-rotation.md`, и простая замена оттуда сюда не переносится:
у секрета оператора платежей и у ключа отпечатка разные последствия ошибки.

## Что версионируется и почему версия — не роль

Пары переменных:

```
HMAC_KEY_CURRENT       + HMAC_KEY_CURRENT_VERSION
HMAC_KEY_PREVIOUS      + HMAC_KEY_PREVIOUS_VERSION   (только на переходный период)
```

**Версия выбирается оператором, а не выводится из материала ключа.** Найдено ревью #97
(MAJOR-3). Если версию считать хешем ключа, то она становится производной секрета, и её
попадание в запись хранилища — утечка признака, по которому ключ можно подбирать. Поэтому
версия — это устойчивая метка вида `2026-08-v1`, а не отпечаток материала.

Запись состояния несёт **значение** версии на момент записи, а не роль «текущий/предыдущий».
Роль меняется при каждой ротации, значение — нет; запись, помеченная ролью, после ротации
стала бы указывать на другой ключ.

Проверка повтора сравнивает версию записи с **обеими** доступными версиями. Запись с версией,
которой в конфигурации нет, даёт «нужна сверка» — не отказ и не создание второго платежа.

## Правило частоты

**Не чаще, чем раз в TTL записей (14 суток), кроме аварийной ротации.** Причина
арифметическая: записи живут 14 суток и несут версию, под которой созданы. Две ротации внутри
TTL оставляют в хранилище записи трёх версий, а конфигурация держит две — значит часть записей
становится непроверяемой и уходит в «нужна сверка» без всякой причины со стороны посетителя.

Аварийная ротация (подозрение на утечку) этим правилом не ограничена — но тогда рост числа
«нужна сверка» ожидаем и должен быть назван в отчёте заранее, а не объяснён потом.

## Правило новой версии — процедурное, и само себя не обеспечивает

**При смене материала ключа версия обязана быть новой, ранее не использованной.** Найдено
ревью #97 (MAJOR-5). Если оставить прежнюю версию с новым материалом, то отпечатки старых
записей перестанут воспроизводиться, а сервис об этом не узнает: версия совпадает, значит он
будет считать несовпадение отпечатка расхождением **содержимого**, а не ключа, и отвечать
«данные изменились» там, где данные те же.

Само по себе правило не гарантируется ничем — только контрольным значением (canary):

- на каждую версию сервис хранит `HMAC(ключ, константа)` в `hmac-canary.json`;
- при старте значение для текущей версии пересчитывается и сравнивается;
- **несовпадение останавливает запуск** (fail-closed) с сообщением про материал ключа.

То есть попытка сменить материал, не сменив версию, ловится **до** открытия порта, а не по
последствиям. Проверено тестами `3.0a-4`, `3.0a-5` и негативными проверками 6.10(16) и
6.10(19).

## Процедура

```bash
# 0. Убедиться, что предыдущая ротация была не позже 14 суток назад.
grep -o 'HMAC_KEY_CURRENT_VERSION=.*' /etc/ikpk-payments/env
ls -l --time-style=long-iso /etc/ikpk-payments/env

# 1. Сгенерировать новый материал (32 байта, hex) и выбрать НОВУЮ версию.
openssl rand -hex 32            # значение не печатать в общий канал
NEW_VERSION=2026-08-v2          # ранее не использованная метка

# 2. Прежний ключ переносится в PREVIOUS вместе со своей версией.
#    Правка env-файла — атомарной подменой, не редактором на месте.
umask 077
cp /etc/ikpk-payments/env /etc/ikpk-payments/env.new
# в env.new: HMAC_KEY_PREVIOUS/_VERSION := прежние CURRENT/_VERSION,
#            HMAC_KEY_CURRENT/_VERSION := новые
chown root:root /etc/ikpk-payments/env.new && chmod 0600 /etc/ikpk-payments/env.new
mv /etc/ikpk-payments/env.new /etc/ikpk-payments/env

# 3. Перезапуск. Canary проверится при старте; если материал не совпал с версией —
#    сервис НЕ поднимется, и это верное поведение.
systemctl restart ikpk-payments
systemctl status ikpk-payments --no-pager | head -20
```

## Свидетельство, которое надо приложить

1. **Новая версия ранее не встречалась** — `hmac-canary.json` до ротации не содержит ключа
   `NEW_VERSION` (показать список ключей, не значения).
2. **Сервис поднялся после замены** — новый `MainPID`, время старта позже времени изменения
   env-файла. Два числа, а не «перезапустил».
3. **Записи старой версии продолжают проверяться** — отправка того же состава, что у
   существующей записи прежней версии, даёт «нужна сверка» либо возврат её состояния, но
   **не** второй платёж.

## Снятие PREVIOUS

Прежний ключ убирается из конфигурации, когда в хранилище не осталось записей его версии, —
то есть не раньше TTL (14 суток) с момента ротации. Проверять по хранилищу, а не по календарю:

```bash
python3 - <<'EOF'
import json
r=json.load(open('/var/lib/ikpk-payments/payments.json'))['records']
from collections import Counter
print(Counter(x['keyVersion'] for x in r))
EOF
```

Пока счётчик прежней версии не ноль, снятие `HMAC_KEY_PREVIOUS` переведёт эти записи в
«нужна сверка» — по вине оператора, а не посетителя.
