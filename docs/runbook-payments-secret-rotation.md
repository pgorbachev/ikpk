# Runbook: секрет ЮKassa — хранение и ротация

Задача 4.5, Решения 1 и 7. **Отдельно от ключа отпечатка** — его runbook
`docs/runbook-payments-hmac-rotation.md`, и процедура оттуда сюда не переносится.

## Хранение

**Обновлено задачей 4.10 (матрица контуров): две УСТАНОВЛЕННЫЕ инстанции, не одна.**
Стенд и production — разные `systemd`-инстансы шаблонного юнита
`payments/deploy/ikpk-payments@.service` (`ikpk-payments@stand`, `ikpk-payments@prod`), и у
каждой свой env-файл:

```
/etc/ikpk-payments/stand.env    владелец root:root, права 0600
/etc/ikpk-payments/prod.env     владелец root:root, права 0600
```

Ниже везде, где раньше стоял единственный `/etc/ikpk-payments/env` и команда
`systemctl … ikpk-payments`, подставляется контур явно: `<contour>` — `stand` либо `prod`,
файл — `/etc/ikpk-payments/<contour>.env`, юнит — `ikpk-payments@<contour>`. Секрет ротируется
**отдельно для каждого контура** — рутинная ротация одного не подразумевает ротацию другого.

**Почему `root:root`, а не сервисный пользователь** (решение владельца 2026-08-18, заменяет
в этой части решение от 2026-08-12): systemd читает `EnvironmentFile=` **до** понижения
привилегий, поэтому сервисному пользователю чтение файла не нужно вовсе. А раз не нужно —
скомпрометированный сервис не может подменить постоянную конфигурацию, в том числе адрес
API оператора платежей.

Изменяемые данные сервиса при этом принадлежат `ikpk-payments` **отдельно и по контурам**:

```
/var/lib/ikpk-payments/stand    владелец ikpk-payments:ikpk-payments
/var/lib/ikpk-payments/prod     владелец ikpk-payments:ikpk-payments
```

**Обычный деплой env-файл не получает и не перезаписывает.** Он обновляет код и unit;
секрет попадает на хост из кабинета ЮKassa вне Git, вне CI и вне shell history. Гейт
`dist_has_no_secret_values` (`scripts/lib/deploy-checks.sh`) отдельно проверяет, что значения
секретов не попали в собранную статику; отсутствие значений для поиска трактуется как
«проверить не удалось», а не «утечек нет».

## Несекретный inventory

| контур | магазин |
|---|---|
| демо-стенд | тестовый `shopId=1440249` |
| production | боевой `shopId=409285` |

`shopId` секретом не является — он виден в checkout любому плательщику. Секретен только ключ.

**Локальные эксперименты — отдельный тестовый магазин либо моки.** Лимит ЮKassa — 20 тестовых
магазинов, и это не повод экономить: перевыпуск ключа на ноутбуке под тем же магазином, что у
стенда, роняет стенд, и наоборот. Один магазин — один потребитель.

## Ротация: три независимых факта плюс отложенная проверка

У ЮKassa старый и новый ключ действуют **одновременно до 48 часов**. Отсюда главное следствие:
успешный платёж сразу после замены **не доказывает**, что сервис взял новый ключ, — он мог
пройти по старому. Поэтому свидетельство составное.

```bash
# 0. Контур: stand либо prod — процедура выполняется на КАЖДЫЙ отдельно.
CONTOUR=stand   # или prod
ENV_FILE="/etc/ikpk-payments/${CONTOUR}.env"

# 1. Новый ключ выпущен в кабинете ЮKassa (магазин 409285 для prod, 1440249 для стенда).

# 2. Атомарная замена env-файла ЭТОГО контура.
umask 077
cp "$ENV_FILE" "${ENV_FILE}.new"
# правка: YOOKASSA_SECRET_KEY := новый
chown root:root "${ENV_FILE}.new" && chmod 0600 "${ENV_FILE}.new"
mv "${ENV_FILE}.new" "$ENV_FILE"
stat -c '%y %U:%G %a' "$ENV_FILE"      # время замены, владелец, права

# 3. Перезапуск ИНСТАНЦИИ этого контура — соседний контур не трогается.
systemctl restart "ikpk-payments@${CONTOUR}"
systemctl show -p MainPID -p ActiveEnterTimestamp "ikpk-payments@${CONTOUR}"
```

**Факт 1 — новый материал действительно в файле, без вывода секрета.** Одноразовый HMAC от
случайного audit-challenge: сравнивается не значение, а его отпечаток под случайной солью,
которая тут же выбрасывается.

```bash
CHALLENGE=$(openssl rand -hex 16); echo "challenge: $CHALLENGE"
# ожидаемое значение считает тот, кто выпускал ключ, у себя:
#   printf %s "$CHALLENGE" | openssl dgst -sha256 -hmac "<новый ключ>" -r | cut -d' ' -f1
# на хосте, из env-файла ЭТОГО контура:
set -a; . "$ENV_FILE"; set +a
printf %s "$CHALLENGE" | openssl dgst -sha256 -hmac "$YOOKASSA_SECRET_KEY" -r | cut -d' ' -f1
```

Совпадение доказывает, что в файле именно новый ключ. Секрет при этом не печатается и в
историю команд не попадает — в неё попадает только challenge и отпечаток.

**Факт 2 — перезапуск случился после замены.** Новый `MainPID` и `ActiveEnterTimestamp`
**позже** времени изменения файла из шага 2. Два времени, а не слово «перезапустил»: сервис,
перезапущенный до замены, работает на старом ключе, и всё остальное свидетельство становится
бессмысленным.

**Факт 3 — платёж проходит через сервис.** Тестовый платёж на 1 ₽ на стенде: в ответе ЮKassa
наблюдаем `test: true`, наш `GET /payments/{requestId}/status` отдаёт `succeeded`. На
production боевой платёж без отдельного согласования **не создавать** — там личность контура
доказывается readiness и конфигурационным свидетельством с замаскированным секретом.

**Отложенная проверка через 48+ часов — неблокирующая.** Убедиться, что **старый** ключ
отвергается оператором платежей. До этого момента старый ключ хранится в защищённом
хранилище (не в env-файле и не в репозитории), после — удаляется.

Почему неблокирующая: 48 часов — свойство оператора, а не нашей процедуры; блокировать
ротацию на двое суток значило бы держать окно, в котором два ключа действуют, дольше
необходимого. Но и молчать нельзя: без этой проверки неизвестно, отозван ли старый ключ
вообще.

## Что записать в отчёт по ротации

1. время замены файла, владелец и права (`stat`);
2. `MainPID` и время старта — оба позже времени замены;
3. совпадение отпечатка по challenge (challenge и оба отпечатка, без секрета);
4. исход тестового платежа с `test: true`;
5. дату, когда предстоит отложенная проверка отзыва старого ключа, и — после неё — результат.

Пункт 5 без даты считается невыполненным: «проверим потом» не отличается от «не проверили».
