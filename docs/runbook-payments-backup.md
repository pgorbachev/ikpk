# Runbook: резервное копирование и восстановление состояния платежей

Задача 4.3a, Решение 4а. Предмет — **состояние**, а не код: по нему сервис отличает
«платёж уже создан» от «создаём впервые». Пересборка его не восстанавливает.

## Что копируется

| файл | зачем |
|---|---|
| `payments.json` | сопоставление `requestId ↔ платёж ЮKassa`, отпечатки, версии ключа |
| `verification-journal.json` | исходы «нужна сверка» — по ним разбирают обращения |
| `hmac-canary.json` | контрольные значения материала ключа по версиям |
| `duplicate-tokens.json` | выданные токены подтверждения повторной оплаты |

## Механизм

`payments/deploy/ikpk-payments-backup.sh`, запускаемый таймером
`ikpk-payments-backup.timer` — `OnUnitActiveSec=4h`, `Persistent=true`.

**Почему не реже четырёх часов.** Окно идемпотентности ЮKassa — 24 часа. Копия обязана
быть заметно свежее окна, иначе восстановление потеряет сопоставления внутри него, и
повторная отправка того же состава создаст **второй** платёж. Четыре часа дают шестикратный
запас.

Установка:

```bash
install -m 0755 payments/deploy/ikpk-payments-backup.sh /opt/ikpk-payments/deploy/
install -m 0644 payments/deploy/ikpk-payments-backup.{service,timer} /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now ikpk-payments-backup.timer
systemctl list-timers ikpk-payments-backup.timer   # проверить следующее срабатывание
```

## Свойства, на которые можно опираться

- **Атомарность.** Файл пишется во временное имя `.part` и переименовывается. Прерванная
  копия не оставляет полуфайла, который при восстановлении выглядел бы годным.
- **Отказ вместо тишины.** Нет каталога состояния или нет в нём ни одного файла — скрипт
  выходит с кодом 1. «Копировать нечего» — это отказ, а не успех: сервис, создавший хотя бы
  один платёж, обязан иметь `payments.json`.
- **Предупреждение про раздел.** Требование «на отдельный раздел диска» исполняется
  монтированием, а не скриптом. Скрипт сравнивает устройства `df` и **предупреждает**, если
  каталог копий на том же. Умалчивать нельзя: иначе «копия есть» прочитают как «копия на
  другом разделе». Копия на том же разделе защищает от повреждения файла, но не от потери
  раздела.
- **Глубина истории** — `KEEP_BACKUPS`, по умолчанию 42 копии: при интервале 4 часа это
  около семи суток, то есть половина TTL записей (14 суток).

Поведенческие проверки — `web/tests/deploy-checks.test.ts`, описание
`ikpk-payments-backup.sh`: копия появляется и совпадает с исходником, копируются все четыре
файла, `.part` не остаётся, отсутствие каталога и отсутствие файлов дают отказ, вытеснение
по `KEEP_BACKUPS` работает и свежая копия остаётся. Плюс проверка таймера: интервал не
дольше четырёх часов и `Persistent=true`.

## Целостность при старте — уже в сервисе, не в этом runbook

Повреждённый или нечитаемый файл хранилища **останавливает** сервис с названной причиной
(fail-closed), а не запускает пустое состояние. Это реализовано в `payments/src/app.ts` и
проверено тестами `3.10c-1`. Здесь важно только следствие для оператора: если сервис не
поднимается с жалобой на хранилище, **не удаляйте файл** — восстанавливайте из копии по
процедуре ниже, иначе потеряете сопоставления и получите двойные платежи.

## Восстановление — явное действие оператора

Автоматического восстановления нет намеренно: сервис, который сам подставляет копию,
не отличает «файл повреждён» от «файла ещё нет», и во втором случае затрёт свежее
состояние старым.

```bash
systemctl stop ikpk-payments

ls -1t /var/backups/ikpk-payments/*.payments.json | head -5   # выбрать метку
STAMP=20260818T120000Z

# Сохранить повреждённое состояние ДО подмены: оно понадобится для разбора,
# и это единственный экземпляр.
mkdir -p /var/lib/ikpk-payments/broken-$STAMP
mv /var/lib/ikpk-payments/*.json /var/lib/ikpk-payments/broken-$STAMP/ 2>/dev/null || true

for name in payments verification-journal hmac-canary duplicate-tokens; do
  src=/var/backups/ikpk-payments/$STAMP.$name.json
  [ -f "$src" ] && install -o ikpk-payments -g ikpk-payments -m 0600 "$src" \
    /var/lib/ikpk-payments/$name.json
done

systemctl start ikpk-payments
systemctl status ikpk-payments --no-pager | head -20
```

**Что проверить после восстановления и записать в отчёт:**

1. сервис поднялся (порт слушает, `/readyz` отвечает ожидаемым режимом и `shopId`);
2. **сколько записей потеряно** — разница числа записей в восстановленной копии и в
   сохранённом повреждённом файле, если тот читается хотя бы частично. Это не формальность:
   потерянные записи — это попытки, по которым повторная отправка создаст второй платёж;
3. окно риска — от метки копии до момента восстановления. Все платежи, созданные в этом
   окне, сопоставления не имеют, и разбираются вручную по панели ЮKassa через `description`
   (по `metadata.requestId` панель искать не умеет — наблюдение 2.2a).

Восстановление без записи пунктов 2 и 3 считается незавершённым: без них неизвестно, что
именно потеряно, а «сервис поднялся» этого не отвечает.
