## 1. Как считалось

Данные о сертификации и часах лежат **не в полях, а в тексте**, поэтому счёт идёт
поиском по нормализованному тексту. Три регулярных выражения, используемые всюду ниже:

| имя | выражение | что ловит |
|---|---|---|
| `NMO` | `НМО\|\bЗЕТ\b\|зач[её]тн\w+\s+единиц\|балл` | любое упоминание непрерывного медобразования, зачётных единиц трудоёмкости, баллов |
| `AH` | `академическ\w*\s*час` | объём в **академических часах** — формулировка, релевантная сертификации |
| `HRS` | `(?:объ[её]м\w*\s+программы\|продолжительност\w*)\s*[:—-]?\s*[^.;]{0,40}?\d[\d\s,/]*\s*(?:академическ\w*\s*)?час` | любой **числовой объём обучения в часах**, включая «4 дня (32 часа)» |

Область поиска для семинара — `description_text` плюс **все** вопросы и ответы
свёрнутых панелей, привязанных к его `legacy_url` (панели — это отдельный файл,
`collapsible_panels.json`; без них половина фактов не видна). HTML-теги снимаются,
`&nbsp;` заменяется пробелом, пробелы сжимаются.

Почему `AH` и `HRS` разделены: `HRS` захватывает и «4 дня (32 часа)» — это тот же
объём обучения, но записанный не как академические часы; `AH` — только каноничную
формулировку. Границу приходится проводить явно, потому что от неё зависит итоговое
число, и разведочная цифра «часы у 13» не воспроизводится ни при одной из рамок
(см. §2).

**Канонический скрипт.** Все агрегатные числа §2 и §3 воспроизводятся одним запуском
из корня репозитория:

```bash
python3 - <<'PYEOF'
import json, re, collections
S = json.load(open('discovery/entities/seminars.json'))
P = json.load(open('discovery/entities/collapsible_panels.json'))
plain = lambda t: re.sub(r'\s+', ' ', re.sub(r'<[^>]+>', ' ', t or '').replace('&nbsp;', ' '))
NMO = re.compile(r'НМО|\bЗЕТ\b|зач[её]тн\w+\s+единиц|балл', re.I)
AH  = re.compile(r'академическ\w*\s*час', re.I)
HRS = re.compile(r'(?:объ[её]м\w*\s+программы|продолжительност\w*)\s*[:—-]?\s*'
                 r'[^.;]{0,40}?\d[\d\s,/]*\s*(?:академическ\w*\s*)?час', re.I)

def blob(s):
    pan = P.get(s['legacy_url']) or {}
    return '\n'.join([plain(s.get('description_text'))]
                     + [plain(q) + ' ' + plain(v) for q, v in pan.items()])

rows = [(s.get('institute_legacy_id', '(нет)'), bool(NMO.search(blob(s))),
         bool(AH.search(blob(s))), bool(HRS.search(blob(s)))) for s in S]
print('семинаров всего        :', len(rows))
print('НМО/ЗЕТ/баллы          :', sum(r[1] for r in rows),
      dict(collections.Counter(r[0] for r in rows if r[1])))
print('академические часы     :', sum(r[2] for r in rows),
      dict(collections.Counter(r[0] for r in rows if r[2])))
print('объём в часах (широко) :', sum(r[3] for r in rows))
print('ни НМО, ни акад. часов :', sum(1 for r in rows if not r[1] and not r[2]))
print('ни НМО, ни часов широко:', sum(1 for r in rows if not r[1] and not r[3]))
PYEOF
```

Фактический вывод на `e26b4fee`:

НМО/ЗЕТ/баллы          : 12 {'institut-klinicheskoy-prikladnoy-kineziologii': 11, 'institut-apledzhera': 1}
академические часы     : 12 {'institut-klinicheskoy-prikladnoy-kineziologii': 12}
объём в часах (широко) : 16
ни НМО, ни акад. часов : 110

## 2. Числа разведки против проверки

Проверялись как заявленные, а не принимались на веру. Два из шести пунктов

| 126 семинаров | 126 | подтверждено |
| панели у 90 | 90 семинаров (96 ключей всего) | подтверждено, см. §3.2 про остальные 6 ключей |

| ничего у 109 | 110 (рамка `NMO ∪ AH`) / 106 (рамка `NMO ∪ HRS`) | **не воспроизводится** |
| duration заполнен у 62/63 | 62 из 63 | подтверждено, пустая запись названа в §3.4 |

Поправка про Апледжера — не придирка: она меняет вывод «НМО есть только у ИКПК»,
на котором иначе строился бы фильтр по институту. Запись у Апледжера — вебинар

(«Можно ли получить баллы НМО?»), а не как выдаваемая единица. Это разные вещи,
и §3.1 их разделяет.

Про «часы у 13»: воспроизводимого определения, дающего 13, найти не удалось.
Ближайшие значения — 12 и 16, и они различаются ровно на четыре семинара цикла ФПК,
где объём записан как «4 дня (32 часа)» без слова «академических». Считать разведочные
13 следует ошибкой счёта, а не третьей рамкой.

Про `duration` важны три свойства, которые надо знать до проектирования бейджей:

1. **Единица измерения не хранится.** Значение — строка с числом, слово «час»

2. **Это не академические часы по определению.** Данные не различают академический
   час и астрономический; совпадение значений `24/36/40` с формулировками панелей
   ПК-цикла («24/36/40 академических часов») — сильное указание, но не доказательство.
3. Пустое значение уже обработано в UI: `'—'` в `SeminarScheduleSection.astro:23`,
   `'-'` в `raspisanie-i-tseny.astro:48`.

НМО, ЗЕТ, баллов и слова «час» в `schedule_entries.json` нет вообще — проверено
поиском по полному JSON каждой записи (0 совпадений).

это. Во-вторых, формулировки неоднородны по силе: «возможность получения» против
«вы получаете … Баллы НМО … (аккредитация)».

## 6. Предложение модели данных

**Только предложение.** Ничего из этого не реализовано, и реализовывать по этому
разделу нельзя: он вход для будущего change, а не спецификация.

### 6.1. Что уже есть в типах и почему это не годится как есть

`web/src/lib/data.ts:98-99` объявляет у `Seminar`:

```ts
hours?: number | string | null;
certificate_type?: string | null;
```

Оба поля **мертвы**: в данных их нет ни у одной из 126 записей, ни один компонент их
не читает (единственные вхождения по репозиторию — сами эти две строки объявления).
Появились они в `b8843940733d43b805318b04db263b903373d779` («Add CI quality gates to
main», 2026-04-04) — то есть как задел, а не по факту данных.

Три возражения против того, чтобы просто начать их заполнять:

1. **`hours` на семинаре противоречит данным.** У восьми ПК-семинаров объём
   вариативный («24/36/40»), у ФПК фиксированный, у вебинаров — длительность эфира,
   а не объём. Единственное фактическое число живёт на **событии расписания**
   (`duration`). Скалярный `hours` у семинара пришлось бы либо врать, либо оставлять
   пустым у большинства.
2. **`hours?: number | string` — тип, снимающий решение вместо того, чтобы его
   принять.** `string` тут нужен только чтобы вместить «24/36/40», то есть чтобы
   протащить неразобранный текст в типизированное поле. Фильтровать и сортировать по
   такому полю нельзя.
3. **`certificate_type: string` не выражает предмет.** В данных одновременно
   присутствуют: вид документа (удостоверение о повышении квалификации / свидетельство
   / сертификат), условие его выдачи (при наличии медицинского образования), баллы НМО,
   и внесение в международный реестр. Это четыре независимых признака, а не одно
   перечисление.

### 6.2. Предлагаемая форма

Разделить по уровню, на котором факт действительно живёт.

**На семинаре — сертификация** (`Seminar`):

```ts
/** Признаки сертификации семинара. Все поля необязательны:
 *  отсутствие означает «в данных не сказано», а НЕ «нет». */
certification?: {
  /** Виды выдаваемых документов. */
  documents?: ('qualification_certificate' | 'institute_certificate' | 'diploma_supplement')[];
  /** Требуется ли медицинское образование для документа гос. образца. */
  documents_require_medical_education?: boolean;
  /** Даются ли баллы НМО. Трёхзначно, а не boolean. */
  nmo?: 'granted' | 'possible' | 'not_stated';
  /** За что именно даются баллы: за этот семинар или за цикл целиком. */
  nmo_scope?: 'seminar' | 'course_group';
  /** Международные реестры (IAHE и подобные). */
  registries?: string[];
  /** Откуда признак взят — для проверяемости и для показа источника в UI. */
  source?: 'panel' | 'description' | 'manual';
};
```

Почему `nmo` — не `boolean`: данные дают **три** состояния, и склеивать их нельзя.
`granted` — «вы получаете … Баллы НМО … (аккредитация)»; `possible` — «возможность
получения баллов по НМО»; `not_stated` — молчание, которое сейчас неотличимо от «нет»
(§7). Boolean заставил бы выбрать между «обещать больше, чем сказано» и «скрывать то,
что сказано».

Почему `nmo_scope` обязателен для честности: у ПК-цикла баллы обещаны за прохождение
всех восьми семинаров. Бейдж на карточке одного семинара без этой оговорки — ложное
утверждение о продукте.

**На событии расписания — часы** (`ScheduleEntry`): поле `duration: string` уже есть.
Предложение — не добавлять новое поле, а перестать терять в нём единицу измерения:

```ts
/** Объём в часах. Единица не хранится в источнике; хранить её явно. */
duration_hours?: number | null;
duration_unit?: 'academic' | 'astronomical' | 'unknown';
```

`'unknown'` здесь — не заглушка, а честное состояние: сейчас источник единицу
не сообщает, и назначить её `'academic'` по совпадению чисел с текстом панелей
значило бы выдать догадку за данные.

**На семинаре — производный, не хранимый объём.** Если бейдж «32 академических часа»
нужен на карточке семинара, брать его следует **вычислением из событий расписания**
(чистой функцией, датой в аргументе — по правилу AGENTS.md «из данных проверять вывод,
а не снимок»), а не хранением снимка в `Seminar.hours`. Иначе повторится история
`status`, разобранная в комментарии `web/src/lib/data.ts:89-97`: снятое на момент
импорта значение со временем начинает лгать.

**Что делать с мёртвыми `hours` / `certificate_type`:** удалить в том же change,
который вводит замену, а не оставлять рядом. Два поля об одном предмете, одно из
которых всегда пусто, — готовый источник вопроса «а какое из них главное».

### 6.3. Заполнение

Автоматически извлечь признаки из текста панелей **нельзя** без разметки вручную:
формулировок мало (по сути четыре шаблона), но различие «granted / possible» несёт
юридический смысл, а из шаблона его вытаскивает не регулярка, а человек. Разумный
порядок для будущего change — ручная разметка 12 покрытых записей как данных
(отдельный файл или поля в CMS) плюс явное `not_stated` у остальных 114, и гейт,
проверяющий, что ни один бейдж не показывается при `not_stated`.

## 7. Чего в данных НЕТ

Раздел намеренно разделён на «проверено, отсутствует» и «не проверено». Смешивать их
нельзя: первое — факт о данных, второе — факт о границах этого аудита.

### 7.1. Проверено, отсутствует

- **Ни одного структурированного поля** про ЗЕТ, НМО, баллы или академические часы —

### 7.2. Не проверено

- **Текущее состояние ikpk.su.** Всё в этом отчёте снято со снимка discovery
  (`981477e`, 2026-08-06 для семинаров, панелей, расписания и курсовых групп).
  Боевой сайт мог измениться после снимка — новые семинары, переписанные панели,
  снятые обещания. Аудит этого не проверял.
- **Панели на боевом сайте отдельно не перепроверялись, и простой `curl`/`fetch`
  для этого не годится.** Свёрнутые Radix-панели на старом сайте отсутствуют в
  исходном DOM: их содержимое попадает в снимок только через браузерный
  восстановитель, раскрывающий панели по одной. Значит обычная выборка страницы
  дала бы ложный вывод «про НМО ничего не написано» ровно там, где написано, —
  и по этой причине быстрая сверка не проводилась, а не по недосмотру.
  Для перепроверки нужен тот же браузерный проход, каким снимался снимок.
- **Отличается ли «возможность получения баллов по НМО» от фактической
  аккредитации.** Данные говорят только о том, что написано на сайте. Аккредитованы ли
  программы на портале НМО в действительности, каких именно баллов и в каком объёме —
  вопрос к заказчику и к самому порталу, не к этому набору данных. Публиковать бейджи
  до такого подтверждения нельзя — это тот же класс, что «критерий подтверждения
  определяется в спеке» для ФИС ФРДО в блоке 4 плана.
- **Означает ли молчание «баллов нет».** У 59 семинаров панель «Выдаваемые документы»
  есть, документ назван, а НМО не упомянут. Из данных невозможно определить, это
  «баллы не даются» или «не написали». Различие несущее: фильтр «с НМО» на первом
  предположении корректен, на втором скрывает семинары, которые баллы дают.
- **Актуальность цен и дат** к предмету аудита не относится и не проверялась,
  хотя одна запись расписания (`id=465`, `startAt` 2026-07-29) уже в прошлом
  относительно даты аудита — признак того, что снимок расписания отстаёт.
